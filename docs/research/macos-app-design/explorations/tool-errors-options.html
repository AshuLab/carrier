The session rows: errors, and exit codes that are not errors

Today the red chip counts every tool call that Claude Code flagged, and a shell command that ends in exit 1 is flagged even when its output is what the agent wanted (a grep with no match, a … | head). In the epic #350 run, 7 of the builder's 7 “errors” were 5 exit codes and 2 real tool errors. The rows below are the four sessions of that run; the second case is an example I made up, with failing tests, to see how each option behaves when there is something to worry about. Click a chip or the arrow to open the list behind it.
Data
  • What the engine would add: each tool result keeps its exit code as its own field, and a call is told apart as error (the tool itself refused or failed: a tool that does not exist, a blocked command), exit (a command that ended non-zero) or ok. SQLite's status column has only ok and err today, so the app cannot tell them apart without this.
  • “Test runs” and “failed”: the row already counts test runs, so C leans on the engine knowing which calls are pnpm test, typecheck or build. If it cannot tell a failed one from a passed one, C falls back to A.
  • What is lost in A, B and C: a non-zero exit that is a real failure but is not a test or build (a git push rejected, say) shows grey. It is one click away and the agent usually says it in its summary, but it is no longer red. That is the cost of not crying wolf.
