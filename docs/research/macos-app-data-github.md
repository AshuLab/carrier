# Research for the macOS app: the GitHub and git data behind the design, file icons, Terminal and login item

> Research of 2026-10-21 for the [macOS app brief](../specs/macos-app.md), [ADR 0005](../adr/0005-engine-independent-of-the-macos-app.md) and the [final design](macos-app-design/diseno.html), which was drawn with invented data. Everything ran on this Mac (macOS 27.0, Apple Swift 6.4, Apple Git 2.54.0, `gh` as the user `vemec`). GitHub calls were read-only (GET and read-only GraphQL queries) against the public repos `AshuLab/carrier` and `cli/cli`; no `carrier` process was started, no source file was touched, and the git experiments ran on the disposable repo created under `/tmp` (deleted) and read-only on the real clone `~/.solve/repos/vemec/encaja` (2,764 tracked files, with real lane worktrees), always with `GIT_OPTIONAL_LOCKS=0`. A sibling file, `macos-app-data-engine.md`, covers the engine's own data; this one covers GitHub, git and the three native questions.

## Short answer

Almost everything the design shows on the GitHub side is already in responses the engine fetches, or costs one more request per active epic. The epics list the engine already polls every cycle (`listOpenEpics`, `src/integrations/github.ts:140`) returns the issue `title`, its `labels`, `assignees` and `issue_dependencies_summary`; the zod row keeps `title` and then the code throws it away at line 144, and the schema does not declare `labels`. So title and labels cost zero new requests. Slices with their state, assignee and dependencies are one request per epic: REST `GET issues/{n}/sub_issues` gives title, state, `state_reason`, `closed_at`, assignees and the *counts* of blockers, and a single GraphQL query gives the same plus *which* issues block each slice, and the epic's PR (draft, mergeable state, review decision, checks already counted by state, additions, deletions, changed files) for 2 points. The reason to prefer GraphQL is that the same facts in REST need four to nine calls per epic. Rate-limit numbers are free: `GET /rate_limit` does not count (verified), and every `gh api -i` answer the engine already parses carries the `x-ratelimit-*` headers, which `api()` reads and discards.

The file lists and the "same file in two lanes" warning should not come from GitHub at all. A local `git diff --numstat` of three-dot form reproduced GitHub's PR totals exactly (91 files, +5,588, -46, 37 commits for PR #110), has no 3,000-file cap, sees uncommitted work in a lane, and costs 10 to 70 ms on a 2,764-file repo. The engine should fetch everything and serve it over the socket: the app has no token, a second GitHub client would burn a second bucket and use a different identity, and ADR 0005 already says the socket is the only contract. Keep the per-second `snapshot` small (scalars only) and add two on-demand commands for the lists. For 5 repos and 5 active epics at the default 5 minute poll the plan adds about 60 GraphQL queries (120 to 180 points) per hour to the 120 REST requests per hour the engine already spends, which is under 4% of each 5,000 bucket.

Three things in the design have no source today and need a decision: the per-lane agent session id for "Continue in Terminal" (the engine stores only the epic's top-level `sessionId`), the "88 passing" test count (not in any GitHub field; `verification.evidence` is free text from the reviewer), and "PR opens with the first merged slice" (the integration PR only opens once every slice is closed, so during ship there is no PR and the epic's totals must come from git). On the native side: do not use `NSWorkspace` icons (they depend on the user's installed apps, carry the opener app's badge and mislabel `.ts`), use SF Symbols by category; open Terminal with a temporary `.command` file through `NSWorkspace`, not AppleScript; and `SMAppService.mainApp` for start at login, with the ad-hoc signing behaviour unverified.

## 1. Epic title and labels

The engine already receives both. `listOpenEpics` calls `GET repos/{repo}/issues?labels=solve:epic&state=open&per_page=100` (`github.ts:142`, one request per repo per poll, called from `refreshProgress`, `engine.ts:493-512`). [List repository issues](https://docs.github.com/en/rest/issues/issues) documents the item as an Issue with `title` (required), `labels` (objects with `name`, `color`, `description`), `assignees`, `sub_issues_summary`, `issue_dependencies_summary`, `state_reason` and `parent_issue_url`; I confirmed the same keys live on `AshuLab/carrier` epic #75 ("Carrier macOS app", labels `enhancement`, `solve:epic`, summary 17 of 17). `epicRow` (`github.ts:41`) extends `issueRow` (line 39), so `title` is parsed, but line 144 pushes only `{ issue, slices }`. `labels` is not in the schema, which zod strips. `listReadyEpics` does return the title, but only for queued epics; running, needs-human and ready-for-test epics are not in that list. Today no title is stored anywhere (the `epics` table has none, `src/storage/schema.ts`).

The cheapest path is therefore to widen `epicRow` with `labels: z.array(z.object({ name: z.string() }))` and return `{ issue, title, labels, slices }`, then keep them in the same in-memory map as the slice progress (`engine.ts:74`), which is the pattern the spec already chose (null after a restart until the first poll). Cost: zero extra requests, one list per repo per poll as now. Two caveats. The list is capped at 100 per page and `pages()` already walks further pages. The labels include the Carrier state labels (`solve:epic:running`, `:needs-human`, `:ready-for-test`) next to user labels such as `backend`, so the app should filter `solve:*` out before drawing the chips the design shows (`solve:epic`, `backend`); the design currently shows `solve:epic` itself as a chip, which is a design choice, not a data limit.

## 2. Slices as sub-issues, and "ready to start" against "after #N"

Sub-issues: [List sub-issues](https://docs.github.com/en/rest/issues/sub-issues), `GET /repos/{owner}/{repo}/issues/{issue_number}/sub_issues`, `per_page` up to 100, default 30, plus `page`; not marked preview or beta, and the page states no cap on the number of sub-issues. Each item is a full issue object. [The earlier research](macos-app.md) (section 1) already established GA status and that nothing in `src/` reads sub-issues. Live on epic #3 of `AshuLab/carrier` (31 slices) one request returned all of them; the keys I used are `number`, `title`, `state`, `state_reason` (`completed`, `not_planned`), `closed_at`, `assignees` and `issue_dependencies_summary`.

Dependencies: [issue dependencies](https://docs.github.com/en/rest/issues/issue-dependencies) are `GET /repos/{owner}/{repo}/issues/{issue_number}/dependencies/blocked_by` (and `/blocking`), paginated with `per_page` (max 100) and `page`, accepting the default API version (the live response said `X-Github-Api-Version-Selected: 2022-11-28`, no preview header). The docs page for the endpoints carries no preview or beta wording and no availability statement, so GA status comes from the GitHub changelog of 21 August 2025, ["Dependencies on issues are now generally available"](https://github.blog/changelog/2025-08-21-dependencies-on-issues/), which also says "Issue dependencies are fully supported in the API and webhooks" and limits each relationship type to 50 issues. This is the same `blocked-by` edge the solve skills create with `--blocked-by` and read as `blockedBy` (`docs/agents/solve.md`, "find the next startable slice").

What decides "ready to start" is already in the sub-issues list, with no extra call. Each slice carries `issue_dependencies_summary` with `blocked_by`, `total_blocked_by`, `blocking`, `total_blocking`. Reading real data: epic #3's issue #6 is closed with `total_blocked_by: 1` and `blocked_by: 0`, whose one blocker (#5) is closed. So `blocked_by` counts the blockers that are still open, `total_blocked_by` all of them (an inference from that data; the docs page does not define the two counters). The engine's rule in `docs/agents/solve.md` is "open, unassigned, no open blocker", so the four states the design needs map to: closed (`closed_at`, and `state_reason: not_planned` is a skipped slice, not a merged one), open and assigned (an agent claimed it, in progress), open, unassigned with `blocked_by > 0` (waiting), and open, unassigned with `blocked_by == 0` (ready to start).

To say "after #N" the app needs the identity of the open blockers, and REST gives it only per issue: one `blocked_by` call for each waiting slice. A typical epic has several, so REST costs `1 + waiting` requests per epic per poll. GraphQL gives it in one request: `Issue.subIssues(first: 100)` with `blockedBy(first: 20) { nodes { number state } }` on each node. Live on epic #3 (31 slices, 100% done, so a worst-case payload) this returned every slice with its blockers and `rateLimit.cost` was 2. The combined epic-plus-PR query I would use costs 2 as well (epic #75 with 17 slices plus PR #110, same query):

```graphql
query { rateLimit { cost remaining }
  repository(owner: "AshuLab", name: "carrier") {
    issue(number: 75) { title labels(first: 20) { nodes { name } }
      subIssuesSummary { total completed }
      subIssues(first: 100) { pageInfo { hasNextPage }
        nodes { number title state stateReason closedAt
                assignees(first: 3) { nodes { login } }
                blockedBy(first: 20) { nodes { number state } } } } }
    pullRequest(number: 110) { number url isDraft state baseRefName headRefName headRefOid
      mergeable mergeStateStatus reviewDecision additions deletions changedFiles commits { totalCount }
      commitsLast: commits(last: 1) { nodes { commit { statusCheckRollup { state
        contexts(first: 1) { checkRunCount statusContextCount
          checkRunCountsByState { state count } statusContextCountsByState { state count } } } } } } } } }
```

Costs follow [the GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api): every connection needs `first` or `last` between 1 and 100, the cost is the requests implied by the connections divided by 100 and rounded, minimum 1. `hasNextPage` handles an epic with more than 100 slices (REST would need page 2). One query per epic per poll replaces the REST list. Note that GraphQL has no conditional requests, so each query always costs its points; REST with ETag would be free on 304 but the per-waiting-slice calls make it worse.

Permission: `list-sub-issues`, `blocked_by` and `list-repository-issues` are all "Issues: read" with no extra permission in [Permissions required for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps); both Forge bots hold `issues:write` (`docs/research/agent-forge.md:32`), which includes read. The `gh` profile used here has the classic `repo` scope (`X-OAuth-Scopes` header).

Not verified: that the GraphQL `subIssues` and `blockedBy` fields work with a Forge installation token on a private repo (all my reads used the user's own login on public repos, the same gap the earlier research recorded); whether a slice in a different repo than its epic appears; and whether `blockedBy` includes blockers outside the epic (cross-epic edges are legal).

## 3. The pull request: state, checks, review, cost and scopes

When the PR exists matters first. `docs/agents/solve.md` and the ship skill (`SKILL.md`, "Every slice closed") open ONE draft integration PR only after the last slice closes. Slice PRs target the epic branch and the engine does not track them. So during ship an epic has no PR, no checks and no review; the design text "No PR yet; it opens with the first merged slice" is wrong for the real flow, and for epics in ship every "PR" element should show its empty state while the totals come from git (section 7). The engine learns the PR when it validates the ship result (`prNumber`, `prHeadSha`, `src/storage/schema.ts:28-29`; `engine.ts:355`), and the review stage re-reads it with `getPullRequest` (`github.ts:155`), whose `pullRow` (line 43) keeps only `number`, `state`, `merged_at`, `body` and `head`.

What the REST PR object gives. [Get a pull request](https://docs.github.com/en/rest/pulls/pulls): `number`, `html_url`, `draft`, `head.ref`/`head.sha`, `base.ref`, `merged`, `mergeable`, `mergeable_state`, `additions`, `deletions`, `changed_files`, `commits`. The page says `mergeable` is true, false or null and that null means "GitHub has started a background job to compute the mergeability" and you should resubmit after a while; it lists `mergeable_state` as a required string without defining the values. Live: PR #110 (merged) answers `mergeable: null`, `mergeable_state: "unknown"`; an open PR in `cli/cli` answered `mergeable: true`, `mergeable_state: "blocked"`. GraphQL types the same facts: `PullRequest.mergeStateStatus` is an enum, and introspection returns `DIRTY` (cannot create a clean merge commit), `UNKNOWN`, `BLOCKED`, `BEHIND` (head ref out of date), `UNSTABLE` (non-passing commit status), `HAS_HOOKS`, `CLEAN`; `reviewDecision` is `CHANGES_REQUESTED`, `APPROVED`, `REVIEW_REQUIRED` or null. For Carrier the useful signals are `DIRTY` (the epic branch conflicts with main, typical after a `Merge branch 'develop' into ...` like the one in the encaja epic) and `UNKNOWN` right after a push (show "checking", not "ok").

Checks. REST has two systems and neither alone is the answer. [List check runs for a Git reference](https://docs.github.com/en/rest/checks/runs), `GET /repos/{o}/{r}/commits/{ref}/check-runs`, returns `total_count` and `check_runs[]` with `status` (`queued`, `in_progress`, `completed`, `waiting`, `requested`, `pending`) and `conclusion` (`success`, `failure`, `neutral`, `cancelled`, `skipped`, `timed_out`, `action_required`, or null); `per_page` max 100, `filter=latest` is the default, and above 1,000 check suites on a ref it limits to the 1,000 most recent. [Get the combined status](https://docs.github.com/en/rest/commits/statuses), `GET .../commits/{ref}/status`, covers the older commit-status API: `state` is failure if any context is error or failure, pending "if there are no statuses or a context is pending", success if all latest are success. That last rule is a trap: on `AshuLab/carrier` PR #110 the combined status is `pending` with `total_count: 0`, and check-runs is `total_count: 0`; a repo with no CI must show "no checks", never "pending". GitHub Actions only produces check runs, so a repo with Actions has an empty combined status that still says pending.

GraphQL does the reduction for you. `Commit.statusCheckRollup` returns `state` and `contexts` with `checkRunCount`, `statusContextCount`, `checkRunCountsByState` and `statusContextCountsByState`, merging both systems. It is null when the commit has no checks (verified on PR #110, where `mergeStateStatus` is `UNKNOWN` because it is merged). On `cli/cli` PR #14784 it returned `state: SUCCESS`, 18 check runs (12 success, 6 skipped). REST `check-runs` for the same head returned 19 (13 success, 6 skipped); one run is counted by REST and not by the rollup, which I could not explain (maybe a run that finished between my two calls), so treat the counts as approximate to one. The reduction I suggest: passing = `SUCCESS` + `SKIPPED` + `NEUTRAL`; failing = `FAILURE`, `TIMED_OUT`, `CANCELLED`, `STARTUP_FAILURE`, `ACTION_REQUIRED` plus status contexts `ERROR` and `FAILURE`; pending = `QUEUED`, `IN_PROGRESS`, `PENDING`, `WAITING`, `EXPECTED`. The design wants "5 passing" or "1 failing", so show failing first if above zero, else pending, else passing, and "-" when the rollup is null. The enum names come from the live introspection and counts; the docs.github.com GraphQL reference pages did not render through my fetch tool (same as the earlier research), so the enum text is from introspection, not the web page.

Review state: [List reviews](https://docs.github.com/en/rest/pulls/reviews) returns chronological reviews with `state`, `user`, `commit_id`, `per_page` max 100; its page does not enumerate `state`. More important: Carrier already owns the review outcome. The reviewer agent's result is stored in `caller_results` (round, blockers) and the engine sets `ready_for_test` with `reviewedSha` (`engine.ts:362`). The reviewer is a bot and `reviewDecision` depends on branch protection requiring reviews, so GitHub's review state would mostly be null. Recommendation: do not fetch GitHub reviews; the design's review tab is the engine's own data.

Cost per epic per poll. REST: `pulls/{n}` + `check-runs` + `status` (+ reviews, not needed) = 3 requests, plus a fourth if you also want the epic's slices. GraphQL: the one query above, 2 points, and it also replaces the sub-issues calls. Ways to cut: (1) only epics with a PR need the PR block (ship-stage epics do not); (2) for REST, conditional requests: the [best practices page](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) says a request "does not count against your primary rate limit if a 304 response is returned" and needs an `Authorization` header. I verified it with a controlled test on `pulls/110` (`X-Ratelimit-Used` 49 before, 50 after the first GET, 50 after two 304s). Adopting it needs a code change that is not trivial: `gh api` exits 1 on a 304 (`gh: HTTP 304`) with the status line still on stdout, so `api()` (`github.ts:102`) would turn it into an `HttpError(304)`, and the engine would have to keep one ETag per URL; (3) GraphQL batching, already counted; (4) finished epics (`ready_for_test`, merged) do not need refreshing until their head changes (`prHeadSha`). The page also says to prefer webhooks and honour `x-poll-interval`, which a local app cannot use.

Scopes. Forge bots mint `issues:write contents:write pull_requests:write checks:read actions:read statuses:read metadata:read` (`agent-forge.md:32`), which covers every call here: the permissions page lists `pulls/{n}`, `pulls/{n}/files`, `pulls/{n}/reviews` and `pulls` under Pull requests read, `check-runs` under Checks read, `commits/{ref}/status` under Commit statuses read, `compare` under Contents read. The `gh` profile is the user's own login; classic tokens "need the `repo` scope to use [check-runs] on a private repository" (the checks docs page), and a fine-grained PAT would need Pull requests, Checks, Commit statuses, Issues and Contents read. Unverified: a GraphQL query for `statusCheckRollup` and `reviewDecision` with an installation token (nothing in the earlier research ran a successful GraphQL read as a bot; `agent-forge.md:103` shows only that `gh issue list` reaches the GraphQL endpoint). If it fails, the REST fallback is the three calls above and needs no new permission.

## 4. Files changed in a PR

[List pull requests files](https://docs.github.com/en/rest/pulls/pulls), `GET /repos/{o}/{r}/pulls/{n}/files`: `per_page` max 100, default 30; "Responses include a maximum of 3000 files". Each file has `filename`, `status` (`added`, `removed`, `modified`, `renamed`, `copied`, `changed`, `unchanged`), `additions`, `deletions`, `changes`, `sha`, `blob_url`, `raw_url`, `contents_url`, `patch` and `previous_filename` for renames. The page documents `patch` as an optional string and says nothing about when it is omitted; I did not verify the size at which GitHub drops it (known in practice for binary and very large diffs, but not stated on this page). Cost: `ceil(files / 100)` requests per PR, so 1 for a normal PR, 30 for the 3,000 cap. Totals for the whole PR come from the PR object itself, no listing needed: `additions`, `deletions`, `changed_files`, `commits` (PR #110: 5,588, 46, 91, 37).

My recommendation is not to use this endpoint for the app. The cap and the per-file `patch` limits make it unreliable exactly for the big epics, and the design needs more than it gives (per lane and per round attribution, uncommitted work), which only git has. I compared the two on PR #110: `git diff --shortstat <merge>^1...<merge>^2` printed `91 files changed, 5588 insertions(+), 46 deletions(-)` and `git log --oneline <merge>^1..<merge>^2 | wc -l` printed 37, identical to the PR object. So the totals strip ("14 files, +420 -46") and the per-file list both come from git (section 7), and the PR object's three numbers serve as a cheap cross-check or as the fallback when the clone is missing. The one thing that needs GitHub is a file's `patch` text if the app ever shows diffs; the engine can serve that from `git diff` on demand without the limit.

## 5. Rate limit

[`GET /rate_limit`](https://docs.github.com/en/rest/rate-limit/rate-limit) states "Accessing this endpoint does not count against your REST API rate limit"; I verified it (`used` was 49 before and after two calls). It returns `resources` with one object per bucket (`core`, `graphql`, `search`, `code_search`, and more), each with `limit`, `used`, `remaining`, `reset`; a deprecated top-level `rate` is documented as closing down but the live response still sends it. The page says that if the body and the `x-ratelimit-*` headers disagree the headers win. The page does not state the unit of `reset`; the [REST rate limit page](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) does for the header: "UTC epoch seconds" (live: `x-ratelimit-reset: 1792618843`). The five headers on every response are `x-ratelimit-limit`, `-remaining`, `-used`, `-reset` and `-resource` (which bucket the call counted against, `core` or `graphql`).

The engine already has them for free. `gh api -i` prints the headers and `parseResponse` (`github.ts:69-78`) puts them in a lowercase map; `api()` returns only the body (`github.ts:103`) and `retryAfterMs` (line 52) reads `retry-after` and `x-ratelimit-reset` only on a failure. Keeping the last `{ resource, limit, remaining, reset }` per resource from the success path is a few lines, adds no request, and is fresher than any poll of `/rate_limit`. Call `/rate_limit` once at startup, so the number exists before the first poll answers, and for the GraphQL bucket (its own limit, 5,000 points; live `graphql.used` was 37 while `core.used` was 49).

To show "4,812 / 5,000, resets in 41 min": the snapshot carries `rateLimit: { limit, remaining, resetAt }` (resetAt in epoch ms, `reset * 1000`) for the orchestrator profile's `core` bucket, and the app formats `remaining / limit` with thousands separators and `ceil((resetAt - now) / 60000)` minutes. Three caveats the app must not hide. The limit is not 5,000 for everyone: a user token has 5,000, a GitHub App installation starts at 5,000 and gains 50 per repository above 20, capped at 12,500 (REST rate-limit page), so show the `limit` the header reports. The bucket is per credential: with a Forge profile it is that installation's, and the author and reviewer bots the agents use are other buckets the engine never sees; with the `gh` profile it is the user's own and moves when the user runs `gh` elsewhere, so a drop is not necessarily Carrier's. And whether `agent-forge gh <agent> api -i` forwards the headers the same way is not verified (the existing code and tests parse its output the same way as `gh`'s, which is only indirect evidence).

## 6. What the engine fetches, what the app asks for, and a polling plan

Everything goes through the engine. The app has no token, ADR 0005 and the spec say the app talks only to the socket and never reads SQLite, and a second client would be a second credential path (the user's `gh` login, a different identity from the Forge bot, with its own bucket and its own PATH problem, [macos-app.md](macos-app.md) section 2). The only GitHub thing the app does itself is open `issueUrl` and `prUrl` in the browser, which the snapshot already carries.

Split the contract by how fast the data changes and how big it is. The 1 second `snapshot` stays small and gains only scalars: per epic `title`, `labels` (without `solve:*`), the PR summary (`number`, `url`, `draft`, `mergeStateStatus`, checks as `{ passing, failing, pending } | null`, base and head names) and totals (`files`, `additions`, `deletions`, `commits`), plus one top-level `rateLimit`. Two new commands serve the lists, pulled only while the view is open: `epic { repo, issue }` returning the slices (number, title, state, kind, blockers, assignee, closedAt) and `files { repo, issue }` returning the per-session file lists with the overlap flags of section 7. Nothing goes to SQLite: like the slice progress, these are caches in memory, null after a restart until the first poll finishes; the one exception is data that already is in SQLite (per-round heads, section 7).

Polling plan, at the default 5 minute interval (12 polls per hour; `src/config/load.ts:5`):

| Tier | What | Source | When |
|---|---|---|---|
| 1 | open epics of each repo with title, labels, summary, ready list | REST, the two lists that exist | every poll, as today |
| 2 | slices with blockers, plus PR block when `prNumber` is set | one GraphQL query per active epic | every poll for epics in ship, review, fix or needs-human; once for a finished epic, then only when its `prHeadSha` changes |
| 3 | files, lanes, overlaps, per-round diffs | local git | when the app asks (`files`), cached about 10 s; `git fetch` of the epic branch first only while the Files tab is open |
| 4 | rate limit | headers of tiers 1 and 2 | free |

Budget for 5 repos and 5 active epics: tier 1 is 2 requests per repo per poll (`engine.ts:511-512`; `ensureLabels` runs once per repo per process, `engine.ts:80-89`), so 10 per poll and 120 per hour, 2.4% of the REST bucket, and unchanged by this plan. Tier 2 adds 5 queries per poll, 60 per hour, 2 points each: 120 points per hour, 2.4% of the separate GraphQL bucket (up to 180 points per hour, 3.6%, if a heavy epic costs 3). If GraphQL cannot be used with a bot token, the REST fallback is about 9 requests per epic per poll (sub-issues, about 4 `blocked_by` for waiting slices, `pulls/{n}`, `check-runs`, `status`, and a spare) = 45 per poll, 540 per hour, plus the 120 baseline = 660 per hour, 13% of the bucket, still fine, and ETag 304s would bring most of it to zero. When `remaining` falls under 10% of `limit`, skip tier 2 and keep the last values; the engine already treats a rate limit as `GitHubUnavailable` with a wait (`github.ts:60-66`). "Check GitHub now" runs tier 1 and 2 immediately.

Effort. Widening `epicRow`: S. A GraphQL method on the port (`getEpicDetail`) with fake and a recorded response test: M (`api()` takes `['graphql', '-f', 'query=...']` as is, `setLabels` already passes arbitrary args; `get()` forces the `repos/` prefix so GraphQL goes through `api()` directly). Rate-limit capture: S. Git side: M (section 7). A second Forge-token integration run: S, but it is the blocker for choosing GraphQL.

## 7. Git: which commits belong to which slice, lane diffs and overlaps

Where lane worktrees come from. Carrier does not create them: Solve's `ship` does. The engine only reads the epic's worktree back (`findWorktree`, `git-workspaces.ts:121-132`, a parse of `git worktree list --porcelain` in the clone `<root>/repos/<owner>/<name>`) and stores that path in `epics.workspace` (`src/storage/schema.ts:24`, written at `engine.ts:344-355`, only after ship ends). Lanes are never recorded in SQLite. Per `WORKTREES.md` of the ship skill and `docs/research/shared-root.md` section 1.4, up to 3 lanes live at `<root>/worktrees/<repo>/<feature>--lane-<N>/`, siblings of the epic worktree, always, whatever the Worktrees setting. The record of a lane exists in three places: `git worktree list` in the clone (the authority: path, HEAD, and `branch refs/heads/...` or `detached`), a "Lane N worktree" comment `ship` posts on the epic issue the first time it creates a lane (path, machine, epic branch, first slice), and the convention itself (`dirname(workspace)/basename(workspace)--lane-N`). A lane is a slot reused across slices: a named slice branch checked out means occupied, detached HEAD means free (WORKTREES.md, "Sizing the round"). I confirmed this on the real clone: `git worktree list --porcelain` shows three `--lane-N` entries, all `detached`, next to the epic worktree. Lanes are only for hub slices, those with no open blocker, so their base is always the epic branch; stacked slices build elsewhere and are not lanes.

Which lane belongs to which epic, given several epics per repo: the slice branch is `feat/<feature>/<NNN-slug>` with `<NNN>` the slice's issue number (`docs/agents/solve.md`, Branching), so match the number against that epic's sub-issue list from section 2, and the epic branch is `<same namespace>/epic`. Before the ship result is imported `epics.workspace` is empty, so this is also how the engine finds the epic branch during ship.

Commits per slice. Slices merge with a merge commit, never squash or rebase (`gh pr merge --merge`, ship `SKILL.md` step 4), so each slice is one merge commit on the epic branch's first-parent line, with the slice's own commits on its second parent. GitHub's subject is `Merge pull request #<pr> from <owner>/<namespace>/<NNN-slug>`; I saw it on the real encaja epic and in this repo's own history. The epic branch also has commits that are not slices: review-fix commits pushed straight to the epic (`fix(billing): address review ...`), a changelog commit, a formatting commit, and `Merge branch 'develop' into ...`. Merged slices:

```
git -C <epic worktree> log --first-parent --format='%H%x1f%P%x1f%ct%x1f%s' origin/<default>..<epic branch>
# keep subjects matching ^Merge pull request #(\d+) from [^/]+/.+/(\d+)-[^/]+$  -> pr, slice issue
git diff --numstat --no-renames <M>^1 <M>              # that slice's files, additions, deletions
git log --format='%h%x1f%s' <M>^1..<M>^2               # that slice's commits
```

On the 2,764-file clone the first-parent log over 14 epic-branch commits took 25 ms and one slice diff 11 ms. The subject format is what GitHub generates by default; a repo can change the default merge-commit message in its settings, which I could not check, so the fallback is `GET pulls?state=closed&base=<epic branch>`, whose items carry `merge_commit_sha`, `head.ref` and the `Closes #n`, one request. The total of the epic is `git diff --numstat origin/<default>...<epic branch>` (138 files on the encaja epic, 19 ms). Careful with the base: when the epic merged `develop` into itself, a three-dot diff against `main` includes everything that came from `develop`; the PR object's own totals would too, so this matches GitHub, but it inflates "files changed" for such epics.

Per fix round. The design's "Round 1, Round 2" sessions need the head after each stage. `epics.prHeadSha` is overwritten each time (`engine.ts:355-356`), but every ship and fix result contains `pr.headSha` (`src/execution/caller-result.ts:4`) and the validated JSON is kept per execution in `caller_results` joined to `executions` (`stage`, `startedAt`; `src/storage/caller-results.ts`, `src/storage/executions.ts`). So round k's changes are `git diff --numstat <head after stage k-1> <head after stage k>` and its commits `git log <a>..<b>`, with no schema change. I did not check that these heads are reachable in every case (they are on the PR branch, so they should be after a fetch).

A lane's diff against the epic branch, merged or not. The lane's current slice branch is checked out there, the epic branch moves under it as other slices merge, and the agent may not have committed yet. Use the merge-base, so epic progress is not counted as removals, and compare against the working tree so uncommitted edits show:

```
cd <lane path>
B=$(git merge-base origin/<epic branch> HEAD)
git diff --numstat -M -z "$B"                        # committed and uncommitted changes of tracked files vs the fork point
git ls-files --others --exclude-standard -z          # new files not yet added (no counts: count lines or show "new")
git status --porcelain=v1 -z                         # what is dirty right now
```

In `-z` form a rename arrives as `ins<TAB>del<TAB>` then NUL, old path, NUL, new path (verified). I built a disposable repo with two lanes (committed and uncommitted edits, an untracked file) and the output was as expected: numstat per file, the untracked file listed apart, status showing modified and untracked. The commands for `git diff` and `git status` take a lock-free route when `GIT_OPTIONAL_LOCKS=0` is set (`git status` otherwise refreshes the index and can collide with the agent's own commit in the same worktree); the engine's `git()` helper (`git-workspaces.ts:28`) builds the environment and would add it. A slice that is detached (free lane) has no diff and no "working" state.

The same file in two lanes. Intersect the changed-path sets of the lanes that are occupied:

```
{ git diff --name-only --no-renames "$B"; git ls-files --others --exclude-standard; } | sort -u > lane1.txt   # per lane
comm -12 lane1.txt lane2.txt
```

On the disposable repo this printed exactly the two files both lanes touched (`src/b.ts`, `src/c.ts`). Path overlap is a warning, not a conflict: two lanes can edit different hunks of one file. To say whether they would really conflict, `git merge-tree --write-tree --name-only <laneA HEAD> <laneB HEAD>` (git 2.38 or later; this Mac has 2.54) merges in memory and exits 1 listing the conflicted paths: on the disposable repo it printed `src/c.ts` and `CONFLICT (content): Merge conflict in src/c.ts` while the clean `b.ts` auto-merged. It sees only committed content, not the working tree. The design shows the path-level "also in Lane 2", which is the right granularity; the merge-tree check is an optional upgrade, and I did not verify the minimum git version a user's machine has.

Cost. Measured on `~/.solve/repos/vemec/encaja` (2,764 tracked files), warm cache: `git worktree list --porcelain` 11 ms, `git merge-base` 14 ms, `git log --first-parent` 25 ms, `git diff --numstat` of 138 files 19 ms (with or without `-M`), `git merge-tree` 12 ms, `git status --porcelain` in a clean lane 70 ms, `git diff --numstat HEAD` 15 ms. A refresh of the epic worktree plus three lanes is about 0.3 s of process time, dominated by spawning, so it is cheap to run on demand every few seconds while the Files tab is open. I did not measure a cold cache, a lane with a populated `node_modules` untracked tree (check that `status` honours the repo's `.gitignore`), or a monorepo ten times larger. The exception is `git fetch`, which goes over the network with the profile's token (`remote()`, `git-workspaces.ts:94`), serialised per repo by `serial()`; fetch only the one epic branch, and only while the view is open.

Not in the engine's data: the per-lane agent session. The design's lane card shows `claude --resume 91d4be02`, but the engine's `executions.sessionId` (`src/storage/executions.ts:11`) is the epic's top-level `ship` session; the lanes are subagents inside it, and I found no place where their session ids are recorded (not verified in Solve's own files, which I did not read beyond `WORKTREES.md` and `SKILL.md`). Until that exists, "Continue in Terminal" can offer only the epic's session in the epic worktree.

## 8. File-type icons in the app

Short answer: use SF Symbols chosen by file category from a small extension table, with `doc` as the fallback. If per-language identity (the "TS", "JS" tiles of the placeholder design) is wanted later, bundle a subset of Material Icon Theme.

(a) `NSWorkspace`. [`icon(for:)`](https://developer.apple.com/documentation/appkit/nsworkspace/icon(for:)) is `func icon(for contentType: UTType) -> NSImage`, macOS 11.0 and later, and "returns a default icon if the operation fails". [`icon(forFileType:)`](https://developer.apple.com/documentation/appkit/nsworkspace/icon(forfiletype:)) takes an extension string and is deprecated since macOS 12.0 in favour of the former. You get the type with `UTType(filenameExtension: "ts")` and cache one `NSImage` per extension (1,000 lookups took 5 ms, so caching is for allocation, not speed). I rendered 31 extensions on this Mac and looked at them. It is native and needs no dependency, and what it gave is not good enough for this design:

- The icon depends on what the user has installed. `.md`, `.json` and `.ts` show a badge of the default app that opens them (here "Antigravity IDE") in the corner; `.html` shows the Chrome logo. A teammate with other apps sees a different set, and at the 14 to 18 pt a file row uses the badge is noise.
- It mislabels `.ts`: `UTType(filenameExtension: "ts")` resolves to `public.mpeg-2-transport-stream` first (the types for `ts` are that and `com.microsoft.typescript`). Here an installed app supplies a "TS" icon for it, on a Mac without one it would be a video file. I could not test a clean Mac.
- Unknown types render a blank generic page: `.prisma`, `.mdx` and an invented `.xyz123` are `dyn.*` types and came out identical to the generic data icon. `.go`, `.rs`, `.lock`, `.env`, `.gitignore` also resolved to dynamic types, but showed some icon here, again because of installed apps.
- It is coloured and bitmap (32 representations, no template flag), so it does not follow the design rule "Colour carries meaning only" and does not adapt to dark mode as a symbol does; I did not view it in dark mode (no display).

(b) SF Symbols. `NSImage(systemSymbolName:accessibilityDescription:)` or SwiftUI `Image(systemName:)`; they scale with text, tint with `foregroundStyle` and adapt to light and dark and to increased contrast on their own. All 24 I tried exist on this macOS (`doc`, `doc.text`, `doc.richtext`, `swift`, `curlybraces`, `chevron.left.forwardslash.chevron.right`, `photo`, `gearshape`, `lock.doc`, `tablecells`, `terminal`, `doc.zipper`, `cylinder.split.1x2`, `shippingbox`, and others). There is no symbol per language beyond `swift`, so the mapping is by category: code, markup and docs, config and data, styles, image, lock, archive, shell, test. That is monochrome and neutral, which matches the design, with no licence work (Apple's SF Symbols licence limits use to apps for Apple platforms, which this is) and the table is about 40 lines in `CarrierCore`. Cost: the app loses the visual cue of the language.

(c) Open-source sets, licences from the GitHub licence endpoint and each README, counts from the repo trees: `vscode-icons/vscode-icons` has the source code under MIT but states "The icons are licensed under ... Creative Commons - ShareAlike (CC BY-SA)" and that "branded icons are licensed under their copyright license" (1,252 file-type SVGs plus 452 folder ones): attribution plus ShareAlike on a bundled app is a burden. `material-extensions/vscode-material-icon-theme` is MIT (906 SVGs). `jesseweed/seti-ui` is MIT (169 SVGs, a small set with the "tile" look closest to the placeholder). `devicons/devicon` is MIT (1,877 SVGs) but covers technologies and logos, not file types. `microsoft/vscode-codicons` is CC-BY-4.0 and is UI glyphs, not file icons. For a brand logo inside any of them (TypeScript, Python), the trademark belongs to its owner whatever the repository licence says; I did not audit each file. Bundling in SwiftPM: put the SVGs in `Sources/<target>/Resources`, declare `resources: [.process("Resources")]` (or `.copy`), and read them with `Bundle.module`; `NSImage(contentsOf:)` loads SVG natively on this macOS (an `_NSSVGImageRep`, verified), so no asset catalog is needed, which matters because the spec builds with only the Command Line Tools and `actool` is part of Xcode. SwiftPM puts resources in a `<Package>_<Target>.bundle` next to the binary, which `build-app.sh` has to copy into `Carrier.app/Contents/Resources` (not checked against the current script). The design says a proper icon set comes later, so (c) is the later step.

Recommendation: (b) now. It is the only option whose look does not depend on the user's machine, and it keeps the design's colour rule. Take (c) Material Icon Theme (copy about 30 SVGs and keep the MIT notice in an about screen) only if file rows must show language identity. Do not use (a).

## 9. "Continue in Terminal" from a sandbox-less, ad-hoc-signed app

Short answer: write a one-use `.command` file and open it with `NSWorkspace`. It needs no permission prompt, no usage string and nothing that a rebuild invalidates, and it follows whatever app the user set to open `.command`.

(a) AppleScript `do script`. Terminal's dictionary (`sdef /System/Applications/Utilities/Terminal.app`) defines `do script` with a text direct parameter, "Runs a UNIX shell script or command", and optional `in` (a tab; without it Terminal opens a new window). Sending Apple events to another app needs the Automation permission: the first call shows the TCC prompt "Carrier wants to control Terminal", and the app needs [`NSAppleEventsUsageDescription`](https://developer.apple.com/documentation/bundleresources/information-property-list/nsappleeventsusagedescription) ("required if your app uses APIs that send Apple events", macOS 10.14 and later). A refusal is remembered and the user must undo it in System Settings, Privacy and Security, Automation. For an ad-hoc signed app the permission is tied to a code identity that changes with each rebuild (the earlier research flagged the same open question for notifications, [macos-app.md](macos-app.md) section 3); I did not run this because it would raise a prompt on the user's desktop, so the re-prompt after a rebuild is unverified. It also stacks two quoting layers (AppleScript string, then the shell line typed into the session) and types the line into a shell that may be mid-startup.

(b) A temporary `.command` file. `UTType(filenameExtension: "command")` is `com.apple.terminal.shell-script` (verified), and `NSWorkspace.shared.urlForApplication(toOpen:)` for such a file returned `/System/Applications/Utilities/Terminal.app` here (verified; the user can change it in Get Info, Open With). Steps: create the file in `NSTemporaryDirectory()` (a per-user directory under `/var/folders`), with a random name and mode 0700 set at creation (`FileManager.createFile(atPath:contents:attributes: [.posixPermissions: 0o700])`, verified: the file came out `-rwx------`), then `NSWorkspace.shared.open(url)` or `open(_:withApplicationAt:configuration:)` ([docs](https://developer.apple.com/documentation/appkit/nsworkspace/open(_:withapplicationat:configuration:completionhandler:))). It is a file written by the app itself, so it carries only `com.apple.provenance` and no `com.apple.quarantine` attribute (verified with `xattr`), and Gatekeeper's "downloaded from the Internet" dialog does not appear. I could not open it here (it would launch Terminal on the user's screen); the claim that Terminal runs a `.command` in a new window without further prompts is standard behaviour I did not observe in this session. The script should delete itself first (`rm -f -- "$0"`, safe because the shell holds the open file), then run, then leave the user in a shell: `exec "${SHELL:-/bin/zsh}" -il` as the last line, otherwise the window's behaviour on exit depends on the user's Terminal profile. Sweep stale `carrier-*.command` files older than a day at app start in case the open failed. For the shell, use the shebang `#!/bin/zsh -il`: under a minimal PATH `-l` found the Homebrew Node and `-il` found the nvm one (`-il` took 1.2 s), the same finding as macos-app.md section 2; but if the engine sends an absolute path for the agent binary, PATH hardly matters.

(c) `open` forms. `open -a Terminal <folder>` opens a window in that folder but runs nothing; `open -a Terminal file.command` is (b) through the shell; `open -na Ghostty.app --args -e <cmd>` runs a command in Ghostty but, per [a Ghostty discussion](https://github.com/ghostty-org/ghostty/discussions/10203), `-e` shows an "Allow Ghostty to Execute" confirmation with no "always allow", and the window closes when the command ends unless `--wait-after-command=true` is passed. I did not run these.

(d) Respecting the user's terminal. The right hook is Launch Services, not a settings list: `urlForApplication(toOpen: commandFileURL)` returns what the user chose for `.command`, and `NSWorkspace.open` of the file uses it, so a user who made iTerm2 the handler gets iTerm2. That works only for terminals that register for `.command`; I believe iTerm2 does and I could not verify it (iTerm2 is not installed here, Ghostty neither; Warp is installed and I did not test what it does with a `.command`). Per-terminal APIs exist but each is its own work: iTerm2 has AppleScript `create window with default profile command "..."` ([iTerm2 scripting docs](https://iterm2.com/applescript.html)) which needs Automation like (a); Warp's [URI scheme](https://docs.warp.dev/features/uri-scheme) has `warp://action/new_window?path=<folder>` and `warp://launch/<launch configuration>` but no documented way to pass a command in the action URIs; Ghostty 1.3 has [AppleScript support](https://ghostty.org/docs/features/applescript). I would not build any of them now: ship (b), and add a "Terminal app" setting only if someone asks.

Safest way to build the command. The id and the path come from the engine, so treat them as untrusted input even though the socket is user-only (ADR 0005 already validates in the other direction). First, do not send a shell string over the socket: send structured fields, for example `{ harness, sessionId, cwd }`, and let the app decide the argv from an allowlist per harness (`claude --resume <id>`, `codex resume <id>`). Second, validate before use: `sessionId` must match a strict pattern (`^[A-Za-z0-9-]{8,64}$`; the engine should check the same, since it receives it from the runner), `cwd` must be an absolute path with no control characters or newlines, must exist as a directory after `realpath`, and must sit under the configured shared root (`<root>/worktrees/` or `<root>/repos/`). Third, quote each value for the shell instead of splicing it: wrap in single quotes and replace each `'` with `'\''`, write them as separate words (`cd -- '<cwd>' || exit 1`, then `exec '<claude path>' --resume '<id>'`), and never use `eval` or backticks. Fourth, keep the file private (0700, random name, deleted by itself). With a validated id from the allowlist pattern and a path with no control characters, single-quoting is injection-proof; the validation is what makes the claim, the quoting is the second layer. With AppleScript the same values would additionally need AppleScript string escaping, which is the main reason to avoid (a).

## 10. Start at login

[`SMAppService.mainApp`](https://developer.apple.com/documentation/servicemanagement/smappservice) (macOS 13.0 and later) is "an app service object that corresponds to the main application as a login item"; `register()` "registers the service so it can begin launching subject to user approval", `unregister()` undoes it, and `status` is one of `notRegistered`, `enabled` ("registered and eligible to run"), `requiresApproval` ("registered, but the user needs to take action in System Preferences") and `notFound` ([Status](https://developer.apple.com/documentation/servicemanagement/smappservice/status-swift.enum)). `SMAppService.openSystemSettingsLoginItems()` opens System Settings at the Login Items pane, which is where the app should send the user when the status is `requiresApproval`. It replaces `SMLoginItemSetEnabled` and needs no helper bundle for the main app, and the app needs the macOS 26 floor the spec already sets. What the user sees: on registering, macOS posts a "background item added" notification attributed to the app, and the app appears in System Settings, General, Login Items and Extensions, in the "Open at Login" list with its icon and name and a toggle; the user can switch it off there at any time, after which `status` reports `requiresApproval`, so the app's own checkbox must read `status` each time it is shown, not a stored boolean. I did not call `register()` (it would change the user's login items), so none of the visible parts were seen.

The ad-hoc signing caveat is unverified. Apple's documentation states no signing requirement for `mainApp`, and an Apple Developer Forums thread I read on registering a login item blamed a crash on two differently signed builds of the same helper, not on `SMAppService`; a secondhand blog report says the call can silently fail for unsigned, un-notarized Electron apps, which I could not confirm. The risks to test with the real `Carrier.app` on a second Mac are: that `register()` succeeds and `status` becomes `enabled` for an ad-hoc signed bundle; that the entry listed in System Settings shows the bundle name rather than an "unidentified developer" label; that the item keeps pointing at the app after a rebuild changes the cdhash; and that the app must live in `/Applications` (the spec builds into the repo). Note the spec lists "opening the app at login" under "out of scope" ("Distribution to other people: signing, notarization, auto-update, opening the app at login and starting Carrier by itself"), so this would be a change to the brief; and even with start at login the engine stays an explicit Start button, as the spec requires.
