Agent output — design spec

What we decided, drawn to the point: every state, the numbers (1 px here = 1 pt in the app), the colours as SwiftUI values, the rules, and what to touch. Dark by default; the button switches the whole page to light so both can be checked.

0 · What was decided

  1. Lines — D (quiet + grouped). A run of ≥ 2 successful calls folds into one group row. A lone call is one quiet line. A failed call is never inside a group; it breaks the run, shows a red ✕ and starts open. No ✓ for success anywhere in the log.
  2. Detail — flat grey. The opened call is a flat grey block (same grey as the message bubble), no glass, no pill. Red only for what failed (Exit code N), the rest in normal text.
  3. Edit — name first. File name bold, folder dim after it, counts once, no ✓, no duration, no inline summary.
  4. Slices — R (the card where it starts). The flow is one chronological list. A slice is a row (two lines, chevron at the side) placed where it was taken; the row is alive (spinner → ✓ / ✕), its lines open in place under it. Lanes are no longer stacked after the main agent.

4 · Rules

Grouping

  1. Walk the items in order. A run is consecutive calls that are finished, ok and of kind shell, read, search or other (not skill, not edit).
  2. Run of 1 → a plain quiet line. Run of ≥ 2 → one group.
  3. Anything else ends the run: a message, note, error, skill, edit, slice row, a failed call, a pending call.
  4. A pending call is always its own line (spinner) after the group; when it finishes ok it joins the run, and the count goes up by one. If it fails, it stays a line with ✕.
  5. Label: counts by kind in the order of the first call, joined by " · ": shell "Ran N command(s)", read "read N file(s)", search "searched N time(s)", other "used N tool(s)". Capitalise the first word. Max two parts, the rest "+N more".
  6. Duration = the sum of its calls' durations (not wall time), formatted like a call's.
  7. Folded by default. What the user opens is remembered by the group's id (the id of its first call), like OutputFolds. A group keeps its id when calls are appended, so it does not close while a live run grows.

Titles

  1. A shell title skips a leading cd … (and cd … && / ;), then is the first real command. If nothing is left, it shows the cd.
  2. "+N" = the other commands chained after it, in tertiary 11 pt, with a help tooltip. Paths (read, search): cut in the middle, the file name stays. Shell: cut at the end.
  3. An edit shows the file name bold and the folder dim, relative to the worktree (strip everything up to and including the worktree folder; if unknown, the last two folders with a leading …/).

What shows on a call line

  1. Duration: on hover or keyboard focus; always for a failed call (red); always for a call ≥ 10 s (tertiary), because slow is information. The column is reserved.
  2. Status: nothing for ok; a 14 pt red ✕ disc for failed; a 12 pt spinner for pending.
  3. Chevron: only on a call with details; on hover/focus, always when open (rotated 90°) and always on a failed call (it is the thing to look at). A call without details (a read with no output) has no chevron and is not clickable.
  4. Failed calls start open (as today). The user's choice wins afterwards.

Detail

  1. Top strip: a shell shows "❯ command"; any other kind shows the tool name in place of ❯ (Read, Grep…), then the argument. Dim, wraps, selectable.
  2. Output: the first 7 lines, then a fade over the last visible line and "Show N more lines"; once expanded, "Show less". Red only on the line that starts with Exit code in a failed call; everything else normal.
  3. No output: "no output" in the body, footer without "Show more". Footer keeps "N lines", Copy.
  4. No outcome pill, no duration (it is on the line above).

Edits

  1. Counts once, from the diff. The engine's summary text is not shown for an ok edit. For a failed edit it is the reason, in red under the header (max 2 lines), and there is no diff.
  2. Diff longer than 30 rows: the first 30, then the console footer "Show N more lines" (same control as the detail).
  3. An edit that creates a file (only added rows) gets a small "new" tag after the name.
  4. Edits are milestones: never grouped, 6 pt around.

Slices in time

  1. Build one list from the main items and the lanes. Order by event id. A slice row sits at the id of its first task event with no status (the start).
  2. Each lane's own lines are the row's body, with the same grouping rules. They are not in the main list.
  3. The row is alive: its state comes from the lane's task events (running / finished / failed), as today. A resume is text in the meta ("resumed once"); the state keeps describing the first run (open question below).
  4. Collapsed by default, every state. The user's choice is kept by lane id.
  5. A main-agent line that happened while a slice ran (an error, a message) sits below that slice's card in the list, because its id is higher. That is the point.
  6. Title: the slice's title in the epic's list; else the lane's own description; else "Subagent". "#N" only when a slice number is known.

Accessibility

  1. A call line reads: "command, failed, 725 milliseconds" / "succeeded, 2 seconds" / "running". Duration is always in the label even when not drawn.
  2. A group: "Ran 4 commands, 5.2 seconds, closed" + hint "Shows the calls".
  3. A slice row: "Slice 246, The engine reads…, lane 1, finished, pull request 250 merged, 17 calls" + closed/open.
  4. Rows are buttons (focus ring 2 pt accent, radius 6); Space/Return toggle. The ✕ and the spinner are hidden from VoiceOver: the label already says it.
  5. The spinner is still under Reduce Motion (no rotation). The chevron turn is 0.12 s and is dropped under Reduce Motion. Nothing else animates.
