# universal-logger logs without breaking the panel

> Spike of 2026-10-15 (issue #9, epic #3). Answers the open question "Logs and panel" of the [spec](../specs/autonomous-orchestrator.md). Everything ran in a real terminal (pty) in a temporary folder under `/tmp`, with no GitHub or agents. The scripts are disposable: [`spike-logging-panel/panel.mjs`](spike-logging-panel/panel.mjs) y [`spike-logging-panel/run-pty.py`](spike-logging-panel/run-pty.py).

## Result

| Definition of done criterion | Result |
|---|---|
| 1. `docs/research/logging-panel.md` with the tested version | passes (`@ashulab/universal-logger` **0.1.1**) |
| 2. Disposable script: INFO, info/warn/error to a file, ANSI panel with no mixed lines | passes |
| 3. With `SIGINT` the file has all the emitted logs | passes |
| 4. `logError` with an `Error` keeps the stack in the file | passes |
| 5. Concrete integration mechanism with a snippet | passes (see [Recommendation](#recommendation)); the library needs no changes |

Conclusion: the library does not need a transport. It calls `console.info/warn/error/log` on every call (I read it in `dist/index.js`; no state is captured at import), so replacing those methods with synchronous writes to a file is enough. That leaves the panel as the only thing writing to the terminal.

## Environment

- macOS 27.0, Node v26.12.0 (nvm), pnpm 12.11.2, Python 3.9.6 (only for the pty).
- `@ashulab/universal-logger` **0.1.1** (the latest published, `pnpm view @ashulab/universal-logger version` → `0.1.1`; it is the one in `pnpm-lock.yaml`).
- Real pty: `run-pty.py` does `pty.fork()`, saves the raw bytes the terminal receives and after N seconds writes `0x03` (what Ctrl+C sends), so the `SIGINT` is generated by the terminal's line discipline, not by a `kill`.

## What the library does (read from the code)

- It writes with `console.log` (debug), `console.info`, `console.warn` and `console.error`. There is no transport or configurable destination.
- `configureUniversalLogger({ minLevel })` filters; the default comes from `LOG_LEVEL` or `NODE_ENV`.
- With `NODE_ENV=development` it emits `console.x(message, object)` (several lines, via `util.inspect`); otherwise, one JSON line `{message, timestamp, ...context}`. **The level does not appear in the JSON**: it is only known from the `console` method used.
- `logError(msg, err)` puts `error` (message) and `stack` (string) in the context.
- `createScopedLogger(...).info/.warn` with an `Error` stores only `error: err.message`: **it loses the stack**. `scoped.error` does keep it (it calls `logError`).

## Experiment

`panel.mjs` configures INFO, replaces the `console` methods with `writeSync(fd, "[level] " + util.format(...))` on an fd opened in append mode, emits a log every 37 ms (info, warn, `scoped.warn` with an `Error` and `logError` with an `Error`, plus a `logDebug` that must not appear) and redraws a 4-line panel every 50 ms with `ESC[4A` + `ESC[2K`. The log markers (`LOGLINE`, `DEBUGLINE`) are never in the panel text.

Commands (from a temporary folder `$T`, `S` = spike folder):

```sh
python3 -I $S/run-pty.py 3 $T/a.tty node $S/panel.mjs --log=$T/a.log --redirect=yes --sigint=handler --count-file=$T/a.count
```

### A. Redirected, `SIGINT` with a handler (criteria 2 and 3)

```
exit status 33280 exited 130
tty bytes:     6011; LOGLINE in tty: 0; seq= in tty: 0; DEBUGLINE in file: 0
emitted(count-file)=80  lines in file=      80  nonmatching lines=0
seq gaps:
last seq 79
```

- The terminal received 6011 bytes and none contains a log (`grep -c LOGLINE a.tty` → 0). Tail of what the terminal sees, with the `^C` and the cursor restored:

  ```
  ^[[2Klogs emitidos: 79
  ^[[2K===================
  ^C^[[?25h
  ```
- After `Ctrl+C`, the file has 80 lines = 79 numbered logs + `shutdown` = the emitted counter the handler wrote (80), with no gaps in `seq` and no lines outside the `[level] ...` format.
- `logDebug` with `minLevel` INFO did not reach the file (`DEBUGLINE in file: 0`).
- File sample:

  ```
  [info] {"message":"LOGLINE seq=1 info","timestamp":"2026-10-15T23:54:35.471Z","epic":"x"}
  [warn] {"message":"LOGLINE seq=3 warn","timestamp":"2026-10-15T23:54:35.547Z","epic":"x"}
  [info] {"message":"LOGLINE shutdown","timestamp":"2026-10-15T23:54:38.430Z"}
  ```

### Control: not redirected (`--redirect=no`)

```
LOGLINE in tty: 53
^[[?25l{"message":"LOGLINE seq=1 info","timestamp":"2026-10-15T23:54:45.239Z","epic":"x"}
^[[2K== carrier panel ==
...
^[[2K===================
{"message":"LOGLINE seq=2 info",...}
^[[4A^[[2K== carrier panel ==
```

Without the redirect the logs interleave with the panel (53 occurrences in 2 s), which is the problem to avoid. The rest of the experiment is valid because the panel changes only in that.

### B. `SIGINT` without a handler (the process dies from the signal)

```
exit status 2 signaled 2
last panel count=77; file lines=      78; LOGLINE in tty=0
last seq 78
```

Without a handler the process dies from signal 2 and still nothing is lost: the file reaches 78 (≥ 77, the last counter drawn), with no gaps. That is the advantage of `writeSync`: when the call returns the data is already in the kernel. **I did not test** an asynchronous `WriteStream`; that is the theoretical reason not to use it (whatever is pending in its buffer is lost on `process.exit`).

### C. `logError` with an `Error` keeps the stack (criterion 4)

JSON output (default, without `NODE_ENV=development`), `seq=5`:

```
[error] {"message":"LOGLINE seq=5 error","timestamp":"2026-10-15T23:54:35.624Z","epic":"x","error":"kaboom-5","stack":"Error: kaboom-5\n    at Timeout.emit [as _onTimeout] (file:///.../docs/research/spike-logging-panel/panel.mjs:31:55)\n    at listOnTimeout (node:internal/timers:685:17)\n    at process.processTimers (node:internal/timers:618:7)"}
```

The full stack is in the `stack` field, on a single line (with escaped `\n`), so the file is still one line per log. With `NODE_ENV=development` the same stack comes out on several lines (object formatted by `util.inspect`):

```
[error] LOGLINE seq=5 error {
  timestamp: '2026-10-15T23:54:55.725Z',
  epic: 'x',
  error: 'kaboom-5',
  stack: 'Error: kaboom-5\n' +
    '    at Timeout.emit [as _onTimeout] (file:///...panel.mjs:31:55)\n' +
    ...
}
```

Also without interfering with the panel (`LOGLINE in tty: 0`), but it breaks "one line per log" (40 continuation lines in 1 s). That is why the app must run with `NODE_ENV` other than `development`, or set it before importing the library.

With `scoped.warn(msg, new Error(...))` the file only has `"error":"scoped-4"`, with no stack (see above). For errors with a stack use `logError` or `scoped.error`.

## Recommendation

A `logging/` module that, on startup and before drawing the panel, opens `orchestrator/logs/orchestrator.log` in append mode and replaces the `console` methods. Every `console.*` in the process (including that of dependencies) stays out of the terminal; the panel writes to `fd 1` without going through `console`.

```ts
import { openSync, writeSync } from 'node:fs';
import { format } from 'node:util';
import { LogLevel, configureUniversalLogger } from '@ashulab/universal-logger';

export function installFileLogging(logFile: string, minLevel = LogLevel.INFO): void {
  process.env.NODE_ENV ??= 'production'; // 'development' emits several lines per log
  const fd = openSync(logFile, 'a');
  for (const level of ['log', 'info', 'warn', 'error', 'debug'] as const) {
    // the level is not in the library's JSON: the console method used adds it
    console[level] = (...args: unknown[]) => writeSync(fd, `[${level}] ${format(...args)}\n`);
  }
  configureUniversalLogger({ enabled: true, minLevel });
}
```

It is the same logic the spike ran (in `.mjs`); it was not compiled or tested as TypeScript. Decisions:

- **`writeSync` on an append fd**: this is what makes `SIGINT` (with or without a handler) lose nothing and removes the need to flush buffers on shutdown. Cost: it blocks the thread during each write; for the orchestrator's log volume (stage events, not the agents' stream) it is irrelevant. If a problem is ever measured, switch to a buffer flushed on `SIGINT`.
- **`console` and not `process.stdout.write`**: it is the extension point the library already uses on every call; intercepting `process.stdout` would also catch the panel.
- **Repo, epic, execution, role and stage context**: the library has no async context; it is passed in the `context` object or in the scope (`createScopedLogger('epic-12/author')`). That layer sits on top of this module and was not tested here.
- **Out of scope for the module**: each agent's full output (`executions/<id>/`) is written by the runner straight to its files and does not go through the library; the 30-day retention is another piece (story 24).
- **Not tested**: uncaught exceptions and native writes to `stderr` (they do not go through `console`); the startup module should hook `uncaughtException`, log and restore the cursor before exiting.

## Impact on the spec and the ADRs

No result contradicts the spec or the ADRs (none covers logging). It confirms what the spec says ("it writes to the console and offers no general transport", "reuse the library") and adds two integration constraints that were noted in the spec: `NODE_ENV` cannot be `development` and the level has to be added from the `console` method.

## Limitations

- A single run per case, 2 to 3 seconds each, macOS and Node 26.12 only.
- `Ctrl+C` was tested in our own pty, not in Terminal.app/iTerm; resizing and a terminal narrower than the panel were not tested.
- The panel is a toy (4 lines, redrawn in place); it does not test the real panel or the mode without an interactive terminal.
- Low load (about 27 logs/s); the cost of synchronous writes was not measured.
