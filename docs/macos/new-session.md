# New session

How a new session is planned in the draft and prepared by the chat host when the first message is sent; the conversation that follows is in [chat](chat.md#conversation).

Nothing is cloned, created or written until the first message is sent, and the draft is blank every time New session opens (the menu, ⌘N, or the + while it is open) and after a send.
Choosing a repository, a project or a folder only fills the plan.
Sending makes one `open` and the chat host prepares the session in the background, in this order and only the steps the plan needs: `clone` (or `fetch` when the repository is already in the projects folder) or `project`; `worktree` or `checkout`; `agent`; `message`.
When the folder is a project with actions on, each one is a step of its own: the after-clone ones right after the `clone`, the new-worktree ones after the `worktree` or `checkout` and before the `agent`, in the listed order ([project actions](../glossary.md)); with none on there is no such step and nothing is shown.
The new-worktree ones run again, as the same kind of step, when a session's next message brings back the folder of a cleaned worktree, before the agent goes on; a worktree whose folder is there runs none.
The conversation lists the steps, each running, done or failed, until the agent answers.
A failed step stops there with its reason in words and the message kept; Try again repeats the steps that did not finish and reuses what was made.
Cancel, while it runs, stops the step, deletes the session with its worktree (a half clone goes too, a finished clone stays in the projects folder) and puts the plan and the text back in the draft.
When the person picks a branch other than the one checked out in the folder (and no worktree), the block under the message box that says what sending does has a step for it, "Change the folder's branch" ("Switches the folder from main to feat/x when you send"), after the repository's update (`NewSessionModel.sendSteps`, `branchChange`); a fresh clone follows the pick and has no such step.
A folder that already existed with uncommitted changes is never switched to the picked branch: the `checkout` step fails and says so, see [Troubleshooting](../troubleshooting.md#a-new-session-does-not-start).
A repository is added to the engine's `repos` only once the agent has answered.
The reasons are in [the spec](../specs/session-prepared-on-first-message.md) and [0018](../adr/0018-a-new-session-is-a-plan-and-the-host-prepares-it-when-the-first-message-is-sent.md); the details follow.

## The draft and the workspace

The + of the Sessions row, the New session button of the Sessions home and ⌘N (always on) select `Selection.newSession`: a draft in the centre (`Carrier/Features/Sessions/NewSessionView.swift`; the logic is `CarrierCore/Sessions/NewSession.swift` and the `NewSessionModel` extensions beside it (`NewSessionModel+Draft`, `+Workspace`, `+Projects`, `+Send`)) that shows a round mark (a placeholder for a logo), "What do you want to work on?", "Pick where it works, then write.", the sentence and a box with the agent chip; the toolbar takes the page's own colour, not the system's band.
Nothing exists until the first message is sent.
The workspace, a chip in the sentence, opens the shared sheet of [Settings' Projects page](projects.md#projects-page) in its own mode (`AddProjectSheet(mode: .newSession)`, `ProjectSheetMode.newSession`; the logic is `projectSheetState` in `CarrierCore/Projects/ProjectSheetState.swift` and `NewSessionModel`), titled "Choose where to work".
It lists, first, the projects that are not hidden (`ProjectRow.hidden`: each with its tile, name and folder), then Suggested folders that are not projects (`recentFolders`: the distinct base folders of the sessions the host lists, active and archived, most recent first, at most eight), then the person's repositories (the host's `githubRepos`), and the field takes typing, a pasted GitHub address or a path as it does in Settings.
Its footer has Open a folder… (the system's folder panel), New project… (only when the host's hello has `createProject`) and Cancel; a folder can be dropped on it too, and the first one fills the plan.
The old chooser (a popover with the projects folder's contents, From a GitHub URL…, My GitHub repositories… and a Projects folder footer with Change…) is gone; the projects folder is changed on the Projects page of Settings.
Choosing only fills the plan, and nothing is cloned, made or written until the first message is sent: a project or a folder fills it with a folder, a repository to clone with a repository (its row says "Cloned into <projects folder>/<owner>/<name> when you send the first message", with no Choose…, since the host clones into the projects folder), New project with a new project.

## A GitHub repository

A pasted address in the sheet's field takes `owner/repo` or a github.com address (`repoReference`), and a listed repository is a row; either only fills the plan (`NewSessionModel.choose(_:)` for a row, then `choose(repo:)`): nothing is cloned, `cloneRepo` is no longer called and nothing is written to the engine's config.
A repository that is not on the Mac (`toClone`) has its default branch and its branches read from GitHub with the person's login (the host's `repoBranches`, the first hundred, with a note when there are more), which fill the same branch picker as a folder's (as plain names, since a fresh clone follows the pick), shows no uncommitted-changes line and says where it will be cloned (`repoNote`); a worktree from a branch is offered like for any folder, with its name left empty, "generated when sent", and no ↻ or name check (the host makes it).
One that is already in the projects folder is read locally with `workspace`, as a folder is, and the note says it will be fetched.
Whatever the person chose, `send` puts the repository in the plan (`PlanWorkspace.repo`) and the host runs its `clone` step (git's progress under it in the conversation) or `fetch`, then the rest.
Under a repository to clone in the sheet, "Let Carrier watch this repo" (`ProjectSheetResult.watch`, a switch; on by default; off, with the reason, when `repoProblem` refuses the repository for the config's `repos`: already there, or a folder name another repo has) is a choice of the plan: once the session is sent, the model looks at each list the host's updates bring (`ChatLink`, `settleWatches`) and, when the session's preparation is over (the `message` step is done: no preparation left), adds `{ "name": "owner/repo" }` to the config's `repos`, the file read again just before the write and once only; a preparation that fails (it waits for Try again) or is cancelled adds nothing.
The session's conversation notes it (`watchNotes`; the repo is added to `repos` and the save asks the engine to reload); a config that cannot be read, is not a JSON object or is not writable is said there as a repository that could not be added to Carrier's list.
Deleting the session undoes neither the clone nor the watch.
Nothing is restarted.

## When a tool is missing or signed out

With the host's `gh` `missing` or `signedOut` the sheet lists the projects, the suggested folders and Open a folder… and New project… as ever, and where the repositories would be it shows the fix button and Open Health in Settings, since the host cannot list or read them; `ready`, `unknown` and a host that reports no health leave the sheet as it was (`NewSessionTests`; the sheet's view has no automated test).
The agent chip lists the configured agents; one that is missing is disabled with "not installed" and one that is signed out with "signed out", while `ready` and `unknown` can be chosen.
The states are the chat host's `health` reply (`HostHealth`: `git`, `gh` and each agent as `ToolState` `ready`, `missing`, `signedOut` or `unknown`), which the app asks for (`HealthStore`, one for the app) when it opens once the host answers, when it becomes active again and on an explicit refresh (`HealthMoment`; opening takes the host's answer kept for thirty seconds, the other two ask for a fresh one), and only of a host whose hello lists `health` (`shouldAskHealth`); with an older host (or none yet) an agent whose binary was found is `ready` and one that was not is `missing`, as before (`agentChoices`).
The draft takes the first available provider and never preselects a blocked one (`pickAvailableAgent`, run again when the states change); when none is available the box says why (`noAgentReason`) and Send is off.
With `git` `missing` (`NewSessionModel.gitMissing`; `ready`, `unknown` or no health change nothing) the draft offers no New worktree and, where the folder's branch would be, the sentence says "in the folder (git is missing: no worktree, no branch. See Health in Settings)" (`workSentence(gitMissing:)`), with no uncommitted-files line; a worktree already chosen goes back to the current folder.
Each reason that Carrier can fix offers its fix (`CarrierCore/Health/HealthFix.swift`): the fixed list `healthFix` is data keyed by what failed (a provider's harness and state, `gh`, `git`), with `claude auth login`, `codex login` and `gh auth login` for a signed-out `claude`, `codex` and `gh`, `xcode-select --install` for a missing `git`, `brew install ashulab/tap/carrier` for a missing `carrier` (`HealthTool.carrier`; the Health tab's `carrier` row), and, for a missing `claude`, `codex` or `gh`, no command but its installation page; the button (`Carrier/Features/Health/HealthFixButton.swift`) names the command and `fixInTerminal` opens Terminal on it with the app's one-use script (`openScript`) and opener (`TerminalOpener`), each word quoted; what a probe, the host or the doctor returned (a name, a harness) is never part of a command, and a harness the list does not name has no fix.
The button shows in the draft under the box (a provider that is blocked, and `git` missing) and in the workspace sheet where the repositories would be (`gh`); coming back from Terminal re-checks the health (`HealthMoment.active`) and the reason goes when the state is `ready`.

## The folder, the branch and the worktree

Above the box the sentence reads "Work in Choose a workspace…" (orange), with the box dimmed and unable to send until one is chosen.
Once one is, the app asks the host what it is (`workspace`) and the sentence reads "Work in <workspace> on Current folder (<branch>)" ("detached HEAD" when there is no branch), with a line under it when the folder has uncommitted files (how many, and that a worktree keeps them out of the agent's way); a folder that is not a git repository (or is bare) reads "in the folder (not a git repository: no worktree)" and offers no worktree.
"Current folder" is a menu of two choices that switches to "New worktree carrier/<name> from <branch>", with a line under the box saying what it creates: the name is the host's `suggestName` with ↻ for another, the part after the fixed `carrier/` is editable and `checkName` asks about it 400 ms after the last keystroke (a taken or invalid name is red with the host's reason and cannot be sent), and the branch control opens a picker with a search, the branches and Fetch now (`fetch`), which says how long ago the remote branches were fetched.
The branch defaults to the one checked out in the folder, else the repository's default branch, else the person is asked.
Sending in a worktree puts `branch` (the one the worktree starts from) and `worktree: {name, startFrom}` in the plan; a refusal is said in the draft.

## Where a worktree starts

A new worktree is cut from the remote copy of the branch by default, and the person can cut it from the local branch instead ([0037](../adr/0037-a-new-worktree-is-cut-from-the-remote-branch-by-default-and-choosing-a-project-fetches-it.md), [the spec](../specs/worktrees-start-from-remote.md)).
The branch picker of a worktree (`BranchSheet`) has two tabs under the search field, Remote and Local, with how many branches each lists, and one list at a time (`BranchPicker.rows`), so a branch is never offered twice: the Remote tab lists the branches on `origin`, the Local tab the local ones.
A local branch with no counterpart on `origin` is only in the Local tab, marked "not on origin" (`BranchRow.localOnly`), and a branch that is only on `origin` is only in the Remote one.
The picker opens on the tab `worktreeStart` of `chat.json` says (`NewSessionModel.startTab`, read when the workspace is chosen, [Settings](settings.md)), Remote when it says nothing.
The tab the person leaves it on is the session's own choice (`chosenStart`): it is sent as `worktree.startFrom` with the branch's bare name, it is forgotten when another workspace is chosen, and it never writes the setting.
Choosing a row of a tab chooses its side with it; choosing a branch that exists on one side only cuts from that side whatever the tab says, so a local-only branch is sent as `startFrom: local` (`startPoint`, pure and tested in `WorktreeChoiceTests`).
The "from" chip of the sentence says `origin/<name>` or `<name>` and wears the colour of its side (teal for Remote, indigo for Local), and the picker's summary says the same ref.
The send steps card has "Bring the latest `origin/<name>`" before "Create a branch of its own" when the start is remote, and not when it is local.
A repository from GitHub has its own step that fetches or clones, so it does not get that one, and an older host (its hello lacks `worktreeStart`) does not fetch a folder, so it does not either.
A host whose hello lacks `worktreeStart` takes no `startFrom`: a Remote choice is sent as `branch: origin/<name>`, as the app always could, and a Local one as `branch: <name>` (`worktreeRequest`; `NewSessionTests`).
A repository that is not on this Mac yet has no local side: no tabs, the two sections it always had, and a plan with no `startFrom`.
The sheet of a session in the person's own folder (`browsing`) is not changed, and neither is its pick.

## Choosing a project fetches it

Choosing a folder, or a repository already in the projects folder, that is a git repository with an `origin` fetches it in the background (`NewSessionModel.choose(folder:)`, then `fetch(whenChosen:)`).
Only a host whose hello lists `fetchIfStale` is asked (`hostFetchesIfStale`); the app sends it `fetch` with `ifStale: true`, which the host answers without a git call when the last fetch is within its window (five minutes).
An older host is not asked and not sent the field: choosing fetches nothing and Fetch now works as it always did.
A folder that is not a git repository, a bare one, one with no `origin` (`WorkspaceInfo.hasOrigin`: the host names a GitHub remote as `repo`, and any remote shows by its `origin/*` branches on disk) and a repository still to clone are not fetched.
This is the one place where choosing a folder writes to it, and only `FETCH_HEAD` and the `origin/*` refs, never a branch, the index or the working tree ([0037](../adr/0037-a-new-worktree-is-cut-from-the-remote-branch-by-default-and-choosing-a-project-fetches-it.md)).
The branches show at once from what is on disk, and the spinner beside the project's chip (the one that marks GitHub's branches loading) turns while the fetch runs (`NewSessionModel.fetching`); when it ends the picker shows the refreshed branches, and a fetch inside the window ends it at once with nothing changed.
A fetch that cannot reach the remote shows no error and asks for nothing: it sets `unreachable`, and the picker's footer says "Could not reach origin" in orange under "Fetched 3 days ago" (or "Never fetched"), in place of the "may be out of date" line (`BranchPicker.unreachable`).
Fetch now ignores the window, fetches again whatever the footer says, shows its own failure in red as before, and clears `unreachable` when it works.
Choosing another workspace drops the answer of a fetch left behind (`fetchRuns`), so a slow one never fills the picker of a project chosen after it.
The request waits 70 seconds for the answer, ten more than the host gives a fetch.

## Behind and not pushed

A local branch that has a counterpart on `origin` carries `behind` (commits of `origin/<name>` it lacks) and `ahead` (commits not pushed) in the `workspace` and `fetch` replies (`WorkspaceInfo.Branch`; both optional, since a host that does not count, and a branch with no counterpart, send neither).
In the Local tab a row shows "N behind origin" and "N not pushed" in orange (`Badge`, with an arrow down and up) when they are not zero (`BranchRow.behindText`, `notPushedText`); a branch level with its copy shows nothing, and one with no counterpart shows only "not on origin".
The summary under the list names the ref the worktree is cut from, and under it a warning (`ProblemLine`, `startWarning`) says, with Local chosen, that the branch is N commits behind `origin/<name>` so the worktree starts without them, and, with Remote chosen, that the local branch has N commits not pushed to `origin/<name>` that the worktree will not have.
A branch with nothing to say, a branch on one side only and a repository to clone have no warning.
The fixtures carry the states: `/Users/dev/carrier` has `main` behind (2, then 12 after the fetch), `feat/retry-sync` not pushed (1) and `wip/spike` on neither, `/Users/dev/web` has a branch level with `origin`, and the fetch of `/Users/dev/work/web` fails, so the footer says it could not reach origin.

## Sending and the preparation

The draft is blank every time it opens (`NewSessionModel.blank`, run by `load` and, for the menu or the + while the draft is already open, by the window's `newSessionOpened` count): no workspace, no worktree choice or name, no text.
The workspace chip has no ✕: another workspace is chosen from the chip itself (`clearWorkspace` is what the blank draft uses: the workspace and its branch, worktree choice and name go, the text stays), and after a send the draft is blank again, so the next send carries nothing of the last one; choosing a repository, a project or a folder only fills the plan.
Opening the draft (`NewSessionModel.load`) starts the chat host when it is not running (`ChatHostStarter.ensureRunning`) and asks it again for the agents and the recent folders; sending (`NewSessionModel.send`) starts it too when it went away (`ChatHostStarter.ensureRunning`), makes one `open` that carries the plan (`SessionPlan`: the folder as a workspace, the agent, the options chosen, the first message, and the branch and worktree name for a worktree) and nothing else, and selects the session, which the host answers at once in the `preparing` state and shows in the sidebar as working.
The app sends a plan only when the host's hello lists `plan`; against one that does not the draft says the host is older and to restart it (`NewSessionModel.hostOlder`, checked again at the send) and sends nothing, and the old `open` of a folder and a worktree is no longer used by the app.
A refusal of `open` is said in the draft and the text stays.
The conversation of that session shows the steps as a list at its top (`preparationSteps` in `CarrierCore/Epics/PreparationSteps.swift`, a pure function from the `step` events and the `preparation` of the `events` reply, with the `progress` line on the running step): each step running, done or failed with a line in words and the reason under a failed one, until the agent answers; an action is a row named with its own title ("Running Install…", "Ran Install", "Install failed") and the terminal icon, shows the last line it wrote as its progress, and a failed one that is set to stop shows the end of its output as the reason (`StepRow.action`, `StepRow.icon`); one set to warn is done, with a notice in the conversation naming it; the first message shows as the person's message until the host records it (`ConversationModel.show(firstMessage:)`), so a failed step does not lose the text.
A first message that names a command of the agent is carried as typed.
A failed preparation shows Try again under the list (`ConversationModel.retryPreparation`, the host's `retryPreparation`: it repeats the steps that did not finish and reuses the worktree and the checkout already made), and one that is preparing shows Cancel (`cancelPreparation`: the host stops the running step and deletes the session with its worktree and answers the plan, which the app hands to the draft with `NewSessionModel.restore`; the draft that opens next, `load`, puts back the folder, the branch or worktree and its name, the agent, its options and the text); a refusal of either is said in words under the list. The same list and Cancel show while a cleaned worktree session's folder comes back and its actions run (the host reports `preparation: running` with the session not `preparing`): the list is the `worktree` step that opens the restore (the host's `bringBack` records it, so there is a row before the first action) and the `action` steps after it, from the latest `worktree` step that ends the log (`preparationSteps(restoring:)`, so earlier turns' rows and an earlier restore's are left out; a restore that goes on after it stopped keeps the first try's step), and the host's Cancel there answers `{plan: null}`, the session stays, nothing goes to the draft and no refusal is said (`cancelPreparation` is nil).
Both are for a host whose hello lists `plan`.
What each agent lists (models, reasoning, access and commands) is kept in the app's cache folder (`AgentOfferStore`) and shown at once; asking for it launches a real agent, so when the app opens only the agents with nothing kept are asked, one at a time (`warm`), and the draft and the model picker ask again when they open, showing the kept list meanwhile.
The model, the sentence and the lists are tested with a fake `ChatHost` (`NewSessionTests`); `--smoke-window` prints what the draft offers, what the sheet lists (`new session sheet:`), a repository through the fixture host whose branches are listed and one that is refused, and a new project.
