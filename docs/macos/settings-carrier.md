# Settings: the Carrier group

The pages of the Carrier group of [Settings](settings.md): how Carrier runs epics and how the app runs Carrier.

## Watching

The Watching page, in the Carrier group of the sidebar, is the repos Carrier takes epics from: the `repos` of `engine.json` (a `Form` page like Roles, in `Carrier/`: `WatchingTab.swift` reads the file, sends each change of the list to the engine (`setWatchedRepos`) and chooses the screen, `WatchingListScreen.swift` is the list and the picker, `WatchingRepoScreen.swift` a repo's groups, `WatchingRole.swift` a role's screen and `WatchingBanner.swift` the refusal; rows in `CarrierCore/Settings/Watching/RepoList.swift`, their order and the picker in `CarrierCore/Settings/Watching/WatchingList.swift`, tested in `WatchingListTests`).
It was called Repos and was a master-detail with its own Add repo; the projects are now where a repo comes from, so Watch a project is the only way in, and a repo's own page is a screen of the window's history (‹ ›) that a row opens.
The first screen is one group of rows titled Repositories, as Projects' list is, with no line of column titles: each repo is a row with the project's tile (the repo's own letters when no project has its origin) and a dot for its health (green ok, red when GitHub refused it, grey when new or Carrier is stopped), `owner/name`, under it the name of the project that has it as its `origin` ("No project" when none does) and what the last check said (the engine's error, in red, when GitHub refused the repo), at the right chips for the epics it has (needs you, running, queued; none when it has none or Carrier is stopped) and a chevron that opens the repo's screen.
GitHub's refusals are first and the others go by name (`watchingOrder`).
A repo with its own map of extra reviewers, or with none, says so with a chip among the ones at the right of its row (Own reviewers, No more reviewers); a repo that follows Roles has none (`RepoRow.extras`).
The toolbar has the page's actions on one glass capsule (`SettingsHeaderButtons`, `ToolbarPillButton`): Check now (the menu's Check GitHub now, off while Carrier is stopped) and Watch a project…, whose popover hangs from the top right of the page.
Watch a project opens a popover of the projects with a GitHub `origin` that are not watched, with a search (`watchChoices`, `WatchPicker`): a project whose repository the engine would refuse next to the watched ones (the same folder name, `repoProblem`) or that has no GitHub origin is there, off, with the reason; a click watches the repo, and Add project… goes to the Projects page.
With nothing watched the page is an empty state with Watch a project….
Changes are saved as they are made, like the Behavior tab's (watching a repo, or stopping to watch one after the question; a list the engine would refuse waits and says why), and nothing restarts Carrier.
The file is read again just before writing, a kept repo's entry is written back as it was (including anything the app does not show) and a new one is only its name, so the two tabs never overwrite each other's keys.
When the engine reads the saved file and refuses it, it keeps the settings it had, so what was just saved (a repo watched, a role changed) is not in use yet whatever page saved it: the page then shows a banner and not the plain note (`refusalBanner`, `RefusalBannerView`), "Carrier is not using your latest settings", with the reason in words when it is a failover step of a role that repeats the role's own provider and model, another step or an undeclared provider (and Open Roles, where it is mended), the engine's own words kept folded under "What Carrier said", and Ask Carrier again.
Any other reason is shown as the engine says it, with no way to mend it from here.

A repository's screen is a group for each thing it says or does, in the order of what a person comes here for (`WatchingRepoScreen.swift`): Status (the epics and the last check), Ready for Carrier, Who works here, Repository (the project, the clone and GitHub) and, last and in a group of its own, Stop watching…, which asks first, with what happens to the repository's epics (they stop where they are and continue if it is watched again; nothing is deleted), and goes back to the list. Open on GitHub and Check again (turning while the doctor runs) are on the toolbar's capsule, and its name is the toolbar's title with `Watching` under it (and, when GitHub refused it or Carrier is stopped, why).

It has three cards.
It starts with its Status card (`CarrierCore/Projects/RepoStatus.swift`, fed with the list's row): the epics ready and running, the last check, the clone with `~` and Reveal (only when the clone exists), the repo on GitHub with Open and the project that has it as its origin, with Open project (or Add project…, which goes to the Projects page, when none has); a repo the running engine has not loaded, and every repo while Carrier is stopped, says "Carrier reads it when it starts" in place of the epics and the last check.
Under it, Ready for Carrier (`CarrierCore/Settings/Watching/RepoChecks.swift`, `repoChecks`, tested in `RepoChecksTests`) shows four rows from the checks of `carrier doctor --json` that are about the repo (their `repo` and `profiles`): Carrier can read it, Author can sign here, Reviewer can sign here and Solve is set up, each ok, failed with the doctor's reason and fix, or waiting.
A role's row is the repo's `can mint a token` check whose `profiles` holds the profile the role resolves to in that repo, so two roles of one identity show the same check; a check the doctor did not report (something before it failed) is waiting, never failed.
A failed sign row offers Use another identity (`RepoCheckRow.anotherIdentity`), which opens that role's screen in this repo (below); no other row offers it.
The doctor (`AppHealth.doctor`, shared with the Health tab) runs when the page opens and on Check again, never in the background; while it runs or when it could not answer, a line says so and the rows wait.
`--fixture` answers the run with `Tests/Fixtures/doctor.json` (copied into the fixture home), which carries the new fields: `acme/web` all ok, `acme/api` with a failing reviewer and no Solve labels, the long-named repo unreadable.
Who works here is the Roles page's rail of roles (`EpicRail`, with `own` set, without the extra reviewers, which have their group below; the repo's roles are `repoRolesPage` in `CarrierCore/Settings/Roles/RepoRoles.swift`: the global `agents` with the repo's own fields over them, and the Lead reviewer only as the global config has it, off included, tested in `RepoRolesTests`): each role with its picture, what it does, its model and identity and a chip, Own when the repo has settings of its own for it and "Same as everywhere" when it follows Roles, and a chevron that opens the role's screen; the group's footer says every repository follows the roles of Roles unless it has its own settings.
A Lead reviewer that is off in Roles is on the rail with the word Off at the right of its row, as on Roles.
More reviewers here, a group after Who works here and before Repository (`more-reviewers-here`), is the repo's extra reviewers, read only: the engine replaces the global map with a repo's whole, so it is one state and not a field by field override (`RepoExtraReviewers`, read from `repos[].agents.extraReviewers` by `repoRoles`): Same as everywhere when the key is not there (the list of Roles runs, each reviewer with "From Roles"), Own list when it is a map with entries, and None when it is `{}` ("Only the Reviewer reviews here").
The state is the chip at the right of the group's title, the footer says what it means and that the app does not change the list yet (the engine has no request that writes it, so nothing on the screen offers to), and each reviewer that runs there is a row with its picture, its name and under it its model, effort and identity, and a chip with its type (`repoExtraReviewers`, the roles page of the repo with its map in place of the global one, in the order of the repo's own file; tested in `RepoRolesTests`). Its persona, failover steps and skills are the Reviewer's.
The fixture's `acme/web` has an own map of one reviewer, the long-named repo has `{}` and `acme/api` follows the two reviewers of Roles.
A role's screen in a repo (`SettingsPlace(.watching, path: [repo, role])`, `Carrier/Features/Settings/Watching/WatchingRole.swift`) is Roles' own with what a repo can set: its picture and who it works as, the strip "In an epic", Who (Identity: a profile of `profiles`, and Model: the account, model and effort from the same panel Roles uses) and Persona (name and prompt), and, when the repo has settings of its own, Reset to Roles. Each field says "Same as everywhere" with what it follows and is not written while it is left there; each one is sent as it changes, with no Save (`EngineConfigChange.repoRole`, the engine's `editRepoRole`, `src/config/role-edit.ts`, tested in `role-edit.test.ts` and `EngineConfigRequestsTests`; the form still checks what it can while you type, `RoleFields.problems`). Skills and When it runs out of tokens are Roles' only: a repo cannot set them.
The save reads the file again, writes only `repos[].agents.<role>` with the fields set (texts trimmed, a model of only spaces and an empty persona not written, an entry that would be empty removed) and keeps every other key; Reset to Roles removes the role's entry.
A profile or account that is not declared (shown as missing) is refused before writing, in words.
Author and Reviewer on the same identity is accepted and the card says the signature will show it.
After a save the doctor runs again, and when the engine refuses the config its reason (the doctor's stderr from `Invalid config`, `DoctorState.refused`) is shown under the roles and in the Ready for Carrier note.
The fixture's `engine.json` (`fixtureConfig`) has the three fixture repos, the profiles, the three roles and the extra reviewers.

## Roles

The Roles page, in the Carrier group before Watching, has the three fixed roles, Author, Reviewer and Lead reviewer, as two kinds of screen, each a place of the window's history (‹ ›) as Providers and Dictation have: a first screen and one screen for each role, whose path is the role's name (`SettingsPlace(.roles, path: [role.rawValue])`; `Carrier/Features/Settings/Roles/RolesTab.swift` and `RolesParts.swift`, model in `CarrierCore/Settings/Roles/RolesPage.swift`, tested in `RolesPageTests`; the views have no test).
The first screen is a status card (`rolesReadiness` in `CarrierCore/Settings/Roles/RolesReadiness.swift`, tested in `RolesReadinessTests`: whether Author, Reviewer and, when it is on, the Lead reviewer each have an identity, an account of `providers.json` and a model, with what is wrong said with the role's name and a button to open it; it says nothing of whether an account is signed in, which is the Providers page's answer), then How an epic runs; the identities are no longer a group of this page, they are the [Identities page](#identities).
The extra reviewers of `agents.extraReviewers`, a map from a key to an entry with a `name` and a `type` ([ADR 0057](../adr/review/0057-an-extra-reviewer-is-an-entry-of-a-map-with-a-key-a-name-and-a-type.md)), are roles too, addressed by their key (`RoleSlot.extra(key:)`, next to `author`, `reviewer` and `lead`), so a role's place is `SettingsPlace(.roles, path: [slot.name])`, the key for an extra reviewer; a place whose key is not in the file (it changed) shows the first screen.
`rolesPage` reads one row per entry of the map, in the order of the file (`jsonKeys` reads it, since a dictionary has none), at most three, titled by the entry's name and with its type, and with the fields of the other roles; a list, which the engine refuses, and an empty map give no row; an entry with no `failover` has the Reviewer's steps (`ownSteps` is false, the engine's `failoverStepsOfSlot` rule), tested in `RolesPageTests` with zero, one and three extra reviewers.
The status card checks every extra reviewer as it checks the others and names it by its name ("Usabilidad: it has no identity yet.") with a button that opens it (`RolesReadinessTests`).
An engine that announces the capability `extraReviewers` in its hello (`EpicStore.canEditExtraReviewers`) lets the page add, change and remove them; one that does not, or none answering, leaves an extra reviewer's screen as quiet values (`ExtraReviewerScreen.swift`: the name as the window's title, the type as a label under it) and offers no Add a reviewer, and its footer says the engine that is running does not edit them.
With the capability an extra reviewer's screen is drawn as the Reviewer's (`RolesTab+Groups.swift`) with three differences: Who starts with its Name and its Type (a lowercase word, `general`, `ux`, `security` or any slug), Skills say "Same as Reviewer", and the last row is Remove <name>.
It is the Reviewer's screen with Who signs (name, type, identity, account, model and effort), Persona, When it runs out of tokens (its own steps, or "Same as Reviewer" with the Reviewer's steps in the line under it) and Skills ("Same as Reviewer", the Reviewer's review stages with "Runs as").
Each field is sent as it changes, through `EngineConfigQueue`, pointing at the reviewer by its key (`RoleSlot.edit`, `.persona`, `.failover`, `.renamed` and `.retyped` in `CarrierCore/Settings/Roles/RoleEdits.swift`, tested in `RoleEditsTests`; the engine's `editRole`, `editPersona` and `editFailover`, `src/config/role-edit.ts`), and the key does not change when the name does; a refusal (a name another reviewer has, a type that is no slug, an account that is not one) is shown under the group it came from with the engine's words, and the field goes back to what the file has.
Switch automatically off, which sends both steps as none, takes the reviewer's own list out and it goes back to "Same as Reviewer"; choosing a first step gives it a list of its own.
Remove <name> asks first (an alert that says running epics keep it) and sends `removeExtraReviewer` for its key: the entry and its steps go, the identity it used stays in `profiles` and the other reviewers are as they were; the window goes back to Roles.
On Roles, under How an epic runs, Add a reviewer (`ExtraReviewerOffer`) says how many more can run ("2 more reviewers can run") and is disabled at three extra reviewers (four reviewers with the Reviewer), where it says four is the most; it is not there while the engine does not announce the capability.
It opens the new reviewer's screen as a draft that says "Not saved yet" and what it still needs (`NewExtraReviewer`, kept in the page as the lead's draft is, tested in `NewExtraReviewerTests`): the type starts on `general`, nothing is written until it has a name, a type, an identity, an account and a model, and then the whole entry goes in one request (`addExtraReviewer`; the engine gives it its key from its name), so the file never holds half a reviewer, and a name another reviewer has is refused with the engine's words and the draft stays.
Its Persona, steps and Skills are on the screen of the reviewer once it is saved, and leaving the draft before that drops it.
The "In an epic" strip of every role's screen lists every role, the extra reviewers included, each a link.
The search of Settings finds each extra reviewer's row by its name or its type: the static `SettingsIndex` has none, and the sidebar adds the ones of the file (`rolesSearchEntries`, as it adds the providers of this Mac).

How an epic runs (`EpicRail`) is the roles in the order an epic goes through them, one row of the form with a rail drawn through it: Author, then "Opens the pull request" and "↺ asks for changes, the author answers", Reviewer, then "When every reviewer agrees · up to N rounds with the author" (N is `limits.maxLeadRounds`, 3 when the file has none: `RolesPage.leadRounds`), Lead reviewer (the last stretch is dashed and says "Lead reviewer is off" while it is).
With extra reviewers the Reviewer and they are one step (`ParallelStep`): a tinted box under "In parallel, on the same commit · one verdict is enough", their rows in the order of the map; with none the rail is as above.
A line under the rail (the group's footer) says each reviewer is one more agent on every epic, when there is more than one.
Each role is a button with its picture (`RoleAvatar`), what it does (`AgentRole.purpose`) and, at the right, its model and effort over its identity, "Off" for a Lead reviewer that is, or "Needs attention" when the card says something of it.
A role's picture is its identity's: a bot of Agent Forge shows the logo of its GitHub App (the registry has no avatar field, but each bot is a GitHub App and `avatars.githubusercontent.com/in/<appId>` is public, so `forgeBots` reads the digits-only `appId` and `forgeAvatarURL` builds the address; `ForgeAvatarStore` fetches it in a task of its own, so leaving the screen that asked does not cancel it, follows the system's URL cache, keeps what is an image of at most 2 MB, tries a failed one again after ten minutes and never fetches under `--fixture`), and with none (no `appId`, offline, not an image) its initials on a color made from its name (`roleInitials`); the person's gh login is their own GitHub picture (`ForgeAvatarStore.fetchUser`: the login comes from the chat host's `githubRepos` reply, is checked by `isGithubLogin` and the picture is `avatars.githubusercontent.com/<login>`, with the same rules as a bot's), a gray person while it is not there; an identity that is not there is a dashed square with a question mark.
The corner wears the mark of the account the role runs on, as a session's avatar does.
A role's screen starts with its picture, who it works as and its model, and a strip "In an epic" (Author ⇄ Reviewer → Lead reviewer) with this role marked and the others links to their screens (a role that is off says "· Off" in its button); the toolbar says the role's name and, under it, its model, effort and identity (`RoleRow.headline`), worded and drawn as a role that is on while the Lead reviewer is being turned on (`RoleRow.drafting`).
Its groups are Who, Persona, Skills and When it runs out of tokens.
The Identity row has a chevron that opens the identity's screen on the Identities page (`SettingsPlace(.identities, path: [key])`), none while the role has no identity the registry knows.
Under Identity the Who group says that Author and Reviewer sign as one account, and why the list of bots is empty (a registry that is missing or does not read).
The Who group is sent as you change it (`EngineConfigChange.role`, the engine's `editRole`, `src/config/role-edit.ts`; the pages' requests go one at a time, in order, through `EngineConfigQueue`): Identity, Provider, Model (on Return or leaving the field) and Effort (the five levels or Default) each change only that key of `agents.<role>`, the engine reading the file again just before and keeping every other key; choosing a bot adds `profiles.<name>` as `{ kind: "forge", agent }` once and reuses it afterwards, and the person's login uses the first `gh` profile or adds `gh`.
An empty model, a provider that is not an account, a bot the registry does not list, or a role that would be left without profile, provider or model is refused before writing, with the reason under the group; a profile that is no longer in the registry stays, marked missing, and is refused only when chosen again.
Create a bot… (`Carrier/Features/Settings/Identities/CreateBotRow.swift`, on the Identities page: a bot is the GitHub account any role can pick) opens Terminal on `agent-forge add` (`CarrierCore/Terminal/ForgeTerminal.swift`, tested in `ForgeTerminalTests`): the command is from a closed list of one entry, quoted, nothing from the registry or the config is part of it, and the one-use script and the opener are the app's shared `openScript` helpers (under `--fixture` the opener only says what it would have run); the page reads the registry again whenever the app becomes active, so the new bot appears without a refresh button.
The Persona group sends the persona as you change it (Persona name and Persona prompt on Return or leaving the field, `editPersona`): either one alone or both, the texts trimmed, a blank field left out and both blank removing the persona, and a name over 40 characters or with a line break, or a prompt over 4000, refused by the engine before it writes, with the reason under the group (the limits are `RoleFields.problems`, the repo form's).
The When it runs out of tokens group changes `failover.roles.<role>` (`editFailover`, same module): Switch automatically on shows Try first (a declared provider and an optional model, written once it has a provider) and Then try (optional, None takes it back), off removes the role's list; a step that repeats the other or is the role's own provider and model is refused with its position, and the steps a file has after the first two are kept when those are edited.
Changing the role's own provider or model onto the one a failover step names drops that step (`dropFailoverSteps` in `role-edit.ts`, tested in `role-edit.test.ts`): falling back to the account that ran out is no fallback, and the engine refuses the file with such a step. The others stay in their order, and a list left empty goes with the role's key, which is Switch automatically off; a step with no model is another model's and stays.
`rolesPage` turns `engine.json`, `providers.json` (or the three default accounts) and the names of the Agent Forge registry (`forgeBots`, from `$AGENT_FORGE_CONFIG`, else `$XDG_CONFIG_HOME` or `~/.config` plus `agent-forge/agents.json`: names and GitHub App ids, never a key; a registry that is missing or does not read gives no bots and a note, not an error) into a row per role: identity (a bot the registry has, the person's own gh login, or missing when the profile is not in `profiles` or its bot is not in the registry, and then it stays in the file), provider (marked missing when it is not an account), model, effort, persona and the failover steps of `failover.roles.<role>` (the page shows a first and a then step and says how many more the file has).
The Skills group shows what the engine runs in each stage of the role (`AgentRole.stages`): the Author's First pass (`ship`) and Answering a review (`code-resolve`), and the Reviewer's Review (`code-review`) and Post findings (`code-post`), each with "Runs as" and the skill spelled the way its account's harness is told to run it (`/ship` for Claude and Antigravity, `$ship` for Codex, `skillInvocation`).
They are not editable yet: the value is a quiet box with "Default" before it, and the footer says choosing another comes with a later version of the engine (the engine reads `skills` from `engine.json`, but the app does not edit them yet, and it shows the defaults).
`AgentRole.stages` is the engine's default skills, and `RolesReadinessTests` reads them from the contract fixture and fails when the two disagree.
The Lead reviewer, which the engine runs once after the reviewers agree and on the head they agreed on, shows Lead review and Post and approve, read only like the others: `skills.lead` takes the review skills while it names none, so they are `code-review` and `code-post`, spelled as its account's harness is told to run them, and `RolesReadinessTests` checks them against the same contract fixture.
While `failover.roles.leadReviewer` is not in the file its When it runs out of tokens group says "Same as Reviewer" (a switch, on) with the Reviewer's steps in the line under it, the engine's rule (`failoverStepsFor`; `ownSteps` is false); turning it off shows Try first and Then try, and the first one written gives the lead steps of its own, while a lead that has its own shows them as the other roles do and Switch automatically off takes them back.
The Lead reviewer has the Use a lead reviewer row on top, and while the file has no `agents.leadReviewer` the row says Off and the rest of its page is dimmed and not usable.
Turning the switch off removes `agents.leadReviewer` and `failover.roles.leadReviewer` and keeps every other key (`setLeadReviewer` with `draft: null`), and the row says so; turning it on sends nothing: the page asks for an identity, a provider and a model (`LeadReviewerDraft`, kept in the page) and, once the three are chosen, sends the whole role in one request (`setLeadReviewer`), so the file never holds a half role (`CarrierCore/Epics/LeadReviewerSwitch.swift`; the engine refuses an incomplete draft before it reads the file).
When Author and Reviewer resolve to one account by the engine's rule (`sameAccount`: two gh logins, or two profiles of one bot) the status card and the Who group say the signature will show it.
A config that is missing or is not a JSON object says the engine is not configured.
Under `--fixture` the app sets `AGENT_FORGE_CONFIG` to `agent-forge.json` in the fixture home (`fixtureForgeRegistry`: the three bots of the roles and the first extra reviewer's, three with a made-up `appId`, and a spare one), and `fixtureConfig` has failover steps for the Author and the Reviewer and two extra reviewers, one with failover steps of its own and one without (it signs as the person's login and has a persona).
The fixture engine announces `extraReviewers` and answers `addExtraReviewer`, `removeExtraReviewer` and `editRole`, `editPersona` and `editFailover` pointing at a reviewer by its key as the engine does (`FixtureServer+ExtraReviewers.swift`, with the engine's checks and words, tested in `FixtureServerTests`), so `--fixture` can add, change and remove a reviewer; it writes the file with its keys in alphabetical order, so a reviewer added there takes its place in the map by its key and not at the end.
Use in a role… on a signed-in account of the Providers page that no role names, and Open Roles on the Watching page (in Who works here, and next to Use another identity on a failed "can sign here" check), open this page.

## Identities

The Identities page, in the Carrier group after Roles, is every GitHub profile a role can sign as (what the engine calls a profile of `profiles`, the glossary's GitHub profile): the bots of the Agent Forge registry and the person's own `gh` login.
It writes nothing, `engine.json` included: a role picks its identity on its own screen, and picking a bot adds its profile as it always did.
Two kinds of screen, each a place of the window's history (‹ ›): the list and one identity's screen, whose path is the identity's key (`bot:<name>` or `gh`, `RoleIdentity.key`; `SettingsPlace(.identities, path: [key])`).
Code: `Carrier/Features/Settings/Identities/IdentitiesTab.swift` and `CreateBotRow.swift`, the model in `CarrierCore/Settings/Identities/IdentitiesPage.swift` (`identitiesPage`), tested in `IdentitiesPageTests` with the doctor's golden output (`Tests/Fixtures/doctor.json`), and `SettingsPageTests` and `SettingsIndexTests` for the page itself; the views have no test.
The list is one group, Identities, with a row for each bot of the registry in its order and then the person's login, each with its picture (`RoleAvatar`, the same as the roles draw), its kind ("A bot from Agent Forge" or "Your own account") and, at the right, a chip for each role that signs as it ("No role" when none does); a row opens that identity's screen.
A role signs as an identity when its profile (`kind: forge` with the bot's name, or `kind: gh`) is that identity's, in the global `agents` or in the `agents` of a watched repo; the Lead reviewer counts only while the file has one.
A profile whose bot the registry does not list belongs to no identity (the role's own screen says it is missing); a registry that is missing or does not read gives no bots and a note under the group.
Create a bot… is the last row of the list (see Roles for what it runs).
Where an identity cannot sign it says so on its row, in orange under the kind: "Cannot sign in acme/api", from the doctor's `can mint a token` check that Watching reads (`isMintCheck`, `checkRow` and `doctorNote`, shared with `repoChecks`).
The page asks the doctor when it opens, as Watching does (`runSettingsDoctor` in `Watching/RunDoctor.swift`, never in the background); while it runs the rows say "Checking…" and when it did not answer (could not start, or refused the config) they say "Could not check where it can sign", with the reason under the group.
An identity no role uses in a repo is not checked there, and a repo the doctor has no check for reads as waiting, never as failed.
An identity's screen starts with its picture, name, kind and, for a bot, its GitHub App id (digits only, from the registry).
Signs as lists each role that signs as it, the global role as "Reviewer" and a repo's own as "Reviewer in acme/api", each opening that role's screen (Roles' for a global one, the repo's in Watching for its own); with none it says "No role".
Can sign in lists each watched repo with whether it can mint a token there, the doctor's words and its fix when it cannot.
Open on GitHub, for a bot only, opens `https://github.com/apps/<name>` in the browser; the name has to be one GitHub accepts (`isGithubLogin`), so a name from the registry that is not never reaches an address.
Under `--fixture` the doctor answers with the golden output, in which the fixture's Reviewer bot cannot mint a token in `acme/api`, so its row and its screen show it.

## Behavior

The Behavior tab (in the Carrier group, before Engine, "How Carrier runs epics"; `Carrier/Features/Settings/Behavior/BehaviorTab.swift`, model in `CarrierCore/Settings/Engine/EngineConfig.swift`) edits nine values of the config file (asked of the engine, `editBehavior`, or of `carrier config` when none answers), in three groups drawn from the model in `CarrierCore/Settings/Behavior/BehaviorPage.swift` (`behaviorGroups`, tested in `BehaviorPageTests`): Pace (`pollIntervalMinutes`, `limits.maxConcurrentEpics`), When something goes wrong (`limits.maxReviews`, `limits.maxLeadRounds`, `limits.maxExecutionRetries`, `limits.maxExecutionHours`, with Unlimited) and Housekeeping (`finishedWindowDays`, whole days from 1 to 30, 15 by default; `limits.githubCallTimeoutSeconds`; `logLevel`).
They are text fields that check the engine's rules as you type; a value equal to the engine's default is taken out of the file by Node's code (`src/config/engine-edit.ts`), and nothing else in the file is touched (the app never makes the file: without a JSON object there it says the engine is not configured).
Review rounds says a round counts once however many reviewers it has.
Lead rounds (`limits.maxLeadRounds`, 3 by default) sits under it with the same rules; while the file has no `agents.leadReviewer` (`fileHasLeadReviewer`) the row is dimmed and its field does not answer, and a row under it says there is no lead reviewer yet, with Open Lead reviewer, which opens the lead's screen in Roles.
The file is read again when the page appears, so turning the lead on in Roles undims it.
Every change the engine would accept is sent (`autosave`; a value still being typed, or one the engine would refuse, waits and says why) after the person pauses for about 700 ms, or at once when the page closes or the app quits, and the request that saves the file also makes the engine run on it, so no `reload` follows; the page's header says nothing when it saved, and says why it could not save or that the file cannot be read, in orange (the page passes it up with `SettingsHeaderNoteKey`), and the Reset group at the end of the page (`behaviorReset`, one card, "Restore the defaults") puts the engine's own defaults back after a confirmation (they are saved the same way, and a value equal to its default is taken out of the file).

## Engine

The Engine page (the last of the Carrier group, "How the app runs Carrier") holds what the app starts Carrier with: its Starting group (`CarrierCore/Settings/Engine/EnginePage.swift`, `engineGroups`, tested in `EnginePageTests`) has "Start Carrier when the app opens" (`engine.startOnOpen`) and "Ask before stopping Carrier" (`stop.confirm`, on by default; it used to be General's), its Programs group (`engineGroups`, also in `EnginePage.swift`, with `EnginePrograms` as the paths and versions it is given, tested in `EnginePageTests`; the versions are what `carrier --version` and `node --version` print, read by `Carrier/Platform/ProgramVersions.swift` when the page opens, a program changes or a detection ends, through `shortRun` in `Carrier/Platform/ProcessRun.swift`, also used by the chat host's version check; "Reading version…" while they run, and a problem when one does not answer or nothing runs at the `carrier` path) shows `carrier` with its path and version, `node` the same, and the `PATH` the engine and the chat host run with (read only; "Not found" in place of a path), then "Look for the tools again" with the button Detect.
"Use another…" on the `carrier` row opens a file picker; while one is set the row says it is the person's own and offers "Use the Homebrew one"; its GitHub identity group has "Carrier acts on GitHub as" (`orchestratorProfile` of `engine.json`, `CarrierCore/Lifecycle/EngineIdentity.swift`, sent as `setOrchestratorProfile`, tested in `role-edit.test.ts`, `EngineConfigTests` and `EnginePageTests`): the default (the author's identity) first, then the file's `profiles`, the default taking the key out of the file and every other key kept (saved with sorted keys); a profile the file names but does not declare stays on the list and shows in orange until another is picked; a refused save is that row's problem, said to VoiceOver; a file that cannot be read leaves the row disabled and says so in orange, and one that is not a JSON object is not changed; the engine runs on the file in the same request like every other change of `engine.json`, so the choice applies without a restart, and its answer is the page's `ReloadNote`.
Its Files group (`engineGroups` again) has "Carrier folder", "Logs" and "Start log", each with its path (`~` for the home folder) and a Reveal or Open button, disabled with "Not created yet" while the path is missing.
The app finds `carrier` by itself (`carrierPath`): the one chosen with "Use another…" when it is set (a path as typed, `~` expanded; one ending in `.ts` or `.js` runs under `node`), else the Homebrew one when it is executable (`/opt/homebrew/bin/carrier`, or `/usr/local/bin/carrier` in the Intel app), else it is missing.
On the first launch (nothing saved in user defaults) the app asks the user's shell once, `zsh -ilc` with markers around what it prints and a 10 second limit, for `node` and the `PATH`, without asking the person; Detect repeats the run.
With saved values the shell is started again only when the person presses Detect, or when a start of the engine or the chat host ends with `spawn <tool> ENOENT` in its log (a folder added to the PATH after the app asked, such as pnpm's): the start is then tried once more with what the shell says now, and the alert says the tool is not on the PATH of the shell either when that was not it.
The `PATH` the engine will get is the detected one (the system's when the shell gave none) with node's directory first and Homebrew's `bin` (`/opt/homebrew/bin`, or `/usr/local/bin` in the Intel app) at the end when it is not in it.
A banner on every section says what Start Carrier lacks, or that it is looking for it, and is not shown when all is found; when something is missing it says to use "Use another…" and then Detect under Programs on the Engine page, and its own button is Detect; the banner's model is `CarrierCore/Settings/Engine/EngineTab.swift`.
