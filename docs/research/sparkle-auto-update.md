# Sparkle auto-update for an ad hoc signed, Homebrew-installed Carrier.app

Researched 2026-11-11 for [0022](../adr/0022-the-app-updates-itself-with-sparkle-and-the-engine-through-homebrew.md) and [the brief](../specs/carrier-updates-itself.md). Primary sources only. "Source" below means the Sparkle repository at tag `2.10.1` (commit `ab7d71291238df6e0492143b120c9b696a35f603`, cloned from https://github.com/sparkle-project/Sparkle), "docs" means the Sparkle documentation site (https://sparkle-project.org/documentation/, read from its source repo https://github.com/sparkle-project/sparkle-project.github.io at commit `6524f21`, 2026-10-31), and "brew" means Homebrew/brew (https://github.com/Homebrew/brew) at tag `7.0.13` (2026-11-09) unless a path says `main` (commit `95d4938`, 2026-11-10). Where I ran something myself on this Mac (Swift 6.4.2, Xcode, macOS 27 host) to check a mechanical claim, the text says "observed here"; that is a reproducible local observation, not a Sparkle or Apple statement, and it is not the spike 0022 asks for.

## The answer in short

Current stable Sparkle is 2.10.1, published 2026-10-25 (https://github.com/sparkle-project/Sparkle/releases/tag/2.10.1), minimum macOS 12.0. By reading the validation code, Sparkle 2.10.1 accepts an update to an ad hoc signed app when the zip carries a valid EdDSA signature made by the key whose public half is in the installed app: the EdDSA check and the code-signature check are alternatives, and for an ad hoc app the code-signature alternative can never pass for a different build, so the EdDSA signature is the whole trust root. Sparkle's own unit tests do not cover an ad hoc host, so this is a code reading, not a tested behavior; the spike in the brief stays necessary. The update installer clears `com.apple.quarantine` recursively on the new bundle before swapping it in. What Gatekeeper does with the relaunched ad hoc, non-notarized, non-quarantined app is not documented by Apple in the pages I could read.

Four findings matter most for 0022. First, Homebrew 7 does not leave an `auto_updates true` cask alone: since at least 6.0.0, a plain `brew upgrade` upgrades it when the installed bundle's version is older than the cask's, and `brew upgrade --cask carrier` with the cask named explicitly reinstalls whenever Homebrew's own record differs from the cask version, even if Sparkle already moved the app to that version (this contradicts the ADR and the brief). Second, `releases/latest/download/appcast.xml` resolves against the newest non-draft release, and the current workflow creates the release (with the zip) before the appcast exists, so there is a window, and a failure mode, in which the feed URL answers 404; the release has to be created as a draft and published only after the appcast is attached. Third, `sign_update --verify` checks against the public key derived from the private key you give it, not against the `SUPublicEDKey` in the built app, so the "verify the zip against the public key" step needs a small extra check. Fourth, a SwiftPM-built executable that links Sparkle has no `LC_RPATH`, so `build-app.sh` must add one or the app dies at launch.

## 1. Version, SwiftPM, embedding, signing, XPC services

Sparkle's latest non-prerelease GitHub release is 2.10.1, published 2026-10-25T14:36:36Z, tag `2.10.1` (no `v` prefix), per `gh api repos/sparkle-project/Sparkle/releases/latest`. The one before is 2.10.0 (2026-09-13), then 2.9.6 (2026-08-17). The only newer-looking tag, 2.10.0-beta.1 (2026-09-07), is a prerelease and older than 2.10.1. The 2.10.1 assets are `Sparkle-2.10.1.tar.xz` (16,346,336 bytes, GitHub digest `sha256:1a856d2a9edb8e628de88121d7be04cf0e2167f8641650b78fca00b14244cf27`) and `Sparkle-for-Swift-Package-Manager.zip` (digest `sha256:4c2e48a3e50ebcc2c88a58a4c7264a1a99c3c31857ce754357afb9cdb323022a`). I downloaded the tar.xz and its SHA-256 matches the digest GitHub reports.

The minimum deployment target is macOS 12.0, stated in the release notes of 2.10.0 and 2.10.1 ("macOS 12.0 or later is required"), in `Package.swift` at the tag (`platforms: [.macOS(.v12)]`), in `Configurations/ConfigCommon.xcconfig` (`MACOSX_DEPLOYMENT_TARGET = 12.0`), and observed here in the framework binary (`LC_BUILD_VERSION minos 12.0` in both the x86_64 and arm64 slices). Carrier requires macOS 26, so that is no constraint. The release notes also say that if you write appcasts by hand you must add `<sparkle:minimumSystemVersion>` to each item.

Sparkle's docs only describe SwiftPM through Xcode ("File > Add Packages", https://sparkle-project.org/documentation/). For a package-based app the dependency is a normal SwiftPM dependency: `.package(url: "https://github.com/sparkle-project/Sparkle", exact: "2.10.1")` and `.product(name: "Sparkle", package: "Sparkle")` on the executable target. Sparkle's manifest at the tag declares a `binaryTarget` that points at `Sparkle-for-Swift-Package-Manager.zip` with the checksum above, so SwiftPM verifies the binary against a checksum committed in the pinned revision. Observed here: `Package.resolved` pins `revision ab7d71291238df6e0492143b120c9b696a35f603, version 2.10.1`, `swift build -c release` copies `Sparkle.framework` (symlinks and `Versions/B` intact) next to the executable under `.build/release/`, and the Sparkle tools land in `.build/artifacts/sparkle/Sparkle/bin/` (the docs mention this location too). The `sign_update` in that folder is byte-identical to the one in the tar.xz (same SHA-256 `43c249771bafc3aa581228abae00731a012d324691b8292860896635050be76b`); the framework binary inside the SPM zip is not byte-identical to the one in the tar.xz, so embed the one SwiftPM resolved and do not mix.

The linked executable has no runtime search path. Observed here: `otool -l` on the SwiftPM-built executable shows no `LC_RPATH` while it links `@rpath/Sparkle.framework/Versions/B/Sparkle`, and running it fails with `Library not loaded ... no LC_RPATH's found`. The docs say for non-Xcode projects to add `-Wl,-rpath,@loader_path/../Frameworks` (https://sparkle-project.org/documentation/, step 1), and the programmatic-setup page says to copy `Sparkle.framework` into `Contents/Frameworks/` "and make sure symlinks are properly preserved" (https://sparkle-project.org/documentation/programmatic-setup/). Observed here: `linkerSettings: [.unsafeFlags(["-Xlinker", "-rpath", "-Xlinker", "@executable_path/../Frameworks"])]` on the executable target produces the `LC_RPATH`, and `install_name_tool -add_rpath @executable_path/../Frameworks` on the copied binary (before signing) also works. Copy with `ditto` (or `cp -R`, which keeps symlinks), then sign. Keep Sparkle only on the `Carrier` executable target, not on `CarrierCore`, so the core tests do not need the framework; whether `swift test` for the `Carrier` target finds the framework without extra rpath is UNVERIFIED.

Signing. The Sparkle distribution is signed ad hoc with the Hardened Runtime flag (observed here: `codesign -dvv` shows `flags=0x10002(adhoc,runtime)` on `Sparkle.framework`; docs say the same: "signed with an ad-hoc signature and Hardened Runtime enabled ... works for common development workflows, but is not ideal for distribution", https://sparkle-project.org/documentation/sandboxing/#code-signing). For a Developer ID build the docs give the re-sign order: `Installer.xpc`, `Downloader.xpc`, `Autoupdate`, `Updater.app`, then `Sparkle.framework`, then the app, each `codesign -f -s ID -o runtime`, and "please do not add `--deep`". For an ad hoc app that order is not required, because the nested code is already validly ad hoc signed and the outer `codesign --force --sign -` seals it. Observed here: I assembled `T.app` (executable, `Contents/Frameworks/Sparkle.framework` copied with `ditto`, plist), ran `codesign --force --sign - T.app` (no `--deep`, no `--options runtime`), and both `codesign --verify --strict` and `codesign --verify --deep --strict` passed, the app's designated requirement was `cdhash H"..."`, and the executable ran and instantiated `SPUStandardUpdaterController`. Library Validation is the one trap: the docs say the system may refuse to load an ad hoc signed Sparkle into an app that enables Library Validation (part of the Hardened Runtime) and that this is only solved by an Apple Development or Developer ID certificate (https://sparkle-project.org/documentation/, "If you enable Library Validation"). Carrier's current `codesign --force --sign -` does not set `runtime` (observed flags `0x2(adhoc)`), so it does not apply today, but adding `--options runtime` later without a certificate would break loading.

Sandbox XPC services are not needed for a non-sandboxed app. The docs say "If you do not sandbox your application, you should skip this guide unless you are interested in Removing the XPC Services" and, in the Info.plist tables, that non-sandboxed apps "should not customize" `SUEnableInstallerLauncherService` and `SUEnableDownloaderService`, both default `NO` (https://sparkle-project.org/documentation/sandboxing/, https://sparkle-project.org/documentation/customization/). The repository's `Documentation/Security.md` adds that XPC services "can be used independent of sandboxing (but this is strongly discouraged)". The framework still ships `XPCServices/Installer.xpc` and `Downloader.xpc` (observed in the tar.xz); they are unused unless enabled in the plist. `SPUUpdater.m` (`checkIfConfiguredProperlyAndRequireFeedURL`) fails the updater start if an enabled service is missing or if the app bundle itself contains `Contents/XPCServices/<service>.xpc`. Removing them is optional (the docs give a run-script that deletes `Downloader.xpc`, or the whole `XPCServices` folder, and then re-signs the framework with `codesign --force --sign ... --preserve-metadata`); if Carrier does that it must re-sign the framework before the app. The framework is a universal binary (x86_64 and arm64); thinning it is not documented.

One more note on how the installer runs for a non-sandboxed app: `InstallerLauncher/SUInstallerLauncher.m` submits a non-permanent launchd job with `SMJobSubmit`, and a comment there says it "is deprecated but is the only way to submit a non-permanent" job. It works in 2.10.1; I found no statement about macOS 26 or 27 behavior beyond the release notes mentioning Xcode 27.

## 2. Does Sparkle install an update for an ad hoc app with only an EdDSA signature

Yes by the code, with the caveat that the test suite does not cover it. The validator is `Sparkle/SUUpdateValidator.m` (`validateUpdateForHost:downloadedToPath:newBundleURL:signatures:error:`, around lines 304-417 at the tag), whose header comment states the rule: "If the update is a bundle, then it must meet any one of: old and new Ed(DSA) public keys are the same and valid (it allows change of Code Signing identity), or old and new Code Signing identity are the same and valid". The steps, in order:

It first applies two policy checks (`passesBasicUpdatePolicy...`, lines 271-294): the update must not drop the (Ed)DSA key if the host has one, and if the host is code signed the update must be code signed too. The error text for the second case says "If no Apple Code Signing certificate is available, adhoc signing can be used at minimum", so Sparkle itself treats ad hoc as a valid "code signed" state. "Code signed" is decided by `SUCodeSigningVerifier bundleAtURLIsCodeSigned:` (`Autoupdate/SUCodeSigningVerifier.m`, lines 248-270), which returns true when `SecCodeCopyDesignatedRequirement` succeeds; Apple's TN3127 says "Ad hoc signed code ... has a DR but it's tied to that specific version of the code" (https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements), and observed here an ad hoc app's DR is `cdhash H"..."`. So an ad hoc host counts as code signed, and the update must be signed at least ad hoc.

Then the "security-critical part" (lines 333-360): if the old app has an EdDSA key, the archive's EdDSA signature is verified against the OLD app's public key ("it's critical to check against the old public key, rather than the new key", `passedDSACheck`); independently, if the host is code signed, `codeSignatureIsValidAtBundleURL:andMatchesSignatureAtBundleURL:` checks that the new bundle satisfies the old bundle's designated requirement (`passedCodeSigning`). If the EdDSA check failed and the new app carries a key, the archive must at least verify against the new app's key (a "future problems" guard). If the EdDSA check passed and the new bundle is code signed but did not match the old one, the new bundle's own signature must still be valid (`codeSignatureIsValidAtBundleURL:`, a shallow check without `kSecCSCheckNestedCode`, lines 364-369). Finally, line 373: `if (passedDSACheck || passedCodeSigning) return YES;`. Only the archive bytes are signed by EdDSA (`SUSignatureVerifier.m`, `ed25519_verify` over the whole file); a mismatch between the appcast `length` or `sparkle:version` and the file only changes the wording of the error.

Team ID is not part of this path for a normal update. The only Team ID uses are: the fallback `codeSignatureIsValidAtDownloadURL:andMatchesDeveloperIDTeamFromOldBundleURL:` (only when `SUVerifyUpdateBeforeExtraction` is on and the EdDSA check failed, requires a Developer ID signed archive with the old app's Team ID; the source comment says `teamIdentifier` "will return nil for ad-hoc or unsigned binaries", so it fails for an ad hoc host); the connection check between the app and the installer (`validateConnection:`, returns "no requirement" success when the host has no Team ID); and `SUPlainInstaller.m` deciding whether it may use an atomic swap and the Gatekeeper pre-scan (it may when the new bundle has no Team ID, which is the ad hoc case). `Documentation/Security.md` says the same about the XPC services and Autoupdate: they check Team IDs "if code signed", and apps that are not code signed with a Team ID are not rejected.

What changes between ad hoc and Developer ID. With Developer ID, the designated requirement is team based (TN3127 shows the pattern `anchor apple generic and ... certificate leaf[subject.OU] = TEAM`), so every release by the same team satisfies it and `passedCodeSigning` is true; that makes either factor enough, which is what allows rotating the EdDSA key or the certificate (one at a time, per the docs and the unit test `testPostValidationWithKeyRotation`). With ad hoc, the DR is the cdhash of the installed build, so a new build never satisfies it (the cdhash covers the code and resources, which change every release) and `passedCodeSigning` is always false; the EdDSA check is the only way in, and nothing can rotate it. Does a second ad hoc build with a different cdhash pass? By this reading yes, through `passedDSACheck` alone, provided the zip's EdDSA signature verifies against the installed app's `SUPublicEDKey`, the new app contains a `SUPublicEDKey` (it may be the same key), and the new app's ad hoc signature is internally valid. Sparkle's tests (`Tests/SUUpdateValidatorTest.swift`) cover unsigned bundles with EdDSA and certificate-signed test bundles (`DevSignedApp.zip` and similar), not an ad hoc host, so UNVERIFIED in practice. Related option: `SUVerifyUpdateBeforeExtraction = YES` makes Sparkle verify the archive before extracting it (docs: Security Settings table, since 2.7.3); the docs warn to use it only if you will not lose the EdDSA key, which for an ad hoc app is true regardless, since the key cannot be rotated.

## 3. Quarantine and Gatekeeper

Sparkle clears the quarantine attribute on the new bundle. `Autoupdate/SUPlainInstaller.m`, `_performInitialInstallationWithFileManager:...`, begins with "Release our new app from quarantine" and calls `releaseItemFromQuarantineAtRootURL:` on the new bundle; failure is logged ("Not big enough of a deal to fail the entire installation") and the install continues. `Sparkle/SUFileManager.m` implements it by removing the `com.apple.quarantine` xattr (`removexattr`, `XATTR_NOFOLLOW`) from the root and from every file under it, without following symlinks, and it keeps trying the rest after a failure. `Documentation/Installation.md` lists "clearing quarantine" among the first-stage installer work, which is "not done if the bundle has to transfer to another volume; in this case, this work will be done in a later stage". So by source the installed app has no `com.apple.quarantine`, unless the xattr removal fails; the spike should check with `xattr -lr /Applications/Carrier.app`. Sparkle sets no quarantine itself (no `setxattr` of it anywhere in the source). Whether macOS attaches one to the downloaded zip depends on the downloading process: Apple's `LSFileQuarantineEnabled` Info.plist key is "a Boolean value indicating whether the files this app creates are quarantined by default" (https://developer.apple.com/documentation/bundleresources/information-property-list/lsfilequarantineenabled), and `build-app.sh` does not set it; either way the installer clears it from the extracted bundle before the swap.

After clearing quarantine, `SUPlainInstaller.m` runs `/usr/bin/gktool scan <app>` on macOS 14.4+ when the swap is atomic ("Perform a Gatekeeper scan to pre-warm the app launch. This avoids users seeing a 'Verifying...' dialog when the installed update is launched"); the docs' Security and Reliability table dates this to 2.6.4 (https://sparkle-project.org/documentation/security-and-reliability/). Failures are logged and ignored. What `gktool scan` concludes for an ad hoc, non-notarized app is not documented in anything I found.

What Gatekeeper does when the relaunched, un-quarantined, ad hoc, non-notarized app opens: not documented in the Apple pages I read. Apple's "Safe software" article says that "Before opening downloaded software for the first time, macOS requests your approval" and that by default macOS Catalina and later requires software outside the App Store to be notarized (https://support.apple.com/en-us/102445); the Platform Security guide says Gatekeeper "verifies that the software is from an identified developer, is notarized ... and hasn't been altered" for software "downloaded and opened", and also that "all software in macOS is checked for known malicious content the first time it's opened, regardless of how it arrived on the Mac" (https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web). Neither page says that a file without the quarantine attribute skips the signature or notarization assessment, and neither says it does not. So the premise of the cask's `xattr -dr` postflight, and of Sparkle's installer, that a quarantine-free ad hoc app opens without a Gatekeeper dialog, is UNVERIFIED by primary sources, and the brief's spike is exactly the right test. Homebrew's own source treats the quarantine attribute (including a "user approved" bit) as what Gatekeeper keys on (`Library/Homebrew/cask/quarantine.rb`, `USER_APPROVED_FLAG`), which is consistent but is not Apple documentation.

## 4. EdDSA keys

`generate_keys` (run once) creates an Ed25519 key pair, stores the private key in the login Keychain and prints the public key; its help says the public key is shown again by running it again, `-p` prints just the public key, `-x <file>` exports the private key, `-f <file>` imports one, and `--account` picks the Keychain account (default `ed25519`); the Keychain item is service `https://sparkle-project.org` (`sign_update/main.swift`, `findKeysInKeychain`). Per the tool's help, for keys generated in the current format "the key file after base64 decoding is 32 bytes" and "the exported key file is the base64 encoding of the private seed", the same value as the password of the Keychain item "Private key for signing Sparkle updates". The public key is the base64 of the raw 32-byte Ed25519 public key (44 characters, e.g. the docs' example `pfIShU4dEXqPd5ObYNfDBiQWcXozk7estwzTnF9BamQ=`) and goes in `Info.plist` as `SUPublicEDKey` (https://sparkle-project.org/documentation/, "EdDSA (ed25519) signatures"). Observed here, without touching a Keychain: a file holding `base64(32 random bytes)` works as a private key for `sign_update`, and `CryptoKit`'s `Curve25519.Signing.PrivateKey(rawRepresentation: seed).publicKey.rawRepresentation` base64 is the matching `SUPublicEDKey` value (a signature made by `sign_update` verified under CryptoKit with that derived key). So the CI secret can simply be the exported file's contents.

`sign_update <file>` prints `sparkle:edSignature="..." length="..."`; `-p` prints only the signature; `-f/--ed-key-file <file>` reads the key from a file, and `-` reads it from standard input, with the help's example `echo "$PRIVATE_KEY_SECRET" | ./sign_update --ed-key-file - ...`; `generate_appcast` has the same `--ed-key-file` including `-`. The old `-s <key>` argument is deprecated as insecure (docs, Security and Reliability table, 2.2.2). `sign_update --verify <file> <signature>` exits non-zero on mismatch; observed here exit 0 on a good signature and exit 1 with "failed to pass signing verification" after appending a byte to the file. Note that `--verify` derives the public key from the private key you provide; it does not take the public key from an app or a command-line argument (`sign_update/main.swift`, the `verify` branch uses `findKeys...` then `ed25519_verify(..., publicKeyBytes)`), so it proves "signed by this private key", not "valid for the key shipped in the app".

Rotation. The docs allow rotating only "if you both code-sign your application with Apple's Developer ID program and include a public EdDSA key", and only one of the two at a time (https://sparkle-project.org/documentation/, "Rotating signing keys"). Reading the validator for an ad hoc host: a new build with a new `SUPublicEDKey` fails `passedDSACheck` (the signature is checked against the OLD key), and `passedCodeSigning` fails because the new build does not match the old cdhash, so it is rejected ("has a new (Ed)DSA key that doesn't match the previous one, and the app is signed with a new Code Signing identity that doesn't match"). The Developer ID fallback needs a Team ID the ad hoc app does not have. So rotation is impossible, confirming 0022. If the private key is lost, the docs only say that "you can still sign new updates for Developer ID signed applications through key rotation" and that the keys "will be erased if your keychain or system is erased"; for an ad hoc app they say nothing, and by the code every installed copy keeps rejecting every update signed with another key. The practical way out is a build with a new key reaching the machine by a different route (the cask's `brew reinstall --cask carrier` installs the current tap version, including its new plist key, because reinstall is uninstall plus install of the tap's cask, `Library/Homebrew/cask/reinstall.rb`); apps that are not reinstalled stay stuck, and see an error on manual checks.

## 5. Appcast format, comparison, redirects, generate_appcast

A one-item feed is valid. The parser (`Sparkle/SUAppcastItem.m`, around lines 470-650) requires an `<enclosure>` with an http(s) `url` (or an info `<link>`), requires a version (`sparkle:version`, or the same attribute on the enclosure, else the item is rejected with "Feed item lacks sparkle:version"), and treats `length` as optional (`_contentLength` 0 when absent; 2.10.0 fixed the fallback when the server reports no size). No source or docs text requires more than one item or any history; the update driver picks the best item (`bestItemFromAppcastItems` in `SUAppcastDriver.m`). The docs' template (https://sparkle-project.org/documentation/publishing/) puts `sparkle:version`, `sparkle:shortVersionString`, `sparkle:minimumSystemVersion` (as a three-part version, "be sure to specify a three-part version") as item children and `url`, `sparkle:edSignature`, `length`, `type="application/octet-stream"` as enclosure attributes; the older style of putting version attributes on the enclosure still works. Minimal feed:

```xml
<?xml version="1.0" encoding="utf-8"?>
<rss version="2.0" xmlns:sparkle="http://www.andymatuschak.org/xml-namespaces/sparkle">
  <channel>
    <title>Carrier</title>
    <item>
      <title>1.2.3</title>
      <sparkle:version>10203</sparkle:version>
      <sparkle:shortVersionString>1.2.3</sparkle:shortVersionString>
      <sparkle:minimumSystemVersion>26.0.0</sparkle:minimumSystemVersion>
      <enclosure url="https://github.com/AshuLab/carrier/releases/download/v1.2.3/Carrier-1.2.3.zip" length="1053964" type="application/octet-stream" sparkle:edSignature="BASE64SIGNATURE"/>
    </item>
  </channel>
</rss>
```

Comparison. The installed side is `CFBundleVersion` (`SUHost.m` `_version` reads `kCFBundleVersionKey`), the feed side is `sparkle:version`; they are compared with `SUStandardVersionComparator`, documented as comparing "the `CFBundleVersion` values of the updates", in the format x, x.y or x.y.z of numbers ("500" is valid), "dumb ... essentially string comparison, in components split by character type" (`SUStandardVersionComparator.h`). `CFBundleShortVersionString` and `sparkle:shortVersionString` are display only; the docs' "Internal build numbers" section describes exactly the split Carrier plans (machine version in `sparkle:version`, human one in `sparkle:shortVersionString`). The derived integer `X*10000 + Y*100 + Z` compares correctly as long as Y and Z stay below 100; the current plist value `1` is lower than any derived value. The installer also refuses downgrades by comparing `CFBundleVersion` of the host and the new app (`SUPlainInstaller.m` `performInitialInstallation:`, "updates that downgrade version of the application are not allowed"). Keep `sparkle:version` equal to the new app's `CFBundleVersion`.

Redirects. The appcast and the zip are both fetched by `SPUDownloadDriver` through `SPUDownloader` (`Sparkle/SUAppcastDriver.m` line 76 creates the driver; `Downloader/SPUDownloader.m` lines 83-84 use `[NSURLSession sessionWithConfiguration:[NSURLSessionConfiguration defaultSessionConfiguration]]`). Sparkle implements no redirect delegate method (no "redirect" handling in `Sparkle/SPUDownloadDriver.m` or `Downloader/SPUDownloader.m`; the only matches in the tree are for web views), so URLSession's default applies, and Apple documents `urlSession(_:task:willPerformHTTPRedirection:...)` as the optional hook to modify or refuse a redirect (https://developer.apple.com/documentation/foundation/urlsessiontaskdelegate/urlsession(_:task:willperformhttpredirection:newrequest:completionhandler:)). Observed here with `curl` against another public repository: `https://github.com/<repo>/releases/latest/download/<asset>` answers `302` to `https://github.com/<repo>/releases/download/<latest-tag>/<asset>`, which answers `302` to a signed `https://release-assets.githubusercontent.com/...` URL, which serves `200` (two redirects, all HTTPS). A missing asset answers `302` and then `404`. I could not run Sparkle itself against GitHub here, so a full check with real Sparkle is UNVERIFIED (the spike's local appcast does not exercise it).

Which release is "latest". GitHub's REST docs: "The latest release is the most recent non-prerelease, non-draft release, sorted by the `created_at` attribute", where `created_at` "is the date of the commit used for the release, and not the date when the release was drafted or published" (https://docs.github.com/en/rest/releases/releases#get-the-latest-release); the linking docs describe `/releases/latest/download/asset-name.zip` for an uploaded asset (https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases). Consequence for the workflow: `release.yml` runs `gh release create` (with the zip) in the "GitHub Release" step, before the "Push the formula and the cask to the tap" step. From the moment that release exists it is the latest, and `releases/latest/download/appcast.xml` points at a release that has no `appcast.xml`: it answers 404 (observed here for a missing asset). Adding the appcast "as the last step", after the tap push, as the brief says, therefore leaves a window (and, if the job fails between, a lasting outage) in which every installed Carrier's feed is a 404. The fix that keeps the ADR's ordering is to create the release as a draft (`gh release create --draft`), upload the zip, push the tap, upload the appcast, and only then publish it (`gh release edit --draft=false`); a draft is never "latest". This is my reading of GitHub's docs plus the observed 404, not an experiment on a draft.

`generate_appcast` versus a hand-written file. The docs prefer `generate_appcast` and call hand-writing "not recommended", but the format is simple and the tool is optional. Observed here, running the 2.10.1 `generate_appcast` on a folder holding one zip of a test bundle with `--ed-key-file -` (key piped on stdin, no Keychain) and `--download-url-prefix https://github.com/AshuLab/carrier/releases/download/v1.2.3/ -o appcast.xml`: it printed "Wrote 1 new update", and the item had `sparkle:version` 10203 and `sparkle:shortVersionString` 1.2.3 read from the bundle, `sparkle:minimumSystemVersion` 26.0 (from `LSMinimumSystemVersion`), `sparkle:hardwareRequirements` arm64 (inferred from the single arm64 slice), `pubDate`, and the enclosure with `length`, `type` and `sparkle:edSignature`. Its help says it infers minimum OS and hardware from the bundle, keeps the 3 newest items per branch by default (`--maximum-versions`), and extracts archives into `~/Library/Caches/Sparkle_generate_appcast`. A fresh folder with only the new zip yields exactly one item, so the "no history" design works with either choice; the tool's advantage is that the version fields come from the shipped bundle instead of the workflow's arithmetic. `sparkle:hardwareRequirements` is supported as of Sparkle 2.9 (docs, Publishing).

## 6. Info.plist keys, user choices, first run, checking, relaunch

Keys (https://sparkle-project.org/documentation/customization/; defaults confirmed in `Sparkle/SPUUpdaterSettings.m`): `SUFeedURL` (string, recommended in the plist); `SUPublicEDKey` (base64 public key); `SUEnableAutomaticChecks` (bool; when absent, automatic checks start disabled and "users will be prompted for permission ... on second launch"; `YES` enables checks by default without asking, `NO` disables without asking); `SUScheduledCheckInterval` (seconds, default 86400, minimum 3600); `SUAutomaticallyUpdate` (bool, default `NO`: download and install silently in the background; "Updates may be downloaded but not installed automatically if authorization is required"); `SUScheduledImpatientCheckInterval` (default 604800, since 2.9); `SUAllowsAutomaticUpdates` (when absent, the option to auto-install is offered if automatic checking is enabled; `NO` forbids it, `YES` allows it even with checking off); `SUVerifyUpdateBeforeExtraction` (default `NO`); `SURequireSignedFeed` (default `NO`, needs the previous one; not needed here). The docs say Info.plist keys "are meant for default configuration, while the runtime APIs are in response to user setting changes" (customization page).

How the two choices are stored. `SPUUpdater.automaticallyChecksForUpdates` and `automaticallyDownloadsUpdates` are backed by `NSUserDefaults` of the app's own domain (`SUEnableAutomaticChecks` and `SUAutomaticallyUpdate`; `SPUUpdaterSettings.m` `setAutomaticallyChecksForUpdates:` calls `setBool:forUserDefaultsKey:SUEnableAutomaticChecksKey`), and user defaults override the plist (`SUHost.m` `boolNumberForKey:` reads user defaults first, then the Info dictionary). Other keys Sparkle writes there (`SUConstants.m`): `SUHasLaunchedBefore`, `SULastCheckTime`, `SUSkippedVersion`, `SUSkippedMajorVersion`, `SUUpdateGroupIdentifier`, `SUSendProfileInfo`. The docs say set the runtime properties only when the user changes a setting, never to apply a default, and not to keep a second copy of the value (https://sparkle-project.org/documentation/preferences-ui/, https://sparkle-project.org/documentation/programmatic-setup/#api-expectations); the SwiftUI example binds a `Toggle` to each property and sets it in `.onChange`. One coupling matters for the two toggles: in `SPUUpdaterSettings.m`, `currentAllowsAutomaticUpdates` is the plist `SUAllowsAutomaticUpdates` if present, else the current value of automatic checking, and `setAutomaticallyDownloadsUpdates:` silently returns when that is false. So with checking off, the install-automatically toggle cannot be changed (the docs' sample disables it with `.disabled(!automaticallyChecksForUpdates)`), and the effective value is `allowsAutomaticUpdates && SUAutomaticallyUpdate`.

First-run prompt. `SPUUpdater.m` `startUpdateCycle`: no prompt if `SUEnableAutomaticChecks` is set in user defaults or in the plist; otherwise the prompt is shown on the second launch (`SUHasLaunchedBefore`), unless the plist sets `SUPromptUserOnFirstLaunch` (present in the source, not in the docs table) or the updater delegate's `updaterShouldPromptForPermissionToCheckForUpdates:` decides. Since 2.4 the prompt also asks about automatic downloading (customization page). To get "check by default, no prompt", put `SUEnableAutomaticChecks = YES` in the plist; the user's later choice goes to user defaults and wins. For "ask before installing" leave `SUAutomaticallyUpdate` unset.

Checking from code. `SPUStandardUpdaterController(startingUpdater: true, updaterDelegate: nil, userDriverDelegate: nil)` created once; `controller.checkForUpdates(nil)` or `controller.updater.checkForUpdates()` is the user-initiated check (shows Sparkle's UI), enabled by `updater.canCheckForUpdates` (KVO-observable; the docs' SwiftUI example wraps it in a view model) (https://sparkle-project.org/documentation/programmatic-setup/). Sparkle's scheduler does not necessarily check at launch: after start it checks immediately only if the last check (`SULastCheckTime`) is older than the interval, otherwise it waits out the remainder (`scheduleNextUpdateCheckFiringImmediately:...`). The docs allow one extra: "If you want to additionally force an update check on every app launch though, only call [`checkForUpdatesInBackground`] immediately after the updater is started, and only ... if ... `automaticallyChecksForUpdates` reads as `YES`"; calling it later "can interfere with Sparkle's update scheduler". So the brief's "asks Sparkle to check when it opens" is implementable that way. The docs also note that for dockless (background) apps scheduled alerts show behind other windows and a delegate should implement gentle reminders (https://sparkle-project.org/documentation/gentle-reminders/); that is UI scope.

Install and relaunch. Interactive path: the user clicks install, the installer sends the app a normal Apple quit event ("allowing the application or user to possibly cancel or delay termination", `Documentation/Installation.md`), waits for it to exit, swaps the bundle, then the progress agent relaunches with `[[NSWorkspace sharedWorkspace] openURL:...]` of the bundle path, only if the app was alive when it started (`Sparkle/InstallerProgress/InstallerProgressAppController.m` `relaunchApplication`, guarded by `_applicationInitiallyAlive`). The old process has already exited when the new one is opened, so Sparkle itself does not create two instances; whether Carrier's own login-item and single-instance logic agree with a LaunchServices open at that moment is not documented and is UNVERIFIED (the repo currently has no `SMAppService` use, so there is nothing to check yet). Delegate hooks exist: `updaterShouldRelaunchApplication:`, `updater:shouldPostponeRelaunchForUpdate:untilInvokingBlock:` (`Sparkle/SPUUpdaterDelegate.h`). Silent path (`SUAutomaticallyUpdate`): the update is downloaded and "installed on quit"; `Documentation/Installation.md` says that if the target is already terminated "the installer will also assume that the target should not be relaunched", so a silent install at quit does not relaunch. Sparkle shows the update to the user anyway if the app has not quit for `SUScheduledImpatientCheckInterval` (default one week), if the update is critical, or if authorization is needed (gentle-reminders page). A menu-bar app that rarely quits will therefore mostly ask after a week unless the delegate method `updater:willInstallUpdateOnQuit:immediateInstallationBlock:` takes control: its header says returning `YES` lets you call the block "to install the update and relaunch the application without any UI interaction shown" when the app judges the moment right (`SPUUpdaterDelegate.h`). That hook is where "free to replace" logic could live.

## 7. Homebrew: `auto_updates true`, upgrade, outdated, reinstall, uninstall, auto-update

What the docs say. The Cask Cookbook: `auto_updates` "Asserts that the cask artifacts auto-update. Use if `Check for Updates…` or similar is present in an app menu, but not if it only opens a webpage and does not do the download and installation for you" (https://docs.brew.sh/Cask-Cookbook). The FAQ section "How does `brew upgrade` handle apps that update themselves?" (`docs/FAQ.md` at 7.0.13, https://docs.brew.sh/FAQ) says: Homebrew's record can be older than the app that is installed; for a versioned cask with a single readable app bundle "Homebrew compares the bundle's version metadata with the cask's current version. The default `brew upgrade` includes the cask when the installed app appears older and skips it when the installed app appears to be the same version or newer"; when the comparison is not reliable it "normally skips the self-updating cask instead of guessing"; `HOMEBREW_NO_UPGRADE_AUTO_UPDATES_CASKS=1` opts out of this automatic upgrade "for all `auto_updates true` casks" and "does not affect upgrades requested with `--greedy` or `--greedy-auto-updates`". The same page for 5.0.0 said the opposite ("which excludes them from `brew upgrade`"); I checked tags: the bundle-comparison code (`auto_updates_bundle_outdated?` in `Library/Homebrew/cask/cask.rb`) is absent from 5.1.0 and present in 6.0.0, 7.0.0 and 7.0.13, so every Homebrew released since mid-2026 behaves as follows, and Homebrew self-updates, so that is what installs in the field will see.

What the code does, for a cask with `auto_updates true`, tap version `T` (the cask's `version`), Homebrew's record `H` (the version directory in the Caskroom; unchanged by Sparkle) and the installed app's `CFBundleShortVersionString` / `CFBundleVersion` `A` (`Cask#outdated_version`, `Cask#auto_updates_bundle_outdated?`, `Library/Homebrew/cask/cask.rb`):

- `brew outdated` and plain `brew upgrade` (no cask named): not outdated if `H == T`; otherwise, unless `HOMEBREW_NO_UPGRADE_AUTO_UPDATES_CASKS` is set, outdated only if the installed bundle compares older than `T`. The comparison reads the app's plist (`installed_app_info_plist`), compares the short version with `T` (equal on either plist field means not outdated; a lower short version means outdated), and only compares the build number as a secondary signal. For Carrier's scheme (cask `version "1.2.3"`, plist short version `1.2.3`, build `10203`): app already at `1.2.3` means not outdated even though `H` is older; app at `1.2.2` means outdated, so `brew upgrade` upgrades the cask exactly as for a normal cask (it quits the running app unless `--no-quit` or `HOMEBREW_NO_UPGRADE_QUIT_CASKS`, `cask/upgrade.rb`). Homebrew's own tests state both cases (`test/cask/upgrade_spec.rb`: `includes "auto_updates true" casks when the installed bundle version is older than the tap version`, `excludes ... when the installed bundle matches the tap version`).
- `brew upgrade --cask carrier` (or any form that names the cask): `Cask::Upgrade.outdated_casks` uses `cask.outdated?(greedy: true)` for named casks, and with greedy the auto-update branch is skipped, so the cask counts as outdated whenever `H != T`. After Sparkle took the app to `T` while `H` is still the old version, naming the cask reinstalls `T` over the identical version, quitting and reopening the app; if the app were ever newer than `T` this would downgrade it, which is the case the FAQ warns about. After that reinstall `H == T` and the command answers "the latest version is already installed".
- `brew outdated --greedy`, `brew upgrade --greedy` / `--greedy-auto-updates`: same as the named case for every `auto_updates true` cask: outdated when `H != T`. `HOMEBREW_UPGRADE_GREEDY=1` makes that persistent.
- `brew reinstall --cask carrier`: `Cask::Reinstall` uninstalls the installed artifacts and installs the tap's cask, whatever the app's version; it replaces a Sparkle-updated app with `T`'s zip (and reruns `postflight_steps`).
- `brew uninstall --cask carrier`: `Cask::Artifact::Moved#move_back` (`cask/artifact/moved.rb`) removes the Caskroom symlink, copies `/Applications/Carrier.app` back into the staged directory ("Backing up App"), then deletes `/Applications/Carrier.app`; there is no version check, so it works on a Sparkle-updated app (and Sparkle's in-place swap keeps the path the symlink points to). If the app is missing it raises "source ... is not there" unless `--force`. `--zap` additionally runs the `zap` stanza (`~/Library/Preferences/dev.ashulab.carrier.plist` in the current cask). Sparkle also writes a cache under `~/Library/Caches/<bundle id>/org.sparkle-project.Sparkle` (`Sparkle/SPULocalCacheDirectory.m`), which the current zap does not list.

`brew upgrade carrier` with a bare name. Carrier's tap has a formula and a cask both named `carrier`. `load_formula_or_cask` in `Library/Homebrew/cli/named_args.rb` prefers the formula (a non-core formula wins over a non-core cask) and prints "Treating carrier as a formula. For the formula, use ... or specify the `--formula` flag. To silence this message, use the `--cask` flag" (`package_conflicts_message`, sic about the flag wording). So `brew upgrade carrier` upgrades only the formula, with a warning; `--formula`, or the fully qualified `ashulab/tap/carrier`, removes the ambiguity. Tap trust adds a second reason to use the qualified name: since Homebrew 6.0.0 non-official taps need explicit trust and "installing a fully qualified formula or cask name trusts only that item", while a bare-name command needs the item trusted beforehand (https://docs.brew.sh/Tap-Trust); `brew upgrade` calls `Homebrew::Trust.trust_fully_qualified_items!` on qualified names (`cmd/upgrade.rb`). A person who installed with the README's `brew install ashulab/tap/carrier` has the formula trusted already.

Does `brew upgrade <formula>` run `brew update` first? Yes, conditionally. `brew.sh` calls `auto-update` before `install`, `outdated`, `upgrade`, `bundle` and `release` (`Library/Homebrew/utils/auto-update.sh`), which runs `brew update --auto-update` only if the Homebrew repository's `FETCH_HEAD` is older than `HOMEBREW_AUTO_UPDATE_SECS`. The documented default is 86400 (24 hours), 3600 if a developer command has run, and 300 (5 minutes) if `HOMEBREW_NO_INSTALL_FROM_API` is set (https://docs.brew.sh/Manpage, Environment); the script also uses 300 when any argument of `install`, `outdated` or `upgrade` looks like `user/repo/name` and is not `homebrew/...`, so `brew upgrade ashulab/tap/carrier` re-checks after 5 minutes while the bare `carrier` waits 24 hours. `HOMEBREW_NO_AUTO_UPDATE` disables the automatic one entirely (Manpage). An explicit `brew update` is not affected by that variable (`cmd/update.sh` never reads it), always fetches, and takes a lock: a second `brew update` at the same time fails with "Another `brew update` process is already running" (`utils/lock.sh`). So the brief's explicit `brew update` before `brew upgrade` is justified and does not conflict with a user-set `HOMEBREW_NO_AUTO_UPDATE`; it also makes the next `brew upgrade` skip its own auto-update inside the window.

Prompts. In Homebrew 7 `brew upgrade` is in "ask" mode by default ("Ask mode is the default", `--no-ask`/`-y`, `HOMEBREW_NO_ASK`); with named arguments it asks only if the plan includes other packages (`Install.ask_prompt_needed?`), and "the confirmation prompt is skipped without a TTY" (`cmd/upgrade.rb` option text; `Homebrew::Ask.confirm?` returns false without a TTY and the run goes on). A GUI-spawned child has no TTY, but setting `HOMEBREW_NO_ASK=1` in its environment makes that explicit and is ignored by older Homebrews, unlike a flag they might not know.

Pins and failures. A pinned formula is skipped ("upgrade only the given cask or formula (unless they are pinned)", Manpage; for casks `cask/upgrade.rb` reports "Not upgrading N pinned package"). An untrusted tap item makes the command fail until trusted (Tap Trust page). Offline or a failing git fetch makes `brew update` print errors; I did not test those.

Dependencies. `brew upgrade carrier` also upgrades outdated `node`, `git` and `gh`. In `Dependency#installed?` (`Library/Homebrew/dependency.rb`) a dependency is "satisfied" if its latest version is installed, and otherwise only if a minimum version recorded from a bottle's tab is met; `FormulaInstaller#expand_dependencies_for_formula_once` skips satisfied ones and installs the rest, and `install_dependency` upgrades an outdated one (`upgrading = dep_formula.outdated?`). Carrier's formula is not a bottle, so there is no recorded minimum, and any outdated dependency counts as unsatisfied and is upgraded; this matches the brief's measurement that installing the formula upgraded `node`. Beyond that, "Unless `$HOMEBREW_NO_INSTALLED_DEPENDENTS_CHECK` is set, `brew upgrade` ... will be run for outdated dependents and dependents with broken linkage" (Manpage), so upgrading `node` can also upgrade other installed formulae that depend on it, and `brew cleanup` runs afterward unless `HOMEBREW_NO_INSTALL_CLEANUP` is set. The app can limit that with those two variables, at the cost the Manpage names ("more breakage").

## 8. CI: pinning, tools, verifying, passing the key

There are two ways to get a pinned Sparkle on a macOS runner, and I checked both.

Through SwiftPM: with `exact: "2.10.1"` in `Package.swift` and `Package.resolved` committed (revision `ab7d71291238df6e0492143b120c9b696a35f603`), `swift build` downloads `Sparkle-for-Swift-Package-Manager.zip` (observed; I did not try `swift package resolve` alone) and SwiftPM checks it against the checksum in Sparkle's manifest at that revision (`4c2e48a3...`, `Package.swift` of the tag, and `.build/workspace-state.json` records it). The tools are then at `.build/artifacts/sparkle/Sparkle/bin/{sign_update,generate_appcast,generate_keys,BinaryDelta}` (observed here; the docs point to the same `artifacts/sparkle/Sparkle/bin/` location). The workflow already builds with `swift build` in `build-app.sh`, so no extra download is needed. This is the option with a checksum chain that comes from the Sparkle project.

By direct download: release asset `Sparkle-2.10.1.tar.xz`, e.g. `gh release download 2.10.1 -R sparkle-project/Sparkle -p 'Sparkle-2.10.1.tar.xz'` or `https://github.com/sparkle-project/Sparkle/releases/download/2.10.1/Sparkle-2.10.1.tar.xz`. Contents (observed): `bin/{sign_update,generate_keys,generate_appcast,BinaryDelta,old_dsa_scripts}`, `Sparkle.framework`, `Symbols`, `SampleAppcast.xml`, `CHANGELOG`, `INSTALL`, `LICENSE`, `Sparkle Test App.app`. The tools are ad hoc signed with the runtime flag (`codesign -dvv bin/sign_update`: `flags=0x10002(adhoc,runtime)`). The only checksum published for it is the `digest` field GitHub computes for each asset (`gh api repos/sparkle-project/Sparkle/releases/latest -q '.assets[]|[.name,.digest]'`); the release page lists no separate checksum file, signature or attestation (the attestations API answers 404 for this asset), and the project's release workflow `.github/workflows/create-draft-release.yml` publishes only the built files. So "checked against its checksum" can mean pinning `1a856d2a9edb8e628de88121d7be04cf0e2167f8641650b78fca00b14244cf27` in the workflow (a pin of what I downloaded, not a maintainer signature); a maintainer-published checksum or signature is not documented.

Where things live: `sign_update` and `generate_appcast` in `bin/`; `generate_keys` is only for a developer Mac (it uses the Keychain) and is not needed in CI.

Passing the private key non-interactively: store the exported key file's single line (from `generate_keys -x file`) as a GitHub secret, expose it as an environment variable, and pipe it: `printf '%s\n' "$SPARKLE_ED_KEY" | .build/artifacts/sparkle/Sparkle/bin/sign_update -p --ed-key-file - "out/Carrier-$VERSION.zip"` (observed here with a locally generated key file: stdin form, `-f file` form and `-p` all work, no Keychain involved; `findKeys(inFile:)` reads one line from stdin when the file argument is `-`). The same `--ed-key-file -` works for `generate_appcast`. Do not use `-s`.

Verifying the zip's signature "against the public key". `sign_update --verify <zip> <signature>` (with the key supplied the same way) checks the signature against the public key derived from the private key; it does not read `SUPublicEDKey` from the app. To check what a client will check, compare two things in CI: (1) the public key derived from the secret equals the `SUPublicEDKey` in `Carrier.app/Contents/Info.plist` (PlistBuddy), and (2) the signature verifies for those zip bytes under that public key. A short Swift script run with `swift script.swift` can do both with CryptoKit: `Curve25519.Signing.PublicKey(rawRepresentation: Data(base64Encoded: SUPublicEDKey)!).isValidSignature(Data(base64Encoded: sig)!, for: zipData)`; observed here, `CryptoKit` accepted a signature produced by `sign_update` with the key derived from the same seed. This also catches a stale `SUPublicEDKey` in `build-app.sh` against a rotated secret. For the dry run, the check step can run with a throwaway key (not a secret) if the real one should not be used.

The zip. The docs' command is `ditto -c -k --sequesterRsrc --keepParent MyApp.app MyApp.zip`; `release.yml` uses `ditto -c -k --keepParent` without `--sequesterRsrc` (which, per `man ditto`, preserves resource forks and HFS metadata in `__MACOSX` when creating a PKZip). Sparkle extracts zips with `/usr/bin/ditto -x -k` (`Autoupdate/SUPipedUnarchiver.m`), the same tool the workflow's "Check the zip" step uses, and that step already runs `codesign --verify --strict` on the extraction. The docs also advise putting nothing but the app in the archive (translocation issues) and say symlinks must be preserved because "their code signature will be broken if your archival tool follows symlinks" (Publishing page); `ditto` does that.

- "`CFBundleVersion` becomes `X*10000 + Y*100 + Z`; Sparkle compares it, not the short version": CONFIRMED (`SUHost.m` reads `CFBundleVersion`; compared to `sparkle:version` with `SUStandardVersionComparator`; short version is display only). Keep Y, Z below 100, set `sparkle:version` to exactly the bundle's value, and note the installer also rejects downgrades.
- "The defaults are to check and to ask first": CONFIRMED with a required change: Sparkle's own default is not to check until a permission prompt on the second launch; to get check-by-default with no prompt, write `SUEnableAutomaticChecks = YES` in the plist. "Ask first" is Sparkle's default (`SUAutomaticallyUpdate` is `NO`), but the install-automatically setting cannot be set while checking is off (section 6).
- The app "asks Sparkle to check when it opens": PARTLY. Sparkle checks at start only if the last check is older than the interval; a forced check at launch is allowed by the docs only through `checkForUpdatesInBackground()` right after the updater starts, and only when automatic checks are on.
- The cask declares `auto_updates true`: "after the install, the app is Sparkle's, and `brew upgrade` leaves it alone": CONTRADICTED for Homebrew 6.0.0 and later (7.0.13 is current). `brew upgrade` leaves it alone only when the installed bundle is not older than the cask version; if the app is older it upgrades the cask like any other. Naming the cask (`brew upgrade --cask carrier`) or `--greedy` reinstalls whenever Homebrew's record differs from the cask version, even if Sparkle already updated the app to that version. What `auto_updates true` really buys is that Homebrew will not replace a Sparkle-updated app with an older cask. Rewrite the ADR sentence, and the brief's "the cask without `auto_updates true`... two paths to the same file" reasoning still stands but the with-flag case also has two paths. Because both paths end at the same version (the workflow pushes the cask before the appcast) the practical risk is a Homebrew-initiated replacement of a running app, which quits it; `HOMEBREW_NO_UPGRADE_AUTO_UPDATES_CASKS` is the opt-out, and the cask cannot set it.
- The brief's "the message for an app older than `carrier` no longer says `brew upgrade --cask carrier`, which does nothing once the cask declares `auto_updates true`": CONTRADICTED. If the app is older than the cask, `brew upgrade` and `brew upgrade --cask carrier` do upgrade it. The message may still prefer "use the app's check for updates" as a product choice, but not on that ground.
- "`brew uninstall --cask` still removes it afterwards": CONFIRMED by source (`cask/artifact/moved.rb`, no version check); UNVERIFIED end to end, and the spike should include `brew uninstall --cask --zap` and check what is left (the Sparkle cache directory is not in the current `zap`).
- "What `brew outdated` and `brew upgrade` say about a cask whose app has moved on": answered by source in section 7 (app equal to tap version: not outdated; named cask or `--greedy`: outdated while the record differs); UNVERIFIED by running them, which the spike should do with a real Sparkle-updated app.
- "The app runs `/opt/homebrew/bin/brew upgrade carrier`": CONFIRMED to work, but change the argument: bare `carrier` is ambiguous with the cask and Homebrew prints a conflict warning while treating it as the formula; use `brew upgrade --formula ashulab/tap/carrier` (or at least `--formula`). A fully qualified name also trusts that formula implicitly under tap trust and shortens the auto-update window to five minutes.
- "The app runs `brew update` first, because Homebrew does not update its taps on every call": CONFIRMED (`auto-update.sh`; default 24 hours, 5 minutes for a qualified third-party name, disabled by `HOMEBREW_NO_AUTO_UPDATE`; an explicit `brew update` is unaffected by that variable and fails if another `brew update` holds the lock).
- "`brew upgrade carrier` may also upgrade what the formula depends on (`node`, `git`, `gh`)": CONFIRMED by source (`dependency.rb` `installed?`, `formula_installer.rb`), and it may also upgrade installed dependents of those formulae (Manpage, `HOMEBREW_NO_INSTALLED_DEPENDENTS_CHECK`). The brief's open question about a pinned `carrier`, a mid-update Homebrew and `HOMEBREW_NO_AUTO_UPDATE` has these source-derived answers: pinned means skipped with a message; a concurrent `brew update` fails on a lock with a message; `HOMEBREW_NO_AUTO_UPDATE` is irrelevant to an explicit `brew update`. UNVERIFIED by running: how those messages come out of a non-TTY child, which the first ticket can capture.
- "Updating from a GUI, no prompt": `brew upgrade` is in ask mode by default in Homebrew 7 but skips the prompt without a TTY; set `HOMEBREW_NO_ASK=1` for the child.
- "The app is Apple Silicon only, so the path `/opt/homebrew/bin/brew` is fixed": outside what I checked, not Sparkle-related.
- "A relaunch must not leave two Carrier icons in the menu bar" (open question in the brief): UNVERIFIED. From source, Sparkle quits the old process, waits for it to exit, swaps, and only then opens the new bundle through LaunchServices, so Sparkle does not itself start a second instance; whether Carrier's login-item registration and single-instance guard behave with that open is not documented. Test with the login item enabled and disabled, in both the interactive and the quit-time paths.
- "The Sparkle tools are downloaded in the workflow at a pinned version and checked against its checksum": CONFIRMED with a caveat. The only checksum is GitHub's asset digest (no maintainer-published checksum or signature), so a pin is a pin of the bytes seen on 2026-11-11. Prefer taking the tools from the SwiftPM artifacts (`.build/artifacts/sparkle/Sparkle/bin/`), where the chain is the committed `Package.resolved` revision plus the binary checksum in Sparkle's manifest, and nothing extra is downloaded.
- "The workflow's check step also verifies the signature of the zip against the public key": PARTLY CONTRADICTED as worded. `sign_update --verify` uses the public key derived from the private key, not `SUPublicEDKey` from the built app; add a comparison of the derived public key with the plist value and verify with that key (section 8).
- "`build-app.sh` embeds `Sparkle.framework` and writes `SUFeedURL` and `SUPublicEDKey` in the plist": CONFIRMED as feasible, with two additions found here: the executable needs `-rpath @executable_path/../Frameworks` (SwiftPM adds none, and the app crashes at launch without it), and the framework must be copied with symlinks preserved before the final `codesign --force --sign -` (verified to pass `--strict` and `--deep --strict`). Also add the plist keys section 6 names (`SUEnableAutomaticChecks`, and `LSMinimumSystemVersion` is already 26.0 for `sparkle:minimumSystemVersion`).
- "The cask's `postflight` that clears the quarantine stays, because Sparkle only acts after the first install": CONFIRMED (Sparkle never touches the first install). A Homebrew upgrade of the cask re-downloads a quarantined zip, and the same postflight clears it again.
- "Notarizing the app, or any change to its ad hoc signature" is out of scope: consistent with the finding that ad hoc leaves EdDSA as the only trust root and removes rotation; moving to Developer ID later would make the key rotatable and key loss recoverable (docs), but the validator also forbids moving from code signed back to unsigned.
- Not in the ADR, worth adding: Sparkle's cache directory (`~/Library/Caches/dev.ashulab.carrier/org.sparkle-project.Sparkle`) beside the preferences file in the cask's `zap`; the docs-recommended `--sequesterRsrc` for the zip; optional `SUVerifyUpdateBeforeExtraction = YES` (no downside here since the key can never be rotated); and an `sparkle:hardwareRequirements arm64` element (done automatically by `generate_appcast`).

## Spike result (2026-11-11): Sparkle 2.10.1 on an ad hoc app installed by Homebrew

This is the run that [0022](../adr/0022-the-app-updates-itself-with-sparkle-and-the-engine-through-homebrew.md) and the brief ask for (ticket #804). Everything below was observed on one Mac (macOS 27.0, arm64, Homebrew 7.0.13, Xcode toolchain with Swift 6.4.2, Developer Mode off, Gatekeeper assessments enabled), with a throwaway app that lives outside this repository and has been deleted. Times are local (UTC-3).

### What was built

A SwiftPM executable (AppKit, `LSUIElement`, one `NSStatusItem`) linking Sparkle pinned with `exact: "2.10.1"` (`Package.resolved`: revision `ab7d71291238df6e0492143b120c9b696a35f603`) and an rpath of `@executable_path/../Frameworks`. It was assembled by hand into an `.app` (the executable, `Sparkle.framework` copied with `ditto` so the symlinks stay, an `Info.plist` with `SUFeedURL`, `SUPublicEDKey`, `SUEnableAutomaticChecks`, `CFBundleVersion`), signed with `codesign --force --deep --sign -`, and `codesign --verify --deep --strict` passed. The Sparkle tools (`sign_update`, from `.build/artifacts/sparkle/Sparkle/bin/`) came from the SwiftPM artifacts, nothing was downloaded separately. The EdDSA keys were two throwaway Ed25519 keys made with CryptoKit and written as the 32-byte seed in base64, which is the format `sign_update --ed-key-file` takes (`common_cli/Secret.swift` at the tag: 32 bytes is the new format, 96 bytes the old one); they never touched the keychain, and the files were deleted. The throwaway ids were a bundle id, an app name and a cask token with a random suffix, none of them shared with Carrier.

The app asks Sparkle for a background check two seconds after it starts. To run unattended it uses a small `SPUUserDriver` that answers "Install" and "Install and Relaunch" instead of Sparkle's standard window. The download, the extraction, the validation, the `Autoupdate` and `Updater` helpers, the swap and the relaunch are Sparkle's own code and the same as with the standard driver; what was not exercised is the standard driver's windows and the quit-time path of "install by itself". The cask was in a local tap (`brew tap-new`), with `auto_updates true`, a `file://` url to the zip, the same `postflight_steps` `xattr -dr com.apple.quarantine` as the real cask, and a `zap` that lists only the preferences plist, like the real one.

Builds: 1.0.0 (build 10000) and 1.0.1 (build 10001), both ad hoc, different code hash, same `SUPublicEDKey`; the second one was the only item of the appcast, signed with the matching key.

### Box by box

**Sparkle installs an ad hoc update that is signed only with EdDSA, and the app relaunches: yes.** The cask installed 1.0.0 to `/Applications`; the app was opened; within the same second its log shows `update found 1.0.1 build 10001` then `terminating`, and a new process (new pid) logged `launched version=1.0.1 build=10001` from the same path. The whole round trip, download from a loopback server included, took under a second; with GitHub as the source about two seconds. Before: 1.0.0 / 10000, cdhash `f15f6fee...`; after: 1.0.1 / 10001, cdhash `2cac2318...`, which is the cdhash of the zip that was offered. The Sparkle lines in `log show --predicate 'subsystem == "org.sparkle-project.Sparkle"'`:

```
Autoupdate: Extracting using '/usr/bin/ditto' '-x' '-k' ... (the zip in ~/Library/Caches/<bundle id>/org.sparkle-project.Sparkle/Installation/...)
Autoupdate: OK: EdDSA signature is correct for update
Autoupdate: Code signature of the new version doesn't match the old version: cdhash H"f15f6fee...". Please ensure that old and new app is signed using exactly the same certificate.
```

The third line is logged at Error level on every successful update of an ad hoc app, and the update goes on. That is the "EdDSA or code signing" rule of `SUUpdateValidator` working as the research read it, but nobody should read that line as a failure.

**A zip signed with a different EdDSA key is refused: yes.** With 1.0.1 installed, the appcast offered 1.0.2 (build 10002, with the right `SUPublicEDKey` embedded in it) signed with the other key. Sparkle logged `EdDSA signature does not match`, `Update validation was a failure`, and the app received `The update is improperly signed and could not be validated`. The app kept running on 1.0.1 / 10001 with the same cdhash, and was not restarted.

**The relaunched app opens with no Gatekeeper dialog: no dialog was observed by any signal a machine can read, but nobody looked at the screen; the owner accepted this evidence on 2026-11-11.** Screen capture does not work in this session (`screencapture`: "could not create image from display"). What was recorded:

- The relaunch happened with no one at the keyboard, and the new process ran and did its work (it logged, started its updater and put its status item up). A blocking Gatekeeper dialog would have held the launch until someone clicked.
- `log show` for `syspolicyd` around the relaunch has `GK process assessment`, `GK Xprotect results` and `GK evaluateScanResult: 2` for the app, `Found provenance data on target`, `Created provenance data for target`, and no prompt, denial or block. `amfid` logged `The file is adhoc signed or signed by an unknown certificate chain` for the executable, the framework, `Autoupdate` and `Updater` (an informational line; the processes ran). `gktool` ran during the install (the pre-warm scan the source describes), and Sparkle's launch went through `CoreServicesUIAgent` ("Launching thru CoreServicesUIAgent").
- A poller listing every window owner (`CGWindowListCopyWindowInfo`, about every 0.2 seconds for the whole update and relaunch) found no owner that was not there before: no `CoreServicesUIAgent`, `UserNotificationCenter` or `SecurityAgent` window. The poller has a limit: the app's own status item window is not in that list either, so it shows that no ordinary dialog window appeared, not more.
- `spctl --assess -vv --type execute /Applications/<app>` says only `rejected`, exit 3, before and after the update and with no `source=` line. So the system's assessment of this app is "reject", and the launch is still not stopped: consistent with a launch gate that applies to quarantined files, which these are not (next box).

Verdict: on this Mac the ad hoc, not notarized, quarantine-free app that Sparkle replaced opened with no dialog that the logs or the window list show. The owner accepted this evidence on 2026-11-11 and the epic goes on. What would still make it stronger, and has not been done: a person watching the screen during the update on a Mac that is not a developer machine (a clean user or a fresh VM).

**`xattr -lr` shows no `com.apple.quarantine`, framework included: yes.** After the cask install (before the first launch) and after every Sparkle update: 0 files with `com.apple.quarantine` in the app and 0 in `Contents/Frameworks/Sparkle.framework`. This run does not show whether Homebrew had put the attribute on a `file://` download before the cask's `postflight` removed it, so what it shows for the cask is the end state. One thing the research did not say: every file of the bundle (159 of them, the framework's included) carries `com.apple.provenance`, an empty attribute. It was there right after the Homebrew install, before any launch, and again after Sparkle's swap; `syspolicyd` logs creating "provenance data" for the bundle when it scans it. It is not the quarantine attribute and nothing stopped on it, but a check written as "no extended attributes" would fail; check for `com.apple.quarantine` by name.

**One menu bar icon after the relaunch, with the login item registered and without: one instance and one status item in both cases, not seen by eye; the owner moved the by-eye check to the slice that embeds Sparkle in the real app.** `CGWindowListCopyWindowInfo` does not list a status item window for the app (not on screen, not with `optionAll`), so the icon cannot be counted from outside this way. What was recorded: `pgrep` finds one `SpikeApp` process after each relaunch; the relaunched process reports `statusItem.isVisible = true` and a button window at x 3040, y 1570 (bottom-left origin), 66 by 30, on a 3840 by 1600 screen, that is, inside the menu bar strip at the right; and `SMAppService.mainApp.status` was `notRegistered` (0) in the run without the login item and `enabled` (1) in the run with it, before and after the relaunch (it registered with no approval step). Two icons would need two processes, and there never were two. Two notes for the real app. First, `SMAppService.mainApp.unregister()` on an app that was never registered throws `SMAppServiceErrorDomain` code 1 "Operation not permitted" (status 3, `notFound`, afterwards); read `status` and call `unregister()` only when it is `enabled`. Second, registration worked for an ad hoc app in `/Applications` and survived Sparkle's swap of the bundle; the Mac may still show its own "background item added" notice, which was not looked at.

**Sparkle follows the redirects of a real GitHub Release: yes.** In a throwaway public repository a release `v1.0.1` carried `appcast.xml` and the zip as assets; the 1.0.0 app was built with `SUFeedURL = https://github.com/<owner>/<repo>/releases/latest/download/appcast.xml` and found, downloaded (the enclosure url is `.../releases/download/v1.0.1/<zip>`, itself a redirect) and installed the update and relaunched, with the same log lines as the local run. `curl -sIL` on the feed counts two redirects. Two details that matter for the release workflow: before the release existed the feed answered 404; right after `gh release create` it kept answering 404 for about ten seconds and then 200, so a check that runs just after publishing has to retry or wait; and the repository was public throughout (nothing was tried against a private one). The repository was deleted at the end.

**Homebrew, for a cask whose app Sparkle has moved past.** Setup S1: the cask is 1.0.0, Homebrew's record is 1.0.0, the app is 1.0.1 (Sparkle took it there from GitHub). Setup S2: the tap's cask is now 1.0.1 (the order the release uses: the cask is pushed before the appcast), the record is still 1.0.0, the app is 1.0.1. "Cask line" means a line with the cask in the output.

| Command | S1 (record 1.0.0 = cask 1.0.0, app 1.0.1) | S2 (record 1.0.0, cask 1.0.1, app 1.0.1) |
| --- | --- | --- |
| `brew outdated` | no cask line | no cask line |
| `brew outdated --greedy` | no cask line | `spike...` is listed (`--verbose`: `(1.0.0) != 1.0.1`) |
| `brew upgrade --dry-run` | no cask line | no cask line |
| `brew upgrade --dry-run --greedy` | not run | `spike... 1.0.0 -> 1.0.1` |
| `brew upgrade --cask <tap>/<name>` | `Warning: Not upgrading <name>, the latest version is already installed`, nothing changes | upgrades (below) |

A plain `brew upgrade` was not run for real in either setup, only `--dry-run`: it would have upgraded the other outdated packages of this Mac (the `--greedy` dry run counted 29). Its decision for the cask is the same code the dry run prints, and the dry run never listed the cask.

The real `brew upgrade --cask <tap>/<name>` in S2 printed `Upgrading ... 1.0.0 -> 1.0.1`, `Backing up App ... to .../Caskroom/<name>/1.0.0/...`, `Removing App '/Applications/...'`, `Moving App ... to '/Applications/...'`, `Purging files for version 1.0.0`, and cleaned the old download. Left on disk: the app (1.0.1, the zip's cdhash, 0 quarantine after the cask's postflight), the Caskroom record now 1.0.1, the Sparkle cache and the preferences untouched. The running app was not quit and not reopened: its pid did not change and it kept running (the cask has no `uninstall quit:`), while its bundle was replaced under it. The research expected the app to be quit and reopened; for a cask like Carrier's, which has no `quit` stanza, it is not. A second run said the latest version is already installed.

`brew uninstall --cask --zap <tap>/<name>` (app running, Sparkle cache present) printed `Zapping Cask`, `Backing up App ... to Caskroom`, `Removing App`, `Trashing files: ~/Library/Preferences/<bundle id>.plist`, `Removing all staged versions`. Left: nothing of the app in `/Applications`, nothing in the Caskroom (no record), the preferences plist moved to the Trash. Still on disk: `~/Library/Caches/<bundle id>/` with `org.sparkle-project.Sparkle/{Installation,PersistentDownloads}` and the app's own URL cache (`Cache.db`, `Cache.db-shm`, `Cache.db-wal`, `fsCachedData`), as the research said the current `zap` would not list them. The running process was not touched: it kept running from the deleted bundle.

### Where this differs from what the research read

- Confirmed as read: Sparkle accepts the ad hoc update with only the EdDSA signature and refuses another key; the update leaves no quarantine on the app or the framework; `gktool scan` runs; Sparkle follows GitHub's redirects; `brew outdated`, `brew upgrade` and `--greedy` decide as section 7 derives them from the source (S1 and S2 match its table); the Sparkle cache folder is not in the current `zap` and stays behind.
- New: Sparkle logs an Error-level "Code signature of the new version doesn't match the old version" line on every successful ad hoc update.
- New: every file of the bundle carries `com.apple.provenance`; it is not quarantine.
- Differs: `brew upgrade --cask <name>` over a running app does not quit or reopen it when the cask has no `quit` stanza; it swaps the files under the running process.
- New: `latest/download` of a fresh release answers 404 for about ten seconds after it is created.
- New: `SMAppService.mainApp.unregister()` throws when the app is not registered; a status item window of the app cannot be counted with `CGWindowListCopyWindowInfo` on macOS 27.
- Not exercised: the standard Sparkle windows, the quit-time path of "install by itself", a private repository, Intel, a clean Mac, and whether a person sees a Gatekeeper dialog or a login-item notice.

### Clean-up

The throwaway app, its local tap and cask, its preferences, caches, keys, scratch folder, local server and the throwaway repository were removed; nothing of them is in this repository. The one trace outside the repository is the preferences plist that `--zap` moved to the Trash of the Mac, which the session cannot read or empty.
