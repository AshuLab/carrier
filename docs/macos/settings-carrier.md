# Settings: the Carrier group

The pages of the Carrier group of [Settings](settings.md): how Carrier runs epics and how the app runs Carrier.

## Repos

The Repos page, the Carrier group of the rail, is a master-detail: the list on the left with Add repo under it, the chosen repo on the right (`Carrier/ReposTab.swift`, model in `CarrierCore/RepoList.swift` and `CarrierCore/AvailableRepos.swift`) lists the repos in the config file's `repos` with a dot (green ok, red when GitHub refused it, grey when new or Carrier is stopped), the last check or the error and the epics each has, from the snapshot's `watched`, `epics` and `queue`.
Add repo opens a picker with the repos the engine's gh login can push to, grouped by owner, with search; it asks Carrier for them with the `availableRepos` request (a capability in the hello: an engine without it, a stopped one or a GitHub failure each show their own message, and there is no typing a name by hand).
The list is loaded a page at a time, 30 repos each, newest push first: while the engine says there is more (`hasMore`) the picker shows a "partial list" notice and a Load more button that appends the next page (the model is `AvailableReposList`; Search filters what is loaded), and a page that fails after the first keeps what is loaded, says so under the list and the button asks for it again.
An engine whose hello lacks `availableReposPaged` is asked once, without `page`, and shows that list with no notice and no button.
A repo already watched shows ticked and off, and one whose folder name matches another watched or ticked repo is off with the reason.
The ✕ on a row asks first, with what happens to the repo's epics (they stop where they are and continue if it is added again; nothing is deleted); the only repo cannot be removed.
Changes are saved as they are made, like the Behavior tab's (adding a repo, or stopping to watch one after the question; a list the engine would refuse waits and says why), and nothing restarts Carrier.
The file is read again just before writing, a kept repo's entry is written back as it was (including anything the app does not show) and a new one is only its name, so the two tabs never overwrite each other's keys.

The chosen repo's page has three cards.
It starts with its Status card (`CarrierCore/RepoStatus.swift`, fed with the list's row): the epics ready and running, the last check, the clone with `~` and Reveal (only when the clone exists) and the repo on GitHub with Open; a repo the running engine has not loaded, and every repo while Carrier is stopped, says "Carrier reads it when it starts" in place of the epics and the last check.
Under it, Ready for Carrier (`CarrierCore/RepoChecks.swift`, `repoChecks`, tested in `RepoChecksTests`) shows four rows from the checks of `carrier doctor --json` that are about the repo (their `repo` and `profiles`): Carrier can read it, Author can sign here, Reviewer can sign here and Solve is set up, each ok, failed with the doctor's reason and fix, or waiting.
A role's row is the repo's `can mint a token` check whose `profiles` holds the profile the role resolves to in that repo, so two roles of one identity show the same check; a check the doctor did not report (something before it failed) is waiting, never failed.
A failed sign row offers Use another identity (`RepoCheckRow.anotherIdentity`), which opens that role's form in Who works here (`RepoRoleSelection`); no other row offers it.
The doctor (`AppHealth.doctor`, shared with the Health tab) runs when the page opens and on Check again, never in the background; while it runs or when it could not answer, a line says so and the rows wait.
`--fixture` answers the run with `Tests/Fixtures/doctor.json` (copied into the fixture home), which carries the new fields: `acme/web` all ok, `acme/api` with a failing reviewer and no Solve labels, the long-named repo unreadable.
Under it, Who works here (`CarrierCore/RepoRoles.swift`) shows the repo's Author and Reviewer, and the Lead reviewer only when the global `agents` has one: `<profile> · <provider> · <model> · <effort>`, labelled "Same as everywhere" when the repo has no entry of its own, else its own fields over the inherited ones; each role has Change and, when the repo has its own entry, Reset.
Change opens a form inside the card with Identity (a profile of `profiles`), Provider (an account of `providers.json`, or the three default accounts without the file), Model, Effort and the persona's name and prompt; each field left on "Same as everywhere" is not written (`CarrierCore/RepoRoleSave.swift`, `saveRepoRole`, tested in `RepoRoleSaveTests`).
The save reads the file again, writes only `repos[].agents.<role>` with the fields set (texts trimmed, a model of only spaces and an empty persona not written, an entry that would be empty removed) and keeps every other key; Reset removes the role's entry.
A profile or account that is not declared (shown as missing in the form) is refused before writing, in words.
Author and Reviewer on the same identity is accepted and the card says the signature will show it.
After a save the doctor runs again, and when the engine refuses the config its reason (the doctor's stderr from `Invalid config`, `DoctorState.refused`) is shown under the roles and in the Ready for Carrier note.
The fixture's `config.json` (`fixtureConfig`) has the three fixture repos, the profiles and the three roles.

## Agents

The Agents page, in the Carrier group after Repos, is a master-detail of the three fixed roles, Author, Reviewer and Lead reviewer (`Carrier/AgentsTab.swift`, model in `CarrierCore/AgentsPage.swift`, tested in `AgentsPageTests`; the views have no test).
The Who card writes as you change it (`saveGlobalRole` in `CarrierCore/GlobalRoleSave.swift`, tested in `GlobalRoleSaveTests`): Identity, Provider, Model (on Return or leaving the field) and Effort (the five levels or Default) each write only that key of `agents.<role>`, with the file read again just before and every other key kept; choosing a bot adds `profiles.<name>` as `{ kind: "forge", agent }` once and reuses it afterwards, and the person's login uses the first `gh` profile or adds `gh`.
An empty model, a provider that is not an account, a bot the registry does not list, or a role that would be left without profile, provider or model is refused before writing, with the reason under the card; a profile that is no longer in the registry stays, marked missing, and is refused only when chosen again.
Create a bot… (`Carrier/CreateBotRow.swift`, under the Identity row) opens Terminal on `agent-forge add` (`CarrierCore/ForgeTerminal.swift`, tested in `ForgeTerminalTests`): the command is from a closed list of one entry, quoted, nothing from the registry or the config is part of it, and the one-use script and the opener are Continue in Terminal's (under `--fixture` the opener only says what it would have run); the page reads the registry again whenever the app becomes active, so the new bot appears without a refresh button.
The Details card writes the persona as you change it (Persona name and Persona prompt on Return or leaving the field, `saveGlobalPersona` in `CarrierCore/RoleDetailsSave.swift`, tested in `RoleDetailsSaveTests`): either one alone or both, the texts trimmed, a blank field left out and both blank removing the persona, and a name over 40 characters or with a line break, or a prompt over 4000, refused before writing with the reason under the card (the limits are `RoleFields.problems`, the repo form's).
The When it runs out of tokens card writes `failover.roles.<role>` (`saveGlobalFailover`, same file): Switch automatically on shows First (a declared provider and an optional model, written once First has a provider) and Then (optional, None takes it back), off removes the role's list; a step that repeats the other or is the role's own provider and model is refused with its position, and the steps a file has after the first two are kept when those are edited.
`agentsPage` turns `config.json`, `providers.json` (or the three default accounts) and the names of the Agent Forge registry (`forgeBots`, from `$AGENT_FORGE_CONFIG`, else `$XDG_CONFIG_HOME` or `~/.config` plus `agent-forge/agents.json`: names only, never a key; a registry that is missing or does not read gives no bots and a note, not an error) into a row per role: identity (a bot the registry has, the person's own gh login, or missing when the profile is not in `profiles` or its bot is not in the registry, and then it stays in the file), provider (marked missing when it is not an account), model, effort, persona and the failover steps of `failover.roles.<role>` (the page shows a first and a then step and says how many more the file has).
A role's page has three cards: Who, Details and When it runs out of tokens.
The Lead reviewer has the Use a lead reviewer row on top, and while the file has no `agents.leadReviewer` the row says Off and the rest of its page is dimmed and not usable.
Turning the switch off removes `agents.leadReviewer` and `failover.roles.leadReviewer` and keeps every other key (`turnLeadReviewerOff`), and the row says so; turning it on writes nothing: the page asks for an identity, a provider and a model (`LeadReviewerDraft`, kept in the page) and, once the three are chosen, writes the whole role in one go through `saveGlobalRole` (`turnLeadReviewerOn`), so the file never holds a half role (`CarrierCore/LeadReviewerSwitch.swift`, tested in `LeadReviewerSwitchTests`).
When Author and Reviewer resolve to one account by the engine's rule (`sameAccount`: two gh logins, or two profiles of one bot) the page says the signature will show it.
A config that is missing or is not a JSON object says the engine is not configured.
Under `--fixture` the app sets `AGENT_FORGE_CONFIG` to `agent-forge.json` in the fixture home (`fixtureForgeRegistry`: the three bots of the roles and a spare one), and `fixtureConfig` has failover steps for the Author and the Reviewer.
Use in an agent… on a signed-in account of the Providers page that no role names, and Open Agents on the Repos page (in Who works here, and next to Use another identity on a failed "can sign here" check), open this page.

## Behavior

The Behavior tab (in the Carrier group, before Engine, "How Carrier runs epics"; `Carrier/BehaviorTab.swift`, model in `CarrierCore/EngineConfig.swift`) edits eight values of the config file in place, in three groups drawn from the model in `CarrierCore/BehaviorPage.swift` (`behaviorGroups`, tested in `BehaviorPageTests`): Pace (`pollIntervalMinutes`, `limits.maxConcurrentEpics`), When something goes wrong (`limits.maxReviews`, `limits.maxExecutionRetries`, `limits.maxExecutionHours`, with Unlimited) and Housekeeping (`finishedWindowDays`, whole days from 1 to 30, 15 by default; `limits.githubCallTimeoutSeconds`; `logLevel`).
They are text fields that check the engine's rules as you type; a value equal to the engine's default is taken out of the file, and nothing else in the file is touched (the app never makes the file: without a JSON object there it says the engine is not configured).
Every change the engine would accept is written to the file at once (`autosave`; a value still being typed, or one the engine would refuse, waits and says why) and the engine is asked after the person pauses for about 700 ms, or at once when the page closes or the app quits, the page's header says "Saved" beside the title for a moment, or why it could not save or that the file cannot be read, in orange (the page passes it up with `SettingsHeaderNoteKey`), and says nothing otherwise, and the Reset group at the end of the page (`behaviorReset`, one card, "Restore the defaults") puts the engine's own defaults back after a confirmation (they are saved the same way, and a value equal to its default is taken out of the file).

## Engine

The Engine page (the last of the Carrier group, "How the app runs Carrier") holds what the app starts Carrier with: its Starting group (`CarrierCore/EnginePage.swift`, `engineGroups`, tested in `EnginePageTests`) has "Start Carrier when the app opens" (`engine.startOnOpen`) and "Ask before stopping Carrier" (`stop.confirm`, on by default; it used to be General's), its Programs group (`engineGroups`, also in `EnginePage.swift`, with `EnginePrograms` as the paths and versions it is given, tested in `EnginePageTests`; the versions are what `carrier --version` and `node --version` print, read by `Carrier/ProgramVersions.swift` when the page opens, a program changes or a detection ends, through `shortRun` in `Carrier/ProcessRun.swift`, also used by the chat host's version check; "Reading version…" while they run, and a problem when one does not answer or nothing runs at the `carrier` path) shows `carrier` with its path and version, `node` the same, and the `PATH` the engine and the chat host run with (read only; "Not found" in place of a path), then "Look for the tools again" with the button Detect.
"Use another…" on the `carrier` row opens a file picker; while one is set the row says it is the person's own and offers "Use the Homebrew one"; its GitHub identity group has "Carrier acts on GitHub as" (`orchestratorProfile` of `config.json`, `CarrierCore/EngineIdentity.swift`, `saveOrchestratorProfile`, tested in `EngineConfigTests` and `EnginePageTests`): the default (the author's identity) first, then the file's `profiles`, the default taking the key out of the file and every other key kept (saved with sorted keys); a profile the file names but does not declare stays on the list and shows in orange until another is picked; a refused save is that row's problem, said to VoiceOver; a file that cannot be read leaves the row disabled and says so in orange, and one that is not a JSON object is not changed; the engine is asked to reload after the write like every other writer's, so the choice applies without a restart, and its answer is the page's `ReloadNote`.
Its Files group (`engineGroups` again) has "Carrier folder", "Logs" and "Start log", each with its path (`~` for the home folder) and a Reveal or Open button, disabled with "Not created yet" while the path is missing.
The app finds `carrier` by itself (`carrierPath`): the one chosen with "Use another…" when it is set (a path as typed, `~` expanded; one ending in `.ts` or `.js` runs under `node`), else `/opt/homebrew/bin/carrier` when it is executable, else it is missing.
On the first launch (nothing saved in user defaults) the app asks the user's shell once, `zsh -ilc` with markers around what it prints and a 10 second limit, for `node` and the `PATH`, without asking the person; Detect repeats the run.
With saved values the shell is never started.
The `PATH` the engine will get is the detected one (the system's when the shell gave none) with node's directory first and `/opt/homebrew/bin` at the end when it is not in it.
A banner on every section says what Start Carrier lacks, or that it is looking for it, and is not shown when all is found; when something is missing it says to use "Use another…" and then Detect under Programs on the Engine page, and its own button is Detect; the banner's model is `CarrierCore/EngineTab.swift`.
