# Research for the macOS app: slice progress, finding Node, notifications, stop and the control socket

> Research of 2026-10-19 for the [macOS app brief](../specs/macos-app.md) and [ADR 0005](../adr/0005-engine-independent-of-the-macos-app.md). Everything ran on this Mac (macOS 27.0, Apple Swift 6.4, Command Line Tools 27.0.0 and Xcode 27.1, Node 22.22.0, 24.14.1, 25.6.0 and 26.12.0 from nvm, `gh` 2.102.0) with no display. The experiments were disposable and are not kept: the `scratch/` paths below name where they ran, the commands and their output are in the text.

## Summary

| Question | Answer | What it changes |
|---|---|---|

About 1 request per repo per poll, about 0.24% of the hourly limit. The permission is Issues read, which both Forge bots already have. | The existing poll does not get it for free: it lists only `solve:epic:ready` (queued) epics and its zod row drops the field. | 2. | 3. Notifications and menu bar | `UNUserNotificationCenter.current()` aborts in a bare SwiftPM executable. ## 1. Slice progress: where Carrier can read it

### Short answer

Use REST. The issue object already carries `sub_issues_summary` with `total`, `completed` and `percent_completed`, it is GA with no preview header, and it needs only the Issues read permission that Carrier's profiles already hold. Carrier already reads GitHub through `gh api` REST, but the list it polls (`solve:epic:ready`) contains only queued epics, not running ones, and its zod schema drops the field. So the cheapest path is one extra list per repo per poll, `GET repos/{repo}/issues?labels=solve:epic:running&state=open`, which returns the summary of every running epic in that repo in one request (about 1 point per repo per poll). GraphQL `subIssuesSummary` also works and can batch epics across repos with aliases for 1 point, but nothing in the engine speaks GraphQL today, so it buys nothing. At the default 5 minute interval this is about 12 requests per hour per repo, roughly 0.25% of the 5,000/h primary limit. Nothing in the engine reads sub-issues today.

### 1. Which API gives sub-issues

REST has four sub-issue operations in the [OpenAPI description](https://github.com/github/rest-api-description) (v1.1.4, API version 2026-03-10): `GET /repos/{owner}/{repo}/issues/{issue_number}/sub_issues` (`issues/list-sub-issues`, paginated with `per_page` and `page`, returns an array of full issue objects, 404 and 410 errors), `POST` on the same path (add), `DELETE .../sub_issue` (remove) and `PATCH .../sub_issues/priority` (reprioritize). All are marked `enabledForGitHubApps: true`, and the OpenAPI carries no preview or beta flag on them. See the [REST docs for sub-issues](https://docs.github.com/en/rest/issues/sub-issues) and, for the permission data, `src/github-apps/data/fpt-2026-03-10/fine-grained-pat-permissions.json` in github/docs.

The issue schema (`components.schemas.issue`, returned by `GET /repos/{o}/{r}/issues/{n}`, by `GET /repos/{o}/{r}/issues` list, and by list-sub-issues) has `sub_issues_summary` (`$ref` `sub-issues-summary`, titled "Sub-issues Summary": `total`, `completed`, `percent_completed`, all integers and all required inside the object) and `parent_issue_url` (nullable URI). `sub_issues_summary` itself is not in the issue's `required` list, so treat it as optional when parsing. Search results (`issue-search-result-item`) also carry the summary.

Version header: `X-GitHub-Api-Version: 2026-03-10` is the latest per the docs page. I observed `sub_issues_summary` returned both with `2022-11-28` and with no header (the response header `X-Github-Api-Version-Selected` was 2022-11-28 by default), so the header is not required for this field.

GraphQL: introspection against the live schema shows `Issue.subIssues(after, before, first, last): IssueConnection!` ("A list of sub-issues associated with the Issue."), `Issue.subIssuesSummary: SubIssuesSummary!` ("Summary of the state of an issue's sub-issues") and `Issue.parent: Issue`. `SubIssuesSummary` has `total: Int!` ("Count of total number of sub-issues"), `completed: Int!` ("Count of completed sub-issues") and `percentCompleted: Int!`. I ran the query with no `GraphQL-Features` header and it worked, so it is GA. (The docs.github.com GraphQL reference pages did not render the Issue object through my fetch tool, so the field text comes from introspection, not the web page.)

Live shape (`AshuLab/carrier` is public, epic #3 has 31 sub-issues): `gh api repos/AshuLab/carrier/issues/3 -q .sub_issues_summary` prints `{"completed":31,"percent_completed":100,"total":31}`. `gh api repos/AshuLab/carrier/issues/3/sub_issues -f per_page=2` returns an array of issue objects (keys include `number`, `title`, `state`, `state_reason`, `sub_issues_summary`, `parent_issue_url`) plus a `Link` header with `rel="next"` and `rel="last"` (page=16 at per_page=2).

### 2. One call for N epics, and what Carrier fetches today

REST: yes, because the list endpoint returns full issue objects. The first array element of `GET repos/AshuLab/carrier/issues?labels=solve:epic&state=all` has `sub_issues_summary`, so one request per repo gives every epic's progress. GraphQL: yes too, with aliases. I ran a query with three `issue(number: N)` aliases under one `repository(...)` and `rateLimit{cost}` returned 1. Aliases over several `repository(owner,name)` roots are possible in one query, so one call could cover all repos (I tested two aliases of the same repo with cost 1; I did not test cross-repo aliases).

What Carrier reads today (all REST through `gh api -i`, `src/integrations/github.ts:86-118`, executed as `gh` or `agent-forge gh <agent>` with `cwd` from `src/integrations/forge-cwd.ts:11`):

- `listReadyEpics` (`github.ts:130-136`) calls `repos/{repo}/issues?labels=solve:epic:ready&state=open&per_page=100` once per repo per poll (`engine.ts:499`). The response does include `sub_issues_summary` for each item, but the zod row schema (`github.ts:39`, `issueRow`: number, title, pull_request) discards it. More importantly, this list holds only queued epics: once an epic starts, the engine swaps the ready label for `solve:epic:running` (`engine.ts:483-485` expects running and no ready label). So the existing poll does NOT list the epics whose progress matters (running ones), and it would not get progress for free. Adding `sub_issues_summary` to `issueRow` would only give progress for queued epics, where it is normally 0/N.
- `getIssue` (`github.ts:138-141`, schema `issueDetail` at `:40`: state and labels only) is called per epic in `fillSlots` (`engine.ts:425`) and in recovery at startup (`engine.ts:483`), not on every poll.

So, minimal option: a new port method (for example `listRunningEpics(repo)` over `labels=solve:epic:running&state=open`, reusing `pages()`/`get()`) called once per repo per poll. Needs-human and ready-for-test epics also carry their own state labels (`orchestration/github.ts:22`), so a list over those labels, or one list of `labels=solve:epic` with all states, would cover them too. `getIssue` per epic would work as well (1 request each) but costs N per poll instead of 1 per repo.

### 3. Rate-limit cost

Poll interval: `pollIntervalMinutes` is a positive number in `src/config/schema.ts:31`, default 5 (`src/config/load.ts:5`, `docs/configuration.md:34`), converted at `src/terminal/cli/compose.ts:98`. That is 12 polls per hour.

- REST primary limit: 5,000 requests per hour for a user token; a GitHub App installation token starts at 5,000, gains 50 per repo and per org user above 20, capped at 12,500; 15,000 for Enterprise Cloud ([REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). Most GETs cost 1.
- GraphQL primary: 5,000 points per hour per user or installation, same cap rules; the cost is the sum of requests implied by each connection divided by 100, rounded, minimum 1 ([GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)). Observed: a query with 3 `issue()` aliases and `subIssuesSummary` returned `cost: 1`; `subIssues(first: 100)` would be about 1 per epic.
- Secondary limits (same two pages): at most 100 concurrent requests, 900 points per minute for REST endpoints, 2,000 per minute for GraphQL; GET costs 1 point. Not a concern here, since Carrier's calls are sequential.
- Conditional requests: the [best practices page](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api) says a conditional request "does not count against your primary rate limit if a 304 response is returned" and the request must carry an `Authorization` header. I confirmed that `issues/3`, `issues/3/sub_issues?per_page=2` and the epic list all return `ETag` and answer `304 Not Modified` to `If-None-Match` through `gh api -i`. I did not isolate the counter delta of a 304 (the `X-Ratelimit-Used` values I saw are consistent with it but not a controlled test). GraphQL has no equivalent. Cost to adopt: `GhGitHub.api` (`github.ts:100`) treats any status of 300 or more as a failure (a 304 would become `HttpError`) and keeps no ETags, so it would need a small cache. Not worth it at this volume.

Estimate for 3 running epics in one repo, 5 minute interval: one `labels=solve:epic:running` list per poll is 12 requests/h (about 0.24% of 5,000). Even the naive per-epic `GET issues/{n}` is 36/h (0.7%). With R repos add R requests per poll. For comparison, the poll already spends at least one list per repo (`engine.ts:499`) plus `ensureLabels`. If the app wants fresher progress than 5 minutes, the budget still allows about 1 request every 10 seconds per repo before reaching even 10% of the hourly limit (this is arithmetic on the 5,000 figure, not a recommendation; GitHub's page recommends webhooks and honouring `X-Poll-Interval`).

### 4. Token permissions

REST: the github/docs permission table for API 2026-03-10 lists `list-sub-issues` (GET), `get-an-issue` and `list-repository-issues` all under "Repository permissions for Issues" with `access: read` and `additional-permissions: false`. Only add/remove/reprioritize need `write`. Metadata read is implicit. For public repos, the [public-access reusable](https://github.com/github/docs/blob/main/data/reusables/rest-api/public-access.md) says some endpoints work on public resources without the permission and tells you to check each endpoint; the list-sub-issues page I fetched did not state it either way, but I read my own public epic with my normal `gh` login, not anonymously. Classic PAT scope: I did not find a primary-source statement for sub-issues; the general rule for issues is `repo` for private and `public_repo` for public (not verified for this endpoint). GraphQL `Issue.subIssuesSummary` access rule was not found in docs; it should follow the same Issues read (unverified).

Carrier's profiles: `docs/research/agent-forge.md:32` records the minted permissions of both Forge bots as `issues:write ... metadata:read` (artanis-agent also `issue_fields:write issue_types:write organization_projects:write`). `issues:write` includes read, and Carrier already calls `GET issues` and `GET issues/{n}` with the orchestrator profile (`orchestratorProfile`, `docs/configuration.md:30`), so no new permission is needed. The `kind: "gh"` profile uses the user's own login (`docs/research/agent-forge.md:92`); here that is a keyring OAuth login for `vemec` (`gh auth status`), which can read.

### 5. Does the engine fetch sub-issues today

No. A grep for `sub_issue`, `subIssue`, `sub-issue` and `subIssues` over `src/` finds nothing. The only hits are docs: `docs/glossary.md:56` ("Carrier does not store it today"), `docs/specs/macos-app.md:17,29`, `docs/preparing-a-repo.md:14` (slices are real sub-issues created with `--parent`), `docs/agents/solve.md:11`. The engine's GitHub port (`src/orchestration/github.ts:36-50`) has no method for it, and the code uses REST only, never GraphQL.

## 2 and 3. Finding carrier and Node from a GUI app; notifications and menu bar from an unsigned SwiftPM executable

Machine: macOS 27.0 (Darwin 27.0.0), `swift --version` = Apple Swift 6.4 (swiftlang-6.4.0.34.1), arm64-apple-macosx27.0.0; `xcodebuild -version` = Xcode 27.1 (27A9275); `xcode-select -p` = /Applications/Xcode.app/Contents/Developer; Command Line Tools 27.0.0 are also installed at /Library/Developer/CommandLineTools. Experiments live under scratch/ (nb/, mb/, *.app); the repo was not touched.

### Short answer A (finding carrier and Node)

Do not shell out to a login shell as the primary mechanism. Store two absolute paths in an app setting (`carrier` bin, and `node`), pre-filled by a one-time detection, and spawn `node <carrier main.js>` directly with an explicit environment whose PATH the app builds. The shebang is `#!/usr/bin/env node` (src/terminal/cli/main.ts line 1 and dist/terminal/cli/main.js line 1, package.json `bin.carrier` -> ./dist/terminal/cli/main.js), so under the launchd PATH (`/usr/bin:/bin:/usr/sbin:/sbin`) running the bin directly fails with `env: node: No such file or directory`. Running with an absolute node path works. The same PATH problem hits the engine's children: host-runner.ts passes `baseEnv: process.env` and `resolveBinary(task.harness)` walks `process.env.PATH`, and doctor.ts / github.ts / git-workspaces.ts call `which`, `gh`, `git`, `agent-forge` by bare name, so whatever PATH the app gives `carrier` is the PATH every agent CLI sees. Detection can be done once by asking the user's own shell (`zsh -ilc`) for `node`, `claude`, `codex`, `agy`, `gh`, `agent-forge`, and the detected values are then saved, not re-run on every start.

### Evidence A

The user's shell resolves Node through nvm: `command -v node` = /Users/vemec/.nvm/versions/node/v25.6.0/bin/node (v25.6.0). `carrier` is not installed on this machine (`command -v carrier` empty). fnm and volta are not installed here, so they were not run; fnm's docs say activation is `eval "$(fnm env)"` in the shell setup ([fnm configuration.md](https://github.com/Schniz/fnm/blob/master/docs/configuration.md)), and nvm's README says its install script adds source lines to `~/.zshrc` (or `.bashrc`, `.bash_profile`, `.profile`) ([nvm README](https://github.com/nvm-sh/nvm#installing-and-updating)). Here nvm is sourced in ~/.zshrc line 107-110 only; ~/.zprofile only adds Docker and `~/.local/bin` to PATH.

`env -i /usr/bin/env node -v` -> `env: node: No such file or directory` (rc=127); same with `PATH=/usr/bin:/bin:/usr/sbin:/sbin`. An app launched with an empty env through LaunchServices (`env -i /usr/bin/open -n -W X.app`, which I used as an emulation of a Dock launch) reports `PATH=/usr/bin:/bin:/usr/sbin:/sbin` from `ProcessInfo`. A plain `open` from my terminal instead passed my whole shell PATH through, so a test launched that way proves nothing. `launchctl getenv PATH` is empty here; `launchctl managername` = Aqua.

Option 1, login shell. zsh reads `/etc/zshenv`, `~/.zshenv`, then for login shells `/etc/zprofile` and `~/.zprofile`, then for interactive shells `/etc/zshrc` and `~/.zshrc`, then for login shells `.zlogin` (`man zsh`, STARTUP/SHUTDOWN FILES). Result with `env -i HOME USER PATH=/usr/bin:/bin:/usr/sbin:/sbin`: `/bin/zsh -lc` finds node=/opt/homebrew/bin/node (v26.8.2, the Homebrew Node via /etc/paths.d, NOT the nvm one), claude, codex, agy under ~/.local/bin, gh=/opt/homebrew/bin/gh, git=/usr/bin/git, and agent-forge empty (pnpm's PATH entry lives in .zshrc). `/bin/zsh -ilc` finds node=/Users/vemec/.nvm/versions/node/v26.12.0/bin/node (the nvm default alias, not the v25.6.0 the open terminal had), and agent-forge=/Users/vemec/Library/pnpm/agent-forge. So `-l` alone is wrong in a silent way: it finds a different Node than the user's nvm Node. `-ilc` takes 0.91s total on this machine (`time` output), runs the whole .zshrc (any prompt frameworks, `compinit`, `read`, `exec tmux` style side effects), and can print to stdout, so output parsing needs a marker. Fine for a one-time detect with a timeout, bad as the launch path for a long-lived engine.

Option 2, setting plus detected default. Needs no shell at run time, is deterministic, survives nvm default changes only if the user re-detects. Downsides: nvm paths contain the version (`.../v25.6.0/bin/node`), so uninstalling that version breaks it; the app should show "node not found at <path>" and offer re-detect. Volta installs shims at a stable location so a fixed path survives upgrades (not run here); with fnm the path is under a per-shell multishell dir that `fnm env` creates, so detection through `-ilc` must be re-run per session or the user must point at the `~/.local/share/fnm/node-versions/...` install (not verified, fnm not installed).

Option 3, launchctl. `launchctl setenv key value` sets variables for all future processes in the caller's domain, not persisted across reboot; `launchctl config user path <value>` persists PATH only, takes effect after reboot, and a service's own PATH takes precedence (`man launchctl`, `config` section: "intentionally scoped to the PATH environment variable and nothing else"). Both are machine-wide, need the user to run them, and nvm's versioned path would go stale. Reject as the mechanism for a source-built app.

Option 4, shebang under minimal PATH: see the short answer; it fails, so spawn `node main.js` with an absolute node, or set PATH for the child to `<dir of node>:` plus the dirs of the agent CLIs.

Agent CLIs carrier spawns: `resolveBinary` (src/harnesses/common.ts) skips any PATH dir containing `/.superset/`; on this machine the real claude/codex/agy are in ~/.local/bin (found by `zsh -l`), gh is /opt/homebrew/bin/gh (Mach-O), git is /usr/bin/git (works under the minimal PATH via the Xcode/CLT shim), agy is a Mach-O, agent-forge is a `#!/bin/sh` script in ~/Library/pnpm (only in the `-i` PATH) and possibly needs node itself. Under the launchd PATH only git would be found. Therefore the app should pass one PATH to `carrier`: the detected PATH from the user's `-ilc` (stored in the setting, editable), prefixed with node's bin dir. A single "PATH to run carrier with" setting plus a "node" detected default is the minimal robust shape.

### Short answer B (notifications and menu bar)

`UNUserNotificationCenter.current()` from a bare SwiftPM executable crashes the process with an uncaught `NSInternalInconsistencyException` ("bundleProxyForCurrentProcess is nil"). A minimal hand-made `.app` (Contents/MacOS/exe + Info.plist with CFBundleIdentifier) loads, but without a re-signature the authorization is denied at once (UNErrorDomain Code 1 = notificationsNotAllowed); after `codesign --force --sign - App.app` (ad-hoc, which binds Info.plist) the request no longer fails and just waits, which is what a pending permission prompt looks like. `MenuBarExtra` is macOS 13+, needs `.accessory` policy (via `setActivationPolicy(.accessory)` in code or `LSUIElement` in Info.plist) which a bare executable has to set itself because its default policy is `.prohibited`. Smallest build step: `swift build -c release`, then a ~15 line shell script that creates `Carrier.app/Contents/{MacOS,Info.plist}`, copies the binary, and runs `codesign --force --sign -`. Only the Command Line Tools are needed, not full Xcode.

### Evidence B

(1) Docs: UNUserNotificationCenter is macOS 10.14+, and the first `requestAuthorization` prompts the user and records the answer, later requests do not prompt ([UNUserNotificationCenter](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter), [Asking permission to use notifications](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications)). Apple does not state the bundle requirement in those pages; the crash message below is the evidence.

Experiment (tmp/nb, Swift 6.4, SwiftPM executable calling `UNUserNotificationCenter.current()` then `requestAuthorization`): bare run `.build/debug/nb` -> `*** Terminating app due to uncaught exception 'NSInternalInconsistencyException', reason: 'bundleProxyForCurrentProcess is nil: mainBundle.bundleURL file:///.../.build/debug/'` from `+[UNUserNotificationCenter currentNotificationCenter]`, then abort; `Bundle.main.bundleIdentifier` was nil. It is an Objective-C exception, so Swift `do/catch` cannot guard it; the app must check `Bundle.main.bundleIdentifier != nil` (or `Bundle.main.bundleURL.pathExtension == "app"`) before touching the center.

Same binary wrapped in tmp/A.app (Info.plist: CFBundleIdentifier, CFBundleExecutable, CFBundlePackageType APPL, LSUIElement true), launched with `env -i /usr/bin/open -n -W`: bundleIdentifier is set, `current()` returns, and `requestAuthorization` calls back at once with `granted=false error=UNErrorDomain Code=1`, `authorizationStatus=0` (notDetermined), `add` also fails Code 1 (`UNErrorCodeNotificationsNotAllowed = 1` in UNError.h of the SDK). `codesign -dv` of that bundle: `Signature=adhoc ... Info.plist=not bound`, the signature is the linker's, `Identifier=nb-<hash>`, and `codesign --verify` says "code has no resources but signature indicates they must be present". After `codesign --force --sign - A.app`: `Identifier=dev.ashulab.carrier.exp`, `Info.plist entries=8`, and the completion handler never fired in the 8-second window (repeated with a fresh bundle id: unsigned wrapper -> Code 1; same wrapper after ad-hoc signing -> pending). So ad-hoc signing was required in my test; a real Developer ID was not needed. arm64 binaries are always at least linker-signed ad hoc.

Not seen: the prompt itself. This session has no display (`screencapture` -> "could not create image from display"), `log show` returned nothing for usernoted, and osascript has no assistive access (-1719). So I cannot confirm that the prompt appears, that "Allow" results in a banner, or what the banner looks like; a person must run `A.app` once on a logged-in desktop. Also the bundle id is the identity of the permission: changing CFBundleIdentifier or moving the app re-asks.

(2) [MenuBarExtra](https://developer.apple.com/documentation/swiftui/menubarextra): macOS 13.0+. Docs: "An app that only shows in the menu bar will be automatically terminated if the user removes the extra from the menu bar", and for no Dock icon set `LSUIElement` to true. [NSApplication.ActivationPolicy.accessory](https://developer.apple.com/documentation/appkit/nsapplication/activationpolicy-swift.enum/accessory): no Dock icon, no menu bar, can be activated by windows; "corresponds to LSUIElement = 1". Experiment (tmp/mb, SwiftUI `App` with `MenuBarExtra`, main.swift calling `CarrierApp.main()`): bare binary reports `activationPolicy().rawValue = 2` (prohibited) and `lsappinfo` shows `type="BackgroundOnly"`; after `NSApplication.shared.setActivationPolicy(.accessory)` in `applicationDidFinishLaunching` it reports 1, and the app builds and runs bundle-less. Inside M.app with LSUIElement it also reports 1 with bundleId set. I could not verify that the status item is drawn (no display, no accessibility). ## 4 and 5. Stop through a control socket; a Unix socket for the macOS app

Environment: macOS 27.0 (Darwin 27.0.0), Apple Swift 6.4 (`swift --version`: swift-driver 1.168.6, target arm64-apple-macosx27.0.0). Default `node` is v25.6.0 (nvm); nvm also has v22.22.0, v24.14.1, v24.16.0, v26.12.0. Carrier needs Node >=22 (package.json engines). Experiments used 25.6.0 unless stated; the length test and the umask test were also run on 22.22.0, 24.14.1 and 26.12.0. The repo was not modified (git status unchanged). Scratch files are in scratch/{sig,kill,sock}.

### 4. Stop

#### Short answer

Today all four routes (Ctrl+C, `q`, `kill -INT`, a raw-mode Ctrl+C key) end in one SIGINT handler, `stopOnSigint` (src/terminal/cli/interrupt.ts:6-18), which runs `engine.shutdown()` (src/orchestration/engine.ts:564-571), then `close()` (src/terminal/cli/compose.ts:107-112), then `process.exit`. A socket `stop` would be equivalent to Ctrl+C only if it runs exactly that sequence, and the sequence is not reachable from outside the signal handler today: it lives in an anonymous closure registered with `process.once('SIGINT')`, and nothing exports it. The only existing outside route is `process.kill(process.pid, 'SIGINT')`, which is what the `q` key already does (compose.ts:63). SIGTERM and SIGHUP are not handled at all: they kill Carrier instantly with no cleanup (observed), which matters because `kill <pid>` and a closed terminal send them. Stopping agents is not fully clean: each agent gets SIGTERM then SIGKILL on its own process group only, and descendants that moved to another group (Codex's command process, per ADR 0004) are orphaned; there is also no timeout on waiting for the agent, so a stop can hang (observed with a synthetic agent, see below).

#### Evidence: the paths into the handler

Ctrl+C on a terminal: the panel puts stdin in raw mode, so Ctrl+C is no longer SIGINT but a keypress (src/terminal/dashboard/keys.ts:6-14). `onKey` maps Ctrl+C and `q` to `{type:'quit'}` (src/terminal/dashboard/ui-state.ts:43), `perform` calls `controls.quit()` (src/terminal/dashboard/interactive.ts:46), and `quit` is `process.kill(process.pid,'SIGINT')` (compose.ts:63, comment at :47). Without a TTY (no raw mode) a real SIGINT arrives directly. Either way the one listener is `process.once('SIGINT', ...)` (interrupt.ts:7), registered by `deps.onSigint({engine, close})` at compose.ts:114, before `engine.start()` so recovery-launched agents are covered. There is no other `process.on/once` for signals in src (grep: only interrupt.ts:7, plus 'exit' hooks for restoring the cursor and raw mode, panel.ts:34, keys.ts:18).

#### Evidence: what the shutdown does

`engine.shutdown()` (engine.ts:564-571): sets `stopping = true`, cancels the poll timer and retention, calls `run.stop()` on every active run in parallel, then waits for `inflight` follow-up work to drain. `stopping` guards every GitHub write and launch (engine.ts:81, 102, 126, 133, 180, 492, 536, 577), so nothing is written to GitHub. Each `run.stop()` makes the run finish with exit `'stopped'`; the `.then` handler writes the execution row as `interrupted` with `finishedAt` and the session id (map at engine.ts:58, update at engine.ts:201-205) and takes none of the settle, retry, needs_human branches. Epics stay `running`; labels are untouched. Then `close()` stops the panel, `engine.stop()`, closes the DB and calls `lock.release()` (compose.ts:107-112; lock release is `db.close()` of the lock connection, lock.ts:20), and `process.exit(0)` (1 if shutdown threw, interrupt.ts:11-17). This is covered by src/terminal/cli/interrupt.test.ts:19-49 (executions `interrupted`, epics `running`, lock reacquirable, no writes after SIGINT) and :51-72 (restart resumes with the saved sessions).

#### Evidence: how agent processes are killed

Each agent is spawned `detached: true` (host-runner.ts:110), so it leads its own process group and the terminal's Ctrl+C never reaches it; only Carrier's handler does. `run.stop()` sets reason `stopped`, calls `terminate(pid, graceMs)` (host-runner.ts:172-176, 60-65): `process.kill(-pid, 'SIGTERM')` to the group (fallback to the pid, host-runner.ts:38-48), polls `alive` every 50 ms, and after `graceMs` (default 5000, host-runner.ts:82) sends SIGKILL to the group. Then it awaits `done`, which resolves on the child's `'close'` event (host-runner.ts:153, 164).

What it leaves behind: ADR 0004 (docs/adr/0004-...md:25) says stopping does not guarantee child processes end and that Codex leaves the command's process orphaned even with SIGTERM; docs/research/headless-agents.md:137-140 and :158-159 record it (Claude with SIGTERM: no orphans; Claude with SIGKILL: orphaned `/bin/zsh -c` and `python sleep`, ppid 1; Codex with SIGTERM and SIGKILL: orphaned `Python -c ...sleep`, ppid 1) and say those children sit in their own process group, so killing the CLI's group is not enough (:159; recommendation :181-187). Both Carrier-side facts below were reproduced with a fake Claude adapter running `sh -c 'sleep 300 & perl -e "setsid(); exec sleep 301" & wait'` through the real `HostAgentRunner`.

```
node runner.mts stop a2   ->  "exit stopped"; `sleep 300` (same group) gone; `sleep 301` (new session) alive, ppid 1
```

Hang: when the orphan keeps the agent's stdout/stderr pipe open (the default when it inherits them), `run.stop()` never resolves, because `'close'` waits for the pipes to end (host-runner.ts:153). In that run `node runner.mts stop a` sat until I killed it, with `sleep 301` still alive. That means `engine.shutdown()` (and so Ctrl+C or a socket stop) can wait forever; there is no timeout around `await done`. Not verified with real Codex: whether its orphans inherit the pipes is unknown.

Next-start cleanup of such orphans: `runner.listActive()` finds live processes by the marker `carrier-exec-<id>` in `ps` (host-runner.ts:24-35, 182-184; marker built in common.ts:37), and `recover()` stops them (engine.ts:442-445, host-runner.ts:186-193). Observed: after `kill -9` of the Carrier-side runner, the agent's whole group stayed alive (ppid 1) because of `detached`; a fresh process with `listActive()` then `stop(id)` ended `sh` and `sleep 300` but, again, not the setsid'd `sleep 301`, whose argv has no marker so Carrier cannot even see it.

Second Ctrl+C: the handler is `process.once`, so a second SIGINT during shutdown falls back to Node's default and the process dies at once (inferred from Node semantics and interrupt.ts:7; not run).

#### Evidence: SIGTERM, SIGKILL and crash

Experiment (src/terminal/cli/interrupt-holder.fixture.ts, the repo's own fixture with fake GitHub/runner, run from the scratch dir, two running epics):

```
SIGTERM: exit=143  epics ["running","running","queued"]  executions [running, running] finishedAt null   lock: acquirable
SIGINT : exit=0    epics ["running","running","queued"]  executions [interrupted(finished=1) x2]       lock: acquirable
SIGKILL: exit=137  epics ["running","running","queued"]  executions [running, running] finishedAt null   lock: acquirable
```

So SIGTERM (and by the same default, SIGHUP, not run) is a crash for Carrier: executions stay `running` with no `finishedAt`, and the agents survive (detached). Restart handles it the same as SIGKILL. Lock: it is an exclusive SQLite transaction on `orchestrator/carrier.lock`, held for the life of the process; the OS drops it on death, so there is no stale lock and no PID file (lock.ts:7-8, test lock.test.ts:43-53 "after kill -9 of the holder a new start gets the lock", and :55-60 one winner among 20). Recovery on the next start, in order (engine.ts:440-487): stop orphan executions found by marker; mark every `running` execution that has no live handle `interrupted` (:446-449); for each `running` epic, if there is no execution launch `ship`, if the last is `interrupted` import its result file when it already parses (:473) else `execute(epic, stage, last)` with the saved session and "verify state first", if the last is `finished` and imported but the next stage never launched, launch it; finally reconcile labels with GitHub. Test: interrupt.test.ts:51-72.

#### Would socket `stop` equal Ctrl+C?

Yes in effect, if it calls the same two steps. Reachability: `startCarrier` returns `{engine, db, close}` (compose.ts:147), so `engine.shutdown()` and `close()` are callable from the code that will own the socket, but the sequence plus `process.exit` exists only inside the closure at interrupt.ts:7-17. Two options: (a) the socket handler calls `deps.quit()` (compose.ts:63), identical to `q`, zero refactor, but it is a self-signal and a second `stop` is ignored once the `once` handler is spent; (b) extract the closure body into a named function used by both the SIGINT handler and the socket command (smaller blast radius, and the place to add SIGTERM/SIGHUP).

Points the socket path must handle that a signal does not: send the ack before `process.exit` (interrupt.ts:17 exits right after `close()`, so an unflushed reply would be lost); close the server and unlink the socket inside `close()` before `lock.release()` so a new instance's fresh socket is never unlinked by the old one; keep the hang risk above in mind (add a timeout around `await done` or the whole shutdown); and the app should treat EOF on the socket as "stopped". Note ADR 0005's "stopping is the same graceful shutdown as Ctrl+C" is accurate only if SIGTERM-from-app is not used instead.

#### Not verified (Q1)

Real Claude/Codex/agy behaviour under `stop` in this tree (only a synthetic agent and the research doc's older measurements); whether real Codex orphans hold the agent's pipes (hang risk); SIGHUP and double-SIGINT behaviour (inferred, not run); `node --test`/vitest suites were not run (the fixture was run directly).

### 5. Unix socket in Node >=22

#### Short answer

(a) macOS `sun_path` is 104 bytes; the default Carrier path on this machine is 45 characters and fits for usernames up to 64 characters, but a relocated root longer than 78 characters overflows: the engine must check the length itself, because Node 22.22.0 silently truncates and creates a mangled socket name, while Node 24/25/26 throw EINVAL. Fix with a short path or a symlink. (b) Default socket mode is 0755 (umask), not 0600; wrap `listen()` in `process.umask(0o177)` (bind is synchronous, so the window is one call) and make the parent 0700; macOS enforces the mode on connect. (c) After a crash the file stays and `listen` gives EADDRINUSE; unlink then listen is right, but only after `acquireLock` succeeds. (d) Swift connects either with Network.framework `NWEndpoint.unix(path:)` (macOS 10.14+) or POSIX `connect` plus `FileHandle`; both round-tripped NDJSON here. (e) Newline-delimited JSON is the recommendation.

#### (a) Path length

Primary sources: `man 4 unix` on this machine ("filesystem pathnames of at most 104 characters", `char sun_path[104]`; also in the SDK's sys/un.h:79); Node docs v22 net, "Identifying paths for IPC connections": "It gets truncated to an OS-dependent length of sizeof(sockaddr_un.sun_path) - 1. Typical values are 107 bytes on Linux and 103 bytes on macOS."

Real paths: `/Users/vemec/.solve/orchestrator/control.sock` = 45 chars. The fixed part of the default layout is `/Users/` (7) plus `/.solve/orchestrator/control.sock` (33) = 40, so at the default root a username up to 64 characters fits (104 limit); a 79-char example with a 40-char username (`/Users/averyveryveryverylongusername1234567890/.solve/...`) still fits. The limit bites only when the shared root is relocated: `<root>/orchestrator/control.sock` adds 26 characters, so a root longer than 78 characters fails (the scratch paths used here, 100+ chars, are an example).

Experiment `len.mjs` (listen then connect on a path of exact length N, then read the file system):

```
Node 22.22.0 (uv 1.51.0): 100/103/104 ok; 105 -> "listen ok", connect ok, but no file at the requested path (a socket with a truncated name was created: observed as an extra entry, 47 chars vs requested 120); 120 same
Node 24.14.1, 25.6.0, 26.12.0: 100/103/104 ok; 105 and 120 -> listen EINVAL "invalid argument <path>"
```

Observed: 104 characters still works on this macOS (the docs say 103); truncation happens on 22.22.0 only. A Node 25 client given the full 111-char path got EINVAL, a Swift/POSIX client would not connect to the truncated name. Not tested on 22.x other than 22.22.0.

Mitigations, observed: a symlink from a short path to the real directory works (real path 173 chars, via symlink 71, server and client both fine, mode `srwxr-xr-x` shown on the real dir); relative path after chdir works but the client must chdir to the same directory too, and chdir is process-wide in the engine (workspaces and agents may rely on cwd), so I would not use it; a fixed short location such as `$HOME/.carrier/control.sock` (34 chars) or `/tmp/carrier-501/control.sock` (29) also works, TMPDIR here is `/var/folders/k_/.../T/` and `${TMPDIR}carrier-xxxxxxxx.sock` is 70 chars. Recommendation: compute `Buffer.byteLength(path) <= 103` in the engine before `listen` and fail with a clear message (never rely on Node), and publish the actual path in a small file in `orchestrator/` (or the app derives it the same way).

#### (b) Permissions

Node docs (v22 net, `server.listen(options)`): `readableAll`/`writableAll` "For IPC servers makes the pipe readable/writable for all users. Default: false." Observed meaning of `false`: nothing is changed, the file gets umask-based mode. `perm.mjs`:

```
process umask 022
default                              : 0755 socket
umask 0177 around listen()           : 0600 socket
readableAll+writableAll              : 0666 socket
chmod 600 right after listen         : 0600 socket   (window of 0755 in between)
bind is synchronous: with umask 0177 set, file exists with mode 600 right after listen() returns, on 22.22.0 and 25.6.0 (sync.mjs)
```

So set `process.umask(0o177)` immediately before `server.listen(path)` and restore it on the next line (no event-loop gap, so SQLite and agent files are not affected). Also make `orchestrator/` 0700: it is currently 0755 (`ls -ld ~/.solve/orchestrator` shows `drwxr-xr-x`; `mkdirSync(..., {recursive:true})` in lock.ts:10 passes no mode), and a 0700 parent removes any race and also keeps logs and results private.

macOS does enforce the mode on connect. `man 4 unix`: "the destination of a connect(2) or sendto(2) must be writable". Observed with the socket owned by me: mode 0755 connects; 0400 -> `EACCES`; 0200 connects; 0000 -> `EACCES`. The same man page documents `LOCAL_PEERCRED`, which a server can use to verify the peer's uid as a second check (not tested). Different-user connect was not tested (no second account).

#### (c) Stale socket after a crash

Node docs (net, IPC paths): "a Unix domain socket will be visible in the file system and will persist until unlinked", including after a crash; `server.close()` unlinks it. `man 4 unix` says the same ("not removed when the socket is closed"). Experiment `srv.mjs`/`cli.mjs`:

```
kill -9 of the server           -> file remains (srw-------)
client to the stale file        -> ECONNREFUSED
listen on the stale path        -> EADDRINUSE (exit 2)
rm then listen                  -> listening, client gets a reply
second server rm+listen while the first is LIVE -> second wins; the first is still running but unreachable (path taken over)
SIGTERM of a server             -> file also left behind (Node does not unlink on signals)
```

So the pattern is `rmSync(path, {force:true})` then `listen`, and it is only safe after `acquireLock(orchestratorDir)` returned ok (compose.ts:75): the lock is held by exactly one live process per `orchestrator/` (lock.test.ts:55-60), so if you hold it, any socket file there is stale by construction; without it the last row above is the failure. Also unlink in `close()` before `lock.release()`.

#### (d) Swift client

Both clients are in scratch/sock/swift (nw.swift 27 lines, posix.swift 19 lines, server.mjs). Built with `swiftc -O -target arm64-apple-macos13.0` and run against the Node server (which writes umask 0177, sends a `log` event on connect, answers `{"cmd":"snapshot"}` and `{"cmd":"stop"}`):

```
./nw   <sock>  -> NW state preparing / ready; <- {"event":"log",...,"chunk":"héllo\n"}; <- {"ok":true,"snapshot":{...}}; <- {"ok":true,"stopping":true}; closed eof
./posix <sock> -> the same three lines, then "POSIX eof"
```

Network.framework: `NWConnection(to: .unix(path: path), using: .tcp)`, `conn.start(queue:)`, `conn.receive(minimumIncompleteLength:maximumLength:)` in a loop, `conn.send(content:completion:)`; `NWEndpoint.unix(path:)` and `NWConnection` are macOS 10.14+ (Apple documentation JSON, developer.apple.com/documentation/network/nwendpoint/unix(path:); also in the SDK Network.swiftinterface:392). POSIX: `socket(AF_UNIX, SOCK_STREAM, 0)`, fill `sockaddr_un`, `connect`, then `FileHandle(fileDescriptor:closeOnDealloc:)` for `write` and `availableData` (blocking, so off the main thread). SwiftNIO: `ClientBootstrap.connect(unixDomainSocketPath:)` exists (apple/swift-nio Bootstrap.swift:1086); main currently declares swift-tools-version 6.1; not tried, and it adds a dependency the first two do not need.

Three observed traps for the client: (1) with Network.framework a missing socket (ENOENT) and a stale one (ECONNREFUSED) do not give `.failed`; the connection sits in `.waiting(POSIXErrorCode 2 / 61)` and retries, so the app must read the error in `.waiting` as "Carrier stopped" and cancel. (2) `NWEndpoint.unix(path:)` with a path over 104 characters crashed the process (exit 133, SIGTRAP; crash report stack mentions `__nwlog_fault_add_description_to_list`), so the app must check the length first. (3) the POSIX route must check `path.utf8.count < MemoryLayout.size(ofValue: addr.sun_path)` itself (my guard printed "path too long: 127 >= 104" and exited 2). Strict-concurrency (Swift 6 language mode) and sandboxed-app entitlements (a sandboxed app cannot reach `~/.solve`) were not checked; the plan is an unsigned app built from source, so probably moot.

#### (e) Framing

Recommendation (my judgment, not a standard): newline-delimited JSON, one JSON value per line, both directions. Why: RFC 8259 section 7 requires control characters U+0000-U+001F inside strings to be escaped, so a compact serialisation (`JSON.stringify` without indent) never contains a raw LF and a line is always one complete value; observed: the `héllo\n` chunk went over the wire as `\n` escape and arrived as one line in both Swift clients. It needs no length prefix, lets Node use `readline` and Swift split on 0x0A, is greppable, and the same stream carries request/response and pushed events (`{"event":"log",...}` vs `{"ok":...}`), distinguished by a field. Costs: no binary payloads (agent output is text, fine) and a very large snapshot is one long line (no max-line limit is set by Node's `readline`; put a cap in the server). Specs for the format (ndjson-spec, jsonlines.org) were not fetched.

#### Not verified (Q2)

Any user other than mine connecting to a 0600 socket (only mode bits observed, owner connecting); macOS versions other than this 27.0 host (Node docs say 103 for macOS, I measured 104); Node 22.x other than 22.22.0 for the truncation; sandboxed or hardened-runtime app behaviour; SwiftNIO and Swift 6 strict concurrency builds; NWConnection with `.tcp` parameters being the officially intended parameters for a stream over a unix endpoint (it worked here; Apple's doc page for `NWEndpoint.unix` only describes it as "an endpoint represented as a UNIX domain path"); concurrent clients, backpressure on a slow client reading a high-volume agent output stream.

## 6. Menu bar icon animation: what it costs

A throwaway SwiftUI/AppKit app (a bar icon with fake data, ad-hoc signed `.app`, kept in [spike-macos-app](spike-macos-app/)) animated the bar while epics were "running". CPU was measured as the difference in process CPU time (`ps -o time`) over 20 to 25 s, for the app and for `WindowServer`, on this Mac (macOS 27.0, Swift 6.4, arm64). `ps -o %cpu` was not used: on macOS it averages with decay and includes startup, and it disagreed with `top` and with the CPU-time deltas. `WindowServer` is measured too because the work can move there: a static bar read 8% to 10% of a core in it, with noise of a few points.

**Swapping the image each frame (what `MenuBarExtra` and a naive `NSStatusItem` do).** Through SwiftUI `MenuBarExtra`: 22.1% at 12.5 fps, 12.3% at 6 fps, 6.1% at 3 fps, about 18 ms of CPU per frame. Pre-rendering the frames into bitmaps barely changed it (20.3% at 12.5 fps), so the drawing is not the cost. Through a plain AppKit `NSStatusItem` with pre-rendered frames: 12.0% at 12.5 fps, 5.5% at 6 fps, 3.3% at 3 fps, 2.2% at 2 fps and 1.4% at 1 fps. A `sample` of the main thread puts the time in `-[NSStatusItem _updateReplicantsUnlessMenuIsTracking:]` and `_redrawReplicantSnapshot:sourceView:`, which AppKit runs each time the status item's image changes. The same invalidation is why the open menu loses its focus on every frame: the person could not change the options while the icon animated.

**Core Animation layers on the status item's button.** The bar is a few `CALayer`s (a `CATextLayer` for the count, a track, a fill and a moving segment) added as a subview of `NSStatusItem.button`, with the motion a `CABasicAnimation`. The app does nothing per frame, so its CPU is 0.3% to 0.4% and the menu is not invalidated. But uncapped, the render server recomposes the translucent menu bar at the display rate and `WindowServer` rose from 8% to 52% and 56% (two rounds), so the cost moved instead of going away. Setting `preferredFrameRateRange` on the animation fixes it: bounce at a 4 fps cap read 8% in `WindowServer` (same as static), discrete keyframes at 3 steps per second 12%, at 1 step per second 4% and 8%, and bounce capped at 8, 12, 20 and 30 fps read 8%, 12%, 8% and 16%. The three motions (bouncing segment, shine sweep, opacity pulse) capped at 20 fps each read 0.4% in the app and 12% in `WindowServer` against 8% static, a difference of about 4 points. So the cost depends on the frame rate the animation asks for, and the cliff is between 30 fps and the display's rate.

Colours are not automatic with layers: the count and the bar use `NSColor.labelColor` resolved against the button's `effectiveAppearance` and are set again when it changes, because a layer does not get the template tinting an `NSImage` gets. That path was built but light and dark were not looked at here.

Not verified: other Macs and other macOS versions (one host; this display's refresh rate was not recorded), several displays attached (AppKit keeps a copy of each status item per display, which is what the profile names), battery impact and low power mode, that the animation keeps the capped rate when the menu bar is on a ProMotion display at 120 Hz, and that the menu stays usable while the icon animates (it is built from a plain `NSMenu` and nothing changes per frame, but it was not clicked through headless).

## 7. How RunCatNeo animates its menu bar icon

Read from the source of [runcat-dev/RunCatNeo](https://github.com/runcat-dev/RunCatNeo) (Apache-2.0, last commit 2026-10-19), only for design ideas: nothing was built, run or copied. The text is the agent's report with the headings lowered.

All paths below are relative to the clone at a shallow clone of https://github.com/runcat-dev/RunCatNeo (not kept). Nothing was built or run. Most source sits under LocalPackage/Sources, abbreviated LPS/.

### Short answer

RunCatNeo uses a SwiftUI MenuBarExtra with .window style (not NSMenu, not NSPopover), and its label is a tiny static SwiftUI Label that only reserves space in the status item (LPS/UserInterface/Scenes/RunnerBarScene.swift:30-35, Views/RunnerBar/RunnerBarView.swift:50-56). The cat itself is a CAKeyframeAnimation on "contents" running on a CALayer that the app adds as a sublayer of the NSStatusBarButton, with discrete calculation mode, infinite repeat, and speed changed via layer speed/timeOffset according to CPU load (Views/RunnerBar/RunnerLayer.swift:27-39, 81-94; Model/Services/RunnerService.swift:89-97). There is no Timer, no CADisplayLink and no per-frame image swap.

Idea 1, the one that matches your finding: do not swap the button image, animate a sublayer with CAKeyframeAnimation (discrete contents) and change speed with beginTime/timeOffset/speed so the phase does not jump. Their own comment measures 7-8% CPU for icon swapping against about 0.1% for the layer animation (RunnerBarView.swift:24-27). Idea 2: the menu is a SwiftUI window-style panel, so animating the icon never touches an NSMenu tracking loop; the dashboard only subscribes to metrics while visible (Model/Stores/Dashboard.swift:75-91). Idea 3: monochrome tinting is done with a backgroundColor on the layer plus a mask layer holding the template frames, with the colour taken from NSColor.textColor resolved in the status button's effective appearance (RunnerLayer.swift:55-63, 74-78; Model/Stores/RunnerBar.swift:94-99).

Caveats worth knowing: they do not cap the frame rate with preferredFrameRateRange (grep for preferredFrameRate, Timer, CADisplayLink finds nothing in Sources), and the layer only renders on the active monitor, so they need a static fallback and a CIFilter hack (RunnerBarView.swift:29-32). They also find the status bar button by walking NSApp.windows, which is fragile.

### Evidence

1. What is in the menu bar and how it is animated.

The scene is MenuBarExtra { DashboardView } label: { RunnerBarView } with .menuBarExtraStyle(.window) (Scenes/RunnerBarScene.swift:30-35). The label view is a Label whose title is "\0" and whose icon is a static NSImage drawn with a closure; once ready it switches to .iconOnly (Views/RunnerBar/RunnerBarView.swift:50-56, Extensions/View+Extension.swift:33-39). A .task then locates the NSStatusBarButton, sets wantsLayer, and adds a BackgroundLayer and a RunnerLayer as sublayers (RunnerBarView.swift:57-71). The button is found by scanning NSApp.windows for a contentView.subviews.first.subviews.first that is an NSStatusBarButton with title "\0" (Extensions/NSApplication+Extension.swift:24-35).

RunnerLayer holds a CAKeyframeAnimation(keyPath: "contents") with calculationMode .discrete, repeatCount infinity and isRemovedOnCompletion false (Views/RunnerBar/RunnerLayer.swift:27, 36-38). Duration is frames.count / 2.0 seconds at speed 1, so a 5-frame runner is 2 fps at speed 1 (RunnerLayer.swift:48). CPU load maps to speed: cpuValue = clamp(cpu% / 5, 1, 20), and the optional "speed decreases under load" mode uses 0.5 * (21 - cpuValue) (Model/Services/RunnerService.swift:89-97). So effective rate is 2 fps up to about 40 fps for 5 frames (my arithmetic from those two lines). setSpeed re-bases the animation clock with timeOffset = convertTime(now) and beginTime = now before changing speed, which avoids a phase jump (RunnerLayer.swift:81-94). CPU samples arrive from SystemInfoKit's SystemInfoObserver via an AsyncStream every 3, 5 or 10 seconds (default 5) (DataSource/Dependencies/SystemInfoObserverClient.swift:30-36, Entities/Metrics/UpdateInterval.swift:21-30, Model/AppDelegate.swift:57-63). No .common run loop mode or menu-open pausing exists in this repo because there is no timer; the sampling timer lives inside the external SystemInfoKit package (not read, see Not verified). The CA animation runs in the render server, so an open window does not stall it; I saw no code that pauses it.

Their rationale is written in the code: swapping the MenuBarExtra icon makes the menu bar snapshot the item in light and dark for other monitors (7-8% CPU measured) against about 0.1% for the layer approach; the layer only draws on the active monitor, so a static icon is drawn as fallback and erased on the active monitor via a sourceOutCompositing backgroundFilter, which they skip on Intel (RunnerBarView.swift:24-32, 36-48, 67-69; Views/RunnerBar/BackgroundLayer.swift:33-36).

2. Frames, light/dark, tint.

Built-in frames are one PNG per frame in an asset catalog, e.g. Media.xcassets/Runners/Cat/cat-frame-0.imageset/Contents.json:2-6 (idiom mac, no vector, no template-rendering-intent key), 5 or 10 frames per runner (DataSource/Entities/Runner/RunnerKind.swift:33-44). Frames are loaded as NSImage via NSImage(resource:) (RunnerBarView.swift:76), re-ordered by FrameOrder (RunnerKind.swift:46-58), and normalised so height is 18 pt (Model/Extensions/NSImage+Extension.swift:38-41). Custom runners are PNGs under Application Support, loaded as Data (Model/Services/RunnerService.swift:40, 121-132). Each runner has isTemplate (monochrome vs colour) (DataSource/Entities/Runner/RenderingMode.swift:29-40, Model/Stores/RunnerBar.swift:121-127).

Monochrome mode does not rely on AppKit template tinting. The frames are set as the contents of a mask layer, and the layer's backgroundColor is the tint colour, so the mask shape is filled with that colour (RunnerLayer.swift:55-63, 74-78). The colour is NSColor.textColor.cgColor resolved with performAsCurrentDrawingAppearance of the status button's window appearance (Model/Stores/RunnerBar.swift:94-99). Appearance changes reach it by overriding viewDidChangeEffectiveAppearance on NSStatusBarButton in an extension and pushing the value into an AsyncStream bridge (Extensions/NSStatusBarButton+Extension.swift:25-29, Model/StatusBarAppearanceBridge.swift:25-38). Colour runners just add the animation on the layer directly (RunnerLayer.swift:64-70).

3. Menu, windows and focus.

The dropdown is a SwiftUI window-style panel (DashboardView), not an NSMenu or NSPopover (RunnerBarScene.swift:35; grep for NSMenu and NSPopover finds nothing). Menu actions are SwiftUI Buttons, a Picker and SettingsLink inside that view (Views/RunnerBar/Dashboard/MenuView.swift:55-115). The Settings window is a SwiftUI Settings scene (Scenes/SettingsWindowScene.swift:26-32) and the licence window is a WindowGroup with .defaultLaunchBehavior(.suppressed) (Scenes/OpenSourceLicenseWindowScene.swift:28-35). A second MenuBarExtra (metrics bar) is toggled with isInserted (Scenes/MetricsBarScene.swift:33-39). Because the icon is a sublayer animation and the content is a separate panel, there is no explicit focus protection in the code; the design itself avoids the problem.

Window opening from a menu-bar-only app: each button first calls NSApp.activate(ignoringOtherApps: true) and then opens the window; for Settings, a custom PrimitiveButtonStyle runs an async pre-action (activation) before configuration.trigger() (Views/RunnerBar/PreActionButtonStyle.swift:30-39, MenuView.swift:67-76, Model/Stores/DashboardMenu.swift:99-114, DataSource/Dependencies/NSAppClient.swift:29). openWindow is wrapped in a Sendable struct to pass from the view into the store (Model/OpenWindowActionWrapper.swift:21-31).

The dashboard store subscribes to the metrics stream on appear and cancels on disappear, so no work happens while the panel is closed (Model/Stores/Dashboard.swift:75-91).

6. Low CPU and energy measures.

The layer-based animation instead of image swapping is the main one, with the measured 7-8% vs 0.1% claim in a code comment (RunnerBarView.swift:24-27). Metrics sampling stops on NSWorkspace.willSleepNotification and restarts on didWakeNotification (AppDelegate.swift:44-55). Sampling interval is user-selectable 3, 5 or 10 s, and each metric group (memory, storage, battery, network) can be switched off; only CPU is always on (UpdateInterval.swift:21-30, Model/Services/SystemMetricsService.swift:43-53). The dashboard stream is cancelled when the panel closes (Dashboard.swift:89-91). I found no App Nap or ProcessInfo activity handling, no preferredFrameRateRange, and no pause of the animation when the screen sleeps or the menu is open (grep for NSBackgroundActivity, beginActivity, preferredFrameRate, screensDidSleep over Sources and RunCatNeo returned nothing).

### What to take for Carrier

Drive the icon with a sublayer CAKeyframeAnimation (discrete contents) on the status button layer and add animation.preferredFrameRateRange (your 20 fps finding) on top, which RunCatNeo does not do. Keep a static template image on the button as fallback for non-active monitors. Use the mask-layer plus backgroundColor technique for tint, fed by the button's effectiveAppearance. Change speed with the timeOffset/beginTime re-basing pattern. Use the PNG-per-frame approach with 18 pt normalised height if you want matching assets. Be aware that their SwiftUI MenuBarExtra route needs the NSStatusBarButton lookup hack; if you own the NSStatusItem you get the button directly and do not need it.

### Not verified

SystemInfoKit's timer scheduling (run loop mode, DispatchSource or Timer) is in an external package that I did not read. Whether the CAKeyframeAnimation really stays smooth during open window panels, and whether the sourceOutCompositing trick works on macOS 27, was not tested; I only read source. Whether any App Nap behaviour comes implicitly from the system for LSUIElement apps is not shown in the repo. The shallow clone limits history, so only the last-commit date is known. The 7-8% and 0.1% numbers are the author's code comment and were not reproduced.

### The prototype's crash, and what it taught

The spike crashed or exited whenever it was used. No system crash report exists for it, so it was an exit and not a fault. Running the menu's actions from code (choose a scenario and a motion, open the window, close it) found three defects of the first design: the "Open window" action did nothing, because SwiftUI's `openWindow` captured outside a view is a no-op; the SwiftUI `App` lifecycle with a `MenuBarExtra` that is not inserted can end the app by itself (Apple's documentation says an app that only shows in the menu bar is terminated when its extra is removed); and the layer view sat on top of the button and took the clicks the button needs to open its menu. With a plain AppKit lifecycle (an `NSApplication` with an `NSStatusItem`, an `NSMenu` and an `NSWindow` hosting the SwiftUI view, and a view that returns `nil` from `hitTest`), the same actions leave the process running: the window opens, closes and reopens. Real mouse clicks were not tried, since this session cannot post them.
