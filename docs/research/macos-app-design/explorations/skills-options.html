Skills: using yours, writing yours

A new Skills tab in Settings. Carrier runs three stages (Ship, Review, Fix) and each one calls a skill. By default those are the solve skills; the user can point a stage at their own or write one. Two questions: A–C how the tab is organized, D–F how a skill is picked, checked and written. Use the bar: skills flips between the defaults and a customized draft; runs on changes which harness the stage uses (the skill has to exist there, and Codex calls skills with $ instead of /). The harness choice is the profile's, shown here only to preview the mismatch; it is not edited in this tab.

1 · How is the Skills tab organized?

Same Settings window as Behavior and Repos: edits are a draft, then “Save and restart” or “Save only”.

A · Three slots, one list

The plainest: a row per stage with its skill. Review has a second row because it publishes its findings as a separate step (it can be the same skill).

B · The loop, then the stage

The three stages drawn as the cycle Carrier runs (review and fix repeat). Click a stage to see its skill and what that skill has to do. Teaches the flow while you configure it.

C · A skill set, with overrides

Pick a whole set at once (solve today, a team's set tomorrow), then override single stages. Fits people who install a bundle rather than choose per stage.

2 · Picking, checking and writing a skill

What happens after clicking a skill pill, and how someone writes one for a stage.

D · Pick from what is installed

A list of the skills the stage's harness can see, grouped by where they live. The ones the harness doesn't have are dimmed with the reason. The engine does the scan (a control request, like the repo list).

E · The contract, with a check

What a skill for this stage has to do, written once, and a short check of the chosen one. Carrier can tell it exists and that a run returns its result; it cannot tell what the skill does, and the panel says so.

F · Write your own

“Write a new skill…” from the picker. Starts from a copy of the solve skill or from a blank one that already carries the contract, saved where the harness reads it, then opens in the user's editor.

  • Why three slots and not four: code-post only makes sense after code-review, so it is the second step of Review, not a stage of its own. One skill can do both.
  • What the skill gets: only the epic or PR number. It reads the rest from GitHub. Carrier appends the result format to the prompt, so a skill never has to know it.
  • What Carrier fixes, not configurable: the states (ready-for-test, needs-human), the result JSON and “never merges”. The contract panel states these as rules, not options.
  • Where the list comes from: the engine (the app never reads the user's home folders), via a new control request advertised in hello.capabilities; an older engine shows the skills as text fields without a list.
  • What is saved: skills: { ship, review: [review, publish], fix } in config.json, defaults omitted. carrier doctor runs the same “found for this harness” check.
  • Not here yet: a different set per repo, and other trackers or label names. Both are separate decisions.
