# In-app sessions for Carrier: talking to the agent of your choice inside the app

> Research of 2026-10-27. Question from the owner: Carrier covers only the automatic half (take ready epics and implement them); the missing half is a place inside the app where the user starts a session with the agent they want (Claude, Codex, any other), talks to it, defines the work, and hands it to Carrier, with no external terminal. This document collects what is known, the decisions taken, the UI that was chosen, and the split into epics. Sources: Carrier at `main` (`e0f2d24`), and primary documentation from Anthropic, OpenAI and the Agent Client Protocol project. Related: [headless agents](headless-agents.md), [interactive resume](interactive-resume.md), [Codex exec stream](codex-exec-stream.md), [Agent Forge](agent-forge.md), [the macOS app](macos-app.md), [ADR 0002](../adr/0002-sqlite-authority-labels-mirror.md), [ADR 0004](../adr/0004-agents-run-on-host-with-terminal-preferences.md), [ADR 0005](../adr/0005-engine-independent-of-the-macos-app.md), [ADR 0006](../adr/0006-agent-events-stored-in-sqlite-with-bounded-output.md), [ADR 0007](../adr/0007-continue-in-terminal-through-a-validated-descriptor.md), [ADR 0011](../adr/0011-author-and-reviewer-may-share-one-github-identity-signed-visibly.md).

## Recommendation

Build a small interactive-session layer as its own process (a chat host), behind a new port (a `ChatRunner`, next to `AgentRunner`, with a fake for tests). Each provider is an adapter behind that port that emits Carrier's own normalized chat events: Claude through the Claude Agent SDK pointed at the user's own `claude` binary (or the CLI headless, or a terminal pane as the fallback), Codex through `codex app-server`, and any other agent through the Agent Client Protocol (ACP) later. The session runs as the user, with the user's own logins and skills. Carrier keeps its own SQLite copy of sessions (an index plus a bounded, redacted transcript) and stores each provider's native session id so a session can be resumed. The app gets a Sessions world, separate from the epics and never attached to them.

Keep the handoff to the automation where it is: a session ends, if it should, by publishing GitHub issues labelled `solve:epic:ready`, and the engine picks them up by polling as it does today ([ADR 0002](../adr/0002-sqlite-authority-labels-mirror.md): that label alone queues an epic). No engine change is needed for it. The skills flow (`sharpen`, `to-spec`, `to-tickets`) and who applies the label are parked: the focus is the session experience itself.

Four things must be closed by a spike before the UI is built on them: multi-turn input, the permission round trip and resume for Claude; the same for Codex's app-server; whether the user's installed skills are visible in a session; and a written confirmation from Anthropic about using a Claude subscription in an app that spawns the user's own binary, before any build with sessions is published.

## Decisions

- Identity. The session runs as the user. The child gets the user's own `CLAUDE_CONFIG_DIR` / `CODEX_HOME` and `gh` login, whichever harness is selected. There is no separate session identity or token. What the agent publishes appears under the user's name; the visible-signature rule of ADR 0011 is available if that should be marked.
- Claude goes through the official Claude Code tooling on the user's machine, never through an API key or a pay-per-token path. Anthropic describes the Agent SDK as "A library that runs the Claude Code binary" and says that for other languages one can "run the CLI as a subprocess with the `-p` flag" (`code.claude.com/docs/en/agent-sdk/overview`), so SDK and CLI drive the same binary. The options for Claude are the Agent SDK pointed at the user's own binary (lean), the CLI headless the way Carrier already runs epics (`claude -p --output-format stream-json`; multi-turn through `--input-format stream-json` and a permission prompt tool is **not yet verified**), or a terminal pane with the unmodified CLI.
- Claude terms, read on 2026-10-27 from `code.claude.com/docs/en/legal-and-compliance` and the SDK overview. What they regulate: the Claude Code binary "must not be modified", and a product may not "remove, disable, or restrict any authentication method built into it"; a product may not "pay for, resell, or intermediate Claude usage"; "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users", and developers "may not collect, store, or intermediate Claude.ai credentials or session tokens". The same page says this does not prevent "an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code". The SDK overview adds: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK." Two more lines: "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK", and, on running Claude Code in a product, "Unless we've mutually agreed otherwise, preinstalling or running Claude Code in your products or services ... requires agreeing to our Commercial Terms of Service and complying with the conditions below"; whether that sentence reaches a local app that only spawns a binary the user installed is not stated.
- My reading, not a legal verdict and not an Anthropic statement: a pattern where the user installs and logs into the unmodified `claude` themselves, the app never touches credentials, never offers a login and never resells usage, is the one the carve-out describes. The guardrails Carrier should keep, all checkable in code review: spawn the user's own `claude` and never a bundled or patched one; never read, copy, store or proxy the Claude token, keychain entry or `~/.claude` credentials; no sign-in screen of our own, the user runs `claude auth login`; no key or plan shared across users; interactive human-driven use only (an unattended loop on a subscription is what the "ordinary, individual usage" line is about, and Carrier's epic runner already does that, so the exposure there is not new); name the feature "Claude", not "Claude Code" (the SDK page forbids "Claude Code" branding for SDK products). A written confirmation is still worth having before publishing a build with sessions.
- Why the SDK is the lean over the headless CLI: a session needs streaming input, a permission callback, interrupt, model switch and resume, and the SDK's TypeScript API is reported to expose them (a permission callback, `interrupt`, `setModel`, resume and fork; confirm each in the SDK reference during the spike), while the CLI route means re-implementing its control messages by hand. Costs to check first: the SDK package is not open source (Commercial Terms), whether its npm package ships its own binary (then the option that points it at the user's binary must override it), and that an option to point at a given binary exists in the version used.
- The seam is Carrier's own port with normalized chat events, and each provider is an adapter behind it. ACP is one adapter among others, not the seam.
- Transcripts live in Carrier's SQLite. The provider keeps owning the conversation context and its native session id is stored so the session can be resumed, but Carrier keeps its own bounded, redacted copy (ADR 0006 pattern, with a retention of its own, since a session belongs to no epic). Reasons: one history across providers and machines without parsing three native formats; pending approvals, search, summaries and a client on another machine need it when the host runs somewhere other than the device showing it; and it survives a provider pruning its own session files. The cost is a second copy of the text and the redaction duty of AGENTS.md ("no secrets in logs"), including whether the user's own typed text is stored at all.
- The chat host is its own process, separate from the engine that polls epics. The engine's `stop` would otherwise kill the sessions it owns, and a session has no business holding epic locks. It shares code with the engine (`childEnv`, logger, config), not state, and exposes its own socket; the macOS app becomes a client of both. The cost is a second lifecycle (lock, start, stop) next to the one settled in ADR 0010.

## UI decisions (sidebar, sessions, Carrier)

The mockups that led here are in `docs/research/macos-app-design/explorations/` (`chat-options.html`, `chat-where-options2.html`, `chat-structure-options.html`, `chat-home-options.html`, `sidebar-chats-options.html`, `sidebar-rail-options.html`, `sidebar-sessions-options.html`). They are history. The spec to build from is `sidebar-w5-spec.html`: every element, its click behaviour, each state, and the sort orders. Where this section and the spec differ, the spec wins.

A conversation with an agent is called a **session** in the app: started by the user, in a **workspace**. The glossary already defines Session as the conversation an agent holds in its harness, with an id the harness can resume; a user session is the same kind of thing, but it belongs to no epic, and the glossary needs an entry for it. A workspace is a folder, a GitHub clone, or a repository already in Carrier's list, and sessions are grouped by it. Carrier is the automation: the epics the engine runs on its own. Sessions and epics are two separate worlds in the sidebar and are never attached to each other: a session is disposable once it has done its job (the user can keep talking or archive it), and archived sessions stay reachable.

The sidebar, top to bottom: **Home** (a plain selectable row; it opens a welcome page; it shows no status), **Sessions** (a row, as clear as Home, with a search button, a three-dots menu to sort by workspace, by age or by status, and a + for a new session; its list is grouped by workspace by default), **Archive** (an item of its own, outside Sessions, always visible), the **Carrier card** (a plain grey card with the engine state, the slots and counters for what needs the user, is running, is next and is ready; selected, it opens into the lists Needs you, Running, Up next, Ready for test, Done and Cancelled, with the same search and group by Status or Repository that exist today) and **Settings** at the bottom. About leaves the sidebar and lives in the app menu. Only one of Sessions or Carrier is open at a time, so neither is squeezed.

A new session opens as a draft in the centre (message box, workspace chip, agent, model, effort and permission); nothing is created until the first message is sent. The workspace chip opens a picker: recent workspaces, the repositories in Carrier's list, open a folder, clone from GitHub, new empty workspace. A session waiting for the user shows as an orange row, and as an orange count on the Sessions row when it is folded; there is no inbox that mixes sessions and epics. The Carrier card is the only place that carries global engine status.

The human intervention that replaces Continue in Terminal (ADR 0007) is decided as a goal and not yet as a design: when Carrier needs a person, the person takes over inside Carrier, on the stopped agent's session, and hands the epic back. The candidates in `chat-structure-options.html` are a decision card with a "talk it through" escape (I3) and a side panel with the resumed session (I1); both reuse the session machinery. The epic ran as the Forge bot; a takeover in the app runs as the user, which is a change to state in whatever builds it.

Still open: what the Home welcome shows; whether the Sessions and Archive pages are plain lists or cards; how the old Overview cards (Your turn, Slots, Agents working, the controls) are arranged on the Carrier page now that the card holds the status; where a GitHub clone is created on disk and whether a repository from Carrier's list is cloned on first use.

## Proposed split into epics

The work is too large for one epic and it mixes two tracks: the macOS app and the backend. Four epics, each shippable on its own, in this order.

1. **Sidebar (macOS only).** The new sidebar without the Sessions parts: Home with a placeholder welcome, the Carrier card with its status, counters, search and group by, the Done and Cancelled lists, Settings at the bottom, About moved to the app menu. The current Overview moves to the Carrier page (the card header). It ships by itself, with nothing behind it from the session side, and the Sessions and Archive rows are not shown until epic 3.
2. **Core chat (backend).** The chat host as its own process, the `ChatRunner` port with a fake, the provider adapters (Claude through the Agent SDK pointed at the user's own `claude`, Codex through its app-server, others through ACP later), sessions and a bounded, redacted transcript in SQLite, the `chat` requests on a control socket of its own, and a terminal-first `carrier chat`. It starts with the spike described in "The first slice" below, plus the written confirmation about Claude subscriptions before anything is published. No app UI.
3. **UI chat (macOS).** The Sessions and Archive rows and pages, the conversation view with streaming, tool rows and approval cards, the composer with the pickers, the new-session draft and the workspace picker, sort and search, archive and restore.
4. **UI Home (macOS).** The real welcome page, once its content is decided.

Epics 1 and 2 do not depend on each other and can run in parallel, one on the macOS side and one on the backend. Epic 3 needs both. Epic 4 is small and is a placeholder inside epic 1 until its content exists.

Not an epic yet, and not lost: **Take over**, the in-app resume of a stopped epic's session with Hand back, replacing Continue in Terminal. It needs the core of epic 2 and the conversation view of epic 3, so it comes after them.

## Options compared

| Option | What it is | Fit with Carrier | Cost | Main risk |
|---|---|---|---|---|
| 1. Native protocols behind a `ChatRunner` port | Claude Agent SDK (TypeScript, in the host) plus Codex app-server (JSON-RPC over stdio), one adapter each | Best fidelity: every provider feature is reachable. Node/TypeScript matches the engine | High and per provider; each adapter wants a replay-fixture harness | Each CLI or protocol change can break an adapter Carrier owns. The Agent SDK is not open source (Commercial Terms) |
| 2. ACP as a seam | Carrier is an ACP client; agents are ACP servers over stdio JSON-RPC | One client implementation. `session/update` (message chunks, tool calls, plans, available commands), `session/request_permission`, `session/cancel`, `session/set_config_option` (model, mode, reasoning level categories) and `session/resume`/`load` cover what a session needs | Medium, once: the client, the permission round trip, the transcript. Adding an agent is a config entry | Quality is capped by the adapter, which wraps the Claude Agent SDK or the Codex app-server and lags them. ACP v1 is stable, v2 is alpha. Same Claude-terms question as option 1 |
| 3. A terminal pane running the unmodified CLI | Embed a terminal emulator (for example SwiftTerm, MIT) and run `claude`, `codex` or `agy` interactively | Smallest build. Provider-agnostic by construction, the user keeps the CLI's own login, skills and permission UI. ADR 0007 already lists it as the better experience for later. Resume of a headless session is verified for all three CLIs ([interactive resume](interactive-resume.md)) | Low, but adds the app's first third-party Swift dependency | Not a conversation view: no structured transcript, no approval UI in Carrier's style, no events for the dashboard. Fine as a fallback |

Ranking: option 1 for Claude and Codex behind Carrier's own port; option 2 as an extra adapter for any other agent; option 3 as the fallback for a provider whose adapter fails the spike, and for Claude if the subscription question comes out badly.

## Carrier today

### What a session can reuse as is

- Engine process and control socket: the engine runs detached, owns the lock, and serves a 0600 Unix socket with a strict allowlisted request union and a `hello` whose `capabilities` list lets an older engine and a newer app degrade gracefully (`src/control/server.ts`). Session requests slot in as a capability of the chat host's own socket, with the same pattern.
- Process handling in `src/harnesses/host-runner.ts`: detached spawn, SIGTERM then SIGKILL on the process group (`signal`, `terminate`), a line reader, orphan listing by an argv marker. `resolveBinary` (`common.ts`) already skips wrapper shims such as `~/.superset/bin`. `childEnv` builds the child environment with a per-execution `GH_TOKEN` and a git credential helper that never puts the token in argv.
- Identities and tokens: `profileCredentials` (`src/harnesses/credentials.ts`) mints a token for a profile (`forge` bot or the user's `gh` login) and `profileToken` in `git-workspaces.ts` does the same for git.
- GitHub port and `availableRepos` (`src/integrations`, `src/orchestration/github.ts`): the repos the `gh` login can push to are already served to the app, paged, and the Repos tab already edits `repos` in the config file.
- Event model and hygiene: `AgentEvent` kinds `say`, `tool_start`, `tool_end`, `note`, `error`, `task`, the bounds (`caps`) and `clean`/`boundOutput` redaction (`src/execution/events.ts`, [ADR 0006](../adr/0006-agent-events-stored-in-sqlite-with-bounded-output.md)), the `events` cursor request, and the app's transcript views (`TranscriptItems.swift`, `TranscriptFlow.swift`, `AgentOutput.swift`, `JSONMessage.swift`).
- Config: `profiles`, `repos`, `agents.*` (harness, model, provider, persona), the persona text and the shared-identity signature rule of [ADR 0011](../adr/0011-author-and-reviewer-may-share-one-github-identity-signed-visibly.md).
- Resume knowledge: sessions of all three CLIs resume interactively by explicit id given the same config folder ([interactive resume](interactive-resume.md)), and the descriptor validation pattern of [ADR 0007](../adr/0007-continue-in-terminal-through-a-validated-descriptor.md).
- The macOS app: a SwiftPM package with no third-party dependency (`macos/Package.swift`), already a socket client with fixtures (`FixtureServer.swift`), a transcript renderer, a repo picker and a Settings model. A fixture-driven conversation view fits its workflow.
- Tests: ports plus fakes and a temp SQLite ([AGENTS.md](../../AGENTS.md)). Recording a real provider transcript, replaying it through the real adapter and faking only the transport fits that rule well.

### What is structurally different

- Shape of a run. `AgentRunner.run(task)` returns an `AgentRun` whose `done` resolves once with `{ exit, sessionId }` (`src/execution/agent-runner.ts`). A session is long-lived, idle between turns, and has many turn ends; "done" has no meaning for it. `listActive`/`stop(executionId)` find orphans by an argv marker (`carrier-exec-<id>` through Claude's `--name` and a Codex `-c carrier_marker=...`); an ACP agent will not take those flags, so sessions need their own tracking.
- Input. The runner spawns with `stdio: ['ignore', 'pipe', 'pipe']` and a prompt in argv. A session needs a bidirectional pipe with a protocol on it.
- The task type. `AgentTask` is epic-shaped: `repo`, `epic`, `stage: 'ship' | 'review' | 'fix'`, `resultPath`, `timeoutMs`, `context.blockers`. None of it applies, and the stage enum is also what the SQLite schema stores.
- The result contract. Every unattended stage ends in a `CallerResult` JSON (`completed | changes_requested | needs_human`) validated by zod and imported with the state transition in one idempotent transaction (`caller-result.ts`, `import-result.ts`). A session produces no such result; its outcome, if any, is a side effect on GitHub (issues, labels). That path must not be reused or bent.
- Permissions. All three unattended harnesses run with bypass flags (`--permission-mode bypassPermissions`, `--dangerously-bypass-approvals-and-sandbox`, `--dangerously-skip-permissions`; [ADR 0004](../adr/0004-agents-run-on-host-with-terminal-preferences.md)). A session is the opposite: approval requests must round-trip to a person and stay pending when the app disconnects.
- Event parsing. `parseEvents` reads the headless output formats (`claude -p --output-format stream-json`, `codex exec --json`). The SDK, the Codex app-server and ACP speak different, richer shapes (typed deltas, plans, permission requests, usage, mode and config updates). `AgentEvent` has no user message, plan, permission request, streaming delta or usage kind, and ADR 0006's retention (30 days after the epic ends) and key (execution id) do not fit a session that belongs to no epic.
- The control socket. It is strict request/reply with one reply per request, lines capped at 16 KiB (`MAX_LINE_BYTES`), no server push; the app polls the snapshot every second and pages `events` by cursor. A streaming session can ride on the same cursor polling (simple, consistent with ADR 0006) or add a push channel (new). A pasted log or spec in a prompt can exceed 16 KiB.
- Roles and harnesses. Config has exactly two roles, `author` and `reviewer`, and `harness` is the enum `claude | codex | agy` (`src/config/schema.ts`, `src/harnesses/names.ts`). Sessions need their own block (the agents the user can start a session with, and the workspaces); that is a config-schema change, which means updating `docs/configuration.md` ([AGENTS.md](../../AGENTS.md)).
- Workspaces. `Workspaces.prepareAuthor(repo, epic)` returns the repo's shared clone (`<root>/repos/<owner>/<name>`), serialized per repo, with a `fetch --prune` on every call, and that is where `ship` runs (worktrees are off by default, `docs/agents/solve.md`). A session must never use that tree: it would race the engine's own git operations. For a repository from Carrier's list the session gets its own clone or worktree; a plain folder or a clone the user manages is used where it is.
- Lifetime. The engine's `stop` and its confirmation dialog are written for epics ([ADR 0005](../adr/0005-engine-independent-of-the-macos-app.md)); with a separate chat host that stop path is untouched, and the host needs its own stop and its own "sessions are open" confirmation in the app.

### Where the chat host sits

The chat host is its own process with its own socket, as a separate module (for example `src/chat`), not inside `src/orchestration`: it reuses the code of the engine (the logger with redaction, the config, the credentials and the process handling) but not its lock, its slots, its epics or its labels. SQLite stays the authority for what Carrier knows: new tables for sessions and session events (the transcript, bounded and redacted per ADR 0006, with its own retention), plus the agent's native session id so the session can be resumed. GitHub stays the authority for what a session published. Nothing needs to be mirrored until a label is applied, and from then on the epic is an ordinary row registered by the poll ([ADR 0002](../adr/0002-sqlite-authority-labels-mirror.md)). The socket gains requests behind a `chat` capability (open, send, respond to a permission request, interrupt, close, list, archive, events by cursor) with the same strict-object validation, and any folder or repo in a request must resolve against Carrier's own config or a folder the user chose through the app, never a path a client makes up.

One consequence to state plainly: today the socket can pause or stop the engine; with sessions it can start an agent that runs commands as the user. The boundary is still the same user and a 0600 socket in a 0700 folder, so the real change is the blast radius of anything that already runs as that user. The conventions in `AGENTS.md` apply unchanged: a port with a fake, no secrets in config, state or logs (prompts and tool output are redacted and bounded before they are stored; the user's own typed text can contain secrets, so decide whether to store it at all), relative imports end in `.ts`, no `enum`.

## What the providers offer, from primary sources

**Claude Agent SDK.** Anthropic's overview lists, among the capabilities of the SDK, built-in tools, hooks, subagents, MCP, permissions ("control which tools run automatically, which need approval"), sessions ("maintain context across exchanges, resume or fork later") and skills, commands and memory that "load automatically from your project's `.claude/` and from `~/.claude/`, same as Claude Code" (`code.claude.com/docs/en/agent-sdk/overview`). So a session driven through the SDK sees the user's installed skills.

**Codex app-server.** OpenAI's page says app-server is "the interface Codex uses to power rich clients" such as its VS Code extension, and also that "The app-server command and WebSocket transport are experimental and aren't supported for production workloads"; the stdio transport's support status is not stated separately.

**ACP.** ACP "standardizes communication between code editors/IDEs and coding agents" and, for local agents, runs them "as sub-processes of the code editor, communicating via JSON-RPC over stdio" (agentclientprotocol.com, Introduction). The repo `agentclientprotocol/agent-client-protocol` is Apache-2.0 and says "The current stable ACP protocol version is `1`"; `schema/v2` exists and the latest release in that repo is `schema-v2.0.0-alpha.9`, marked pre-release (GitHub releases, 2026-10-16). Official SDKs exist for TypeScript (`@agentclientprotocol/sdk`, Apache-2.0), Python, Rust, Kotlin and Java. The v1 schema (`schema/v1/meta.json`) defines the agent methods `initialize`, `authenticate`, `session/new`, `session/load`, `session/resume`, `session/list`, `session/prompt`, `session/cancel`, `session/set_mode`, `session/set_config_option`, `session/close`, `session/delete`, `logout`, and the client methods `session/request_permission`, `session/update`, `fs/read_text_file`, `fs/write_text_file`, `terminal/*` and `elicitation/create`. Config options carry a semantic category (`mode`, `model`, `model_config`, `thought_level`, ...) "for UX purposes". Who implements it: the agents page lists, among others, Gemini CLI, Cursor, GitHub Copilot, OpenCode, Goose, Kimi CLI and Qwen Code, and names adapters for the two that matter here: "Claude Agent" via `claude-agent-acp` (repo `agentclientprotocol/claude-agent-acp`, Apache-2.0, "implements an ACP agent by using the official Claude Agent SDK") and "Codex CLI" via `agentclientprotocol/codex-acp` (Apache-2.0, "starts the Codex App Server, translates ACP requests into Codex operations", with ChatGPT login, API key and gateway auth methods). Gemini CLI documents its own `--acp` mode: "a JSON-RPC protocol over stdio" (`docs/cli/acp-mode.md` in `google-gemini/gemini-cli`, Apache-2.0). So for Claude and Codex ACP support is by adapter, not first-party in the vendor's own CLI; for Gemini it is first-party. There is also an ACP registry, "a curated set of agents, including only the ones that support authentication", fetchable as JSON from a CDN. `claude-agent-acp` sits on the same Agent SDK as option 1 and so inherits the same terms question; that is why ACP is an extra adapter and not the path for Claude.

## Flow and the handoff seam

1. In the app the user starts a session in a workspace with an agent and a model. The host builds the child environment (`childEnv` with the user's own login and the user's normal `CLAUDE_CONFIG_DIR`/`CODEX_HOME`, so that login and skills are present) and spawns the agent with the workspace as its working folder. Carrier does not install the solve skills today; the unattended agents find them in the user's own CLI configuration and `invoke()` only spells the call (`/skill` for Claude and Antigravity, `$skill` for Codex, `src/prompts/invoke.ts`). A session inherits the same availability.
2. The solve flow is conversational by design: `sharpen` is "a conversation; the product calls are the user's", `pushback` stress-tests, and `to-tickets`, `code-post` and `file-issue` show text for approval before publishing (`docs/agents/solve-flow.md`). That is what a session gives that the unattended runner cannot. The agent needs `gh` authenticated (`to-tickets` uses `gh issue create --parent --blocked-by`, `docs/agents/solve.md`) and git push rights to its folder.
3. `to-spec` publishes the PRD as the epic issue and `to-tickets` publishes the slices as sub-issues and "marks the epic ready" (skill description): the label `solve:epic:ready` appears on GitHub.
4. The engine's next poll registers it (`listReadyEpics`), and from there nothing differs from today: `ship` runs unattended in the shared clone, a reviewer with another identity reviews, the epic ends `ready-for-test` or `needs-human`, and Carrier never merges the final PR.

What must be true for the seam to be safe:

- The label is the only contract. A session never writes SQLite epic rows and never launches `ship` itself.
- Applying `solve:epic:ready` starts an unattended run with bypass permissions on the host, so whoever can apply the label can cause that. A prompt-injected session (for example one that read a hostile issue) could apply it. The mitigation inside the flow is that `to-tickets` shows the text for approval first; a stronger one is for the app to announce every epic that entered through a session. Who applies the label is parked for later.
- Identity: the session runs as the user, so issues and PR text appear under the user's name. The author/reviewer distinction (a reviewer is not the author) is untouched because a session is neither.
- Never merging: a session must not be the path to merging the final PR. `land` is "invoked by a person who has read and accepts the feature" and merges. The safe default is that sessions do not run it in v1.
- No shared tree: a session never works in the shared clone of a watched repository, so the engine's `fetch --prune`/worktree operations and the session's edits cannot collide.

## Workspaces

A workspace is a folder, a GitHub clone, or a repository already in Carrier's list.

- Repos Carrier knows: the `repos` list in the config; the picker offers them and the existing `availableRepos` request serves the rest (repos the `gh` login can push to). Adding one to the config already works from the Repos tab (it edits `repos` in place and offers a restart). A session on a repo that is not in `repos` produces epics the engine will not poll, so the app should offer to add it when the first epic is published.
- A folder: any folder the user opens; the session works where it is. A GitHub clone: created by the user's `gh`/`git` at a location still to decide.
- A new GitHub repo: created with the user's `gh` (`gh repo create`) and cloned. I did not verify whether an Agent Forge installation token can create repositories, so assume the user's login, not a bot.
- An empty workspace: a scratch folder under the root. The agent can talk and write there, but `to-spec` needs a repo to publish the epic issue to, so a session must bind a repo before publishing; this is the one place the flow needs a decision mid-session.
- Models and agents: a config block listing the agents a session can start with (harness, command, optionally a model), with the model and reasoning level taken from the agent's own options where the protocol exposes them, rather than a Carrier enum.

## Risks

- Provider terms on subscriptions: see Decisions. Where a tool that spawns the user's own `claude` through the SDK or an SDK-based adapter falls is not answered by Anthropic's texts. Carrier's current unattended runner spawns the CLI directly (`claude -p`), which is closer to the "unmodified binary" case than the SDK is. For Codex I found OpenAI saying only that enterprise integrations should identify themselves with `clientInfo.name` and contact OpenAI to be added to a known-clients list; I found no statement either way on third-party use of a ChatGPT login, so that is also unverified. Carrier is MIT and published as `@ashulab/carrier`; the README calls it built for personal use. Public distribution of sessions that use subscriptions raises the stakes.
- Security. Approvals are the user's only real brake in a session; if the default is permissive the session is an unattended run with the user watching, so it starts supervised. No token in argv, config or logs (use the existing `childEnv`). Prompt injection through anything the agent reads (issues, PR text, web pages) is the main route to an unintended `solve:epic:ready`. The socket gains a command-execution surface (see "Where the chat host sits").
- Protocol maturity. ACP v2 is alpha; the Codex app-server is described as experimental for production workloads, and `codex-acp` sits on top of it. Pin versions, record replay fixtures, expect churn.
- Maintenance burden. Every provider is an adapter to keep alive: one client plus a per-agent smoke test with ACP; an adapter plus a recorded-transcript harness per provider with native ones.
- Scope creep. Checkpoints and revert, forks, provider switching mid-session, worktrees, PR review inside the app, mobile and remote are each a plausible next ask; none is needed to prove the experience.
- Skills availability is the user's machine state, not Carrier's. A session on a machine without the solve skills will not run `/sharpen`.
- Stopping and orphans: ADR 0004's limitation (children can survive) applies to session children too. Running each agent as the leader of its own process group, with a watcher that kills the group if the host dies, is the hardening to consider.

## The first slice

Prove the experience, not the product. It is the start of epic 2 (core chat), terminal-first and without any Swift:

1. `carrier chat --workspace <path>` (one new command under `src/terminal/cli/commands`). A `ChatRunner` port with a fake, one real adapter (Claude through the SDK pointed at the user's own `claude`, or Codex through its app-server, whichever the owner prefers first), supervised permissions, text in and out, approvals answered at the prompt. Pass criteria, each answerable yes or no: input works across several turns; a permission request round-trips and a decline is honoured; a session id comes back and a second run resumes it; the model and reasoning options can be set and changed; the user's installed skills are visible (or typing `/sharpen` works); and, when the skills flow is back in focus, a `to-tickets` run publishes sub-issues and `solve:epic:ready` and the unchanged engine registers the epic. If a check fails for a provider, that provider falls back to the terminal pane instead of a native adapter.
2. Then the host as a process with a socket of its own and SQLite tables for sessions and events, bounded and redacted events using the ADR 0006 pattern, `carrier chat` moved to be a socket client.
3. Only then the macOS conversation view, against the golden-file fixture first (the existing `FixtureServer.swift` workflow), reusing the transcript components, with an approval card and the pickers.

Defer: more than one agent, images and attachments, checkpoints and revert, forks and provider switching, plan-mode UI, subagent UI, Take over, mobile and remote, and any web UI.
