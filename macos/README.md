# Carrier.app

Menu bar app for Carrier. A SwiftPM package for macOS 26 or later: `CarrierCore` (library), `Carrier` (the AppKit shell), `CarrierCoreTests` and `CarrierTests` (Swift Testing). Building needs **Xcode** (see Toolchain).

## Install

A person does not build the app: `brew install ashulab/tap/carrier` installs the `carrier` command and `brew install --cask ashulab/tap/carrier` this app in `/Applications` (an Apple Silicon Mac on macOS 26 or later), and the app finds that `carrier` by itself. `brew upgrade carrier` moves the command and `brew upgrade --cask carrier` the app; the app says which one when their protocols differ. The app also updates itself: it embeds Sparkle, checks for a new release by itself and asks before it installs, and when it opens at the new version it upgrades `carrier` with Homebrew (log: `<folder>/engine/logs/app-upgrade.log`) and replaces the chat host and the engine that were running when they are free to replace (see the end of [Start Carrier](#start-carrier)). Whether it checks and whether it installs by itself are Sparkle's preferences and have no Settings page yet. The whole flow is in [releasing](../docs/releasing.md#2-what-the-installed-app-does). The app is signed ad hoc, not notarized, and the cask clears the quarantine attribute after the download; if macOS still refuses it, see [troubleshooting](../docs/troubleshooting.md#macos-will-not-open-the-app). [Install](../docs/install.md#uninstall) has the uninstall and what it leaves. The rest of this file is for developing the app.

## Toolchain

Xcode is required, not just the Command Line Tools. With the macOS 27 SDK SwiftUI's `@State` is a macro whose plugin ships only with Xcode, so with only the Command Line Tools selected `swift build` fails with `external macro implementation type 'SwiftUIMacros.StateMacro' could not be found`. Install Xcode and select it. The app builds with the macOS 26 SDK too (the release workflow builds it on `macos-26` with Xcode 26.6; the macOS 27 menu item API is set by key, not by name, so no SDK is needed for it):

```sh
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer   # or: export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
xcode-select -p                                                  # should print the Xcode path, not .../CommandLineTools
```

`build-app.sh` checks this first: with the Command Line Tools selected it prints how to select Xcode and exits 1 without building.

Workaround, unsupported: `swift build --sdk /Library/Developer/CommandLineTools/SDKs/MacOSX26.sdk` does build the package under the Command Line Tools (verified), because the older SDK has no `@State` macro. `swift test` that way was not verified and `build-app.sh` does not use it.

## Build and open

This is how the app is developed; it is not how it is installed.

```sh
cd macos
./build-app.sh          # release build wrapped in Carrier.app (bundle id dev.ashulab.carrier), signed ad hoc
./build-app.sh --open   # same, then opens it
./build-app.sh 1.2.3    # same, with 1.2.3 as the app's version in the plist (0.1.0 when none is given); the release workflow does this with the tag's version

`build-app.sh` also embeds Sparkle (`Contents/Frameworks/Sparkle.framework`, with an rpath so the app finds it) and writes `SUFeedURL`, `SUPublicEDKey` (the content of `update-key.pub`) and `SUEnableAutomaticChecks` into the plist. `CFBundleVersion`, the number Sparkle compares, is `X*10000 + Y*100 + Z` for the version given (1 when none is given); a minor or patch of 100 or more is refused. The app starts Sparkle's updater and asks for a background check when it opens from a bundle that has `SUFeedURL`, never under `--fixture` or `--selftest`. It also writes `NSMicrophoneUsageDescription` (dictation's microphone prompt) and fails when it is missing or empty, as it does for a missing icon; FluidAudio and WhisperKit are linked by the `Carrier` target only, pinned with `exact:`. `scripts/check-app.sh` builds the app and asserts all of this (the workflow runs it); `update-key.pub` holds the update key's public half (the private half is the repository secret `SPARKLE_PRIVATE_KEY`, see [releasing](../docs/releasing.md#4-the-update-key)); change it only to start a new key pair. The build number is that `CFBundleVersion`: the same version always gives the same number, and a build with no version is `1`, so a local build is older than any release.
open Carrier.app
```

`Carrier.app` is an app of the Dock: it has its icon there (`Resources/AppIcon.icns`, made by `swift scripts/make-icon.swift`), opens on its window, keeps its menu bar (Carrier, File, Edit, View, Conversation, Engine, Window, Help: `MainMenu.swift`, built from the shortcut table of `CarrierCore/Shortcuts.swift`, the Edit menu being what gives ⌘C and ⌘V to a text field), remembers where its window was, stays running when the window is closed and opens it again from the Dock icon (whose menu has New Session and Open Window). Besides, it shows one menu bar item at the right of the screen. Its menu opens with a heading (a dot, green while running, orange when intake is paused, an epic needs you or there is a problem, grey when stopped; a bold title and the epic and slot counts), then, while Carrier runs, the epics (needs you, running, waiting, ready; at most twenty, then "… and N more") with a state glyph, a secondary line and a badge, rebuilt each time the menu opens; the Settings switch "Show epics in the menu" (user default `menu.showEpics`, on by default) turns the list off, and choosing an epic opens the window on its section. Then only the controls that apply: while Carrier is stopped, Start Carrier (enabled only when the engine is configured and `carrier` is found, and `node` too when it is a script; it says what is missing otherwise); while it runs, Pause intake (Resume intake while paused), Check GitHub now and Stop Carrier, which asks first when epics are running, since it interrupts them (they resume on the next start), and stops straight away when none are. Last, Open window (⌘O), Settings… (⌘,) and Quit Carrier (⌘Q). The line comes from Carrier's control socket, `<folder>/engine/state/control.sock`, where `<folder>` is the Carrier folder: `CARRIER_HOME` from the app's own environment, else `~/.carrier`. The app finds the engine from the folder alone, with no config file read, and has no setting for a config path; it works the folder out again at each connection attempt. The engine's config is `<folder>/config.json`, and while that file does not exist the Carrier home and the Carrier section of the sidebar say that the engine is not configured (with nothing to do about it here: the setup wizard makes the file) and Start Carrier is off, with that as the reason. The app asks for the snapshot every second while connected and tries to connect every three seconds while not. Check the signature with `codesign --verify Carrier.app` and `codesign -dv Carrier.app` (it should say `Signature=adhoc`).

## Settings

Settings is a sheet over the window (`Carrier/SettingsSheet.swift`, the shape of the workspace chooser: a rail of thirteen pages in four groups, App (General, Notifications, Appearance, Sidebar, Chat, Keybindings), Providers (the one page, with no heading), Carrier (Repos, Agents) and Legacy (Engine, Behavior, Sessions, Health), `RailHeader` and `RailRow` of `SheetParts.swift`, the chosen one on the right and Done in the foot). The menu's Settings…, ⌘, and the sidebar's Settings row open it over whatever page is selected (`WindowShell.showSettings`, `settingsShown`; it is not a `Selection`), on the Engine section unless a caller asks for another (`openHealth` asks for Health). It holds what the app starts Carrier with. The app finds `carrier` by itself (`carrierPath`): the Advanced setting "Use this carrier" when it is set (a path as typed, `~` expanded; one ending in `.ts` or `.js` runs under `node`), else `/opt/homebrew/bin/carrier` when it is executable, else it is missing. On the first launch (nothing saved in user defaults) the app asks the user's shell once, `zsh -ilc` with markers around what it prints and a 10 second limit, for `node` and the `PATH`, without asking the person; "Detect again" repeats the run. A banner on every section says what Start Carrier lacks, or that it is looking for it, and is not shown when all is found, in which case the Engine section is one card ("Carrier is ready to start", with the path of the `carrier` found and Detect again) and the Advanced "Use this carrier" field under it; the banner's model is `CarrierCore/EngineTab.swift`. The Notifications tab (`CarrierCore/NotificationsTab.swift`, the logic in `CarrierCore/Notifications.swift`) has three groups. What to tell me: Needs you and Ready for test (user defaults `notify.needsYou` and `notify.readyForTest`, on by default) and A problem (`notify.problem`, off by default), which says once when the snapshot's `problem` text appears or changes, once when GitHub starts refusing a watched repo (until it recovers) and once when Carrier stops without the app having asked: Stop in the menu and the app's own restart call `NotificationWatcher.expectStop()`, which lapses after 30 seconds. How: Only when Carrier is not in front (`notify.onlyWhenAway`, on by default), which holds the banner back while the app is active (`shouldPresent`; the test notification always shows). Play a sound (`notify.sound`, on by default) sets whether a banner plays the notification sound; the style of the banner belongs to macOS, per app, in System Settings › Notifications › Carrier. Permission shows what macOS says (`UNNotificationSettings`: allowed with banners, alerts or None and the sound on or off, denied, not asked, or only from `Carrier.app`), Open System Settings (always, to change those), Allow (when it has not been asked) and Send a test, which says why instead when macOS would swallow it. A click on a notification opens the window, on the epic when it is about one (the repo and issue travel in the notification's `userInfo`; the delegate is attached at launch so a click on an older notification works too). The General page (`GeneralTabView` in `Carrier/SettingsTabs.swift`) changes Ask before stopping Carrier (`stop.confirm`, on by default), the icon style, the animation and "Show epics in the menu" (`menu.iconStyle`, `menu.animate`, `menu.showEpics`); the keys of the App pages are read by `CarrierCore/AppPreferences.swift`. The Behavior tab (`Carrier/BehaviorTab.swift`, model in `CarrierCore/EngineConfig.swift`, footer rules in `CarrierCore/BehaviorSave.swift`) edits eight values of the config file in place, in four groups: Rhythm (`pollIntervalMinutes`, `logLevel`), Finished epics (`finishedWindowDays`, whole days from 1 to 30, 15 by default), Capacity (`limits.maxConcurrentEpics`, `limits.maxReviews`) and Agent runs (`limits.maxExecutionRetries`, `limits.maxExecutionHours`, with Unlimited, and `limits.githubCallTimeoutSeconds`). They are text fields that check the engine's rules as you type; a value equal to the engine's default is taken out of the file, and nothing else in the file is touched (the app never makes the file: without a JSON object there it says the engine is not configured). The engine reads them only when it starts, so the tab only writes: every change the engine would accept is saved as it is made (`autosave`; a value still being typed, or one the engine would refuse, waits and says why), the footer says "Saved", and Reset to defaults puts the engine's own defaults back (they are saved the same way, and a value equal to its default is taken out of the file). Nothing here restarts Carrier. The Repos page, the Carrier group of the rail, is a master-detail: the list on the left with Add repo under it, the chosen repo on the right (`Carrier/ReposTab.swift`, model in `CarrierCore/RepoList.swift` and `CarrierCore/AvailableRepos.swift`) lists the repos in the config file's `repos` with a dot (green ok, red when GitHub refused it, grey when new or Carrier is stopped), the last check or the error and the epics each has, from the snapshot's `watched`, `epics` and `queue`. Add repo opens a picker with the repos the engine's gh login can push to, grouped by owner, with search; it asks Carrier for them with the `availableRepos` request (a capability in the hello: an engine without it, a stopped one or a GitHub failure each show their own message, and there is no typing a name by hand). The list is loaded a page at a time, 30 repos each, newest push first: while the engine says there is more (`hasMore`) the picker shows a "partial list" notice and a Load more button that appends the next page (the model is `AvailableReposList`; Search filters what is loaded), and a page that fails after the first keeps what is loaded, says so under the list and the button asks for it again. An engine whose hello lacks `availableReposPaged` is asked once, without `page`, and shows that list with no notice and no button. A repo already watched shows ticked and off, and one whose folder name matches another watched or ticked repo is off with the reason. The ✕ on a row asks first, with what happens to the repo's epics (they stop where they are and continue if it is added again; nothing is deleted); the only repo cannot be removed. Changes are saved as they are made, like the Behavior tab's (adding a repo, or stopping to watch one after the question; a list the engine would refuse waits and says why), and nothing restarts Carrier. The chosen repo's page has three cards. It starts with its Status card (`CarrierCore/RepoStatus.swift`, fed with the list's row): the epics ready and running, the last check, the clone with `~` and Reveal (only when the clone exists) and the repo on GitHub with Open; a repo the running engine has not loaded, and every repo while Carrier is stopped, says "Carrier reads it when it starts" in place of the epics and the last check. Under it, Ready for Carrier (`CarrierCore/RepoChecks.swift`, `repoChecks`, tested in `RepoChecksTests`) shows four rows from the checks of `carrier doctor --json` that are about the repo (their `repo` and `profiles`): Carrier can read it, Author can sign here, Reviewer can sign here and Solve is set up, each ok, failed with the doctor's reason and fix, or waiting. A role's row is the repo's `can mint a token` check whose `profiles` holds the profile the role resolves to in that repo, so two roles of one identity show the same check; a check the doctor did not report (something before it failed) is waiting, never failed. A failed sign row offers Use another identity (`RepoCheckRow.anotherIdentity`), which opens that role's form in Who works here (`RepoRoleSelection`); no other row offers it. The doctor (`AppHealth.doctor`, shared with the Health tab) runs when the page opens and on Check again, never in the background; while it runs or when it could not answer, a line says so and the rows wait. `--fixture` answers the run with `Tests/Fixtures/doctor.json` (copied into the fixture home), which carries the new fields: `acme/web` all ok, `acme/api` with a failing reviewer and no Solve labels, the long-named repo unreadable. Under it, Who works here (`CarrierCore/RepoRoles.swift`) shows the repo's Author and Reviewer, and the Lead reviewer only when the global `agents` has one: `<profile> · <provider> · <model> · <effort>`, labelled "Same as everywhere" when the repo has no entry of its own, else its own fields over the inherited ones; each role has Change and, when the repo has its own entry, Reset. Change opens a form inside the card with Identity (a profile of `profiles`), Provider (an account of `providers.json`, or the three default accounts without the file), Model, Effort and the persona's name and prompt; each field left on "Same as everywhere" is not written (`CarrierCore/RepoRoleSave.swift`, `saveRepoRole`, tested in `RepoRoleSaveTests`). The save reads the file again, writes only `repos[].agents.<role>` with the fields set (texts trimmed, a model of only spaces and an empty persona not written, an entry that would be empty removed) and keeps every other key; Reset removes the role's entry. A profile or account that is not declared (shown as missing in the form) is refused before writing, in words. Author and Reviewer on the same identity is accepted and the card says the signature will show it. After a save the doctor runs again, and when the engine refuses the config its reason (the doctor's stderr from `Invalid config`, `DoctorState.refused`) is shown under the roles and in the Ready for Carrier note. The fixture's `config.json` (`fixtureConfig`) has the three fixture repos, the profiles and the three roles. The Agents page, in the Carrier group after Repos, is a master-detail of the three fixed roles, Author, Reviewer and Lead reviewer (`Carrier/AgentsTab.swift`, model in `CarrierCore/AgentsPage.swift`, tested in `AgentsPageTests`; the views have no test). The Who card writes as you change it (`saveGlobalRole` in `CarrierCore/GlobalRoleSave.swift`, tested in `GlobalRoleSaveTests`): Identity, Provider, Model (on Return or leaving the field) and Effort (the five levels or Default) each write only that key of `agents.<role>`, with the file read again just before and every other key kept; choosing a bot adds `profiles.<name>` as `{ kind: "forge", agent }` once and reuses it afterwards, and the person's login uses the first `gh` profile or adds `gh`. An empty model, a provider that is not an account, a bot the registry does not list, or a role that would be left without profile, provider or model is refused before writing, with the reason under the card; a profile that is no longer in the registry stays, marked missing, and is refused only when chosen again. Create a bot… (`Carrier/CreateBotRow.swift`, under the Identity row) opens Terminal on `agent-forge add` (`CarrierCore/ForgeTerminal.swift`, tested in `ForgeTerminalTests`): the command is from a closed list of one entry, quoted, nothing from the registry or the config is part of it, and the one-use script and the opener are Continue in Terminal's (under `--fixture` the opener only says what it would have run); the page reads the registry again whenever the app becomes active, so the new bot appears without a refresh button. The Details card writes the persona as you change it (Persona name and Persona prompt on Return or leaving the field, `saveGlobalPersona` in `CarrierCore/RoleDetailsSave.swift`, tested in `RoleDetailsSaveTests`): either one alone or both, the texts trimmed, a blank field left out and both blank removing the persona, and a name over 40 characters or with a line break, or a prompt over 4000, refused before writing with the reason under the card (the limits are `RoleFields.problems`, the repo form's). The When it runs out of tokens card writes `failover.roles.<role>` (`saveGlobalFailover`, same file): Switch automatically on shows First (a declared provider and an optional model, written once First has a provider) and Then (optional, None takes it back), off removes the role's list; a step that repeats the other or is the role's own provider and model is refused with its position, and the steps a file has after the first two are kept when those are edited. `agentsPage` turns `config.json`, `providers.json` (or the three default accounts) and the names of the Agent Forge registry (`forgeBots`, from `$AGENT_FORGE_CONFIG`, else `$XDG_CONFIG_HOME` or `~/.config` plus `agent-forge/agents.json`: names only, never a key; a registry that is missing or does not read gives no bots and a note, not an error) into a row per role: identity (a bot the registry has, the person's own gh login, or missing when the profile is not in `profiles` or its bot is not in the registry, and then it stays in the file), provider (marked missing when it is not an account), model, effort, persona and the failover steps of `failover.roles.<role>` (the page shows a first and a then step and says how many more the file has). A role's page has three cards: Who, Details and When it runs out of tokens. The Lead reviewer has the Use a lead reviewer row on top, and while the file has no `agents.leadReviewer` the row says Off and the rest of its page is dimmed and not usable. Turning the switch off removes `agents.leadReviewer` and `failover.roles.leadReviewer` and keeps every other key (`turnLeadReviewerOff`), and the row says so; turning it on writes nothing: the page asks for an identity, a provider and a model (`LeadReviewerDraft`, kept in the page) and, once the three are chosen, writes the whole role in one go through `saveGlobalRole` (`turnLeadReviewerOn`), so the file never holds a half role (`CarrierCore/LeadReviewerSwitch.swift`, tested in `LeadReviewerSwitchTests`). When Author and Reviewer resolve to one account by the engine's rule (`sameAccount`: two gh logins, or two profiles of one bot) the page says the signature will show it. A config that is missing or is not a JSON object says the engine is not configured. Under `--fixture` the app sets `AGENT_FORGE_CONFIG` to `agent-forge.json` in the fixture home (`fixtureForgeRegistry`: the three bots of the roles and a spare one), and `fixtureConfig` has failover steps for the Author and the Reviewer. Use in an agent… on a signed-in account of the Providers page that no role names, and Open Agents on the Repos page (in Who works here, and next to Use another identity on a failed "can sign here" check), open this page. The file is read again just before writing, a kept repo's entry is written back as it was (including anything the app does not show) and a new one is only its name, so the two tabs never overwrite each other's keys. With saved values the shell is never started. The `PATH` the engine will get is the detected one (the system's when the shell gave none) with node's directory first and `/opt/homebrew/bin` at the end when it is not in it.

The Health tab (`Carrier/HealthTab.swift`; its checks are cards side by side, as many as fit, and the doctor's many checks are grouped into one card each for tools, provider logins and repository access, `groupedChecks` in `CarrierCore/HealthRows.swift`; the tab is `SettingsPage.health`, which `WindowShell.openHealth()` selects) answers whether everything Carrier needs is ready, in layers, each row with a mark (green ready, yellow warning, orange needs attention, grey not known) and a line. The rows are one pure function, `healthSections(host:facts:)` in `CarrierCore/HealthRows.swift`, tested in `HealthRowsTests`; the view has no automated test. "This Mac" is the chat host's `health` reply (`HealthStore.latest`): `git`, `gh` and each chat agent, as ready, not installed, signed out or could not check, each with the fix of `healthFix` (a button that opens Terminal on the command, or the installation page). Without a reply it says, in place of the rows, that the chat host is not running, that it is too old to check this Mac (its hello does not list `health`: `CarrierFacts.hostReportsHealth`), or that the check has not answered yet or failed and Check again retries it. "Carrier" is what only the app knows (`CarrierFacts`): `carrier` found and its version (`carrier --version`, the one that decides on replacing the host), the chat host running and whether it is older than the installed `carrier` (`hostReplacement`, so it needs a restart), and the engine not configured (no `config.json`), configured and stopped, or running. "Engine setup" is a third section, the checks of `carrier doctor --json` (`CarrierCore/DoctorChecks.swift`): `DoctorStore` runs `node <carrier> doctor --config <folder>/config.json --json` (`doctorCommand`: the engine's `PATH` and `CARRIER_HOME`, run by the shell's `runProcess`, replaceable in the store's tests) when the tab opens and on Check again, never in the background (the doctor makes GitHub calls and mints tokens), without waiting for it (the layer says "Running carrier doctor…" and the rest of the tab stays usable), not again while a run is in progress, and only when `<folder>/config.json` exists; without one the section is a line saying the engine's setup needs the config and nothing runs. Each check is a row with its state (green ok, yellow warn, orange fail), its detail and its fix text, shown as text and never run. The doctor exits 1 when a check fails and still prints the checks, so its output decides; a doctor that cannot start, prints something that is not its JSON array (or an empty one), or takes longer than `doctorTimeout` (90 s, then ended) is one grey row, "Could not check" with the reason, never a pass. The decoding, the outcomes, the command, the store and the rows are tested (`DoctorChecksTests`, `HealthRowsTests`); the process runner and the view have no automated test. Check again asks the host for a fresh health (`HealthMoment.refresh`) and reads the version and the host's socket again; the tab reads the last health the app has (it asks when the app opens and when it becomes active) and does not ask when it opens. The reasons in the draft and the workspace sheet that point to Health (a blocked provider, `gh` or `git`) come with an "Open Health in Settings" button.

## Providers page

Settings has a Providers page (`Carrier/ProvidersTab.swift`, `SettingsPage.providers`, a group of its own between App and Legacy) that lists the AI tools of this Mac: a master-detail with Claude Code, Codex, Antigravity, LM Studio and Ollama. The rows are one pure function, `providersPage(_:config:chat:)` in `CarrierCore/ProvidersPage.swift`, tested in `ProvidersPageTests`; the view has no automated test. The list gives each tool its state (Signed in, Signed out, Not installed, Could not check, or Found, not added for a CLI no account has); the detail gives the version and path and, for Claude, Codex and Antigravity, the accounts, each saying who uses it: a role of `config.json`, a repo's override of a role, a failover list (only while failover is enabled) or a chat agent of `chat.json` (without `chat.json` the chat's default agents `claude` and `codex` use the accounts of that name). A local server shows its models, or that it is not running. The state is the chat host's `providers` reply (`ProvidersStore`, asked when the page opens, when the app becomes active and on Check again); a host that is not running, one too old to list `providers`, one that fails, and a `providers.json` that does not match each say so in words in place of the page.

- **Sign in and Update** (`CarrierCore/ProviderTerminal.swift`, tested in `ProviderTerminalTests`): a signed-out account shows Sign in and a found tool shows Update beside its version and path; both open Terminal with Continue in Terminal's one-use script and opener (`openScript`, `WorkspaceTerminalOpener`). The command is built from a closed list, harness by action, every value single-quoted: `CLAUDE_CONFIG_DIR='<folder>' 'claude' '/login'`, `CODEX_HOME='<folder>' 'codex' 'login'`, `'agy'` (the variable only when the account has a folder), and `'claude' 'update'`, `'codex' 'update'`, `'agy' 'update'` (none of them can only check, they install). The account's `command`, when set, is the binary that runs; it and the folder are accepted only as absolute paths, and a harness outside the list is refused before anything is written. With `--fixture` the opener is `FixtureTerminalOpener`: it logs the line to stderr (`carrier: fixture terminal: ...`) and removes the script, so nothing opens. The buttons have no automated test.

`providers.json` is the app's to create (`CarrierCore/ProvidersFile.swift`, `ProvidersStore`). When the app opens (once the chat host answers) and the file is missing, `createFileIfMissing` writes one account per harness the host found, named after it, and nothing when none was found; with a file there it writes nothing, so an account the person removed stays removed. A harness found with no account is the tool's "Found, not added" row with an Add button, which writes the account and asks the host again. Every write (`applyingAccounts`) keeps the keys the app does not know, writes the whole file in one atomic step as `chat.json` is, and never overwrites a file that is not a JSON object with a `providers` map. Under `--fixture` the fixture home has a `providers.json` and the fake host's `providers` follows it, so Antigravity shows the row and Add makes it go. Tested in `ProvidersFileTests` and `FixtureServerTests`.

- **Account editor** (`Carrier/ProvidersEditor.swift`; the rules and the writing are `CarrierCore/ProvidersEdit.swift`'s, tested in `ProvidersFileTests`): each account row has Edit, which opens its fields under the accounts: Display name, Binary path, Config folder (`CLAUDE_CONFIG_DIR` or `CODEX_HOME`), Auto-compact after, Launch arguments (one per line) and, for Claude only, Compact idle threads (Use default, which removes `idleCompaction`, or Never). Antigravity has only Display name and Binary path. A filled field writes its key and an emptied one removes it (`applyingEdit`), and every other key of the account stays. Add account (Claude Code and Codex) takes a name and a config folder and writes `{ harness, configDir }` (`applyingNewAccount`). Remove (`applyingRemoval`) is refused while a role, a repo's override, a failover list (even one that is off, which the engine still checks) or a chat agent names the account, and says which; `ProvidersStore` reads `config.json` and `chat.json` for that, and a `chat.json` that is there and cannot be read stops it. Before writing, the app applies the engine's rules for what it can check cheaply (`draftProblems`: the name's pattern, Auto-compact's range per harness, absolute paths, the flags Carrier sets itself, nothing Claude-only on Codex or Antigravity) and says what is wrong in words that name the field; it never writes a file those rules refuse. After a save the store asks the host for `providers` again, and a `problem` it answers is shown in place of the page with its key (the file stays as written). The page's footer says the engine reads `providers.json` when it starts, so a running engine needs a restart. Under `--fixture` the fake host's `providers` follows the file (a display name, binary, folder, a Remove giving the tool its "Found, not added" row back), so each of these can be done against the fixture folder. The views have no automated test.

## Health tab

Settings has a Health tab (last of the Legacy group) that answers "is everything Carrier needs ready?". It has three layers, each row with a mark and a line saying what is wrong and what to do.

Settings has a Sessions tab (between Behavior and Health) with the session clock's two ages, `archiveAfterDays` and `deleteAfterDays` of the chat's `<folder>/chat/chat.json`: each a number of days or Never, shown with the values the file has (15 and 30 when it has none). A change is saved as it is made (`applyingSessionAges` in `CarrierCore/SessionAges.swift`, as `applyingProjectsFolder` does: the file's other keys are kept, an age equal to its default is left out, a file that is not a JSON object is never overwritten); the host reads the file each pass, so nothing is restarted. Delete is off, with the reason, while archive is Never, and an age that breaks the host's rule (a number under 1, or delete not greater than archive) is not saved and the field says why (`sessionAgeProblems`, `deleteAgeOffReason`). The functions are tested in `SessionAgesTests` and the tab in `WindowShellTests`; the view (`Carrier/SessionsTab.swift`) has no automated test.

- **This Mac**: `git` and `gh` (and whether it is signed in to GitHub). These are checked by the chat host, because a session runs in the host's environment, so a tool the app finds but the host does not would pass in the app and still fail in the session. The agent CLIs are on the Providers page.
- **Carrier**: the `carrier` command found (and its version), the chat host running (and whether it is older than the installed `carrier`, so it needs a restart), and the engine configured and running.
- **Engine setup**: the checks of `carrier doctor`, shown only when `<folder>/config.json` exists. Without it the layer says the engine's setup needs the config.

Each check on This Mac ends in one of four states:

| State | Row says | Meaning | What the app switches off |
|-------|----------|---------|---------------------------|
| `ready` | Ready | It is installed and, where it needs one, signed in. | Nothing. |
| `missing` | Not installed | The command is not found where the chat host runs. | A `claude` or `codex` that is missing cannot be chosen for a new session. With `gh` missing, My GitHub repositories and From a GitHub URL are off in the workspace sheet. With `git` missing, New worktree is off in the new-session draft. Each says why and points to the Health tab. |
| `signedOut` | Signed out | The command is there but has no login (`git` is never signed out). | A signed-out `claude` or `codex` cannot be chosen for a new session, and a signed-out `gh` switches off the same two GitHub rows as a missing one, each with its reason. |
| `unknown` | Could not check | The check timed out, could not start or could not be read. | Nothing: it is shown as such and never blocks. |

Only what is broken is switched off: opening a local folder keeps working without `gh`, and a session that is already open is never blocked (if its provider loses the login it fails with the provider's own message).

A failure Carrier knows how to fix has a button that opens Terminal with the command: `claude auth login`, `codex login`, `gh auth login` or `xcode-select --install`. A missing `claude`, `codex` or `gh` has no button: its row links to the installation page. The doctor's own fix texts are shown as text and never run.

The checks run when the app opens, when it becomes active again (for example after coming back from Terminal) and on Check again; the chat host keeps its answer for thirty seconds, which Check again skips. The engine's setup runs `carrier doctor --json` only when the tab opens and on Check again, never in the background, because the doctor makes GitHub calls. A check that could not answer is "Could not check", never a pass. The health only reads whether a login works: no email, organisation or token is shown or kept.

When something fails, look here first: [troubleshooting](../docs/troubleshooting.md#start-with-the-health-tab).

## Start Carrier

Start Carrier (the menu item, and a button in the window while Carrier is stopped) runs `carrier` (`node <carrier>` for a `.ts` or `.js` script, the developer's "Use this carrier") with that `PATH` and `CARRIER_HOME=<folder>` (the engine finds its config, state and logs from the folder, so there is no config path to pass), in its own session (`posix_spawn` with `POSIX_SPAWN_SETSID`, so quitting the app leaves Carrier running), stdin from `/dev/null` and stdout and stderr in `<folder>/engine/logs/app-start.log`, which it creates (with mode 0700) when missing. It is never started on its own when the app opens, unless the person turned on "Start Carrier when the app opens" on the Engine tab's ready card (user default `engine.startOnOpen`, off by default): then, at the first state the monitor delivers after launch, the app starts Carrier once when that state is stopped and Start Carrier is enabled (so never while the engine is not configured), never under `--fixture` (`shouldStartOnOpen`; the wiring in `AppDelegate` has no automated test, as it would start the real Carrier). When the control socket answers within 15 seconds the state becomes running (the next connect attempt shows it, within 3 seconds); when the process exits first, or 15 seconds pass without the socket, an alert shows the end of `app-start.log`. A second press while it starts does nothing. The decision and the command line are in `CarrierCore/StartCarrier.swift`; the spawn and the alert have no automated test. The self-test only checks the start (what it would run), as it does for Stop.

The chat host does not need the engine, so the app starts it on its own terms. Every time the app opens, once the settings are known (and again when the Settings window closes), it looks at the host's socket, `<folder>/chat/state/chat.sock`, and starts the host when nothing answers, not only when a session is created: the host runs no agent until a session exists, and the sessions in the sidebar are what it holds. `<folder>` is the Carrier folder: `CARRIER_HOME` from the app's own environment, else `~/.carrier`. The host needs `carrier`, found as above (and `node` only when it is a script), and nothing else: no config path, no engine config. It runs `carrier chat-host` (`node <carrier> chat-host` for a script) with the same `PATH` and `CARRIER_HOME=<folder>`, in its own session, stdin from `/dev/null`, output in `<folder>/chat/logs/app-start.log` (the `chat/` folder with mode 0700), waits 15 seconds for the socket and shows an alert with the end of the log when the process exits first or the socket does not come; a `chat.json` the host refuses (see [configuration](../docs/configuration.md#chat-configuration)) is shown that way, with the host's message naming the key. A second request while it starts does nothing, and under `--fixture` it never starts (the fake host answers). Because the folder comes from the app's environment, a build run from a terminal with `CARRIER_HOME=/tmp/scratch` starts its host in the scratch folder and never touches the real sessions in `~/.carrier` (the guide is in the [README](../CONTRIBUTING.md#developing-against-a-throwaway-folder)).

When `carrier` is missing (or `node`, when "Use this carrier" is a script) the app opens with no alert. The Sessions section of the sidebar and the Sessions home say what is missing ("The chat host cannot start", "The app did not find carrier. Run brew install ashulab/tap/carrier in Terminal.") until the app finds it; coming back from Terminal (the app becoming active) looks for `carrier` on the disk again and starts the host, with no restart. Creating a session while it is missing keeps the alert, which says the same as the notice, because there the person asked for something that cannot happen. The decision, the command line and the notice are in `CarrierCore/StartChatHost.swift` (`chatHostAtOpen`, `startChatHostCommand`, `chatHostNotice`); `Carrier/ChatHostStarter.swift` reuses the engine's spawn and alert, and neither the wiring nor the views have an automated test.

When a host answers, the app asks the installed `carrier` for its version (`carrier --version`) once per launch and compares it with the version in the host's hello (`CarrierCore/HostReplacement.swift`, `hostReplacement`). If the host is older, no session is working or waiting for an approval and the sessions could be listed, the app stops it, waits up to 15 seconds for its socket to go and starts the installed one. If a session is working or waiting, it leaves the host running and the Sessions section and the Sessions home say "The chat host is older than Carrier", to restart it when the session finishes, because stopping a host closes its agents' processes and the work in them. A version that cannot be read on either side leaves the host alone and writes why to the app's stderr. A build under development keeps the same version, so there the host is restarted by hand (`carrier chat --stop`). The rule is tested; the replacement itself is not.

The engine gets the same comparison (`engineReplacement`, and the sequence `replaceEngine` in `CarrierCore/EngineReplacement.swift`), right after the host, with the version read after any Homebrew upgrade. It is replaced only if it was running: a stopped engine stays stopped. With no execution in flight (the snapshot's `sessions`) the app stops it, waits for its socket to go and starts the installed `carrier` with the Start Carrier path (a failed start keeps its alert). With executions in flight the app pauses intake, reads the snapshot every 5 seconds without blocking, and replaces the engine when the last one ends; intake the person had paused is paused again on the new engine, intake the person resumes during the wait is left resumed, and an engine that stops answering ends the wait. The sequence is tested against a scripted engine on a real socket (`EngineReplacementTests`). Known edges: an execution that starts between the last read and the stop is closed with the engine, and an app that quits during the wait leaves intake paused (the next launch reads that as the person's).

## Fixture mode

`--fixture [folder]` runs the app against a fake Carrier, so the window can be looked at with no engine. The app starts an in-process control server (`CarrierCore/FixtureServer.swift`) on a socket in a temporary folder under `/tmp`, points `CARRIER_HOME` at it and connects as to any Carrier. It answers `snapshot`, `sessions`, `events`, `epic` and `files` from the golden files in `Tests/Fixtures`, `fileDiff` with the first reply of `reply-filediff.json` for any file (so a file row of any card in the Files changed tab, a lane's included, opens to a fragment), pause, resume, check now, stop and `resumeEpic` with a plain ok that does nothing (so a Resume in the fixture is confirmed and the card stays on "Resuming…": the snapshot never changes), and anything else with an error. A second socket, `<home>/chat/state/chat.sock`, is a fake chat host (the app finds it through `CARRIER_HOME` like the real one at `<folder>/chat/state/chat.sock`): it answers `agents` and `list` from `chat-agents.json` and `chat-list.json`, `events` (by cursor, in pages, as the real host does) from the `chat-events-*.json` files, each naming its session: a finished conversation with markdown, a code block, tool calls, an approval and a failed turn (`chat-events-finished.json`), one with a message streaming (`chat-events-streaming.json`), and a Codex session waiting for an approval with four choices (`chat-events-approval.json`; its card answers through `answer`, which the fixture host records as an event, and the golden finished one has Claude's three); a listed session with no file has no events, one that is not listed is an error, and the worktree requests: `workspace` (by folder, from `chat-workspace.json`; a folder it does not list is a plain one), `fetch` (`chat-fetch.json`), `cloneRepo` (`chat-clone.json`, by `owner/repo`; one it does not list is refused), `createProject` (`chat-project.json`, by name; one it does not list is refused as taken), `githubRepos` (`chat-github-repos.json`, by page, the login on page 1 only; a page it does not list is refused), `suggestName` (cycling through `chat-names.json`'s suggestions) and `checkName` (free unless that file says why not), plus `open` (a session in memory, in a worktree when asked, refused as the host does for a folder that is not a repository, a branch it did not list and an invalid or taken name) and `send` (adds the message to the session's events); anything else is an error too. `setOption` changes the current value of an option a file lists, or is refused for one it does not list. So the Sessions + is enabled and a selected session shows a conversation. `folder` defaults to the copy of the golden files that `build-app.sh` puts in `Carrier.app/Contents/Resources/Fixtures`; give one when running without the bundle. The temporary folder is removed when the app quits. In this mode the menu also has "Empty states", a window listing the empty states (`CarrierCore/EmptyStates.swift`). It combines with `--selftest`. `--fixture-long-transcript` (with `--fixture`) answers `events` with a made-up transcript of 3,600 events (edits with diffs, passing and failing commands with output) instead of the golden file, to scroll a long one, and every session of the chat host with a made-up conversation of 3,500 events (`longChatEvents`).

Under `--fixture` the app registers the fixture recognizer (`CarrierCore/FixtureRecognizer.swift`, the only one so far, so a build without `--fixture` draws no microphone): the microphone in the message box of the new session and of a conversation answers a click with a canned Spanish phrase, word by word as partial text (secondary) and then final (normal), at the caret. `--fixture-dictation-at-the-end` gives the phrase only after the click that stops it (the box says "Transcribing…") and `--fixture-dictation-fails` fails to start with a cause shown in red under the box. The logic is `CarrierCore/Dictation.swift` (the boundary and the registry), `DictationSession.swift`, `TentativeText.swift` and `DictationPresentation.swift`, tested with the scripted recognizer and capture of `ScriptedDictation.swift`.

```sh
./Carrier.app/Contents/MacOS/Carrier --fixture --selftest /tmp/carrier-selftest.log
```

## New session

Nothing is cloned, created or written until the first message is sent, and the draft is blank every time New session opens (the menu, ⌘N, or the + while it is open) and after a send. Choosing a repository, a project or a folder only fills the plan. Sending makes one `open` and the chat host prepares the session in the background, in this order and only the steps the plan needs: `clone` (or `fetch` when the repository is already in the projects folder) or `project`; `worktree` or `checkout`; `agent`; `message`. The conversation lists the steps, each running, done or failed, until the agent answers. A failed step stops there with its reason in words and the message kept; Try again repeats the steps that did not finish and reuses what was made. Cancel, while it runs, stops the step, deletes the session with its worktree (a half clone goes too, a finished clone stays in the projects folder) and puts the plan and the text back in the draft. A folder that already existed with uncommitted changes is never switched to the picked branch: the `checkout` step fails and says so, see [Troubleshooting](../docs/troubleshooting.md#a-new-session-does-not-start). A repository is added to the engine's `repos` only once the agent has answered. The reasons are in [the spec](../docs/specs/session-prepared-on-first-message.md) and [0018](../docs/adr/0018-a-new-session-is-a-plan-and-the-host-prepares-it-when-the-first-message-is-sent.md); the details follow.

The + of the Sessions row, the New session button of the Sessions home and ⌘N (always on) select `Selection.newSession`: a draft in the centre (`Carrier/NewSessionView.swift`; the logic is `CarrierCore/NewSession.swift`) that shows a round mark (a placeholder for a logo), "What do you want to work on?", "Pick where it works, then write.", the sentence and a box with the agent chip; the toolbar takes the page's own colour, not the system's band. Nothing exists until the first message is sent. The workspace, a chip in the sentence, opens one popover that drills in (`CarrierCore/WorkspaceSources.swift` and `NewSessionModel`): the recent folders (`recentFolders`: the distinct base folders of the sessions the host lists, active and archived, most recent first, at most eight, with their paths), what is in the projects folder (the `<owner>/<repo>` and `local/<name>` folders on disk), Open local folder… (the system's folder panel), From a GitHub URL… (listed only when the host's hello has `repoBranches`, which comes with the plan for a repository), My GitHub repositories… (when it has `githubRepos` as well), New project… (only when it has `createProject`) and a footer with the projects folder's path and Change…, which opens the folder panel and sets `projectsFolder` in the chat's own `<folder>/chat/chat.json` (`applyingProjectsFolder`; the file is made when it is not there and its other keys are kept; the engine's config is not touched), absolute; the popover comes back showing the new path and what that folder holds, and what was in the old one stays where it is. A folder inside the Carrier folder's `engine` or the chat's `state`, `logs` or `worktrees` (symlinks resolved, `projectsFolderRefusal`) is refused before anything is written, and a file that cannot be read or written is too, each said in red under the footer with the old folder still in place; the host reads the folder at each request, so the next clone or new project goes to the new one with no restart. The URL step takes `owner/repo` or a github.com address (`repoReference`; its button stays off until the text is one repository), says beforehand when the repository is already in the projects folder (the button reads "Use (updated when sent)", else "Use (cloned when sent)") and only fills the plan (`NewSessionModel.choose(repo:)`): nothing is cloned, `cloneRepo` is no longer called and nothing is written to the engine's config. A repository that is not on the Mac (`toClone`) has its default branch and its branches read from GitHub with the person's login (the host's `repoBranches`, the first hundred, with a note when there are more), which fill the same branch picker as a folder's (as plain names, since a fresh clone follows the pick), shows no uncommitted-changes line and says where it will be cloned (`repoNote`); a worktree from a branch is offered like for any folder, with its name left empty, "generated when sent", and no ↻ or name check (the host makes it). One that is already in the projects folder is read locally with `workspace`, as a folder is, and the note says it will be fetched. Whatever the person chose, `send` puts the repository in the plan (`PlanWorkspace.repo`) and the host runs its `clone` step (git's progress under it in the conversation) or `fetch`, then the rest. Under the field, "Let Carrier watch this repo" (on by default; off, with the reason, when `repoProblem` refuses the repository for the config's `repos`: already there, or a folder name another repo has) is a choice of the plan: once the session is sent, the model looks at the host's list every two seconds (`settleWatches`) and, when the session's preparation is over (the `message` step is done: no preparation left), adds `{ "name": "owner/repo" }` to the config's `repos`, the file read again just before the write and once only; a preparation that fails (it waits for Try again) or is cancelled adds nothing. The session's conversation says Carrier will listen from its next start (`watchNotes`); a config that cannot be read, is not a JSON object or is not writable is said there as a repository that could not be added to Carrier's list. Deleting the session undoes neither the clone nor the watch. Nothing is restarted. ## Conversation

Selecting a session (`.session(id:)`) shows its conversation (`Carrier/ConversationView.swift`; the logic is in `CarrierCore/ChatConversation.swift`). While the view is on screen a task runs `ConversationModel.run()`, which asks the chat host for `events` by cursor about every 250 ms, in pages of at most 200 (a full page is followed at once by the next), and ends with the task when the person selects something else. `chatFeed` turns the events into rows: the person's messages (a bubble on the right), the agent's (markdown), a closing line per turn (model, how long, and the input and output tokens the provider reported, each only when there), a tool call as one plain line completed by its end (tool, argument, the first line of its output or "failed"), an approval as one plain line completed by its answer, an error in red and, last, the `streaming` text as the message in progress. A poll that fails shows its reason under the feed and is logged once; polling goes on.

The conversation's title bar is the window's: the title (`conversationTitle`, "New session" while the host has none), under it `conversationSubtitle` ("workspace · ⑂ branch" in a worktree, "workspace · base folder" in a folder) and, on the right, the Open menu (`OpenMenu`, items from `openMenuItems`: Reveal in Finder, Copy path and, for a worktree, Copy branch name; a copy item says "Copied" for a moment). The words are tested; the Finder and pasteboard calls are not.

Markdown: SwiftUI's `AttributedString` parses what is inside a line (bold, italics, inline code, links) and covers what the agents write there; the blocks around it are `markdownBlocks` (`CarrierCore/SessionSections.swift`), the line-by-line reader the epics' Agent output already used, which now also reads fenced code as a block of its own (language after the fence, an open fence runs to the end, as in a message being written). `CodeBlockView` draws it with the language and a Copy button (`CopyButton`, the one of the console blocks). Numbered lists and tables are not read as blocks: a numbered item shows as a line with its number.
