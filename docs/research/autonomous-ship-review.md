# Autonomous ship with iterative review

> Research from 2026-10-14, kept as a record. The maximum number of reviews ended up as five, configurable, not four.

We can add a small orchestrator that selects an authorized epic, invokes `ship` and coordinates author/reviewer until there is a PR ready for test. The current components cover implementation and identity, but they do not implement that full workflow; `code-resolve` keeps an explicit per-batch approval. Research from 2026-10-14 on skills `004a876afac6180c34ca973a184f307ec5f7ce45` and agent-forge `8dee1b0ea5e3d4dd6f8bfc8f8f233f6b7adab3f2`. [ship](https://github.com/AshuLab/skills/blob/004a876afac6180c34ca973a184f307ec5f7ce45/solve/skills/ship/SKILL.md), [code-resolve](https://github.com/AshuLab/skills/blob/004a876afac6180c34ca973a184f307ec5f7ce45/solve/skills/code-resolve/SKILL.md), [launcher](https://github.com/AshuLab/agent-forge/blob/8dee1b0ea5e3d4dd6f8bfc8f8f233f6b7adab3f2/src/launcher.js).

`ship` takes one epic; it does not discover a queue of ready epics. It drains the epic's open, refined, unassigned slices with no open blockers; it dispatches up to three subagents per batch and serializes merges into the epic branch. `solve-next-startable` requires an epic number and selects only its slices, with a query limit of 500 issues. The assignee claim expresses occupancy, but the observed code provides no atomic epic-execution lock. [ship contract](https://github.com/AshuLab/skills/blob/004a876afac6180c34ca973a184f307ec5f7ce45/solve/skills/ship/SKILL.md), [selector](https://github.com/AshuLab/skills/blob/004a876afac6180c34ca973a184f307ec5f7ce45/solve/skills/ship/scripts/solve-next-startable).

The result of `ship` is a draft integration PR into the target branch; it never merges that PR or closes the epic. It can stop on slices that cannot be completed, unverifiable dependencies, conflicts or unknown work state. `land` stays outside the loop: it requires human review, verifies gates and asks for a yes on the exact merge and cleanup. [ship](https://github.com/AshuLab/skills/blob/004a876afac6180c34ca973a184f307ec5f7ce45/solve/skills/ship/SKILL.md), [land](https://github.com/AshuLab/skills/blob/004a876afac6180c34ca973a184f307ec5f7ce45/solve/skills/land/SKILL.md).

`code-review` produces evidence and a Ready/Not ready/Inconclusive verdict, without publishing; it already supports re-review of open threads with new commits. In that pass it verifies threads and adds a risk review of the new commits. `code-post` on main publishes a review that has been read when its invocation authorizes delivering it and the package is still intact; it asks for approval on a changed head, findings that no longer hold, new tickets/ADRs, Inconclusive, or a requested preview. That policy changed from the description of the local plugin 0.21.0: pinning versions is advisable. [code-review](https://github.com/AshuLab/skills/blob/004a876afac6180c34ca973a184f307ec5f7ce45/solve/skills/code-review/SKILL.md), [code-post](https://github.com/AshuLab/skills/blob/004a876afac6180c34ca973a184f307ec5f7ce45/solve/skills/code-post/SKILL.md).

The current `code-resolve` requires explicitly approving the batch before commit, push, replies or resolution; it documents no unattended mode and no advance-authorization exception. An automatic loop needs an explicit contract for review by authorized bots, or it must stop for approval on every batch. The author leaves the Blockers open and the reviewer who raised them verifies and closes. [code-resolve](https://github.com/AshuLab/skills/blob/004a876afac6180c34ca973a184f307ec5f7ce45/solve/skills/code-resolve/SKILL.md), [code-post](https://github.com/AshuLab/skills/blob/004a876afac6180c34ca973a184f307ec5f7ce45/solve/skills/code-post/SKILL.md).

Agent Forge launches CLIs with a GitHub App token, a bot author/committer and an identity prompt; it allows agents with different Apps and scopes. Separate author and reviewer identities need distinct botName/App: two registry names pointing at the same App are still the same GitHub bot. The reviewer can have contents:read and pull_requests:write, and the author additionally needs contents:write and issues:write for the ship lifecycle. These scopes alone do not prevent merging the integration: the boundary must exist in the orchestrator and the repository policy. [README](https://github.com/AshuLab/agent-forge/blob/8dee1b0ea5e3d4dd6f8bfc8f8f233f6b7adab3f2/README.md), [identity in launcher](https://github.com/AshuLab/agent-forge/blob/8dee1b0ea5e3d4dd6f8bfc8f8f233f6b7adab3f2/src/launcher.js).

The current launcher spawns the provider with inherited stdio and identity argv; it receives no task, does not pass exec/headless arguments, does not persist workflow runs/sessions and offers no scheduler. The parser does not offer provider argv passthrough either. `agent-forge token` and `agent-forge gh` renew credentials per call; the initial token lasts about one hour and has no automatic renewal in the environment of an already launched process. The launcher must be extended for headless execution, or an external adapter must take identity/credentials and launch the real CLI. [launcher.js](https://github.com/AshuLab/agent-forge/blob/8dee1b0ea5e3d4dd6f8bfc8f8f233f6b7adab3f2/src/launcher.js), [providers.js](https://github.com/AshuLab/agent-forge/blob/8dee1b0ea5e3d4dd6f8bfc8f8f233f6b7adab3f2/src/providers.js), [cli.js](https://github.com/AshuLab/agent-forge/blob/8dee1b0ea5e3d4dd6f8bfc8f8f233f6b7adab3f2/src/cli.js).

Own proposal: a local process with SQLite and polling of allowed repos, an epic authorization label separate from solve:refined, a per-repo/epic lock and a dedicated worktree. States queued → shipping → reviewing → fixing → reviewing → ready-for-test / needs-human. Store PR, head SHA, round, report, threads, session handles, budgets and events; resume from persisted state without recreating PRs. Each review must refer to the exact head; a new head invalidates the previous verdict. Maximum four reviews: the fourth can declare ready or escalate; if another fix is applied afterwards, it becomes needs-human because that head received no review. Ready requires a conclusive reviewer with no blockers, blocking threads closed and required CI green. This design is a recommendation, not an existing capability of the inspected repos.

## Universal Logger: orchestrator logs

Review from 2026-10-15 at commit `16eabc1e3d78bf145f6619f60f5419e1565075b7`. The package is `@ashulab/universal-logger`, declared version 0.1.1, ESM for Node >=18; the public import points to `dist/index.js` and the types to `dist/index.d.ts`. It was not installed and registry publication was not verified. [package.json](https://github.com/AshuLab/universal-logger/blob/16eabc1e3d78bf145f6619f60f5419e1565075b7/package.json).

On Node outside development it emits one JSON line per call with `{message,timestamp,...context}`, with no native level field. debug uses console.log, info console.info, warn console.warn and error console.error: under the standard Node console debug/info go to stdout and warn/error to stderr. The default level outside development is WARN, so set INFO when starting the worker. `createScopedLogger(scope)` only adds `[scope]` to the message; to query events by epic/run, pass `{repo,epic,runId,role,round,event,level}` as context on every call through a small local helper. Avoid message/timestamp keys in the context because they can overwrite the envelope. [src/index.ts](https://github.com/AshuLab/universal-logger/blob/16eabc1e3d78bf145f6619f60f5419e1565075b7/src/index.ts), [level and scope tests](https://github.com/AshuLab/universal-logger/blob/16eabc1e3d78bf145f6619f60f5419e1565075b7/test/logger.test.js).

`logError(message,error,context)` with an Error emits error as text and the stack separately; an Error nested in the context is serialized as `{name,message,stack}` on Node. Serialization does not preserve cause or custom Error attributes. The reporter receives the original error intact and the original context; only logError invokes it, and disabling the logger also disables it. There is no general transport/sink or file configuration: setErrorReporter does not capture info/warn/debug and does not replace console output. The server's JSON path and the reporter call have no catch, so use serializable context and a reporter that does not throw. [implementation](https://github.com/AshuLab/universal-logger/blob/16eabc1e3d78bf145f6619f60f5419e1565075b7/src/index.ts), [reporter and Error tests](https://github.com/AshuLab/universal-logger/blob/16eabc1e3d78bf145f6619f60f5419e1565075b7/test/logger.test.js).

Minimal proposal: use this dependency for the worker's operational logs, keep panel events/state in SQLite and redirect both worker streams to a file outside the TUI. Do not print these logs in the same terminal that repaints the panel: stdout and stderr can interfere with rendering, and redirecting only stdout loses warnings/errors. The logs of each agent execution are saved in separate files; Universal Logger records orchestrator transitions and errors, without copying every agent chunk. If worker and panel stay in one process, a general sink in the library or a deliberate console adapter is needed; the current API does not allow routing all logs to a file per logger. This recommendation is our own design based on the observed public surface. [current API](https://github.com/AshuLab/universal-logger/blob/16eabc1e3d78bf145f6619f60f5419e1565075b7/src/index.ts).
