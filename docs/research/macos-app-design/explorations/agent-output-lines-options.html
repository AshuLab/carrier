Agent output — the log lines, quieter

The data is the Builder run you sent. In all your sessions ~95 % of the calls are OK, so a green tick on each line says nothing: the eye should land on what failed, on what the agent said and on what it changed.

What shows today

Items: agent message (grey bubble, markdown or JSON card) · note (grey line) · error (red line) · tool call as a line (coloured icon, title, duration, ✓/✕ disc, chevron; opens a terminal block, failed ones start open) · edit as a card (header + diff) · around them the lane cards (subagents), the result card and "Continue in terminal".
Noise: (1) ✓ disc and duration on every line; (2) the same coloured terminal icon on every line; (3) the title is the first command, so cd /Users/…/worktrees/… && … shows ten identical cd /Users/vemec/.solve/worktrees/carrier/the-… +6 lines; (4) the "+N" is cryptic; (5) the open detail is heavy dark glass and paints the whole output red; (6) an edit's +N −N shows twice and the path is absolute.

4 · Taking a slice, in the order it happened

How the app builds it today (EpicPoller.swift route, Lanes.swift, SessionSectionsView.swift): every event has a global id and an at time, but an event with an agentId goes to its lane and the rest to the main list. The view then draws all the main rows first, then every lane (each with its glass header, open by default, in order of first appearance), then the result card. The task event is what says a slice was taken (start, no status) or returned (end, ok/err), and TranscriptBuilder drops it, so the main flow never shows it.
So: "starting the first batch (#246, #247, #248)" is followed by the next main line, not by the slices it started; an error of the main agent that happened while a slice ran sits above all the lanes; nothing marks taken / returned / resumed. The fix needs no engine change: the ids already give the order; the view builds one list from the main items and the lane events, placing each slice at the id of its task start.
Scenario below: the Builder starts three slices at once; #247 finishes first, #248 fails and is resumed.
My pick: D for the lines, R for the slices (a live card where the slice starts, so the flow keeps its order and the card says taken → returned → PR; S on top if a run fans out many). Q is the cheap first step. Lines: (groups for the OK runs, quiet lines inside, the failure out on its own), "flat grey" for the detail and "name first" for the edit. If you want even less, E reads like a chat: only what the agent says, with one dim line of calls between. F is the most compact but you lose what each call was without hovering.
Independent of the choice: the title skips a leading cd. Grouping needs a small change in the item list (a run of OK lines becomes one group item); the rest is view-only.
