# Chat spike: the Claude and Codex paths against the real tools

> Spike of 2026-10-27 for ticket #434 of epic #433 ([spec](../specs/chat-host.md), [ADR 0013](../adr/0013-the-chat-host-is-its-own-process-with-an-adapter-per-provider.md), [in-app sessions research](in-app-sessions.md)). Question: do the two provider paths the port is going to be built on do what the research assumed? Answer: yes for both, with the differences listed in the verdict. The recordings are in [chat-spike/](chat-spike/). The throwaway scripts that made them are not kept.

## Recommendation

Build both. Claude through the Agent SDK with `pathToClaudeCodeExecutable` and a custom `spawnClaudeCodeProcess` (that is what makes the process lead its own group). Codex through `codex app-server` over stdio, with no npm dependency. Every item the ticket asks about passed for both, except the ones marked "partly" or "not tried" below. Three things the spec has to absorb are in [What the port has to carry](#what-the-port-has-to-carry).

## What was run

- Machine: macOS arm64, Node 26, both tools already logged in with the user's own login (`claude auth status` says `loggedIn: true`, `authMethod: claude.ai`; `codex login status` says "Logged in using ChatGPT"). No token was read, stored, printed or injected: the scripts passed the process environment through and never opened `auth.json` or the Claude credentials.
- Claude: CLI 2.1.312 at `~/.local/bin/claude` (the `~/.superset/bin/claude` wrapper script also works as the path), `@anthropic-ai/claude-agent-sdk` 0.3.311 (it bundles Claude Code 2.1.311) installed with pnpm in an empty scratch directory, model `haiku`. Nothing was added to this repo's `package.json`.
- Codex: `codex-cli 0.153.4`, `codex app-server` (its help says `[experimental]`), speaking JSON-RPC over stdio, model `gpt-5.6-luna`. The protocol types came from the binary itself: `codex app-server generate-ts --out <dir>` (and `generate-json-schema`).
- The agent ran in an empty scratch folder with tiny prompts. The Claude script drove `query()` with streaming input (an async iterable of user messages), `includePartialMessages`, a `canUseTool` callback and the control methods. The Codex script was a 40-line JSON-RPC client over the child's stdio. Each ran as several separate processes: one for the conversation, one that resumes it, and for Codex one for the `cancel` decision and one for the lists.
- Not exercised for either: a conversation of more than about ten turns, images, a resume from a different folder than the one the session started in, running without a network.

What the stream looks like (all in the fixture): `system/init` arrives at the start of every turn, not once; `stream_event` messages carry the text deltas (`content_block_delta` / `text_delta`); an `assistant` message is a finished block (text or `tool_use`); the tool output is a `user` message with a `tool_result`; the turn ends with `result`, which has `usage` (the turn's tokens), `modelUsage` and `total_cost_usd` (cumulative for the query), `model_usage_since_last_result`, `duration_ms`, `num_turns`, `stop_reason`, `terminal_reason` and `permission_denials`. User hooks (SessionStart) and the user's MCP servers also run in the SDK session, because the settings sources default to all; that is "as the user" but the host should expect `system/hook_*` messages.

## Not tried

- The CLI headless fallback for Claude (`claude -p --output-format stream-json`) and the terminal pane: the SDK passed, and the SDK itself runs the CLI as `claude --input-format stream-json --output-format stream-json`, so the fallback speaks the same stream.
- Claude: the `AskUserQuestion` and plan-mode (`ExitPlanMode`) prompts, which go through `canUseTool` as tools; a message sent while a turn is running; `Options.effort` at open; resuming from another folder.
- Codex: `item/fileChange` and permission requests, setting a permission profile, `granular` approval policy, `thread/list`, a skill named in the input.
- Anthropic's and OpenAI's terms for using a subscription login from an app are not part of this spike and stay as in the spec's Out of scope.

## What the port has to carry

These are what the real providers force; the spec's `ChatOption`, `ChatChoice` and `ChatEvent` are close, with these adjustments.

1. **The values of an option depend on another option.** Claude's and Codex's reasoning levels are listed per model (`supportedEffortLevels` / `supportedReasoningEfforts`; `ultra` exists on one Codex model and not on the other), and a model change can leave the current level unsupported. The `option` event of the spec carries only `id` and `value`; it must be able to carry the options again (or the host re-reads `options` after a change) so the values of `effort` follow the model.
2. **Options are of two kinds.** Runtime lists (models, with their efforts) and fixed lists that the adapter has to write down from the provider's typings (Claude's six permission modes; Codex's approval policy and sandbox, which are two separate options, and not one mode as in Claude). Codex's `granular` approval policy is an object; list only the plain values.
3. **When a change applies differs.** Claude applies `setModel` and `setPermissionMode` at once, even mid-turn; Codex applies an override from the next `turn/start`. `ChatConversation.setOption` is fine for both; the adapter keeps the Codex overrides and sends them with the next turn, and answers the host at once.
4. **Approvals.** Claude gives a callback with the tool, its input, an optional `title`, `displayName`, `description`, `decisionReason`, `blockedPath` and `suggestions` (permission updates such as "always allow `touch allowed.txt`" that go back as `updatedPermissions`). The choices to show are Allow, Deny and one per suggestion; deny takes a message the model sees. Codex gives a JSON-RPC request with a numeric id and `availableDecisions` (`accept`, `acceptWithExecpolicyAmendment`, `cancel`); `decline` also works but is not listed. So the `choices` of an `approval` event are built by the adapter, `ChatChoice.allow` is enough to tell allow from deny, and `cancel` is a third kind: it denies and ends the turn. The `approvalId` is Claude's `toolUseID` and Codex's request id; both live only inside the running process.
5. **A pending approval does not survive its process.** It is a live callback or an open request. Spec story 3 holds only while the session is kept live, which the spec already says; after a host crash the approval is gone and `--resume` starts from the provider's own history.
6. **Turn end.** Claude marks an interrupt as `error_during_execution` with `is_error: true`; Codex as `status: 'interrupted'`. The adapter decides `outcome: 'interrupted'` from its own `interrupt()` call. Usage is per turn from Claude's `result.usage` (cumulative `total_cost_usd`), and from `thread/tokenUsage/updated` for Codex; keep it as given. The model for `turn_end` is on Claude's `assistant` message and on Codex's thread or last override.
7. **Claude replays an init each turn and runs the user's hooks and MCP servers;** the adapter ignores `system/init` after the first and `system/hook_*`.
8. **Claude's launch.** `pathToClaudeCodeExecutable` plus `spawnClaudeCodeProcess` with `detached: true`, `env` the host's. The recorded `pid` and `pgid` are the child's.

## Verdict

**Claude: build the SDK path.** Every item passed against the user's own binary. The two prices are in the dependency below. The fallback (CLI headless) needs no research: it is the same stream the SDK reads. The terminal pane stays as the last resort.

**Codex: build.** It passed everything it was asked, with the caution that the server is marked experimental, so pin the version it was built against, generate the types from that binary, and keep the gated integration test.

## The recordings

[`chat-spike/claude-conversation.fixture.jsonl`](chat-spike/claude-conversation.fixture.jsonl) and [`chat-spike/codex-conversation.fixture.jsonl`](chat-spike/codex-conversation.fixture.jsonl), one JSON object per line. A line with `host` is something the driver did or saw outside the provider's stream (`recording` starts a separate process; `sent` is the user message; `canUseTool` / `answer`; `setModel`, `setPermissionMode`, `interrupt_called`, `check` for the files that the approvals should or should not have created); every other line is the provider as it spoke: Claude's SDK messages as the iterator yielded them, Codex's JSON-RPC lines with `dir` `in` (from the server) or `out` (ours).

- Claude, process 1: remember a word, recall it, a read-only tool call (`echo`, no approval), an approved `touch`, a declined `touch`, a mode and model change, an interrupt and the next message. Process 2: a resume that recalls the word. Every turn ends with its `result` (usage).
- Codex, process 1: the same conversation with the approved and declined `touch`, per-turn overrides, an interrupt. Process 2: a resume that recalls the word. Process 3: the `cancel` decision. Process 4: the lists (`model/list`, `permissionProfile/list`, `skills/list` cut to names).

Cleaning, done by a script and not by hand: the home directory became `~`, the scratch folder became `/work`; the hook messages, Claude's `rate_limit_event`, the init's plugin paths, memory paths and socket path, the thinking `signature`, and Codex's `remoteControl`, `account/rateLimits`, `hook/*` and `mcpServer/startupStatus` notifications were dropped; `initializationResult` keeps the models and not the account. A search of both files finds no `/Users/`, no user name, no email address, no token shape (`ghp_`, `gho_`, `github_pat_`, `sk-`, `eyJ`, `Bearer`, `AKIA`), no `access_token`, `refresh_token` or `id_token`, and no installation or organisation id. The only hit for "api key" is Claude's own field `apiKeySource`, whose value is `none`.
