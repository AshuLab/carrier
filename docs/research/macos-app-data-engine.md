# What the macOS app design needs from the engine, and what the engine has

> Research of 2026-10-21 for the final design in [`macos-app-design/diseno.html`](macos-app-design/diseno.html), the [macOS app spec](../specs/macos-app.md) and [ADR 0005](../adr/0005-engine-independent-of-the-macos-app.md). Read only: no source file was changed and no `carrier` was started. Two things on this machine were read without touching them: the real state under `~/.solve/orchestrator/` (a Carrier of Diego's was already running, pid 47703; I opened `carrier.db` with `sqlite3 -readonly` and read the execution logs and Claude's session folders, looking at event shapes and sizes, not at what the agents wrote) and the CLIs' own `--help` (`claude` 2.1.306, `codex` 0.153.4, `agy` 1.4.4; no agent was run). The design's data is invented, so every claim below is about the engine, with `file:line` for each. What I could not check is listed at the end.

## Short answer

Carrier already stores more than the snapshot shows. SQLite has one row per agent execution with its stage, status, start, end, session id and technical error (`src/storage/executions.ts:6-17`), the review result of each execution as validated JSON with the blocker titles (`src/storage/caller-results.ts`, `src/execution/caller-result.ts:20-26`), the epic's timestamps, stage, round, worktree, PR number, head sha, agents and models frozen at reservation (`src/storage/schema.ts:6-38`), and the whole raw output of every execution on disk (`orchestrator/logs/executions/<id>/stdout.log`, `src/logging/logger.ts:37-42`). The snapshot only exposes a thin slice of that, and the control socket only serves a stateless "last N lines" tail.

What is **derivable** with moderate work, and no new engine concepts: the list of sessions per epic with agent, model, role, round, timing and the exact resume command; review rounds with who reviewed, blocker counts and titles, and round and fix durations; stage times and total time; the epic's worktree and the reviewer's checkout; the "needs you" detail; engine health that is already in memory (version, next poll, intake).

What is **missing**: an event model for the agent's output (the only thing the engine keeps is the raw JSON stream, with no time per line, no structure the app can page through and no cursor); a record of slices (the engine reads only the counts); blocker identity across rounds (blockers are free-text titles from the reviewer, with no id and no "fixed" mark); lane information (the engine does not know lanes exist); per-repo last poll and the GitHub rate limit; the epic title, which the poll reads and throws away.

Two parts of the design cannot be built as drawn, whatever the engine does. First, **lane sessions with their own `claude --resume <id>`** (`diseno.html:612-621`): Carrier runs exactly one `ship` execution per epic and the lanes are Claude subagents inside it (`~/.solve/worktrees/skills/solve-claude-mod/solve/skills/ship/SKILL.md:47-49,95,172-181`, a file of the Solve skills, not of this repo). A subagent has no session id of its own: on disk its transcript is `<session>/subagents/agent-<id>.jsonl`, under the parent session, and the CLIs offer no way to resume it. The only session that can be resumed is the ship execution as a whole. Second, **"slot 2 of 3"** (`diseno.html:814`): a slot is a counter (`src/orchestration/reserve.ts:12-13`), not an object with an identity.

The single most expensive missing piece is **structured agent events** (item 2 below): three different stream formats, of which only Claude's carries timestamps and a reliable tool call and result pairing that I could verify on real logs; Codex and `agy` have no captured real run in this repo, only the shapes in the research notes. Second most expensive is **slices and lanes**, because the data is on GitHub and in the model's own conventions, not in the engine.

## Method and the real data I used

The engine's own 12 executions on this Mac (3 days of use, 5 epics, 7.6 MB of raw output) are the sample. All 12 are Claude. The largest is a `ship` of 3.2 MB, 1,657 lines, 729 content blocks (text, tool use, tool result), 10 background subagents and 12 `system/init` events, all with the same `session_id`. Each Claude stream line is one JSON object; the useful ones I counted in it: `assistant` (text, tool_use, thinking) and `user` (tool_result), `system/task_started`, `task_progress`, `task_notification`, `task_updated`, `background_tasks_changed`, `code_change_published`, `vcs_state_changed`, and a `result` per turn with `duration_ms`, `num_turns` and `total_cost_usd`. Messages from subagents carry `parent_tool_use_id`, `agent_id`, `subagent_type` and `task_description`. Assistant and user lines carry an ISO `timestamp`.

## Recommendation: how to expose it

### Principle

Keep the snapshot small and cheap (the app asks for it every second, spec "Decisions"), put everything that is per epic or per session behind new requests, and keep `protocol: 1`. Every change below is additive: Swift's `JSONDecoder` ignores unknown keys (`macos/Sources/CarrierCore/Snapshot.swift:81`), the app only checks `protocol == 1` in the hello (`ControlClient.swift:66-71`), and the engine's request schema is a strict allowlist, so a request the engine does not know gets `invalid request` instead of doing anything (`server.ts:20-23,52-57`). A protocol bump is only needed if an existing field changes type or meaning: `repos: number` and `executionId` (latest execution of the epic) must stay as they are, which is why the additions use new names. To let a new app talk to an older engine, the hello advertises what the engine can do, so the app does not have to probe by failing.

### Hello

```json
{ "event": "hello", "protocol": 1, "pid": 47703, "startedAt": 1792371200000,
  "version": "0.1.0", "capabilities": ["sessions", "events", "epic"] }
```

```json
      "title": "…", "queuedAt": 0, "startedAt": 0, "finishedAt": null,
      "branch": "feat/<slug>/epic", "workspace": "/Users/…/worktrees/encaja/<slug>",
      "needsHumanKind": null, "blockerTitles": ["…", "…"],
      "agents": { "author": { "…": "…" }, "reviewer": { "…": "…" } } } ]

```

What each addition is for: `engine`, `watched` and `rateLimit` feed Overview's Carrier box and the watched repositories (`diseno.html:735-738`); `sessions` lists only the running executions (at most one per running epic, so a handful of rows) and feeds "Agents working", with `last` the newest event so the overview needs no tail call (`diseno.html:733`); the extra queue and epic fields feed the sidebar, the details tab and the "needs you" card. `queue` currently is `{repo, issue}` (`types.ts:29`): adding keys to those objects is additive. `rateLimit` is null until the first call. The cost on the engine is one indexed lookup of the newest event per running execution per snapshot, like `lastExecution` does today (`snapshot.ts:16`). `blockerTitles` is capped (10 titles of 200 characters). The golden file `macos/Tests/Fixtures/snapshot.json` is regenerated with `UPDATE_FIXTURES=1` (`src/status/snapshot-contract.test.ts:51`), and the Swift types gain the new fields as optional.

### New requests

Same framing and the same strict zod style as today (`server.ts:20-23`); each reply stays under the client's 8 MiB line limit (`ControlClient.swift:12`) because every request is bounded by count and by bytes.

- `sessions` `{id, cmd: 'sessions', repo, issue}` returns every execution of an epic, newest first: `executionId, stage, role, round, harness, model, provider, status, error, startedAt, finishedAt, sessionId, resume: {cwd, command, env}`, plus per stage totals. It works for any epic in SQLite (queued, running, needs_human, ready_for_test), so the "ready for test" view has its history. The engine builds `resume.command` from the harness (`claude --resume <id>`, `codex resume <id>`, `agy --conversation <id>`), so the app does not know CLI syntax; a session that is `running` has `resume: null`, because resuming it from a terminal while the engine owns it would be two writers on one session.
- `events` `{id, cmd: 'events', executionId, after, limit}` with `after` an opaque cursor (the last `next` the app got, or empty) and `limit` 1 to 200. Reply: `{events: [...], next, running}`. Event kinds: `say` (text), `tool_start` and `tool_end` (a call id, tool name, one-line argument, result summary, status `ok` or `err`, `durationMs`, optional capped `output`, optional `diff`), `note`, `error`, and `task` (a subagent started or ended, with its description and, for ship, the slice number as a hint). A tool call is two immutable events joined by the call id, so a cursor that only moves forward never misses an update; the app merges them. Keep `tail` as it is for the plain output window (it is in the spec and the tests).
- `epic` `{id, cmd: 'epic', repo, issue}` returns what the right panel and the center need that is per epic and not per session: `stages` (queued, ship, review, fix, ready with start and end), `rounds` (round, reviewer, blockers `{id?, title, url?, state}`, review and fix durations, head shas, commit list), `slices` (number, title, state, blockedBy, prNumber, closedAt, lane hint), `worktree` (epic path, lane paths), `branch`. Polled every few seconds only for the epic on screen.
- `files` `{id, cmd: 'files', repo, issue, executionId?}` last, optional: per session or per slice commit range with `git diff --numstat` run by the engine in the epic worktree. The GitHub-side file list is the other researcher's.

All of it is pull, as the spec decides ("There are no pushed events in this version"). A 1 to 2 s poll of `events` with a cursor is a few hundred bytes per call when nothing happened.

### SQLite changes

Generated with `pnpm db:generate` (`AGENTS.md`), one migration.

1. `executions`: add `harness`, `model`, `provider` (nullable), `workspace` (the cwd the child started in, `task.workspace`) and `round` (nullable). All set in `execute` where the row is inserted (`engine.ts:183`). Cheap and the foundation for sessions and rounds.
2. `epics`: add `title`, `branch`, `needsHumanKind`. `title` at insert (`engine.ts:511,518`), `branch` in the ship import (`engine.ts:342,355`), `needsHumanKind` in `toNeedsHuman`'s callers.
3. New table `execution_events`: `id` integer autoincrement (the cursor), `executionId` (foreign key), `at` integer ms, `kind` text, `callId` text null, `agentId` text null (the Claude subagent, for lanes), `name` text null, `arg` text null, `summary` text null, `status` text null, `durationMs` integer null, `payload` text (JSON) null for the capped output or diff; index on `(executionId, id)`. Same append-only pattern as `epic_events` (`src/storage/events.ts:5-11`).
4. New table `epic_slices`: `epicId`, `number`, `title`, `state`, `blockedBy` (JSON), `assignee`, `prNumber`, `closedAt`, `readAt`; replaced per epic on each poll for running epics. This reverses one line of the spec ("not stored in SQLite", `docs/specs/macos-app.md:82`) for the list, not the counts; the reason is that a finished epic must still show its slices after a restart. If the owner prefers to keep it in memory, the `epic` request returns slices only for running epics and the ready-for-test view shows the count only.
5. Retention: `purgeExpired` (`retention.ts:74-105`) also deletes the `execution_events` of the executions it purges, with the logs, after 30 days. Without that the table would outlive the files it was built from.
6. No change to `caller_results`: rounds are read from it, joined to `executions.round`. If blocker ids are adopted (below) they live inside its JSON.

Size, from the real sample: 12 executions made about 1,600 content blocks in total, the biggest 729. With arguments capped at 1 KB, result summaries at 200 characters and output at 4 KB (first and last lines), a large ship is under 1 MB of rows and a review or fix tens of KB. A hundred epics stay in tens of MB. Write cost is one batched insert per output chunk, in a transaction, like the existing `lastActivityAt` write at `engine.ts:196` but without its 10 s throttle.

### Capturing events from each agent

The hook already exists. `HostAgentRunner.run` splits both streams into lines and hands each to `adapter.parseLine` (`host-runner.ts:115-138`), which today returns only `{session, authFailed, sessionUnavailable}` (`src/harnesses/common.ts:14-24`). Add to the adapter `parseEvents(line, state): ExecEvent[]` (the state holds the open calls by id), add `AgentRun.onEvent` beside `onOutput` (`agent-runner.ts:28-34`), and let the engine insert the rows next to `writeOutput` (`engine.ts:188-197`). The engine stamps arrival time, so Codex and `agy` get a time; for Claude it prefers the line's own `timestamp`. Redact every string with the existing `redact` (`logger.ts:8-9`) before it is stored; it only knows GitHub token shapes, and a tool output can hold other secrets (an `env` dump, a `.env` read). The same is already true of `stdout.log`, but a database that the app queries makes it more visible, and `AGENTS.md` says "no secrets in state" (open question 5).

Per harness:

- **Claude** (`stream-json --verbose`, `claude.ts:14-19`). Complete and reliable on the 12 real logs: text blocks, `tool_use` and `tool_result` paired by id, timestamps, `structuredPatch` for edits, `parent_tool_use_id`/`agent_id` on subagent messages. Skip `thinking`, `thinking_tokens`, `rate_limit_event`, `hook_*` and `tool_progress`. Subagents: turn `task_started`, `task_notification` and the `Agent` tool call into `task` events (the notification's summary even carries `{"slice": …, "outcome": …}`, which `logs.ts:19` already matches). One version note: the shapes were seen on 2.1.303 to 2.1.305; `claude --help` now lists `--forward-subagent-text` for subagent messages with `parent_tool_use_id` (2.1.306), which the real logs already show without it. The adapter must ignore unknown events and never throw.
- **Codex** (`exec --json`, `codex.ts:19-20`). `thread.started`, `turn.*`, and `item.started`/`item.completed` for `agent_message`, `command_execution` and `file_change`, as `logs.ts:41-42` and the research notes show. Pair `item.started` with `item.completed` by item id; time from arrival. I have no real captured Codex stream (all 12 executions are Claude), so field names beyond those need a capture first: run one real review through the real `codex exec --json` once and save the stdout as a test fixture.
- **agy** (`stream-json`, `agy.ts:14-20`). `step_update` with `step_index`, `state` ACTIVE then DONE, `step_type`, `tool_name`, `tool_info` (the call as a Python-like string, to be parsed loosely), `duration_seconds` on DONE (`antigravity.md:36-44`). Whether the tool result appears is not documented. Treat agy as the last to cover.

Keep `stdout.log` untouched: it is the replay source. A small script that feeds an old `stdout.log` through the adapter backfills `execution_events` for existing executions, which also gives the first real fixtures for the parser tests (the repo has only fake CLIs, `src/harnesses/fake-*.fixture.mjs`).

For lanes and slices, derive from the Claude events only, and label them as hints: an `Agent` call whose description matches `slice #(\d+)` gives the slice number, the `code_change_published` event gives the PR number and branch, and `background_tasks_changed` gives how many sub-tasks are live. That is the model's wording and Claude Code's internals; it can break with a new version or another harness. The robust lane source is GitHub (assignee and open PR of each slice) and `git worktree list`, not the stream.

### Review rounds and blocker identity

Rounds need no new table: order the review executions of an epic by start, keep those that produced a `caller_results` row, number them with `executions.round`, and attach the fix execution that followed. For "fixed, carried over, new" the reviewer has to say it. Extend the review result (`caller-result.ts:20-26`) with an optional stable `id` per blocker and an optional `resolved: string[]` listing earlier ids now fixed, pass the previous blockers (id and title) into the review prompt (`review.ts`, `intro.ts`), and tell the reviewer to reuse the id when a finding persists. Both are optional in the schema, so existing results and a reviewer that ignores it still validate; the app then falls back to normalised exact-title matching and marks it as approximate. This changes what the reviewer is asked, so it deserves one real run before relying on it.

### Order to build it, so the app shows real data early

1. **Hello and snapshot fields already in SQLite** (no migration): `version` and `capabilities`, `queuedAt`, `startedAt`, `finishedAt`, `workspace`, `agents` per epic, `watched` with the in-memory last poll, `engine.pollIntervalMs`. The app gets real Overview, Details and a correct "needs you" card. S.
2. **Migration 1: `executions` columns, `epics.title/branch/needsHumanKind`, and the `sessions` request.** Real session headers, agent and model per session, the resume command (`Continue in Terminal`), and Overview's "Agents working" without the output. S to M.
3. **`epic` request with rounds and stage timeline** from `executions` and `caller_results`. Real Review tab (blockers listed, counts, durations, approximate carry-over by title) and Details timings. M.
4. **`events` for Claude first**, with the two tables and backfill from `stdout.log`, then `last` in the snapshot. Real transcripts and a real "current action". The largest step. L. Codex next (after a real capture), agy last.
5. **Slices**: `GitHub.listSlices`, `epic_slices`, and the slice part of `epic`. Real Slices tab with merged, working and waiting. M. Lane hints from events afterwards.
6. **Blocker identity** in the review contract, **`files`** with git numstat, **rate limit** and per-repo health if the owner wants them. M.

Steps 1 to 3 are small, give most of the Overview, the Review and the Details tabs, and carry no risk from the agents' output formats.

## Open questions only the owner can answer

1. **Lane sessions.** The design draws each lane as a session with its own resume command (`diseno.html:612-621`). The engine has one session per ship execution and the CLIs cannot resume a subagent. Accept one Builder session per ship with lanes shown as read-only sub-tasks, or keep the lane look without a resume button? And is the "Lane" column worth its heuristic (it depends on the model naming its subagents "Build slice #N")?
2. **"Continue in Terminal" identity and conflicts.** The agent ran with the bot's `GH_TOKEN`, git identity and the engine's `CLAUDE_CONFIG_DIR`/`CODEX_HOME` (`common.ts:44-63`); a terminal resume would act as Diego with his own config unless the app copies that environment. Should the app reproduce the environment (the engine can send `resume.env` with the config dirs only, never a token), and is it acceptable that it acts as Diego? Offer it only when the epic is `needs_human` or finished, never while the engine owns the session?
3. **Where the resume runs.** The ship session started in the shared clone, the fix session in the epic worktree, the review in `reviews/…`. Should the command `cd` to the stored cwd of that session, or to the epic worktree whatever the stage (what the design shows)?
4. **Slices in SQLite.** The spec chose memory only (`docs/specs/macos-app.md:82`). Persist the list so finished epics keep it, at the cost of one more table and one more GitHub call per running epic per poll?
5. **Secrets in events.** Is it acceptable to store capped tool output in SQLite for 30 days, given that only GitHub-token-shaped strings are redacted today? Alternatives: store no output (arguments and summaries only, and open `stdout.log` on demand), or a wider redaction list.
6. **Blocker contract.** Is the owner willing to change what the reviewer is told and what it returns (ids and `resolved`), knowing it needs a real run to see whether the models comply, with title matching as the fallback?
7. **Codex and agy parity in the first version?** Claude events can ship first; for Codex and agy sessions the transcript could show the plain summarised lines (`tail`) until their parsers exist.
8. **Rate limit and "slot N".** The rate limit shown would be the orchestrator profile's only, not the agents'. Show it labelled so, or drop it? Drop the slot numbers (a slot has no identity) and show the occupying epics instead?
9. **Tests count and checks.** `verification.evidence` is free text, so "242 passing" is not available as a number from the engine. Show the text, or ask the reviewer for a structured count (another contract change)?
