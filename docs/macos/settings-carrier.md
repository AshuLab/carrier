# Settings: the Carrier group

The pages of the Carrier group of [Settings](settings.md): how Carrier runs epics and how the app runs Carrier.

## Watching

The Watching page, in the Carrier group of the sidebar, is the repos Carrier takes epics from: the `repos` of `engine.json` (a `Form` page like Agents, in `Carrier/`: `WatchingTab.swift` reads and writes the file and chooses the screen, `WatchingListScreen.swift` is the list and the picker, `WatchingRepoScreen.swift` a repo's groups, `WatchingRole.swift` a role's screen and `WatchingBanner.swift` the refusal; rows in `CarrierCore/RepoList.swift`, their order and the picker in `CarrierCore/WatchingList.swift`, tested in `WatchingListTests`).
It was called Repos and was a master-detail with its own Add repo; the projects are now where a repo comes from, so Watch a project is the only way in, and a repo's own page is a screen of the window's history (‹ ›) that a row opens.
The first screen is one group of rows titled Repositories, as Projects' list is, with no line of column titles: each repo is a row with the project's tile (the repo's own letters when no project has its origin) and a dot for its health (green ok, red when GitHub refused it, grey when new or Carrier is stopped), `owner/name`, under it the name of the project that has it as its `origin` ("No project" when none does) and what the last check said (the engine's error, in red, when GitHub refused the repo), at the right chips for the epics it has (needs you, running, queued; none when it has none or Carrier is stopped) and a chevron that opens the repo's screen.
GitHub's refusals are first and the others go by name (`watchingOrder`).
The toolbar has the page's actions on one glass capsule (`SettingsHeaderButtons`, `ToolbarPillButton`): Check now (the menu's Check GitHub now, off while Carrier is stopped) and Watch a project…, whose popover hangs from the top right of the page.
Watch a project opens a popover of the projects with a GitHub `origin` that are not watched, with a search (`watchChoices`, `WatchPicker`): a project whose repository the engine would refuse next to the watched ones (the same folder name, `repoProblem`) or that has no GitHub origin is there, off, with the reason; a click watches the repo, and Add project… goes to the Projects page.
With nothing watched the page is an empty state with Watch a project….
Changes are saved as they are made, like the Behavior tab's (watching a repo, or stopping to watch one after the question; a list the engine would refuse waits and says why), and nothing restarts Carrier.
The file is read again just before writing, a kept repo's entry is written back as it was (including anything the app does not show) and a new one is only its name, so the two tabs never overwrite each other's keys.
When the engine reads the saved file and refuses it, it keeps the settings it had, so what was just saved (a repo watched, a role changed) is not in use yet whatever page saved it: the page then shows a banner and not the plain note (`refusalBanner`, `RefusalBannerView`), "Carrier is not using your latest settings", with the reason in words when it is a failover step of a role that repeats the role's own provider and model, another step or an undeclared provider (and Open Agents, where it is mended), the engine's own words kept folded under "What Carrier said", and Ask Carrier again.
Any other reason is shown as the engine says it, with no way to mend it from here.

A repository's screen is a group for each thing it says or does, in the order of what a person comes here for (`WatchingRepoScreen.swift`): Status (the epics and the last check), Ready for Carrier, Who works here, Repository (the project, the clone and GitHub) and, last and in a group of its own, Stop watching…, which asks first, with what happens to the repository's epics (they stop where they are and continue if it is watched again; nothing is deleted), and goes back to the list. Open on GitHub and Check again (turning while the doctor runs) are on the toolbar's capsule, and its name is the toolbar's title with `Watching` under it (and, when GitHub refused it or Carrier is stopped, why).

It has three cards.
It starts with its Status card (`CarrierCore/RepoStatus.swift`, fed with the list's row): the epics ready and running, the last check, the clone with `~` and Reveal (only when the clone exists), the repo on GitHub with Open and the project that has it as its origin, with Open project (or Add project…, which goes to the Projects page, when none has); a repo the running engine has not loaded, and every repo while Carrier is stopped, says "Carrier reads it when it starts" in place of the epics and the last check.
Under it, Ready for Carrier (`CarrierCore/RepoChecks.swift`, `repoChecks`, tested in `RepoChecksTests`) shows four rows from the checks of `carrier doctor --json` that are about the repo (their `repo` and `profiles`): Carrier can read it, Author can sign here, Reviewer can sign here and Solve is set up, each ok, failed with the doctor's reason and fix, or waiting.
A role's row is the repo's `can mint a token` check whose `profiles` holds the profile the role resolves to in that repo, so two roles of one identity show the same check; a check the doctor did not report (something before it failed) is waiting, never failed.
A failed sign row offers Use another identity (`RepoCheckRow.anotherIdentity`), which opens that role's screen in this repo (below); no other row offers it.
The doctor (`AppHealth.doctor`, shared with the Health tab) runs when the page opens and on Check again, never in the background; while it runs or when it could not answer, a line says so and the rows wait.
`--fixture` answers the run with `Tests/Fixtures/doctor.json` (copied into the fixture home), which carries the new fields: `acme/web` all ok, `acme/api` with a failing reviewer and no Solve labels, the long-named repo unreadable.
Who works here is the Agents page's rail of roles (`EpicRail`, with `own` set; the repo's roles are `repoAgentsPage` in `CarrierCore/RepoRoles.swift`: the global `agents` with the repo's own fields over them, and the Lead reviewer only when the global config has it, tested in `RepoRolesTests`): each role with its picture, what it does, its model and identity and a chip, Own when the repo has settings of its own for it and "Same as everywhere" when it follows Agents, and a chevron that opens the role's screen; the group's footer says every repository follows the roles of Agents unless it has its own settings.
A role's screen in a repo (`SettingsPlace(.watching, path: [repo, role])`, `Carrier/WatchingRole.swift`) is Agents' own with what a repo can set: its picture and who it works as, the strip "In an epic", Who (Identity: a profile of `profiles`, and Model: the account, model and effort from the same panel Agents uses) and Persona (name and prompt), and, when the repo has settings of its own, Reset to Agents. Each field says "Same as everywhere" with what it follows and is not written while it is left there; each one saves as it changes, with no Save (`CarrierCore/RepoRoleSave.swift`, `saveRepoRole`, tested in `RepoRoleSaveTests`). Skills and When it runs out of tokens are Agents' only: a repo cannot set them.
The save reads the file again, writes only `repos[].agents.<role>` with the fields set (texts trimmed, a model of only spaces and an empty persona not written, an entry that would be empty removed) and keeps every other key; Reset to Agents removes the role's entry.
A profile or account that is not declared (shown as missing) is refused before writing, in words.
Author and Reviewer on the same identity is accepted and the card says the signature will show it.
After a save the doctor runs again, and when the engine refuses the config its reason (the doctor's stderr from `Invalid config`, `DoctorState.refused`) is shown under the roles and in the Ready for Carrier note.
The fixture's `engine.json` (`fixtureConfig`) has the three fixture repos, the profiles and the three roles.

## Agents

The Agents page, in the Carrier group before Watching, has the three fixed roles, Author, Reviewer and Lead reviewer, as two kinds of screen, each a place of the window's history (‹ ›) as Providers and Dictation have: a first screen and one screen for each role, whose path is the role's name (`SettingsPlace(.agents, path: [role.rawValue])`; `Carrier/AgentsTab.swift` and `AgentsParts.swift`, model in `CarrierCore/AgentsPage.swift`, tested in `AgentsPageTests`; the views have no test).
The first screen is a status card (`agentsReadiness` in `CarrierCore/AgentsReadiness.swift`, tested in `AgentsReadinessTests`: whether Author, Reviewer and, when it is on, the Lead reviewer each have an identity, an account of `providers.json` and a model, with what is wrong said with the role's name and a button to open it; it says nothing of whether an account is signed in, which is the Providers page's answer), then How an epic runs, then Identities.
How an epic runs (`EpicRail`) is the three roles in the order an epic goes through them, one row of the form with a rail drawn through it: Author, then "Opens the pull request" and "↺ asks for changes, the author answers", Reviewer, then "When the review passes", Lead reviewer (the last stretch is dashed and says "Lead reviewer is off" while it is).
Each role is a button with its picture (`RoleAvatar`), what it does (`AgentRole.purpose`) and, at the right, its model and effort over its identity, "Off" for a Lead reviewer that is, or "Needs attention" when the card says something of it.
A role's picture is its identity's: a bot of Agent Forge shows the logo of its GitHub App (the registry has no avatar field, but each bot is a GitHub App and `avatars.githubusercontent.com/in/<appId>` is public, so `forgeBots` reads the digits-only `appId` and `forgeAvatarURL` builds the address; `ForgeAvatarStore` fetches it in a task of its own, so leaving the screen that asked does not cancel it, follows the system's URL cache, keeps what is an image of at most 2 MB, tries a failed one again after ten minutes and never fetches under `--fixture`), and with none (no `appId`, offline, not an image) its initials on a color made from its name (`roleInitials`); the person's gh login is their own GitHub picture (`ForgeAvatarStore.fetchUser`: the login comes from the chat host's `githubRepos` reply, is checked by `isGithubLogin` and the picture is `avatars.githubusercontent.com/<login>`, with the same rules as a bot's), a gray person while it is not there; an identity that is not there is a dashed square with a question mark.
The corner wears the mark of the account the role runs on, as a session's avatar does.
A role's screen starts with its picture, who it works as and its model, and a strip "In an epic" (Author ⇄ Reviewer → Lead reviewer) with this role marked and the others links to their screens (a role that is off says "· Off" in its button); the toolbar says the role's name and, under it, its model, effort and identity (`RoleRow.headline`), worded and drawn as a role that is on while the Lead reviewer is being turned on (`RoleRow.drafting`).
Its groups are Who, Persona, Skills and When it runs out of tokens.
Under Identity the Who group says that Author and Reviewer sign as one account, and why the list of bots is empty (a registry that is missing or does not read).
The Who group writes as you change it (`saveGlobalRole` in `CarrierCore/GlobalRoleSave.swift`, tested in `GlobalRoleSaveTests`): Identity, Provider, Model (on Return or leaving the field) and Effort (the five levels or Default) each write only that key of `agents.<role>`, with the file read again just before and every other key kept; choosing a bot adds `profiles.<name>` as `{ kind: "forge", agent }` once and reuses it afterwards, and the person's login uses the first `gh` profile or adds `gh`.
An empty model, a provider that is not an account, a bot the registry does not list, or a role that would be left without profile, provider or model is refused before writing, with the reason under the group; a profile that is no longer in the registry stays, marked missing, and is refused only when chosen again.
Create a bot… (`Carrier/CreateBotRow.swift`, in the Identities group of the first screen: a bot is the GitHub account any role can pick) opens Terminal on `agent-forge add` (`CarrierCore/ForgeTerminal.swift`, tested in `ForgeTerminalTests`): the command is from a closed list of one entry, quoted, nothing from the registry or the config is part of it, and the one-use script and the opener are the app's shared `openScript` helpers (under `--fixture` the opener only says what it would have run); the page reads the registry again whenever the app becomes active, so the new bot appears without a refresh button.
The Persona group writes the persona as you change it (Persona name and Persona prompt on Return or leaving the field, `saveGlobalPersona` in `CarrierCore/RoleDetailsSave.swift`, tested in `RoleDetailsSaveTests`): either one alone or both, the texts trimmed, a blank field left out and both blank removing the persona, and a name over 40 characters or with a line break, or a prompt over 4000, refused before writing with the reason under the group (the limits are `RoleFields.problems`, the repo form's).
The When it runs out of tokens group writes `failover.roles.<role>` (`saveGlobalFailover`, same file): Switch automatically on shows Try first (a declared provider and an optional model, written once it has a provider) and Then try (optional, None takes it back), off removes the role's list; a step that repeats the other or is the role's own provider and model is refused with its position, and the steps a file has after the first two are kept when those are edited.
Changing the role's own provider or model onto the one a failover step names drops that step (`dropFailoverSteps` in `saveGlobalRole`, tested in `GlobalRoleSaveTests`): falling back to the account that ran out is no fallback, and the engine refuses the file with such a step. The others stay in their order, and a list left empty goes with the role's key, which is Switch automatically off; a step with no model is another model's and stays.
`agentsPage` turns `engine.json`, `providers.json` (or the three default accounts) and the names of the Agent Forge registry (`forgeBots`, from `$AGENT_FORGE_CONFIG`, else `$XDG_CONFIG_HOME` or `~/.config` plus `agent-forge/agents.json`: names and GitHub App ids, never a key; a registry that is missing or does not read gives no bots and a note, not an error) into a row per role: identity (a bot the registry has, the person's own gh login, or missing when the profile is not in `profiles` or its bot is not in the registry, and then it stays in the file), provider (marked missing when it is not an account), model, effort, persona and the failover steps of `failover.roles.<role>` (the page shows a first and a then step and says how many more the file has).
The Skills group shows what the engine runs in each stage of the role (`AgentRole.stages`): the Author's First pass (`ship`) and Answering a review (`code-resolve`), and the Reviewer's Review (`code-review`) and Post findings (`code-post`), each with "Runs as" and the skill spelled the way its account's harness is told to run it (`/ship` for Claude and Antigravity, `$ship` for Codex, `skillInvocation`).
They are not editable yet: the value is a quiet box with "Default" before it, and the footer says choosing another comes with a later version of the engine (the engine reads `skills` from `engine.json`, but the app does not edit them yet, and it shows the defaults).
`AgentRole.stages` is the engine's default skills, and `AgentsReadinessTests` reads them from the contract fixture and fails when the two disagree.
The Lead reviewer has no stage, because the engine does not run it yet (`agents.leadReviewer` is read and kept and nothing uses it), and its Skills group says so.
The Lead reviewer has the Use a lead reviewer row on top, and while the file has no `agents.leadReviewer` the row says Off and the rest of its page is dimmed and not usable.
Turning the switch off removes `agents.leadReviewer` and `failover.roles.leadReviewer` and keeps every other key (`turnLeadReviewerOff`), and the row says so; turning it on writes nothing: the page asks for an identity, a provider and a model (`LeadReviewerDraft`, kept in the page) and, once the three are chosen, writes the whole role in one go through `saveGlobalRole` (`turnLeadReviewerOn`), so the file never holds a half role (`CarrierCore/LeadReviewerSwitch.swift`, tested in `LeadReviewerSwitchTests`).
When Author and Reviewer resolve to one account by the engine's rule (`sameAccount`: two gh logins, or two profiles of one bot) the status card and the Who group say the signature will show it.
A config that is missing or is not a JSON object says the engine is not configured.
Under `--fixture` the app sets `AGENT_FORGE_CONFIG` to `agent-forge.json` in the fixture home (`fixtureForgeRegistry`: the three bots of the roles, two with a made-up `appId`, and a spare one), and `fixtureConfig` has failover steps for the Author and the Reviewer.
Use in an agent… on a signed-in account of the Providers page that no role names, and Open Agents on the Watching page (in Who works here, and next to Use another identity on a failed "can sign here" check), open this page.

## Behavior

The Behavior tab (in the Carrier group, before Engine, "How Carrier runs epics"; `Carrier/BehaviorTab.swift`, model in `CarrierCore/EngineConfig.swift`) edits eight values of the config file in place, in three groups drawn from the model in `CarrierCore/BehaviorPage.swift` (`behaviorGroups`, tested in `BehaviorPageTests`): Pace (`pollIntervalMinutes`, `limits.maxConcurrentEpics`), When something goes wrong (`limits.maxReviews`, `limits.maxExecutionRetries`, `limits.maxExecutionHours`, with Unlimited) and Housekeeping (`finishedWindowDays`, whole days from 1 to 30, 15 by default; `limits.githubCallTimeoutSeconds`; `logLevel`).
They are text fields that check the engine's rules as you type; a value equal to the engine's default is taken out of the file, and nothing else in the file is touched (the app never makes the file: without a JSON object there it says the engine is not configured).
Every change the engine would accept is written to the file at once (`autosave`; a value still being typed, or one the engine would refuse, waits and says why) and the engine is asked after the person pauses for about 700 ms, or at once when the page closes or the app quits, the page's header says nothing when it saved, and says why it could not save or that the file cannot be read, in orange (the page passes it up with `SettingsHeaderNoteKey`), and the Reset group at the end of the page (`behaviorReset`, one card, "Restore the defaults") puts the engine's own defaults back after a confirmation (they are saved the same way, and a value equal to its default is taken out of the file).

## Engine

The Engine page (the last of the Carrier group, "How the app runs Carrier") holds what the app starts Carrier with: its Starting group (`CarrierCore/EnginePage.swift`, `engineGroups`, tested in `EnginePageTests`) has "Start Carrier when the app opens" (`engine.startOnOpen`) and "Ask before stopping Carrier" (`stop.confirm`, on by default; it used to be General's), its Programs group (`engineGroups`, also in `EnginePage.swift`, with `EnginePrograms` as the paths and versions it is given, tested in `EnginePageTests`; the versions are what `carrier --version` and `node --version` print, read by `Carrier/ProgramVersions.swift` when the page opens, a program changes or a detection ends, through `shortRun` in `Carrier/ProcessRun.swift`, also used by the chat host's version check; "Reading version…" while they run, and a problem when one does not answer or nothing runs at the `carrier` path) shows `carrier` with its path and version, `node` the same, and the `PATH` the engine and the chat host run with (read only; "Not found" in place of a path), then "Look for the tools again" with the button Detect.
"Use another…" on the `carrier` row opens a file picker; while one is set the row says it is the person's own and offers "Use the Homebrew one"; its GitHub identity group has "Carrier acts on GitHub as" (`orchestratorProfile` of `engine.json`, `CarrierCore/EngineIdentity.swift`, `saveOrchestratorProfile`, tested in `EngineConfigTests` and `EnginePageTests`): the default (the author's identity) first, then the file's `profiles`, the default taking the key out of the file and every other key kept (saved with sorted keys); a profile the file names but does not declare stays on the list and shows in orange until another is picked; a refused save is that row's problem, said to VoiceOver; a file that cannot be read leaves the row disabled and says so in orange, and one that is not a JSON object is not changed; the engine is asked to reload after the write like every other writer's, so the choice applies without a restart, and its answer is the page's `ReloadNote`.
Its Files group (`engineGroups` again) has "Carrier folder", "Logs" and "Start log", each with its path (`~` for the home folder) and a Reveal or Open button, disabled with "Not created yet" while the path is missing.
The app finds `carrier` by itself (`carrierPath`): the one chosen with "Use another…" when it is set (a path as typed, `~` expanded; one ending in `.ts` or `.js` runs under `node`), else the Homebrew one when it is executable (`/opt/homebrew/bin/carrier`, or `/usr/local/bin/carrier` in the Intel app), else it is missing.
On the first launch (nothing saved in user defaults) the app asks the user's shell once, `zsh -ilc` with markers around what it prints and a 10 second limit, for `node` and the `PATH`, without asking the person; Detect repeats the run.
With saved values the shell is started again only when the person presses Detect, or when a start of the engine or the chat host ends with `spawn <tool> ENOENT` in its log (a folder added to the PATH after the app asked, such as pnpm's): the start is then tried once more with what the shell says now, and the alert says the tool is not on the PATH of the shell either when that was not it.
The `PATH` the engine will get is the detected one (the system's when the shell gave none) with node's directory first and Homebrew's `bin` (`/opt/homebrew/bin`, or `/usr/local/bin` in the Intel app) at the end when it is not in it.
A banner on every section says what Start Carrier lacks, or that it is looking for it, and is not shown when all is found; when something is missing it says to use "Use another…" and then Detect under Programs on the Engine page, and its own button is Detect; the banner's model is `CarrierCore/EngineTab.swift`.
