# Carrier macOS app

Status: spec

## Problem

The only way to follow Carrier today is the ANSI panel of the terminal where it was started. It cannot show anything at a glance while Diego works in another window, it cannot notify him when an epic needs him or is ready to test, and it shows the epic but not how its issues are going: Carrier does not keep the progress of an epic's slices, because the agent running `ship` works them inside its own session. The people it matters to are those who run Carrier on their own Mac; on a remote machine the terminal panel is already right and stays as it is.

What is wanted to see is the flow of each epic: its stage, the review rounds, the state of its issues (how many are closed out of the total) and what blocks it, as the terminal shows it now plus the issues. It is not a preview of the app the agents are building.

## Solution

A native macOS app, `Carrier.app`, built from source in this repo under `macos/`, with two surfaces: an icon in the menu bar and a window. It is for Diego and whoever clones the repo and runs it locally: not signed by a developer, not notarized, no auto-update. It only operates and observes; `carrier init` and `carrier doctor` stay in the terminal.

The icon is a count and a bar. The number is how many epics are being worked, the bar fills with the slices closed over the total of those epics, and while they run a short segment bounces over the unfilled part so it reads as alive. Stopped is the same icon faded, idle is the empty bar with no number, and an orange dot in the corner marks that an epic needs Diego or that there is a problem, without a separate alarm state. The detail is in the window, not in the icon. Clicking the icon opens a plain menu: the state in one line, Start or Stop Carrier, Pause or Resume taking epics, Check GitHub now, Open window and Quit.

The window shows what the terminal panel shows (uptime, repos watched, slots, the next check, a card per running epic with its stage chain, review round, blockers, time in stage, last activity and now its slices closed out of the total, the queue, the epics that need Diego and those ready to test, and the problem when GitHub is stalled) and lets him open an epic's PR or issue and read what its agent is doing. It does not act on an epic (cancel, reactivate, change stage): reactivating is still the `solve:epic:ready` label. The app sends a native notification when an epic goes to `needs_human` or `ready_for_test`; a problem (GitHub down, a profile rejected) only turns the icon's dot on and shows in the window. Start Carrier is always an explicit button, never automatic when the app opens, because Carrier runs agents with the user's permissions. Stop Carrier asks for confirmation when epics are running, since it interrupts their agents (they resume on the next start), and stops straight away when nothing is.

The app does not own the engine ([0005](../adr/0005-engine-independent-of-the-macos-app.md)). `carrier` runs by itself and, once the engine is up, opens a control socket at `orchestrator/control.sock`. Over it the app asks for the panel snapshot as JSON, pauses or resumes intake, asks for a GitHub check, reads the last lines of an execution's output and stops Carrier. The app is a client of any live instance, including one started from a terminal, and can start one that is detached from it. Closing or crashing the app leaves Carrier running; stopping is an explicit command. The app never reads SQLite: the snapshot JSON is the only contract, and a golden file of it, generated by the engine's tests, is decoded by the app's tests, so a change on either side breaks the other's build.

The slice progress goes into the snapshot, so the terminal panel gets it too. Every issue GitHub returns over REST carries `sub_issues_summary` (`total`, `completed`), but the engine's poll does not see it: it lists only the queued epics (`solve:epic:ready`) and drops the field. So the engine gains one more list per repo per poll over the open `solve:epic` issues, about 12 requests an hour per repo at the default interval, with the Issues read permission both Forge bots already have ([research](../research/macos-app.md), section 1). The number shown is the one GitHub reports; if GitHub counts a sub-issue closed as not planned or a nested one differently from what a person expects, that is GitHub's definition and Carrier does not redefine it.

Stopping through the socket has to be the same shutdown as Ctrl+C. Today that shutdown is an anonymous closure inside the SIGINT handler, SIGTERM and SIGHUP are not handled (they act as a crash: executions stay `running` with no end time), and it can wait forever on an orphaned agent child that keeps the agent's pipes open ([research](../research/macos-app.md), section 4). So the shutdown becomes one named function that Ctrl+C, SIGTERM, SIGHUP and the socket's stop all call; it answers before the process exits, it has a time limit, and a second signal during it exits at once. The terminal gets all of this too.

The socket is private to the user: created with mode 0600 inside an `orchestrator/` folder of mode 0700, removed when Carrier closes (before it releases the instance lock), and a leftover one from a crash is replaced only after Carrier holds that lock, which is what makes it certain to be stale. macOS limits a socket path to 104 bytes and some Node versions truncate a longer one silently, so the engine checks the length itself; when the path does not fit, Carrier still starts, logs a warning, opens no socket, and `carrier doctor` reports it, so a long shared root never breaks the terminal ([research](../research/macos-app.md), section 5).

The app finds Carrier through a setting, not a shell: the absolute path of `carrier` and of `node`, the `PATH` to run them with, the config path (by default `$CARRIER_HOME/config.json`, else `~/.carrier/config.json`, as `carrier` itself resolves it) and the shared root, filled once by asking the user's own shell (`zsh -ilc`) and editable. An app started from the Dock does not see the shell's `PATH`, and a plain login shell silently finds a different Node than nvm's ([research](../research/macos-app.md), section 2). To start Carrier the app runs `node <carrier> --config <config path>` (Carrier has no `run` subcommand: the orchestrator is the default command) with that `PATH`, which is also the one the agent CLIs get, in its own session so it outlives the app, with no terminal, so Carrier already uses its plain output and needs no new mode. The shared root, where `orchestrator/` and the socket live, is the `root` of that config file (default `~/.solve`, with `~` expanded), read by the app and editable in the same settings. If the socket does not appear within 15 seconds, or the process exits first, the app shows the tail of the start log.

The app is `Carrier.app`, built by `macos/build-app.sh`, which compiles with SwiftPM, wraps the binary in an `.app` and signs it ad hoc; notifications need the signature and the bundle identity, and the Command Line Tools are enough, Xcode is not ([research](../research/macos-app.md), section 3). It uses a plain AppKit lifecycle, not SwiftUI `App` scenes: with a `MenuBarExtra` that is not inserted SwiftUI can end the app on its own, `openWindow` outside a view does nothing, and the first prototype broke on use for exactly those reasons. The icon is an `NSStatusItem` drawn with Core Animation layers on its button, and the menu is a plain `NSMenu`; the window is SwiftUI inside a plain `NSWindow`. Swapping the icon image on every frame costs 10% to 22% of a core and resets an open menu, and uncapped layers move the cost into `WindowServer` (8% to 55%); an animation capped at 20 fps with `preferredFrameRateRange` costs 0.4% in the app and about 4 points in `WindowServer` ([research](../research/macos-app.md), sections 6 and 7, and the [prototype](../research/spike-macos-app/)). The layer that draws the icon must not take the clicks the button needs to open its menu, the window is always preceded by `NSApp.activate`, and the icon's colours are resolved against the button's appearance and set again when it changes, because a layer does not get the tint an image gets.

What lost: Tauri or Electron (they reuse TypeScript, but they are not native and weigh more); a SwiftUI `App` lifecycle and `MenuBarExtra` for the menu bar part; animating by swapping the image, and a continuous animation at the display's rate; a ring with the count and a number in a box for the icon (the ring is harder to read next to a count, the box shows no progress); the app launching `carrier` as a child over stdio, which ties the epics' life to a window; the app only attaching to an engine someone else started, which gives up controlling the process from a window; rewriting the engine in Swift; the app reading SQLite, which couples Swift to the schema and gives no way to send commands; a separate repo for the app, because the snapshot contract would need two versions kept in sync.

## Scope

Engine, in TypeScript:

1. Diego presses Ctrl+C, sends SIGTERM, or closes the terminal (SIGHUP), and Carrier stops through the same shutdown: executions are marked interrupted with their sessions saved, epics stay running, the lock is released and nothing is written to GitHub. SIGTERM and SIGHUP no longer behave as a crash.
2. A shutdown that cannot finish because an agent's orphaned child holds its pipes ends after a time limit instead of waiting forever; the epics stay running and the next start resumes them.
3. A second signal while Carrier is shutting down exits at once.
4. A client connects to the control socket of a running Carrier and receives a hello with the protocol version and the process id.
5. The client asks for the snapshot and gets the panel's data as JSON, slice progress included.
6. The client pauses and resumes intake and asks for a GitHub check, and the next snapshot reflects it.
7. The client reads the last lines of an execution's output by its id, which must be a UUID.
8. The client stops Carrier, receives the reply before the process exits, and sees the connection close.
9. A line that is not JSON, an unknown command, an extra field, a wrong type, an id that is not a UUID, or a line over 16 KiB gets an error reply and never reaches the engine or the file system; an oversize line also closes that connection.
10. The socket is reachable only by the user, a socket left by a crash is replaced only after the instance lock is held, it is removed on close before the lock is released, and a path that does not fit makes Carrier start without a socket, warn in the log and show in `carrier doctor`.
11. On every poll the engine reads `sub_issues_summary` of the open epics of each watched repo, and each epic in the snapshot carries `slices` (`done` and `total`), or `null` until it is known.
12. When that read fails the last known values stay and the poll goes on as before.
13. The terminal panel shows each running epic's slices closed out of the total.

The app, in Swift:

14. Whoever clones the repo runs one script in `macos/` and gets a signed `Carrier.app` that opens with only the Command Line Tools installed.
15. On first launch, and from a settings pane afterwards, the app finds `carrier`, `node` and the `PATH` by asking the user's shell, takes the config path and the shared root from where Carrier keeps them, shows what it could not find, and lets the person edit each value.
16. The app finds a running Carrier through the socket, started from a terminal or by the app, and shows "stopped" when there is none, the socket is stale or the protocol version is not one it understands.
17. Diego presses Start Carrier and the app starts it detached; if it does not come up in 15 seconds, or exits, the app shows the tail of the start log.
18. Diego presses Stop Carrier and the app asks for confirmation when epics are running, and stops straight away when none are.
19. Diego pauses and resumes taking epics and asks for a GitHub check from the menu and the window.
20. The icon shows stopped, idle, working with the count and the filled bar, and the orange dot when an epic needs Diego or there is a problem, in light and dark appearance.
21. While epics run, a segment bounces over the bar at a capped 20 fps, the app does no work per frame, and the menu can be opened and its options chosen while it moves.
22. The window shows the panel's contents with each epic's slices, and opens an epic's PR or issue.
23. Diego reads what an epic's agent is doing from its card, refreshed every two seconds while it is open.
24. A native notification appears when an epic goes to `needs_human` or `ready_for_test`; the first snapshot after connecting never notifies for what was already there.
25. Closing the window or quitting the app leaves Carrier running; a menu bar app with no windows stays open.

## Decisions

Engine and app talk over one socket with newline-delimited JSON, one value per line in each direction. The app pulls: it asks for the snapshot every second while connected and retries the connection every three seconds while it is not, and it builds its notifications by comparing consecutive snapshots. There are no pushed events in this version. The engine validates every request with a strict schema before acting on it (an allowlist of commands, strict objects, a UUID for the execution id); it was run against empty, wrong-typed, oversized-number, inherited-name, `__proto__` and path-traversal inputs and rejects all of them.

```ts
const id = z.number().int().positive();
export const request = z.union([
  z.strictObject({ id, cmd: z.enum(['snapshot', 'pause', 'resume', 'checkNow', 'stop']) }),
  z.strictObject({ id, cmd: z.literal('tail'), executionId: z.uuid(), lines: z.number().int().min(1).max(500) }),
]);
type Hello = { event: 'hello'; protocol: 1; pid: number; startedAt: number };
type Reply = { id: number; ok: true; data?: unknown } | { id: number | null; ok: false; error: string };
```

The socket module reuses what the interactive panel already has: the snapshot function and the `controls` (`poll`, `setPaused`, `logs`). It lives in `src/control/`, starts in `startCarrier` once the engine is up, and is closed in `close()` before the lock is released. The shutdown becomes one named function in `src/terminal/cli/interrupt.ts`, idempotent, called by SIGINT, SIGTERM, SIGHUP, the `q` key (which already signals itself) and the socket's `stop`; its time limit is 20 seconds, the agent runner's 5 second grace plus a margin, after which it logs an error, closes and exits with code 1. A second signal exits with 130. `orchestrator/` is created with mode 0700 and an existing one is tightened. The socket path is `orchestrator/control.sock` and must fit 103 bytes.

Slice progress is read by a new method of the GitHub port that lists the open `solve:epic` issues of a repo (one paged request, `sub_issues_summary` optional in its schema because GitHub does not require it) and is kept in the engine's memory, by repo and issue, until the next poll; it is not stored in SQLite, so after a restart it is `null` until the first poll finishes. `PanelEpic` gains `slices: { done: number; total: number } | null`. The icon's bar uses only the running epics with known slices; with none known it is empty and the segment still moves.

The app is a SwiftPM package in `macos/` for macOS 26 or later with a library target `CarrierCore` (the snapshot model, the socket client and its framing, the icon state, the notification comparison, the setup detection and its parsing) and an executable target for the AppKit shell, and tests with Swift Testing, which the Command Line Tools include (XCTest they do not). The detached start uses its own session for the process, stdin from `/dev/null` and its output in `orchestrator/logs/app-start.log`. The detection runs `zsh -ilc` with markers around its output and a 10 second limit, and the `PATH` it gives the engine is the detected one with node's directory first. The bundle identifier is `dev.ashulab.carrier`, and the shell checks it exists before touching the notification centre, because without a bundle that call aborts the process.

Testing seams, story by story:

- Stories 1 to 3: the shutdown's existing seam, a real process run from a fixture (`interrupt.test.ts` and `interrupt-holder.fixture.ts`), now sent SIGINT, SIGTERM and SIGHUP, plus a fixture whose runner never finishes stopping, with the time limit injected short. It observes exit codes, execution and epic rows and the lock, as the existing tests do.
- Stories 4 to 10: a real Unix socket in a temporary folder with a fake snapshot and fake controls, driven by a plain client through the same lines the app sends. It covers every command, the invalid inputs, the oversize line, the file modes, the stale socket against a held and a free lock, the removal order, and a path that does not fit. One test in `compose.test.ts` with fake dependencies checks that `startCarrier` opens the socket and that `stop` runs the shared shutdown. The `carrier doctor` line is tested in `doctor.test.ts`.
- Stories 11 and 12: the engine's seam with the fake GitHub in `src/orchestration/fake.ts` (a poll fills the progress, a failing read keeps it), `snapshot.test.ts` for the field, and the adapter's test against a recorded GitHub response in `github.test.ts`, including an issue with no `sub_issues_summary`. Verified once with a Forge bot token against a private repo as a separate integration, outside the usual suite.
- Story 13: `dashboard.test.ts` and `plain.test.ts`, by their output, as for the rest of the panel.
- The contract between engine and app: a test in the engine writes the snapshot to `macos/Tests/Fixtures/snapshot.json` and fails when the file differs, with a flag to regenerate it; `CarrierCore`'s tests decode that file.
- Stories 15, 16, 20, 24: pure code in `CarrierCore`, tested with Swift Testing: the parsing of the detection's output, the client against a small server in the test, the icon state from a snapshot, and the notification comparison, including that the first snapshot only seeds.
- Stories 17, 18, 19, 22, 23: the logic that decides (when to confirm, the start's outcomes) is in `CarrierCore` and tested; the buttons and the window have no automated tests.
- Stories 14, 21, 25: no automated tests, they are the AppKit shell. A launch flag runs the menu's actions from code and logs each step, as a smoke check that the process stays alive. What only a person with a screen can see is a checklist in the ticket for Diego: that the menu works with real clicks while the icon moves, that the count and the bar read well in light and dark, that re-signing after a rebuild does not make macOS ask for the notification permission again, that the capped animation keeps its rate on a 120 Hz display, and that on a second display the icon shows its static state; the static fallback icon RunCatNeo draws there is added only if that last check fails.
- Stopping with the real agents (Claude, Codex, `agy`), including whether real Codex orphans keep the agent's pipes open, is a separate integration run by hand against real tools, like the other real-agent checks, and does not run in the usual suite.

## Out of scope

Acting on an epic from the app (cancel, reactivate, change stage). Setting Carrier up from the app, the `init` wizard and `doctor`: wanted later, not now. Distribution to other people: signing, notarization, auto-update, opening the app at login and starting Carrier by itself. History of past epics in the app, since it does not read SQLite and shows "stopped" when the engine is not running. A preview of the app the agents are building. Linux and Windows. Changing how the terminal panel works beyond showing the slices and the shutdown. Notifications for a problem. Events pushed from the engine. A SwiftUI panel instead of the plain menu for the icon's dropdown, which would show the epic cards without leaving the menu bar: worth deciding once the window's content settles.
