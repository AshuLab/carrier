# Carrier.app

Menu bar app for Carrier. A SwiftPM package for macOS 26 or later: `CarrierCore` (library), `Carrier` (the AppKit shell), `CarrierCoreTests` and `CarrierTests` (Swift Testing). Building needs **Xcode** (see Toolchain).

## Toolchain

Xcode is required, not just the Command Line Tools. With the macOS 27 SDK SwiftUI's `@State` is a macro whose plugin ships only with Xcode, so with only the Command Line Tools selected `swift build` fails with `external macro implementation type 'SwiftUIMacros.StateMacro' could not be found`. Install Xcode and select it:

```sh
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer   # or: export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
xcode-select -p                                                  # should print the Xcode path, not .../CommandLineTools
```

`build-app.sh` checks this first: with the Command Line Tools selected it prints how to select Xcode and exits 1 without building.

Workaround, unsupported: `swift build --sdk /Library/Developer/CommandLineTools/SDKs/MacOSX26.sdk` does build the package under the Command Line Tools (verified), because the older SDK has no `@State` macro. `swift test` that way was not verified and `build-app.sh` does not use it.

## Build and open

```sh
cd macos
./build-app.sh          # release build wrapped in Carrier.app (bundle id dev.ashulab.carrier), signed ad hoc
./build-app.sh --open   # same, then opens it
open Carrier.app
```

`Carrier.app` is an app of the Dock: it has its icon there (`Resources/AppIcon.icns`, made by `swift scripts/make-icon.swift`), opens on its window, keeps its menu bar (Carrier, File, Edit, View, Window, Help: `MainMenu.swift`, the Edit menu being what gives ⌘C and ⌘V to a text field), remembers where its window was, stays running when the window is closed and opens it again from the Dock icon (whose menu has New Session and Open Window). Besides, it shows one menu bar item at the right of the screen. Its menu opens with a heading (a dot, green while running, orange when intake is paused, an epic needs you or there is a problem, grey when stopped; a bold title and the epic and slot counts), then, while Carrier runs, the epics (needs you, running, waiting, ready; at most twenty, then "… and N more") with a state glyph, a secondary line and a badge, rebuilt each time the menu opens; the Settings switch "Show epics in the menu" (user default `menu.showEpics`, on by default) turns the list off, and choosing an epic opens the window on its section. Then only the controls that apply: while Carrier is stopped, Start Carrier (enabled only when the engine is configured and the settings have `node` and `carrier`; it says what is missing otherwise); while it runs, Pause intake (Resume intake while paused), Check GitHub now and Stop Carrier, which asks first when epics are running, since it interrupts them (they resume on the next start), and stops straight away when none are. Last, Open window (⌘O), Settings… (⌘,) and Quit Carrier (⌘Q). The line comes from Carrier's control socket, `<folder>/engine/state/control.sock`, where `<folder>` is the Carrier folder: `CARRIER_HOME` from the app's own environment, else `~/.carrier`. The app finds the engine from the folder alone, with no config file read, and has no setting for a config path; it works the folder out again at each connection attempt. The engine's config is `<folder>/config.json`, and while that file does not exist the Carrier home and the Carrier section of the sidebar say that the engine is not configured (with nothing to do about it here: the setup wizard makes the file) and Start Carrier is off, with that as the reason. The app asks for the snapshot every second while connected and tries to connect every three seconds while not. Check the signature with `codesign --verify Carrier.app` and `codesign -dv Carrier.app` (it should say `Signature=adhoc`).

## Settings

The menu's Settings… opens the values the app starts Carrier with: `carrier`, `node` and the `PATH`, each editable and marked "not found" when empty. On the first launch (nothing saved in user defaults) the app asks the user's shell once, `zsh -ilc` with markers around what it prints and a 10 second limit, for `carrier`, `node` and the `PATH`. "Detect again" repeats the run. The window's Settings screen (sidebar, bottom) shows the same three values as the Engine tab; a banner on every tab says what Start Carrier lacks, or that it is looking for it, and is not shown when all is found, in which case the Engine tab is one line ("Carrier is ready to start", with Show paths and Detect again) and opens the paths only on request (`enginePathsShown`: they are open by themselves while something is missing or being detected); Choose opens a file or folder chooser, Reveal opens Finder, and the model is `CarrierCore/EngineTab.swift`. The Notifications tab (`CarrierCore/NotificationsTab.swift`, the logic in `CarrierCore/Notifications.swift`) has three groups. What to tell me: Needs you and Ready for test (user defaults `notify.needsYou` and `notify.readyForTest`, on by default) and A problem (`notify.problem`, off by default), which says once when the snapshot's `problem` text appears or changes, once when GitHub starts refusing a watched repo (until it recovers) and once when Carrier stops without the app having asked: Stop in the menu and the restart of the Behavior and Repos tabs call `NotificationWatcher.expectStop()`, which lapses after 30 seconds. How: Only when Carrier is not in front (`notify.onlyWhenAway`, on by default), which holds the banner back while the app is active (`shouldPresent`; the test notification always shows). There is no sound switch: sound and the style of the banner belong to macOS, per app, in System Settings › Notifications › Carrier. Permission shows what macOS says (`UNNotificationSettings`: allowed with banners, alerts or None and the sound on or off, denied, not asked, or only from `Carrier.app`), Open System Settings (always, to change those), Allow (when it has not been asked) and Send a test, which says why instead when macOS would swallow it. A click on a notification opens the window, on the epic when it is about one (the repo and issue travel in the notification's `userInfo`; the delegate is attached at launch so a click on an older notification works too). There are no General or Menu bar tabs since the Settings screen has these four: their models (`CarrierCore/GeneralTab.swift`, `CarrierCore/MenuBarStore.swift`) and views stay in the code, but nothing in the app changes Open at login, Ask before stopping Carrier (`stop.confirm`, on by default), the icon style, the animation or "Show epics in the menu" (`menu.iconStyle`, `menu.animate`, `menu.showEpics`) any more; they keep their defaults, or what was saved before. The Behavior tab (`Carrier/BehaviorTab.swift`, model in `CarrierCore/EngineConfig.swift`, footer rules in `CarrierCore/BehaviorSave.swift`) edits eight values of the config file in place, in four groups: Rhythm (`pollIntervalMinutes`, `logLevel`), Finished epics (`finishedWindowDays`, whole days from 1 to 30, 15 by default), Capacity (`limits.maxConcurrentEpics`, `limits.maxReviews`) and Agent runs (`limits.maxExecutionRetries`, `limits.maxExecutionHours`, with Unlimited, and `limits.githubCallTimeoutSeconds`). They are text fields that check the engine's rules as you type; a value equal to the engine's default is taken out of the file, and nothing else in the file is touched (the app never makes the file: without a JSON object there it says the engine is not configured). The engine reads them only when it starts, so with Carrier stopped the button is Save, and with it running there are Save and restart and Save only; a restart (Stop, wait for the socket to go, Start Carrier) asks first only when epics are running and `stop.confirm` is on, and is off while Start Carrier lacks something. The Repos tab (`Carrier/ReposTab.swift`, model in `CarrierCore/RepoList.swift` and `CarrierCore/AvailableRepos.swift`) lists the repos in the config file's `repos` with a dot (green ok, red when GitHub refused it, grey when new or Carrier is stopped), the last check or the error and the epics each has, from the snapshot's `watched`, `epics` and `queue`. Add repo opens a picker with the repos the engine's gh login can push to, grouped by owner, with search; it asks Carrier for them with the `availableRepos` request (a capability in the hello: an engine without it, a stopped one or a GitHub failure each show their own message, and there is no typing a name by hand). The list is loaded a page at a time, 30 repos each, newest push first: while the engine says there is more (`hasMore`) the picker shows a "partial list" notice and a Load more button that appends the next page (the model is `AvailableReposList`; Search filters what is loaded), and a page that fails after the first keeps what is loaded, says so under the list and the button asks for it again. An engine whose hello lacks `availableReposPaged` is asked once, without `page`, and shows that list with no notice and no button. A repo already watched shows ticked and off, and one whose folder name matches another watched or ticked repo is off with the reason. The ✕ on a row asks first, with what happens to the repo's epics (they stop where they are and continue if it is added again; nothing is deleted); the only repo cannot be removed. Changes are a draft until Save and use the Behavior tab's footer (Save, or Save and restart and Save only with Carrier running, and the same question before a restart that interrupts epics). The file is read again just before writing, a kept repo's entry is written back as it was (including anything the app does not show) and a new one is only its name, so the two tabs never overwrite each other's keys. With saved values the shell is never started. The `PATH` the engine will get is the detected one with node's directory first.

## Start Carrier

Start Carrier (the menu item, and a button in the window while Carrier is stopped) runs `node <carrier>` with that `PATH` and `CARRIER_HOME=<folder>` (the engine finds its config, state and logs from the folder, so there is no config path to pass), in its own session (`posix_spawn` with `POSIX_SPAWN_SETSID`, so quitting the app leaves Carrier running), stdin from `/dev/null` and stdout and stderr in `<folder>/engine/logs/app-start.log`, which it creates (with mode 0700) when missing. It is never started on its own when the app opens, unless the person turned on "Start Carrier when the app opens" on the Engine tab's ready card (user default `engine.startOnOpen`, off by default): then, at the first state the monitor delivers after launch, the app starts Carrier once when that state is stopped and Start Carrier is enabled (so never while the engine is not configured), never under `--fixture` (`shouldStartOnOpen`; the wiring in `AppDelegate` has no automated test, as it would start the real Carrier). When the control socket answers within 15 seconds the state becomes running (the next connect attempt shows it, within 3 seconds); when the process exits first, or 15 seconds pass without the socket, an alert shows the end of `app-start.log`. A second press while it starts does nothing. The decision and the command line are in `CarrierCore/StartCarrier.swift`; the spawn and the alert have no automated test. The self-test only checks the start (what it would run), as it does for Stop.

The chat host does not need the engine, so the app starts it on its own terms. Every time the app opens, once the settings are known (and again when the Settings window closes), it looks at the host's socket, `<folder>/chat/state/chat.sock`, and starts the host when nothing answers, not only when a session is created: the host runs no agent until a session exists, and the sessions in the sidebar are what it holds. `<folder>` is the Carrier folder: `CARRIER_HOME` from the app's own environment, else `~/.carrier`. The host needs `node` and `carrier` from the settings and nothing else: no config path, no engine config. It runs `node <carrier> chat-host` with the same `PATH` and `CARRIER_HOME=<folder>`, in its own session, stdin from `/dev/null`, output in `<folder>/chat/logs/app-start.log` (the `chat/` folder with mode 0700), waits 15 seconds for the socket and shows an alert with the end of the log when the process exits first or the socket does not come; a `chat.json` the host refuses (see [configuration](../docs/configuration.md#chat-configuration)) is shown that way, with the host's message naming the key. A second request while it starts does nothing, and under `--fixture` it never starts (the fake host answers). Because the folder comes from the app's environment, a build run from a terminal with `CARRIER_HOME=/tmp/scratch` starts its host in the scratch folder and never touches the real sessions in `~/.carrier` (the guide is in the [README](../README.md#developing-against-a-throwaway-folder)).

When `node` or `carrier` is missing the app opens with no alert. The Sessions section of the sidebar and the Sessions home say what is missing ("The chat host cannot start", "The app did not find carrier. Install it or set its path in Settings.") until the settings have it. Creating a session while it is missing keeps the alert, which names what the settings lack, because there the person asked for something that cannot happen. The decision, the command line and the notice are in `CarrierCore/StartChatHost.swift` (`chatHostMissing`, `chatHostAtOpen`, `startChatHostCommand`, `chatHostNotice`); `Carrier/ChatHostStarter.swift` reuses the engine's spawn and alert, and neither the wiring nor the views have an automated test.

When a host answers, the app asks the installed `carrier` for its version (`carrier --version`) once per launch and compares it with the version in the host's hello (`CarrierCore/HostReplacement.swift`, `hostReplacement`). If the host is older, no session is working or waiting for an approval and the sessions could be listed, the app stops it, waits up to 15 seconds for its socket to go and starts the installed one. If a session is working or waiting, it leaves the host running and the Sessions section and the Sessions home say "The chat host is older than Carrier", to restart it when the session finishes, because stopping a host closes its agents' processes and the work in them. A version that cannot be read on either side leaves the host alone and writes why to the app's stderr. A build under development keeps the same version, so there the host is restarted by hand (`carrier chat --stop`). The rule is tested; the replacement itself is not.

## Resume card

An epic stopped in needs-human shows a card between its title and its tabs (`CarrierCore/Resume.swift` builds it from the stuck kind, `Carrier/ResumeCardView.swift` draws it): the reason, one line of what resuming does for that kind, orange when a person's input is needed and red when something failed. It has a Resume button only when the engine's hello lists `resumeEpic` (`EpicStore.canResume`, read from the connection the epic poller uses); against any other engine the card shows the reason and the words with no button. Resume opens a sheet saying what will happen; confirming sends `resumeEpic` with the epic's repository and number on a connection of its own (the engine answers when the epic has started, up to 30 seconds), the button reads "Resuming…" until then and until the snapshot shows the epic out of needs-human, or stopped again after the answer (kept in `EpicStore.resuming`, so selecting another epic and coming back does not lose it), and a refusal (`unknown epic`, `not stopped`, `github unavailable`, `did not restart`) is shown in words in the card. The words and the request are tested; the sheet, the "Resuming…" state and the layout have no automated test.

## File icons

`fileIcon(path)` (`CarrierCore/FileIcons.swift`) is the one place that picks a file's icon: a bundled SVG from Material Icon Theme (MIT) for the languages in `bundledIconName`, else the category's SF Symbol. The SVGs and the upstream licence text are in `Sources/CarrierCore/Resources/FileIcons` (about 12 KB; release pinned in `SOURCE.txt`, notice in `THIRD-PARTY-NOTICES.md`, line in About). `build-app.sh` copies SwiftPM's `Carrier_CarrierCore.bundle` into `Contents/Resources` and fails when an icon or the licence text is missing from it.

## Test

```sh
cd macos
swift build && swift test
```

The shell's layers have no automated tests (`CarrierTests` only checks that the icon's layer host takes no clicks); the logic behind them is tested in `CarrierCoreTests`. Its smoke check is the self-test flag: it runs the menu's actions from code, one a second (pause, resume and check now are sent to a running Carrier, resume putting back the pause state it found; Stop is only checked, as it would end the Carrier under test), appends a line per step to the file and ends with a line saying the process was still alive.

```sh
./Carrier.app/Contents/MacOS/Carrier --selftest /tmp/carrier-selftest.log
cat /tmp/carrier-selftest.log   # last line: "end: process still alive ..."
```

With `--fixture` the log also has `rings, window open` and `rings, window closed` (`rings=N animating=M`): the spinning rings of running epics turn only while the window is visible and Reduce Motion is off, so the second line must say `animating=0`.

The app keeps running afterwards; quit it from the menu or with `osascript -e 'tell application id "dev.ashulab.carrier" to quit'`.

## Fixture mode

`--fixture [folder]` runs the app against a fake Carrier, so the window can be looked at with no engine. The app starts an in-process control server (`CarrierCore/FixtureServer.swift`) on a socket in a temporary folder under `/tmp`, points `CARRIER_HOME` at it and connects as to any Carrier. It answers `snapshot`, `sessions`, `events`, `epic` and `files` from the golden files in `Tests/Fixtures`, `fileDiff` with the first reply of `reply-filediff.json` for any file (so a file row of any card in the Files changed tab, a lane's included, opens to a fragment), pause, resume, check now, stop and `resumeEpic` with a plain ok that does nothing (so a Resume in the fixture is confirmed and the card stays on "Resuming…": the snapshot never changes), and anything else with an error. A second socket, `<home>/chat/state/chat.sock`, is a fake chat host (the app finds it through `CARRIER_HOME` like the real one at `<folder>/chat/state/chat.sock`): it answers `agents` and `list` from `chat-agents.json` and `chat-list.json`, `events` (by cursor, in pages, as the real host does) from the `chat-events-*.json` files, each naming its session: a finished conversation with markdown, a code block, tool calls, an approval and a failed turn (`chat-events-finished.json`), one with a message streaming (`chat-events-streaming.json`), and a Codex session waiting for an approval with four choices (`chat-events-approval.json`; its card answers through `answer`, which the fixture host records as an event, and the golden finished one has Claude's three); a listed session with no file has no events, one that is not listed is an error, and the worktree requests: `workspace` (by folder, from `chat-workspace.json`; a folder it does not list is a plain one), `fetch` (`chat-fetch.json`), `cloneRepo` (`chat-clone.json`, by `owner/repo`; one it does not list is refused), `createProject` (`chat-project.json`, by name; one it does not list is refused as taken), `githubRepos` (`chat-github-repos.json`, by page, the login on page 1 only; a page it does not list is refused), `suggestName` (cycling through `chat-names.json`'s suggestions) and `checkName` (free unless that file says why not), plus `open` (a session in memory, in a worktree when asked, refused as the host does for a folder that is not a repository, a branch it did not list and an invalid or taken name) and `send` (adds the message to the session's events); anything else is an error too. `setOption` changes the current value of an option a file lists, or is refused for one it does not list. So the Sessions + is enabled and a selected session shows a conversation. `folder` defaults to the copy of the golden files that `build-app.sh` puts in `Carrier.app/Contents/Resources/Fixtures`; give one when running without the bundle. The temporary folder is removed when the app quits. In this mode the menu also has "Empty states", a window listing the empty states (`CarrierCore/EmptyStates.swift`). It combines with `--selftest`. `--fixture-long-transcript` (with `--fixture`) answers `events` with a made-up transcript of 3,600 events (edits with diffs, passing and failing commands with output) instead of the golden file, to scroll a long one, and every session of the chat host with a made-up conversation of 3,500 events (`longChatEvents`).

```sh
./Carrier.app/Contents/MacOS/Carrier --fixture
./Carrier.app/Contents/MacOS/Carrier --fixture --selftest /tmp/carrier-selftest.log
```

## Sessions home

Selecting the Sessions row shows the Sessions home (`Carrier/SessionsHomeView.swift`; the values are `CarrierCore/SessionsHome.swift` and `sessionGroups`): the title with its count ("5 active · 1 waits for you", "1 of 5 · …" with a filter on, "N results" with a search), one glass group with Search and Filter, and New session, which follows the Sessions flag and does nothing yet. The list is grouped by workspace (or by age or status), one row per session with the state glyph, title, agent, the branch of a worktree session and the age; a session that waits for the person is orange and a click selects it. Search is a field in the group (Escape or ✕ closes and clears it) that finds by title, workspace and agent across active and archived sessions, flat, with the workspace as a tag and archived matches dimmed and tagged. Filter is one popover with the sort (`sidebar.sessionSort`, the sidebar's own, so both agree) and what to show by status and by agent; the button shows how many are on, chips under the header remove one each and Clear filters removes them all. The search and the filters are not remembered. Without sessions the page says "No sessions yet"; a search or filter that matches none says "No sessions match" with Clear filters.

## Archive

Selecting the Archive row shows the Archive page (`Carrier/ArchiveView.swift`; the values are `CarrierCore/ChatArchive.swift`, `archivePage`): the title with its count ("5 sessions", "N results" with a search), the same glass group with Search and Filter, and, on the right, Clear sessions…, disabled when nothing is archived. Filter only sorts, by date archived (Last 30 days, Older) or by project, remembered in `SidebarStore.archiveSort` (the host does not say when a session was archived, so the date is the session's last activity). Search finds by title, workspace and agent. Nothing archived says "Nothing archived" ("Archived sessions are kept here."), a search with no result "No sessions match". On hover a row shows Open (selects the session's conversation, read only: the session stays archived and the message box gives way to a notice with Resume), Resume (`archive` with false, then opens it) and Delete (asks first, then `delete`). Clear sessions asks with an alert that names the count ("Delete all 5 archived sessions?", Cancel is the default button) and deletes all of them, not only what a search shows; a refusal of the host is told in an alert in its words. A session row's context menu in the sidebar and on the Sessions home has Archive (Restore for an archived match), Reveal in Finder and Copy session id. `SessionActions` runs archive, restore, delete and clear through `ChatHost` and tells `ChatSessionsPoller.invalidateArchived()` after each, so the Archive row's count is right within a second. Before a Delete and before Clear sessions the app asks the host `deletePreview` (`SessionActions.confirmDelete` and `confirmClear`; the words are `deleteSessionQuestion` and `clearSessionsQuestion`): a session in a worktree says "3 uncommitted files and 2 commits that exist nowhere else will be removed with its worktree" (or only that its worktree will be removed when it holds nothing to lose), a session in a base folder keeps the plain text, and the Clear alert adds how many of the sessions work in worktrees that would lose work and the totals of files and commits; if the preview itself is refused or the host does not answer, that is told in words and nothing is deleted. A refusal of `delete` (a worktree that cannot be removed) is told in the host's words and the session stays in the list. The fixture host answers `deletePreview` from `chat-delete-preview.json`. It keeps the changes in memory and refuses to archive or delete a working or waiting session, as the real one does. `--smoke-window` ends by selecting the Archive and printing an `archive:` line (the count, the groups, `listed` or the empty state, and whether Clear is enabled) and the layout again.

## Window shortcuts

The window's sidebar is five sidebar sections drawn by `SidebarSectionRow` (Home, Sessions and Carrier with its epics in the scrolling list, and, fixed in the foot, Archive above the divider and Settings alone under it): an icon, a title and its actions, no fill at rest and a light grey one when selected, drawn by the row and not by the list, so it never covers what unfolds under it. Sessions carries a soft grey badge with the number of open sessions, every one that is not archived (`Sessions.open`, named aloud `1 open session`; not drawn with none), and its list and its search never show an archived session: a query keeps the groups of the chosen order, filtered to the sessions whose title, workspace or agent match. Carrier's row is its title, the engine's state word (Running, Paused, Stopped, Problem or Connecting), the search and group-by actions and the slots bar at full width, with no counters and no line about the next check; a stopped engine draws the bar in grey from the total it last reported (`SidebarStore.slotsTotal`, kept between launches; none drawn while connecting or when no total was ever seen), and each epic group header shows its row count (`SidebarGroup.count`); About is an item of the menu bar item's menu. Archive (`Carrier/ArchiveSection.swift`) shows its count (hidden with nothing archived) and a magnifier; choosing it opens it (`OpenSection.archive`, so Sessions and Carrier fold, and it is remembered like them) and moves the row up, with its archived sessions under it, grouped by the age buckets of Sessions (Today, Yesterday, Last 7 days, Older), newest first and each with `SessionRowView`, as tall as its rows up to about five and then scrolling. `archivedGroups(_:query:now:calendar:)` (`CarrierCore/Sessions.swift`) returns only archived rows, and with a query the ones whose title, workspace or agent match, keeping the buckets; they show nowhere else in the sidebar. A session chosen in that list keeps Archive open (the list puts it back, since selecting a session opens Sessions). The title of every section row is a button, and so is each archived session, so Tab (with Full Keyboard Access) and Space reach and choose Archive, Settings and an archived session without a pointer; a click on the rest of the row still chooses it. The search is one view for the sections (`Carrier/SidebarSearch.swift`): the magnifier, or ⌘F for the open section, opens a field under the row with a clear button once it has text; esc, a second click on the magnifier or emptying it closes it. What a list says comes from `SidebarListState` (rows, empty, or no match for what was typed; `CarrierCore/Sidebar.swift`): with no match the list is replaced by the `No results` block (`EmptyState.noResults`, a magnifier with a minus as the nearest SF Symbol to a struck one, and `Nothing matches “query”`) with a Clear search button. A section with nothing in it says so in the same shape (`SidebarEmptyBlock`): Archive with nothing archived shows `Nothing archived` (`EmptyState.nothingArchived`); Sessions with no open session shows `No sessions yet` (`EmptyState.noSessions`) and a `New session` button; unfolded Carrier with no epics shows `No epics yet` (`EmptyState.noEpics`) and that an issue labelled `solve:epic:ready` starts one. While one is empty its count is not drawn and its magnifier is dimmed and does nothing, ⌘F included. While the window is the key window, ⌘1 selects Home, ⌘2 the Sessions home, ⌘3 the Carrier home and ⌘F opens the search of the section that is open (Sessions, Carrier or Archive; nothing when all are folded). The window handles them (`shortcutAction` in `CarrierCore/WindowShell.swift`, a key monitor in `WindowController`), not the menu bar item's menu, and each is in the tooltip of its row or magnifier.

## Window smoke check

`--smoke-window` opens the window, selects the first epic Carrier reports, waits three seconds, prints what it sees and exits: the minimum content size (980 wide; the height is 600 plus the 52 point title band), the width of the sidebar (268) and of the inspector (316), one `scroll pocket` line per scroll pocket (the epic view's pipeline bar makes one in the centre column, at x 268, taller than the 52 point title band) the toolbar items (Sidebar, Open PR and Open issue when the epic has them, Inspector), a `sessions home:` line (what the Sessions home says under its title, and `listed` or the empty state it shows), a `transcript:` line saying how the Agent output tab is laid out (`lazy stack, pinned section headers`, read from the constants the view itself uses) and a `transcript merge:` line, the time to merge a made-up transcript of 5,004 events (a few milliseconds). It then selects the first session the chat host lists and, a second and a half later, prints a `chat transcript:` line (how the conversation is laid out, from the constants of its view: a lazy stack, pages of 200 events, polled every 250 ms) and a `chat feed:` line (the rows the model makes of that session's events, how many of them are runs of tool calls, asked of the chat host as the view does, and the time it took). It needs a screen and combines with `--fixture`.

```sh
./Carrier.app/Contents/MacOS/Carrier --smoke-window --fixture
```

## New session

The + of the Sessions row, the New session button of the Sessions home and ⌘N (always on) select `Selection.newSession`: a draft in the centre (`Carrier/NewSessionView.swift`; the logic is `CarrierCore/NewSession.swift`) that shows a round mark (a placeholder for a logo), "What do you want to work on?", "Pick where it works, then write.", the sentence and a box with the agent chip; the toolbar takes the page's own colour, not the system's band. Nothing exists until the first message is sent. The workspace, a chip in the sentence, opens one popover that drills in (`CarrierCore/WorkspaceSources.swift` and `NewSessionModel`): the recent folders (`recentFolders`: the distinct base folders of the sessions the host lists, active and archived, most recent first, at most eight, with their paths), what is in the projects folder (the `<owner>/<repo>` and `local/<name>` folders on disk), Open local folder… (the system's folder panel), From a GitHub URL… (listed only when the host's hello has `cloneRepo`), My GitHub repositories… (when it has `githubRepos` as well), New project… (only when it has `createProject`) and a footer with the projects folder's path and Change…, which opens the folder panel and sets `projectsFolder` in the chat's own `<folder>/chat/chat.json` (`applyingProjectsFolder`; the file is made when it is not there and its other keys are kept; the engine's config is not touched), absolute; the popover comes back showing the new path and what that folder holds, and what was in the old one stays where it is. A folder inside the Carrier folder's `engine` or the chat's `state`, `logs` or `worktrees` (symlinks resolved, `projectsFolderRefusal`) is refused before anything is written, and a file that cannot be read or written is too, each said in red under the footer with the old folder still in place; the host reads the folder at each request, so the next clone or new project goes to the new one with no restart. The URL step takes `owner/repo` or a github.com address (`repoReference`; its button stays off until the text is one repository), says beforehand when the repository is already in the projects folder (the button reads "Update and use"), asks the host for `cloneRepo` (the sentence says "Cloning…" with a spinner and the box waits; Cancel closes the request's connection, which stops the clone on the host) and, when it ends, chooses the folder like any other; a refusal is shown in words with Try again and the chip stays orange. Under the field, "Let Carrier watch this repo" (on by default; off, with the reason, when `repoProblem` refuses the repository for the config's `repos`: already there, or a folder name another repo has) adds `{ "name": "owner/repo" }` to the config's `repos` when the clone succeeds, the file read again just before the write, and the draft says Carrier will listen from its next start; a config that cannot be read, is not a JSON object or is not writable leaves the clone standing and the draft says the repository could not be added to Carrier's list. Nothing is restarted. My GitHub repositories asks the host for `githubRepos`, a page at a time (thirty repositories the person's `gh` login can read, newest push first, owner, collaborator and organisation member, archived and disabled left out, with no filter on push permission, unlike the Repos tab's Add repo picker, which keeps its own), and shows "Signed in to GitHub as <login>" (the login comes with page 1 only), a search over what is loaded, each repository with a lock when it is private, when it was last pushed and a "watched" tag when the config's `repos` already has it, a "Partial list" notice and a Load more button while the host says there is more (the paging is `AvailableReposList`, the Repos tab's, reused). A first page that fails shows the host's reason in words with Try again; a later page that fails keeps what is loaded and offers Try again for that page. Choosing a row clones it as the URL step does (the spinner and Cancel show in this step) and "Let Carrier watch the repo I choose", under the list and on by default, adds it to the config's `repos` the same way; for a repository that is already watched it does nothing, and a row whose folder name another watched repo has says Carrier will not watch it and why (`repoProblem`). The logic is `NewSessionModel` (`showRepos`, `loadRepos`, `repoRows`, `cloneAndUse(repo:)`) and `githubRepoRows`, tested with a fake host in `NewSessionTests`. New project asks for a name only, shows the path it will make (`<projects folder>/local/<name>`), keeps its button off for a name the host would refuse (`projectNameProblem`, the host's own pattern, or a `local/<name>` already in the projects folder), asks the host for `createProject` (a folder with `git init -b main`) and chooses the folder; it has no watch box, and having no commits (`WorkspaceInfo.offersWorktree` needs a branch) the sentence reads "in the folder (new project, no commits yet: no worktree)". The agent chip lists the configured agents; one that is missing is disabled with "not installed" and one that is signed out with "signed out", while `ready` and `unknown` can be chosen. The states are the chat host's `health` reply (`HostHealth`: `git`, `gh` and each agent as `ToolState` `ready`, `missing`, `signedOut` or `unknown`), which the app asks for (`HealthStore`, one for the app) when it opens once the host answers, when it becomes active again and on an explicit refresh (`HealthMoment`; opening takes the host's answer kept for thirty seconds, the other two ask for a fresh one), and only of a host whose hello lists `health` (`shouldAskHealth`); with an older host (or none yet) an agent whose binary was found is `ready` and one that was not is `missing`, as before (`agentChoices`). The draft takes the first available provider and never preselects a blocked one (`pickAvailableAgent`, run again when the states change); when none is available the box says why (`noAgentReason`) and Send is off. With `git` `missing` (`NewSessionModel.gitMissing`; `ready`, `unknown` or no health change nothing) the draft offers no New worktree and, where the folder's branch would be, the sentence says "in the folder (git is missing: no worktree, no branch. See Health in Settings)" (`workSentence(gitMissing:)`), with no uncommitted-files line; a worktree already chosen goes back to the current folder. The rule, the host client's decoding and the draft are tested (`HealthTests`, `ChatHostTests`, `NewSessionTests`); the wiring in `AppDelegate` has no automated test. Above the box the sentence reads "Work in Choose a workspace…" (orange), with the box dimmed and unable to send until one is chosen. Once one is, the app asks the host what it is (`workspace`) and the sentence reads "Work in <workspace> on Current folder (<branch>)" ("detached HEAD" when there is no branch), with a line under it when the folder has uncommitted files (how many, and that a worktree keeps them out of the agent's way); a folder that is not a git repository (or is bare) reads "in the folder (not a git repository: no worktree)" and offers no worktree. "Current folder" is a menu of two choices that switches to "New worktree carrier/<name> from <branch>", with a line under the box saying what it creates: the name is the host's `suggestName` with ↻ for another, the part after the fixed `carrier/` is editable and `checkName` asks about it 400 ms after the last keystroke (a taken or invalid name is red with the host's reason and cannot be sent), and the branch control opens a picker with a search, the local and the remote branches in two sections (the checked-out one marked, the default one tagged) and Fetch now (`fetch`), which says how long ago the remote branches were fetched. The branch defaults to the one checked out in the folder, else the repository's default branch, else the person is asked. Sending in a worktree calls `open` with `worktree: {from, name}`; a refusal is said in the draft. The logic is `CarrierCore/WorktreeChoice.swift` (pure values over the `workspace` reply, tested against the golden files in `WorktreeChoiceTests`) and `NewSessionModel` (tested with a fake host). Opening the draft (`NewSessionModel.load`) starts the chat host when it is not running (`ChatHostStarter.ensureRunning`) and asks it again for the agents and the recent folders; sending (`NewSessionModel.send`) starts it too when it went away (`ChatHostStarter.ensureRunning`), calls `open` with the agent and folder (the agent's `options` apply on the host's side) and then `send`, and selects the session. A refusal of `open` is said in the draft and the text stays; a `send` that fails after `open` still selects the session, whose conversation shows the failure with Try again. The model, the sentence and the lists are tested with a fake `ChatHost` (`NewSessionTests`); `--smoke-window` prints what the draft offers, what the popover lists (`new session picker:`), a clone through the fixture host that works and one that is refused, and a new project that works and one that is refused.

## Conversation

Selecting a session (`.session(id:)`) shows its conversation (`Carrier/ConversationView.swift`; the logic is in `CarrierCore/ChatConversation.swift`). While the view is on screen a task runs `ConversationModel.run()`, which asks the chat host for `events` by cursor about every 250 ms, in pages of at most 200 (a full page is followed at once by the next), and ends with the task when the person selects something else. `chatFeed` turns the events into rows: the person's messages (a bubble on the right), the agent's (markdown), a closing line per turn (model, how long, and the input and output tokens the provider reported, each only when there), a tool call as one plain line completed by its end (tool, argument, the first line of its output or "failed"), an approval as one plain line completed by its answer, an error in red and, last, the `streaming` text as the message in progress. A poll that fails shows its reason under the feed and is logged once; polling goes on.

The conversation's title bar is the window's: the title (`conversationTitle`, "New session" while the host has none), under it `conversationSubtitle` ("workspace · ⑂ branch" in a worktree, "workspace · base folder" in a folder) and, on the right, the Open menu (`OpenMenu`, items from `openMenuItems`: Reveal in Finder, Copy path and, for a worktree, Copy branch name; a copy item says "Copied" for a moment). The words are tested; the Finder and pasteboard calls are not.

Markdown: SwiftUI's `AttributedString` parses what is inside a line (bold, italics, inline code, links) and covers what the agents write there; the blocks around it are `markdownBlocks` (`CarrierCore/SessionSections.swift`), the line-by-line reader the epics' Agent output already used, which now also reads fenced code as a block of its own (language after the fence, an open fence runs to the end, as in a message being written). `CodeBlockView` draws it with the language and a Copy button (`CopyButton`, the one of the console blocks). Numbered lists and tables are not read as blocks: a numbered item shows as a line with its number.
