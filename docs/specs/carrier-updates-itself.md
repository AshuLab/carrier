# Carrier updates itself

Status: spec

## Problem

Once Carrier is installed with Homebrew ([carrier-installs-with-homebrew.md](carrier-installs-with-homebrew.md)), a person stays on that version until they think to run `brew upgrade`, and nothing tells them there is a newer one. The app and `carrier` are two things Homebrew moves, so after an upgrade of only one of them the app complains about a protocol or runs an old engine without saying so. The app's first spec put auto-update out of scope because the app was for its author; with the tap, it is for other people.

We know it is solved when a person who has Carrier installed gets the next release without typing anything beyond accepting it: the app finds the new version, replaces itself, brings `carrier` up to date, and replaces the chat host and the engine that were running, each only when doing so loses nothing.

## Solution

The app embeds Sparkle, the updater native Mac apps use, and reads an appcast at a fixed address. The decision and what lost are in [0020](../adr/0020-the-app-updates-itself-with-sparkle-and-the-engine-through-homebrew.md); the facts behind it, read from Sparkle 2.10.1 (2026-10-25) and Homebrew 7.0.13, are in [the research](../research/sparkle-auto-update.md); the terms are in the glossary (Appcast, Update key, Free to replace). What the grilling cut: only telling the person to run `brew upgrade` (the owner wants the app to do it), an appcast committed to the repository as CodexBar does (a commit to `main` per release and a token to push it), a cask without `auto_updates true`, and any update of the engine by Sparkle (the engine stays Homebrew's, as 0017 decided).

**A spike comes first.** The research settled most of what the design assumed by reading code, but one thing no documentation says: whether Gatekeeper opens an ad hoc, not notarized app that Sparkle has just replaced and relaunched. The rest of the epic depends on the answer. A throwaway app signed ad hoc and embedding Sparkle is installed from a cask with `auto_updates true` into `/Applications`, and a local appcast offers it a second ad hoc build signed only with the EdDSA key. It has to show that Sparkle installs it; that a zip signed with another key is refused; that Gatekeeper opens the relaunched app with no dialog; that `xattr -lr` finds no quarantine, framework included; that the menu bar keeps one icon after the relaunch with the login item on and off; that Sparkle follows the redirects of a real GitHub Release in a throwaway public repo; and what `brew outdated`, `brew upgrade` and `brew uninstall --cask --zap` leave behind for a cask whose app has moved on. The result goes into the research file. If the Gatekeeper dialog appears, 0020 is revisited before any other slice starts.

**The release.** `build-app.sh` embeds `Sparkle.framework` (from the SwiftPM package; copied with its symlinks kept, before the final ad hoc `codesign`) and adds `-rpath @executable_path/../Frameworks` to the executable, which SwiftPM does not and without which the app dies at launch. It writes `SUFeedURL`, `SUPublicEDKey` and `SUEnableAutomaticChecks` in the plist. `CFBundleVersion`, `1` today, becomes the number derived from the tag, `X.Y.Z` as `X*10000 + Y*100 + Z` (a build without a version keeps `1`); Sparkle compares that number, not the short version, so minor and patch stay below 100. The workflow, after zipping (with `--sequesterRsrc`), signs the zip with Sparkle's `sign_update` and the update key's private half, a secret named `SPARKLE_PRIVATE_KEY` passed through the environment and never written to disk or the log, and writes a one-item `appcast.xml`: the version, the short version, the minimum system, the architecture, the zip's URL, its length and its signature; no history and no deltas. The Sparkle tools come from the SwiftPM artifacts (`.build/artifacts/sparkle/Sparkle/bin/`), pinned by `Package.resolved`, so nothing else is downloaded.

The order of the publishing matters, because the moment the appcast is attached an app may update, and `brew upgrade` must already find the new formula. `releases/latest` ignores drafts, so the release is created as a draft, gets the zip and its checksum, then the formula and the cask are pushed to the tap, then the appcast is attached, and last the release is published with `gh release edit --draft=false`. Until then the feed keeps answering with the previous release. Today the release is created before an appcast could exist and the feed would be a 404 in between. A re-run finds the release as it was left, draft or published, and goes on. The workflow's check step verifies the zip's signature with the public key derived from the private one and compares that key with the `SUPublicEDKey` in the built app (`sign_update --verify` does not read the plist). The dry run builds the appcast and publishes nothing. The `release` skill (`.claude/skills/release`) is the same procedure by hand and changes with the workflow.

The cask gains `auto_updates true` and the Sparkle cache folder in its `zap`; its `postflight` that clears the quarantine stays, because Sparkle only acts after the first install. `auto_updates true` does not keep `brew upgrade` away from the app: it upgrades it when it is older than the cask, which is how a person on a release before this one reaches the first release with Sparkle. What it does is stop Homebrew from replacing an app that Sparkle has already taken past the cask. Both paths end at the same version, because the release pushes the cask before it publishes the appcast.

One setup is the owner's, once: generate the update key pair with Sparkle's `generate_keys`, put the public half in `build-app.sh`, the private half in the repository secret and in a second place that survives a lost laptop, and write that in the release documentation. Losing the private half strands the installed apps (it cannot be rotated with an ad hoc signature); `brew reinstall --cask carrier` brings a new zip with a new public key, only to those who run it.

**The check.** Sparkle checks on its own schedule, and the app also asks for a check in the background right after it starts the updater, because Sparkle alone checks at start only when the last check is older than its interval. The person can choose two things: that the app checks by itself (on by default) and that it installs by itself (off by default, so Sparkle asks before it installs). Both are Sparkle's own preferences, and installing by itself cannot be on while checking is off. With install by itself, Sparkle installs when the app quits and does not relaunch it; that is enough, because the engine step below runs when the app next opens. Where the person sees and changes the two choices, and the "Check for updates" action, are the Settings UI and are not part of this epic.

**The engine and the chat host.** After Sparkle has replaced the app and it opens, the app asks the installed `carrier` for its version, as it already does once per launch for the chat host. If that version is older than the app's, the app runs `/opt/homebrew/bin/brew update` and then `brew upgrade --formula ashulab/tap/carrier` with `HOMEBREW_NO_ASK=1` (the bare name is also the cask's, and Homebrew warns), one background job at a time whose output goes to a log under the Carrier folder. The app accepting the update is the person's consent: no second question. When the job ends the installed version is read again, and the rules that already exist take over: a chat host that answers with an older version is replaced when no session is working or waiting for an approval ([chat-in-the-carrier-folder.md](chat-in-the-carrier-folder.md); `hostReplacement` in `CarrierCore/HostReplacement.swift` and `ChatHostStarter.replaceIfOlder`), and the engine, by the same comparison of its hello's version with the installed one, is replaced when it is free: it was running, and it has no execution in flight. A person who had the engine stopped keeps it stopped (0010). While the engine waits to be free, the app pauses intake, because an engine with a queue may never have a moment with nothing running; when its last execution ends the app stops it, starts it with the new `carrier`, and pauses it again if the person had it paused. A build under development keeps the same version, so none of this triggers there.

When Homebrew fails (no network, no `brew`, a pinned formula, a `brew update` running in another terminal that holds the lock), the app keeps the old `carrier` and the old engine, does not retry by itself, and shows the reason with the same kind of notice the chat host's restart advice already uses. The old `carrier` keeps working with the new app through the capabilities of the hello. The protocol check of [carrier-installs-with-homebrew.md](carrier-installs-with-homebrew.md) stays as it is, with one change: the message for an app older than `carrier` says that the app updates itself and, if it has not, to run `brew upgrade --cask carrier`, which does upgrade an app that is older than the cask (the app's own check for updates is Settings UI and is not part of this epic).

## Scope

1. The owner can tell, with a throwaway ad hoc app, whether Sparkle updates an ad hoc app installed by Homebrew without Gatekeeper stopping it, and the research records what was seen, including what `brew outdated`, `brew upgrade` and `brew uninstall --cask --zap` do afterwards.
2. `build-app.sh` embeds Sparkle 2.10.1 or the version the spike settles, keeps it launchable (rpath, symlinks, ad hoc signature valid under `--deep --strict`), and writes the feed URL, the public key, automatic checks on and a build number derived from the version; the app starts the updater and asks for a background check when it opens.
3. A person's two choices, check by itself and install by itself, exist in Sparkle's preferences with the defaults check on, install off, so a later Settings page only has to show them.
4. Pushing a tag publishes the release in the new order (draft, zip, tap, appcast, publish), with a signed one-item appcast whose public key matches the app's, and the dry run builds everything and publishes nothing; a re-run of a half-published release finishes it.
5. The cask declares `auto_updates true` and cleans Sparkle's cache folder on `--zap`; the formula is untouched.
6. After the app updates and opens, an installed `carrier` older than the app is upgraded through Homebrew with a log and no question, and the installed version is read again; a failure leaves everything as it was and says why.
7. A chat host or an engine older than the installed `carrier` is replaced when free: the host when no session is working or waiting, the engine only if it was running and once it has no execution in flight, with intake paused while it waits and restored after; a stopped engine stays stopped.
8. An app older than `carrier` is told that the app updates itself and, if it has not, to run `brew upgrade --cask carrier`.
9. The owner has the update key generated, its public half in the repository and its private half in a secret and in a second safe place, and the release documentation (the `release` skill, the README, `macos/README.md`, the troubleshooting guide) describes the update flow, the key and what to do if it is lost.

## Decisions

Testing seams, per story. The release has no unit tests of its own: its seam is the workflow's dry run and the check step that already opens the zip and reads the plist.

Story 1: no tests; the spike is the test, and its result is a note in `docs/research/sparkle-auto-update.md`.

Story 2: the seam is the built bundle, read the way the release workflow's check step reads it (`PlistBuddy` for the keys and the build number, `otool -l` for the rpath, `codesign --verify --deep --strict`). A step in `.github/workflows/macos-app.yml` builds the app on a pull request and asserts these. The derived build number is a few lines of `bash` in `build-app.sh` and is asserted by that step with a version and without one. No Swift test for the updater wiring: it is Sparkle's.

Story 3: no tests; it is Sparkle's own preference storage with two plist values and a call, read in the spike and in the built plist.

Story 4: the seam is `release.yml` in dry run on a branch and the check step: it extracts the appcast, checks the version, the build number, the length of the zip, that the signature verifies with the derived public key, that this key equals `SUPublicEDKey` in the app, and that nothing was published. The draft-then-publish order is read from the workflow and exercised by the first real tag.

Story 5: the seam is `brew audit --cask --strict` in the existing Cask step of the workflow.

Stories 6 and 7: pure decisions in `CarrierCore` beside `hostReplacement`, tested in `CarrierCoreTests` the way `HostReplacementTests` does. One decides whether the installed `carrier` is older than the app (it reuses `versionNumbers`; an unreadable version is never older). One decides what the engine does, from the running version, the installed one, whether it was running, whether it is paused and how many executions are in flight, with the outcomes keep, wait (pausing), replace and restore the pause. The run of `brew` is behind a small port with a fake in tests, like the app's other commands, and its outcomes (done, failed with the reason's last lines, brew missing) are plain values. The sequence on the engine is tested against the fixture engine (`FixtureServer`, which answers pause, resume and stop). The replacement of the chat host keeps its existing tests.

Story 8: the existing tests of the protocol-version function in `CarrierCore` (`Commands`, `ControlMonitor`) get the new message; one assertion.

Story 9: no tests. The `release` skill and `release.yml` change together (AGENTS.md).

The notice for a failed upgrade reuses the chat host notice's shape (`ChatHostNotice`) in the places that already show it; no new screen. Where the log lives and its name are decided when the slice is built, under `<folder>/engine/logs/` or the app's own folder, whichever the other `app-*.log` files use.

The first release with Sparkle reaches the people who already have Carrier through `brew upgrade`, because their app is older than the cask; from then on Sparkle moves it. The spike's findings override this document where they differ.

## Out of scope

The Settings UI for the two choices, the "Check for updates" action and the display of progress and errors beyond the notice above; this epic is the flow. Release notes shown to the person. A beta channel, a canary feed and downgrading. Delta updates and an appcast with history. Notarizing the app, or any change to its ad hoc signature (moving to a Developer ID later would make the key rotatable, and is a decision of its own). Updating the Homebrew formulae `node`, `git` and `gh` on purpose (a `brew upgrade` of `carrier` may move them, which is Homebrew's behavior). Intel Macs. Updating a `carrier` that is not Homebrew's, such as the author's repository build, whose version never changes. An immediate relaunch after an install-by-itself update (Sparkle has a hook for it; the engine step does not need it).
