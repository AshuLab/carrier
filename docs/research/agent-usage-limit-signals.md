# Usage-limit signals of Codex and Antigravity, and an agy login check

> Research of 2026-10-27 for epic #454 ([choose the agent option per epic](../specs/choose-the-agent-option-per-epic.md), its two open questions). Sources: the Codex source at tag `rust-v0.153.4` (the installed `codex-cli 0.153.4`, cloned shallow into a scratch folder and only read), `agy` 1.4.6 (`--help`, `agy changelog`, `strings` over `~/.local/bin/agy`, the official page <https://antigravity.google/docs/cli/headless>) and a few runs of `agy` in throwaway folders. No account was exhausted and no model was called: the only `agy` runs were `-p "/usage"`, which the changelog says does not start a turn (1.1.11) and whose output shows zero tokens. No token, email or id was read or saved; files on disk are described by shape only. The two fixtures are **constructed from the sources, not captured** (see the end).

## Short answer

Codex: the signal is text only. `codex exec --json` ends a run that hit a usage limit with a `turn.failed` whose `error.message` starts with `You've hit your usage limit`, preceded by an `error` event with the same text, and exits 1; exit 1 is the exit for every failed turn, and the event carries no error code, no type and no structured reset time.

Codex does separate a usage limit from a transient rate limit, in its own code, but the separation does not reach the JSON: the usage limit is a non-retryable error that surfaces at once as its own text, a transient rate limit is retried inside Codex and only shows as `Reconnecting... n/5` error events, and a plain HTTP 429 that was retried to exhaustion ends as `exceeded retry limit, last status: 429 Too Many Requests`. The rule for `parseCodexLine` is to match only the final `turn.failed` message, never the `error` events that precede it, since a retry notice is also an `error` event.

Codex reset time: a human string in the machine's local time zone at the end of the message (`Try again at 3:45 PM.` today, `Try again at Oct 28th, 2026 3:45 PM.` another day), or `Try again later.` when the server sent none. It is for display, not for arithmetic.

Antigravity: for a plan quota that is used up and an AI-credits balance that cannot cover the request, the changelog and the binary give the text `Your AI credits balance is too low to continue.` (1.2.15, shown at once instead of after ~2.5 minutes of retries); for the individual quota the binary has `individual quota reached` and `You have exhausted your quota on this model.`; the changelog says an individual quota, a daily quota or a billing cap stops right away while a per-minute 429 and a model-capacity error are retried inside `agy` with the server's delay. What the stream-json `result` of such a run looks like was **not observed**: the shape `status: "ERROR"` plus an `error` string is the one seen for a failed login, and the exit code of a model-API failure is documented as `3` with an `AGY_ERROR: {...}` line on stderr (1.2.6, 1.2.10), whose exact keys could not be read from the binary. So for `agy` the rule is: a `result` with `status` `ERROR` whose `error` matches the quota texts, with the exit code `3` and the stderr line as supporting evidence, not as the key.

Antigravity reset time: not in the failure text. It is available as structured data, in UTC, from a call that spends nothing: `agy -p "/usage" --output-format json` returns per-bucket `remaining_fraction` and `reset_time`. That is a way to fill the reset time for the needs-human card (and a way to check before a run), not something the failure carries.

`carrier doctor` for agy: `agy -p "/usage" --output-format json` in a throwaway folder. Logged in it answers in about 5 seconds with exit 0 and `status: "SUCCESS"`, no model call. Logged out it prints `Authentication required. Please visit the URL to log in:` on stderr at once and then waits 60 seconds before ending with exit 1 and `status: "ERROR"`, `error: "authentication failed or timed out"`, so the check has to treat that stderr line as the answer and kill the process, and must set `BROWSER` to something inert so no browser opens. The official page says an unauthenticated headless run "exits with an `authentication required` error instead of hanging"; on 1.4.6 it hangs, with or without a controlling terminal.

`configDir` for agy: there is no variable. The folder is `~/.gemini/antigravity-cli/` (plus `~/.gemini/config/`), derived from `HOME`. I tried `XDG_CONFIG_HOME` and `ANTIGRAVITY_CONFIG_REL_DIR` on the real login and both changed nothing (still logged in, nothing created); `HOME` is the only thing that moves it, and an empty `HOME` is a fresh, logged-out agy. `~/.antigravity` is not agy's: it is the Antigravity IDE. So `configDir` stays refused for agy, as the spec already says; a second account would have to be a different `HOME`, which also hides `~/.gitconfig` and `~/.config/gh`, so it is not an option to offer.

## Codex: what the code does

Every provider error is mapped to `CodexErr` in `codex-rs/codex-api/src/api_bridge.rs` and `codex-rs/codex-api/src/sse/responses.rs`. A usage limit has three entries, all of them non-retryable (`CodexErr::is_retryable` in `codex-rs/protocol/src/error.rs` lists `UsageLimitReached`, `QuotaExceeded` and `UsageNotIncluded` under `false`) and all three mapped to the client-facing `CodexErrorInfo::UsageLimitExceeded` (`to_codex_protocol_error`, same file).

`UsageLimitReached`: an HTTP 429 whose JSON body has `error.type == "usage_limit_reached"` (`api_bridge.rs`, the `TOO_MANY_REQUESTS` branch). The body also carries `error.resets_at` (epoch seconds) and `error.plan_type`; the response headers carry `x-codex-rate-limit-reached-type` and the `x-codex-*` snapshot of the windows and credits. This is the same discriminator Claude uses (429 plus `usage_limit_reached`), which is a coincidence of naming, not of code.

`QuotaExceeded`: a `response.failed` event inside the stream whose error code is `insufficient_quota` (`is_quota_exceeded_error` in `sse/responses.rs`, test `quota_exceeded_error_is_fatal`). Its text is the fixed `Quota exceeded. Check your plan and billing details.` and the core test `quota_exceeded_emits_single_error_event` asserts exactly one error event with that text. This is the credits-ran-out case of an API-key login.

`UsageNotIncluded`: a 429 with `error.type == "usage_not_included"`, text `To use Codex with your ChatGPT plan, upgrade to Plus: https://chatgpt.com/explore/plus.`. It is an account that has no Codex access at all, not a limit that resets; I would still map it to `usage_limit` for Carrier (stop retrying, name the option, let failover move on), but that is a judgment, and it never has a reset time.

The text of `UsageLimitReached` comes from `impl Display for UsageLimitReachedError` (`protocol/src/error.rs`) and depends on plan and on `rate_limit_reached_type`. Plain: `You've hit your usage limit. Try again at <time>.` or `... Try again later.`; with a plan hint: `You've hit your usage limit. Upgrade to Pro (...), visit https://chatgpt.com/codex/settings/usage to purchase more credits or try again at <time>.`; per model limit: `You've hit your usage limit for <limit_name>. Switch to another model now, or try again at <time>.`; admin plans: `... To get more access now, send a request to your admin or try again at <time>.`. The workspace variants do **not** start with that phrase: `Your workspace is out of credits. Add credits to continue.` (and `... Ask your workspace owner to refill in order to continue.`), `You hit your spend cap set in your workspace. Increase your spend cap to continue.` (and `... set by the owner of your workspace. Ask an owner to increase your spend cap to continue.`). The workspace variants have no reset time. All of this is pinned by `protocol/src/error_tests.rs`.

The time is formatted by `format_retry_timestamp`: converted to the machine's local zone, `%-I:%M %p` if it is today, else `%b %-d<st|nd|rd|th>, %Y %-I:%M %p`. No zone name or offset is printed, so the string is only meaningful on the machine that ran Codex, which is the one running Carrier; it is not parseable without guessing the locale of `%p`, and I would store it as text, as the spec says.

A transient rate limit is a different path. A `response.failed` with code `rate_limit_exceeded` becomes `ApiError::RateLimitExceeded` and then `CodexErrorDetails::RateLimitExceeded`, which `is_retryable` marks `true`; `core/src/responses_retry.rs` retries it with the delay the server gave (`try_parse_retry_after`, which parses `Please try again in 11.054s`) and, from the second attempt, notifies `Reconnecting... n/max`. A 429 whose body is not `usage_limit_reached` or `usage_not_included` becomes `RetryLimitReachedError`, displayed `exceeded retry limit, last status: 429 Too Many Requests, request id: ...`, non-retryable at that level because the transport already retried. A 503 with `server_is_overloaded` or `slow_down` is `Selected model is at capacity. Please try a different model.`; a 500 is `We're currently experiencing high demand, which may cause temporary errors.`. None of these contain `usage limit`.

What reaches `exec --json` is only text. `codex-rs/exec/src/event_processor_with_jsonl_output.rs` turns the server's `Error` notification into `{"type":"error","message":...}` (`ThreadErrorEvent` has only `message`, `exec/src/exec_events.rs`), appending ` (<additional_details>)` when there are details, and a failed turn into `{"type":"turn.failed","error":{"message":...}}`, taking the turn's error or, failing that, the last critical error, or `turn failed`. The `codex_error_info` that carries `UsageLimitExceeded` exists in the notification but the exec processor never reads it (a search for `codex_error_info` in `codex-rs/exec/src` finds only a `None` in a test). Exit code: `exec/src/lib.rs` sets `error_seen` for a non-retrying error (`!payload.will_retry`) or a failed or interrupted turn and ends with `std::process::exit(1)`; there is no other code for provider failures, so the exit code says "failed", not "why".

The existing adapter already depends on this shape: `parseCodexLine` reads `turn.failed` and its comment records that the `Reconnecting... n/5 (... 401` error events before it "are retries, not the end". The usage-limit case is the same two-event shape, with the difference that the retry events do not appear (non-retryable, so no `Reconnecting`).

Structured alternative, not recommended for the adapter: the app-server protocol has `account/rateLimits/read` (`app-server-protocol/src/protocol/common.rs`), which carries `resets_at` per window. It would need a second process and a login; the text is enough for the `usage_limit` kind.

## Antigravity: what the changelog and the binary give

The changelog (`agy changelog`, read in full, 1.0.1 to 1.4.8) is the only primary statement of behavior, and it never shows an actual quota error in stream-json. The relevant lines: 1.1.1 print mode returns a non-zero exit and writes the error to stderr when a request fails server-side; 1.2.6 and 1.2.10 a turn that ends on a model or agent API failure prints a structured `AGY_ERROR: {...}` line on stderr (canonical status, HTTP or gRPC code, retryability, error id) and exits `3` instead of `1`, also when part of the response was already streamed, while multi-turn `stream-json` sessions "warn and continue"; 1.2.13 the CLI waits the retry delay the server asks for and "stops right away instead of retrying when the delay is longer than 30 seconds or the quota is a daily or billing cap"; 1.2.15 "requests made after your plan quota is used up and your AI credits balance cannot cover them" end at once with "Your AI credits balance is too low to continue." instead of retrying for about two and a half minutes and printing the generic "Agent execution terminated due to error."; 1.3.3 "reaching your individual quota is reported right away instead of being retried"; 1.3.1 a subagent stopped by "running out of quota or model capacity" shows `Error:` with the reason; 1.1.11 a spurious "Out of credits" was fixed (an empty credits response read as a balance of zero), which tells us the message can be wrong on a bad response.

The binary has the strings behind those lines: `Your AI credits balance is too low to continue.`, `individual quota reached`, `You have exhausted your quota on this model.`, `Agent execution terminated due to error.`, the error-code names `MODEL_CAPACITY_EXHAUSTED` and `PREFILL_QUEUE_OVERLOADED` (capacity, not quota), `RESOURCE_EXHAUSTED` (the gRPC code, which Google uses for both quota and rate limits, so the code alone does not separate them), a `retryable` field in a JSON type of the print mode, and `AGY_ERROR: {"short_error":%q}`. The status line shows `Model unavailable (attempt 2/10), retrying in 12s` for the retried case (1.4.6).

So what separates a usage or credit limit from a transient one in `agy` is again text plus the changelog's behavior promise: the limit texts above are the ones that end the run without a retry, while a capacity error or a per-minute 429 is retried inside `agy` and only fails after its attempts, with a different message. The exit code `3` does not separate them (any model-API failure), and `AGY_ERROR` has a `retryable` flag that probably does; I could not confirm the key names or values without a failing run, so it is a lead, not a rule.

Quota in Antigravity is per bucket, not per account. `agy -p "/usage" --output-format json` on this machine returns groups `Gemini Models` (buckets `gemini-weekly` and `gemini-5h`), `Claude and GPT models` (`3p-weekly`, `3p-5h`) and one for `Gemini 4 Argon`, each bucket with `id`, `name`, `window` (`weekly`, `5h`), `remaining_fraction` and `reset_time` (UTC, `2026-10-28T07:36:20Z`), plus `description` for the group. An option on a Gemini model can be out of quota while the same login still has Claude or GPT quota. That matters for the spec's wording "the option that ran out": for agy the unit that ran out is the option's model group, and a failover list that names two agy options with different models is meaningful. This also shows that a `-p "/usage"` preflight can be exact where the failure text is not.

`settings.json` of agy has a `useG1Credits` key (1.0.3: G1 credits are used automatically when the standard quota runs out). With it on, the first quota exhaustion is not a failure and the failure text appears only when the credits are gone too; the "credits balance is too low" message is the end of that chain. Carrier does not manage that setting.

## Antigravity: login check and config folder

Where agy keeps its state, verified by running it with an empty `HOME`: it created `$HOME/.gemini/antigravity-cli/` (`conversations/`, `log/`, `cache/`, `cli.log`, `conversation_summaries.db`, `installation_id`, `jetski_state.pbtxt`, ...) and `$HOME/.gemini/config/`, and nothing else. On the real home the same folder holds `antigravity-oauth-token` (mode 0600, a small JSON object with the keys `token` and `auth_method`), `settings.json` and `history.jsonl`. The official headless page names `~/.gemini/antigravity-cli/settings.json` and no other path or variable.

`~/.antigravity` is the IDE, not agy: it holds `argv.json` (keys for hardware acceleration and the crash reporter, as a VS Code fork has), `extensions/` of VS Code extensions, and `antigravity/bin/` with two symlinks, `agy` and `antigravity`, that point at `/Applications/Antigravity.app/Contents/Resources/app/bin/antigravity` and are broken on this machine. That is an older `agy` launcher of the IDE, a different program from `~/.local/bin/agy`; `which -a agy` finds only the CLI. The IDE's own data is in `~/.gemini/antigravity-ide/` and `~/Library/Application Support/Antigravity IDE`. Credential storage is also not only a file: the changelog says tokens are kept in the OS keychain/keyring, with a private secrets file as fallback for oversized ones (1.4.7, 1.4.6, 1.1.3) and the binary has `Using file-based token storage because the caller requested it`, so the presence of the token file is not a reliable login test, and I would not use it.

Environment variables found in the binary and what each does, as far as tested. `XDG_CONFIG_HOME` and `ANTIGRAVITY_CONFIG_REL_DIR`: tried with the real `HOME`, no effect on the login or on where files go. `ANTIGRAVITY_EXECUTABLE_DATA_DIR`: the data folder of a sidecar (a plugin process), from the text around it, not the CLI's own state; not tested. `AGY_ACCOUNT`: the binary has `AGY_ACCOUNT=%q matches no signed-in account; available accounts: %s` next to text about the Plugins Manager, which suggests it selects the account of a plugin or MCP connection, not the sign-in of the CLI; the changelog never mentions it; not tested. `AGY_ADC_AUTH`: documented (1.4.7 and earlier): sign-in with Google Application Default Credentials for Business accounts; it changes how the login is made, not where, and ADC would be a different account model than a personal one. `GEMINI_API_KEY` with `modelProvider: "gemini"` in `settings.json` (1.1.13): runs on the Gemini API without a sign-in, which is the only route where an option could be fully described by environment; it needs a settings change, and has its own quota behavior (1.2.12: it stops at once on an exhausted daily quota, a spend cap or depleted prepaid credits, and retries per-minute limits). `AGY_CLI_CDE_AUTH_ACTION` takes `check` or `login` (the binary prints `Unknown AGY_CLI_CDE_AUTH_ACTION: %q (supported: check, login)`); it is undocumented, its context is a cloud-development-environment mode, and I did not run it, since `login` is its other value and its output is unknown.

The login check I recommend is therefore a behavior test, not a file test: run `agy -p "/usage" --output-format json` with `BROWSER` set to an inert command, in a throwaway working folder, stdin closed, reading both streams. Logged in (observed, 5 seconds): stdout is one JSON object with `status: "SUCCESS"`, `num_turns: 0`, all token counts `0` and a `command.data.groups` list. Logged out (observed twice, with an empty `HOME`, once also under `setsid` so there is no controlling terminal): stderr says `Authentication required. Please visit the URL to log in:` followed by a Google OAuth URL, `Waiting for authentication (timeout 60s)...` and `Or, paste the authorization code here and press Enter:`; 62 seconds later stdout is `{"status":"ERROR","error":"authentication failed or timed out",...}` and the exit code is 1, with `Error: authentication timed out.` on stderr. The same two strings are the ones `parseAgyLine` already uses. Doctor should call it logged out as soon as the first line appears and kill the process (the `-p` flow does not honor `--print-timeout` during the login wait, per [antigravity.md](antigravity.md)). The OAuth URL on stderr must not be logged: it is not a credential, but there is no reason to keep it.

`/usage` is not documented as a login check; it is documented as a read-only print-mode command that "spends no quota" (changelog 1.1.11). Two risks: a future version may answer `/usage` without a sign-in, and a signed-in Business account with admin controls could differ; both are cheap to notice, since the check would stop reporting a logged-out state in a clean `HOME`. Doctor can only run it for the environment's own login: with no `configDir` for agy there is one agy account per `HOME`, and doctor would warn if two agy options exist.

## What could not be established

The real output of a quota failure from `agy`: stream-json `result.error` text and the keys of `AGY_ERROR` were not observed, and cannot be without exhausting a real account, which was ruled out. The `agy` fixture is grounded on the shape of the observed failed-login `result` (`status: "ERROR"`, `error`, `usage` of zeros, `duration_seconds`, `num_turns`) with the message string taken from the binary and the 1.2.15 changelog; the claim that this exact message reaches `result.error` for a quota failure is an inference. The text may also differ per account type (the Business and ADC paths have their own messages; 1.1.15 and 1.1.11 fixed false "Out of credits" cases).

Whether `agy` exits with `3` for the quota failure in `stream-json` (the changelog says `3` for "a turn that terminates on an agent or model API failure" in headless runs; 1.2.10 says multi-turn `stream-json` sessions warn and continue instead); the Carrier adapter uses a single-turn `-p` run, so `3` is expected, but it was not seen. The existing research recorded exit 1 for unknown model, interruption and failed auth, which is consistent with `3` being a different class.

The real output of Codex was not captured either: the fixture is the two events the code emits for a non-retryable error followed by a failed turn, and the exact text of the message is the one pinned by `error_tests.rs` for an unknown plan with a reset time. A real run would add the `item.completed` error notices Codex prints for flags (as in `codex-exec.fixture.jsonl`) and may have a plan-specific message.

Codex messages are English strings of a 0.153 source. A later version can reword them; the match on `usage limit` (case-insensitive) as a fallback to the exact prefixes costs nothing, and the fixture test will notice a rewording only when the fixture is updated from a real run. Codex's `error` JSON line printed when serialization fails is a different shape (`{"type":"error","message":"failed to serialize exec json event: ..."}`) and would not match the quota prefixes.

Whether `agy` keeps one login per `HOME` when the credential is in the keychain: the empty-`HOME` run was logged out, but macOS keychains are per user and `HOME`-relative lookups of the login keychain can change; I did not test an `agy` with the real keychain and a different `HOME` together, so "a second account is a second `HOME`" holds for the file-based store only.

The docs contradiction: the official headless page says an unauthenticated run exits with `authentication required` instead of hanging; 1.4.6 hangs for 60 seconds. The changelog (1.1.2) promises a fail-fast for "truly headless" runs; the `setsid` test is the nearest I could get to that, and it still waited.

## Detection rule for the adapters

`parseCodexLine`: on `type == "turn.failed"` and `error.message` starting with one of `You've hit your usage limit`, `You hit your spend cap`, `Your workspace is out of credits`, `Quota exceeded. Check your plan and billing details.` or `To use Codex with your ChatGPT plan, upgrade to Plus`, return `{ failure: { kind: 'usage_limit', detail: message } }`; any other `turn.failed` that is not the 401 returns `api_error` with the message. Do not match on `error` events.

`parseAgyLine`: on `event == "result"` and `result.status == "ERROR"`, return `usage_limit` when `result.error` contains `AI credits balance is too low`, `individual quota reached` or `exhausted your quota`; otherwise `api_error` with the error text (keeping the login error as `authFailed`). Treat the exit code `3` and the stderr `AGY_ERROR` line as support, to be re-read once a real failure is captured.

The reset time of the `usage_limit` detail is the tail of the Codex message, or, for agy, a read of `agy -p "/usage" --output-format json` made after the failure for the bucket of the option's model (`reset_time`, UTC); both are display text for the needs-human card.
